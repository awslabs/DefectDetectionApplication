# Requirements Document

## Introduction

A review of the Edge CV Portal's authorization and IAM posture (trunk `48841a0`) found a set of consistency gaps that sit next to, but outside, the use-case bucket binding delivered by the `portal-usecase-bucket-config` spec. That spec binds every S3 sink to the use case's configured buckets, adds `additional_s3_buckets`, the bucket-eligibility rule (portal-created or tagged `dda-portal:managed=true`), auto-add of portal-created buckets, the browse-time allow button, the DataScientist requirement on `POST /models/validate`, authorization on the pre-labeled dataset routes, and a role gate on `POST /s3-buckets`. This spec resolves what that one deliberately left out, and is implemented stacked on it: that branch landed on the trunk `integration/all-specs` at `f191d580` and on main (merged 2026-10-14).

The eight items, each confirmed by reading the trunk (file:line citations are in `design.md`):

- **I1 — Use-case creation and account grants.** `POST /usecases` has no role requirement (the handler's own docstring says any authenticated user may create one and becomes its UseCaseAdmin), even though the permission matrix in `shared_utils.py` already defines `Permission.CREATE_USECASES` and grants it only to PortalAdmin — the handler never checks it. During creation the portal writes a bucket policy on its own Greengrass component bucket granting read to a **caller-supplied** `account_id`, adds an EventBridge `PutEvents` permission for that account, and attempts to assume a caller-supplied Data Account role ARN and external id, all before any proof that the caller controls that account. `PUT /usecases/{id}` lets a UseCaseAdmin change `account_id` and `cross_account_role_arn` freely. Bucket-policy statements are added per account and never removed (use-case deletion only deletes the DynamoDB item), and the existing `verify_role` function is unreachable because the handler's generic `POST` branch shadows the `/verify-role` branch. The portal's own Lambda role may assume only `DDAPortalAccessRole` in the accounts listed at deploy time (`trustedUseCaseAccountIds`), and no portal role may assume `DDAPortalDataAccessRole` — a bound the proof of control must respect, not rediscover through STS errors.
- **I2 — Auto-trigger derived from the request body.** `POST /training/{id}/compile` does not apply its DataScientist check whenever the body sets `auto_triggered: true`. The flag is meant to mark internal Lambda-to-Lambda invocations (training events, model import auto-compile), but any API caller can set it. Packaging and publish use a sibling convention (`user_id == 'system'`).
- **I3 — One API method with no authorizer.** `POST /shared-components/provision` is registered in `api-gateway-stack.ts` with no authorization options. The handler skips its permission check whenever the body carries a `user_id`, on the assumption that such requests are SigV4-signed Lambda calls — but API Gateway never evaluates a SigV4 signature on a method whose authorization type is not IAM, so the assumption does not hold. Its only callers are the frontend (Cognito JWT) and the UseCases Lambda (an HTTP hop to the portal's own API). API methods are registered by ten stack files across four top-level stacks (seven nested API stacks under the compute stack, one under the node-designer stack, and the build-fleet and synthetic-data stacks registering directly on the imported REST API); no committed inventory lists them.
- **I4 — Dead and dormant code.** `manifest_validator.py` parses caller-supplied S3 URIs and reads/writes them with the execution role, performs no authorization, and is not wired to any Lambda or route; `data_management.py` has a `/transform-manifest` branch that calls an undefined function.
- **I5 — Wildcard S3 data-plane grants on portal Lambda roles.** `createLambdaRole` in `compute-stack.ts` resolves its data-plane statement from the `dataBucketAllowlist` CDK context and defaults to `arn:aws:s3:::*` (object level `*/*`) for `s3:GetObject`/`s3:PutObject`; `cdk.json` sets no value and every deploy script passes an empty `DATA_BUCKET_ALLOWLIST`. `synthetic-data-stack.ts` duplicates the same default, and `node-designer-stack.ts` grants `s3:GetObject/PutObject/DeleteObject/ListBucket` on `arn:aws:s3:::*` with no allowlist at all. A comment on the compute-stack grant still claims tag scoping that was removed. The committed IAM synth baseline pins the wildcard.
- **I6 — Device token-exchange role drift.** The live `GreengrassV2TokenExchangeRole` carries two hand-attached customer-managed policies that no template in the repository produces: one granting `s3:GetObject` on all buckets, one granting `s3:*` on all resources. The repository's own templates for that role are prefix-scoped.
- **I7 — Enforcement flag posture.** `PORTAL_REGISTRY_ENFORCED` is default-off in code, CDK and docs. The deploy scripts now preserve the deployed value, but a bare `npx cdk deploy` still resolves it off, the legacy resolver remains, and the spec and the admin guide disagree on whether a user holding only a global role should pass per-request checks on use cases they are not assigned to.
- **I8 — Composition with the bucket-config change.** Everything here must reuse that change's refusal convention, audit style and single bucket allowlist; it has landed, and this spec is stacked on it.

The product and operations decisions these items needed (D1–D8) have been taken by the owner and are recorded as decision records in `design.md`; the requirements below state the chosen behaviour only. The owner has also approved running every task, including the account operations, once the design is approved; the timing of the device-role policy detachment (formerly gate G2) is fixed at "immediately after the portal deploy, with the evidence window taken from historical data". One owner gate remains and is asked only when reached: **G1** (the I5 fallback, if the tag-condition verification fails for a required action).

Scoping decisions:

- **Stacked, not parallel.** `portal-usecase-bucket-config` landed on the trunk at `f191d580` (and on main); this spec's branch is stacked on it, and task 0.1 re-confirmed the composition against the landed code before any code was written. This spec reuses its refusal envelope (`error` + `error_code`), its audit-event style, its single bucket allowlist and its vendored SDK; it introduces no second allowlist mechanism and no second SDK pin.
- **Three classes of work, kept visible.** Portal-only changes (code, CDK, docs) are implemented and verified here. Account operations (tagging and enabling attribute-based access control on already-registered buckets, detaching hand-attached device policies, generating IAM last-accessed reports, the portal deploy itself) are Runbook_Tasks: approved in advance by the owner, written as executable runbooks (exact commands, pre-checks, expected output, rollback), and executed by the implementation only when every pre-check passes — a failed pre-check stops the task and asks instead of guessing. Device-affecting changes (anything that alters what the device role may do, and any step that runs the station installer on a lab device) are Runbook_Tasks too and are verified on real hardware before being called done, per `.kiro/steering/builds.md`.
- **Neutral register.** Spec files, code comments, commit messages and test names describe authorization consistency, IAM scoping, dead-code removal and deploy safety.
- **Verification record outside the repository.** Other specs in this repository commit a `verification-notes.md` beside their tasks. This spec does not: its record names live account resources (policy names, bucket names, device identifiers) even in masked form, so it lives in the workflow's uncommitted state directory (see Verification_Notes in the glossary) and the committed spec directory carries counts, test names and decisions only, inside `design.md`.

## Glossary

Terms from the portal JWT-role spec (Portal_Identity, Effective_Role, Claimed_Role, Unprovisioned_Principal, Registry_Enforcement) and from `portal-usecase-bucket-config` (Allowed_Bucket_Set, Additional_Buckets, Attach, Eligible, Portal_Created, Managed_Tag, Refusal) keep their definitions; where this document says Refusal_Envelope it means that spec's Requirement 5 body (`error`, `error_code`, plus `bucket`, `usecase_id`, `purpose`, `reason`, `remedy` where relevant). New or constrained terms:

- **Attach_Validator**: the single attach validator of `portal-usecase-bucket-config` (its design §1.6; Requirements 10.1–10.3) that every record writer calls before writing a bucket into a use case — `create_usecase`, `update_usecase`, `create_s3_bucket` (auto-add) and `data_management.configure_data_account` (its Requirement 10.10 enumerates exactly these four). Landed as `check_bucket_attachable` (`shared_utils.py:2646`) with the keyword list `(*, target_usecase_id, usecase_like, bucket, user, event, purpose, evidence=None, retry=False)`, confirmed by task 0.1, and the Attach_Step forwards every keyword it receives (`retry` included). This spec never calls it directly from a handler: handlers call the Attach_Step.
- **Attach_Step**: this spec's shared-layer wrapper `attach_bucket(...)` around the Attach_Validator: the validator's result on success, followed — for a Portal_Account_Bucket only — by the ABAC_Registration (read status, enable if disabled, audit) and the Registration_Report. Every Attach path therefore gets both, whichever writer performs it.
- **Portal_Account_Bucket**: a bucket for which the sibling's role selector (`_select_s3_role_for_bucket`, its design §1.5 — the verbatim move of the trunk's `get_s3_client_for_bucket` selection, `shared_utils.py:2110–2127`) picks a role ARN `r` with `r is not None and r.endswith(':root')` — the exact test `assume_usecase_role` makes before returning the Lambda's **own** credentials (`shared_utils.py:1580`): a bucket the portal reaches with its execution role rather than through `DDAPortalAccessRole` or `DDAPortalDataAccessRole`. A legacy Single_Account_Record that stores no `cross_account_role_arn` yields `None` from the selector and is therefore not a Portal_Account_Bucket by this test (the sibling's eligibility probe refuses such a record with `credentials_unavailable` before the Attach_Step runs). Exactly these buckets are subject to the Tag_Condition on the Lambda roles, so exactly these get the ABAC_Registration. A `data_s3_bucket` is a Portal_Account_Bucket when the record names no separate data account (`data_account_id` absent or equal to `account_id`); otherwise it is reached through `DDAPortalDataAccessRole` and is left alone.

- **Use_Case_Creator_Permission**: `Permission.CREATE_USECASES`, already defined in `shared_utils.py` and held by PortalAdmin only in the role matrix; the permission `POST /usecases` requires (D1).
- **Account_Grant**: any write the portal performs that extends access to an AWS account named in a request — the component-bucket policy statements, the EventBridge `PutEvents` permission, the Data Account bucket-policy and CORS writes (performed through the assumed Data Account role; the Data Account tag write no longer exists after `portal-usecase-bucket-config` R10.7, which made `tag_bucket_for_portal` read-only), and the shared-component bucket-policy principals.
- **Trusted_Account_List**: the deploy-time CDK context `trustedUseCaseAccountIds`, the only accounts in which the portal Lambda roles may assume `DDAPortalAccessRole` (`compute-stack.ts:547–552`); exported to the handlers as the environment variable `TRUSTED_USECASE_ACCOUNT_IDS` (comma-separated) by this spec.
- **Proof_Of_Control**: a successful `sts:AssumeRole` by the portal on `arn:aws:iam::<account_id>:role/DDAPortalAccessRole` (the only role name the portal's own IAM grant permits and the only one the account template creates) with the supplied external id, returning an `AssumedRoleUser` whose account equals the supplied `account_id`; attempted only after the account has passed the Trusted_Account_List check, so an STS `AccessDenied` means "the role or external id in that account is wrong", never "the portal is not allowed to try".
- **Single_Account_Record**: a use-case record for which the shared layer's existing predicate `is_cross_account_setup(record)` (`shared_utils.py:1497–1514`: true only when both `cross_account_role_arn` and `account_id` are set and the ARN contains `:role/`) is **false** — the account-root ARN the trunk writes for single-account use cases (`arn:aws:iam::<account>:root`), and also a legacy record with no `cross_account_role_arn` at all. This is the one definition (`get_usecase_client` already decides the credentials by it); this spec defines no second regex. Such records are exempt from the role-ARN grammar and from Proof_Of_Control.
- **Account_Field_Change**: one of the seven account fields (`account_id`, `cross_account_role_arn`, `external_id`, `data_account_id`, `data_account_role_arn`, `data_account_external_id`, `sagemaker_execution_role_arn`) whose body value, after normalization (`None`, `''` and whitespace-only → absent), differs from the stored record's normalized value. Key presence is not a change: the frontend's Edit modal (`UseCases.tsx:208–252`, `api.ts:1852–1857`) echoes five of the seven fields on every save (every one but `external_id` and `sagemaker_execution_role_arn`; the data triple as `''` when unset), including the stored `:root` `cross_account_role_arn` of a Single_Account_Record, so every `PUT` rule of Requirement 2.5 is evaluated on the set of Account_Field_Changes and never on which keys the body carries.
- **Component_Bucket_Name**: the portal's Greengrass component bucket, `<COMPONENT_BUCKET_PREFIX>-<AWS_REGION>-<PORTAL_ACCOUNT_ID>` (the derivation `shared_components.py:53–54` already uses; `compute-stack.ts:1068` builds the same name for the IAM grant), overridable by the `COMPONENT_BUCKET` environment variable where the CDK sets one (today only on the camera functions, 1828 and 2595); resolved by one shared helper so the two writers of the component bucket policy can never disagree.
- **Internal_Invocation**: a direct `lambda:InvokeFunction` of a portal handler by another portal Lambda, carrying an `Internal_Marker` and no API Gateway request context.
- **Internal_Marker**: a top-level event key (`dda_internal`) naming the calling function, purpose and acting user. API Gateway Lambda-proxy events cannot carry it (clients control only method, path, headers, query and body).
- **Source_Derived_Gate**: a role-check decision that depends on `Internal_Invocation` (the event's provenance) and never on a body field such as `auto_triggered` or a claim such as `sub == 'system'`.
- **Route_Auth_Inventory**: the committed list (`ROUTE_AUTH.md`) of every synthesized `AWS::ApiGateway::Method` resource in the four top-level stacks that register API methods, with its authorization type and the justification for every non-Cognito method, generated from one exported stack list (`API_STACK_INVENTORY`). CORS_Preflight_Methods are counted separately and excluded from the authorizer assertion.
- **CORS_Preflight_Method**: an `OPTIONS` method with a `MOCK` integration emitted by `defaultCorsPreflightOptions`; `AuthorizationType: NONE` by construction (a browser preflight carries no token), present on every API resource that declares CORS.
- **Portal_Managed_Tag**: the bucket tag `dda-portal:managed=true` that the bucket-config spec's eligibility rule requires.
- **ABAC_Enabled**: the per-bucket state (S3 `PutBucketAbac` status `Enabled`) under which Amazon S3 evaluates bucket-tag condition keys for requests against that bucket; disabled by default on general-purpose buckets. The API operations are `PutBucketAbac` / `GetBucketAbac` on the **`s3`** client (service-model casing, used for every operation name in this document). **IAM action spelling (ABAC_Action_Spelling):** IAM matches action names case-insensitively, but this spec's jest assertions and baseline/approved-addition records compare strings exactly, so one casing is fixed here. The bucket-config spec landed **`s3:PutBucketABAC`** on the UseCases role (its Requirement 9.12 and design §6.1; verified in its `compute-stack.ts` on branch `portal/usecase-bucket-config` at this revision — the spelling the vendored SDK's `PutBucketAbac` documentation gives the permission); it grants no `GetBucketABAC`, so the second action has no landed string. THIS spec therefore spells **both** IAM actions with that casing — **`s3:PutBucketABAC`** and **`s3:GetBucketABAC`** — everywhere it writes them: the DataManagement role's statement, the Tag_Discovery_Statement, every jest assertion, every record entry and the carve-out allow-list of Requirement 7.10. Task 0.1 confirms the landed `s3:PutBucketABAC` string on the trunk and records that the `Get` action is spelled by the same rule; a landed string other than `s3:PutBucketABAC` is a landed difference that stops 0.1 (Requirement 10.1).
- **Bucket_Tag_Operations**: `TagResource`, `UntagResource`, `ListTagsForResource` — operations of the **S3 Control** service (`s3control` client; parameters `AccountId`, `ResourceArn`, `Tags`; CLI `aws s3control tag-resource --account-id <id> --resource-arn arn:aws:s3:::<bucket> --tags Key=...,Value=...`), not of the `s3` client; the IAM actions are `s3:TagResource`, `s3:UntagResource`, `s3:ListTagsForResource`. `PutBucketTagging` / `GetBucketTagging` remain `s3` operations; `PutBucketTagging` stops working on a bucket once it is ABAC_Enabled.
- **Tag_Condition**: the IAM condition `StringEquals aws:ResourceTag/dda-portal:managed = true` (key confirmed per action by Requirement 7.5) on a portal Lambda role's S3 statement.
- **Tag_Discovery_Statement**: the unconditioned statement `s3:GetBucketTagging`, `s3:GetBucketABAC` on `arn:aws:s3:::*` that every data-plane role carries in every Data_Plane_Scoping, because both are read on a tagged bucket **before** ABAC is enabled on it (the Tag_Condition would deny them there). Neither action reveals object data. Under the one determined contingency of Requirement 7.2 (the `HeadBucket` region header absent on a 403) it additionally carries `s3:GetBucketLocation`, which reveals a region and nothing else.
- **Data_Plane_Scoping**: the single exported constant (`'tag'` | `'tag-objects-only'` | `'allowlist'`) that selects how the three data-plane-granting stacks bound their S3 resources; set from the verification of Requirement 7.5.
- **Pinned_SDK**: the `boto3`/`botocore` that `portal-usecase-bucket-config` vendors into `edge-cv-portal/backend/layers/shared/python/` (its Requirement 9.13 and design §6.2: installed with `--no-deps`, exact pins, with a unit test asserting the `s3control` model carries the Bucket_Tag_Operations and the `s3` model carries `PutBucketAbac`/`GetBucketAbac`; `boto3==1.43.101` / `botocore==1.43.101` in that spec's current text). **Relied on, not changed:** this spec adds no pin, no vendoring step and no second operation test; a version bump is a joint change to both specs' text, never made here. Task 0.1 records the landed version.
- **ABAC_Registration**: the step the Attach_Step performs on a Portal_Account_Bucket after the Attach_Validator has passed it: `GetBucketAbac`; if the status is not `Enabled`, `PutBucketAbac(Enabled)`; one `bucket_abac_enabled` audit event per enable (success or failure). Never performed on a bucket that is not a Portal_Account_Bucket, never on an untagged bucket (the validator has already required the tag), never by any code path other than the Attach_Step and `create_s3_bucket`'s creation-time enable (the sibling's Requirement 9.5).
- **Verification_Notes**: this spec's working record of commands run, counts, probe tables and live evidence. It lives at `.agents/portal-authz-scoping/verification-notes.md` in the workflow's **uncommitted** state directory; the committed spec directory carries no verification notes (unlike other specs in this repository), because the record names live account resources even in masked form.
- **Portal_Own_Buckets**: the portal artifacts bucket, the component bucket (Component_Bucket_Name), and the inference-results bucket (`dda-inference-results-<account>`); granted by explicit ARN, never by tag.
- **Results_Bucket_Override**: the optional use-case attribute `inference_uploader_s3_bucket` (set by operators through a direct DynamoDB update per `INFERENCE_UPLOADER_CONFIG.md`; no portal API writes it) that replaces `dda-inference-results-<account>` as the destination of device inference-result uploads and of the workflow-tuning Sample_Store (`captures.py:90`, `tuning_settings.py:199–206`, `deployments.py:1501`). When set to a name outside `dda-inference-results-*` it is a use-case bucket like any other: part of the Lifecycle_Set and of the device need list.
- **Lifecycle_Set**: the portal-account buckets over which the ABAC lifecycle (tag, enable, audit, backfill, report) runs: `s3_bucket` ∪ `data_s3_bucket` ∪ `additional_s3_buckets` ∪ Results_Bucket_Override of every use case, minus the Portal_Own_Buckets (excluded by name). A Portal_Own_Bucket that a use case nevertheless lists (the bucket-config spec refuses the artifacts and component buckets as `portal_bucket` but treats the inference-results bucket as a use-case-account bucket) stays excluded: it is reached on the roles that hold its explicit statement (Captures, WorkflowTuning, Deployments) and on no other role unless an administrator tags and enables it by hand; the audit script reports such a listing as `listed-portal-own` (information, not a compliance failure).
- **Resolved_Allowlist**: the bucket list computed at deploy time from the Portal_Own_Buckets plus the Lifecycle_Set of every use case; used for bucket-level statements under `'tag-objects-only'` and for everything under the `'allowlist'` fallback (owner gate G1).
- **Registration_Report**: the fields `tagged` (the bucket carries the Portal_Managed_Tag `dda-portal:managed=true` — not mere eligibility, which the sibling also grants for `dda-portal:created-by=portal` alone), `abac_enabled`, `iam_reachable`, `remedy` computed by the Attach_Step for every bucket Attached in a request and returned by every writer's success response: `POST /usecases` (`s3_bucket`, `data_s3_bucket`, each `additional_s3_buckets` entry), `PUT /usecases/{id}` (a changed `s3_bucket` or `data_s3_bucket`, each `additional_s3_buckets_add` entry), `POST /usecases/{id}/data/configure` (a changed `data_s3_bucket`) — as a per-bucket map `registration: {<bucket>: {...}}` — and `POST /s3-buckets` (the one created bucket, **inside the sibling's `bucket` object** beside its `name`, `region`, `portal_created`, `tags`, `abac`, `added_to_usecase` — its design §5.5 step 7; task 0.1 pins the nesting; there `abac_enabled := abac == 'enabled' or abac_action in ('enabled', 'already_enabled')`, because the auto-add's Attach_Step runs on the created bucket and may enable ABAC after a failed creation-time enable, the sibling's `abac` being `'enabled' | 'failed'` by its Requirement 9.5). **On `POST /s3-buckets` without `usecase_id`** (the wizard's `S3BucketPicker` path, where no Attach_Step runs because there is no record to attach to) the handler computes the same four fields itself: `tagged` is `true` (the tag write succeeded or the sibling's 500 was returned), `abac_enabled := abac == 'enabled'`, and `iam_reachable`/`remedy` come from calling the Attach_Step's `_probe` directly on the execution role with `just_enabled = (abac == 'enabled')` and `registration_remedy(tagged, abac_enabled, iam_reachable, 'portal', data_plane_scoping())` — so the report is never `null` on either creation path and the wizard shows the same `remedy` text as the allow button.
- **Device_Role**: `GreengrassV2TokenExchangeRole` in a use-case (or single) account, assumed by devices through IoT credentials.
- **Device_Read_Buckets**: for a use case, the buckets devices may read that the Device_Role_Template's name patterns do not already cover — `s3_bucket` and every `additional_s3_buckets` entry whose name matches neither `dda-*` nor `*-dda-*` (the out-of-pattern members of the sibling's Allowed_Bucket_Set, except `data_s3_bucket`: no device code path reads training data, and that bucket may live in a separate data account where an identity-policy grant is inert). Devices read these for component artifacts (`s3_bucket`) and for workflow or trigger payload references (`python_bridge.py:482`, `payload_fetch.py:476` — any `s3://` URI a workflow names). A bucket in another account is not device-readable even when allowed (its own bucket policy would also have to admit the Device_Role, which the portal does not write).
- **Device_Access_Document**: one inline policy named `DDAUseCaseDeviceAccess` on the Device_Role, written by `deployments.py` (on deployment create, on the Deployments role) and by `usecases.py` (on `PUT /usecases/{id}` when the Device_Read_Buckets change — `s3_bucket`, `additional_s3_buckets_add`/`_remove` — and on `DELETE /usecases/{id}`, on the UseCases role), holding **one read statement per use case** (`Sid: UseCase<usecase_id without hyphens>`, `Resource` = the bucket and `/*` ARNs of every bucket in its Device_Read_Buckets) and one write statement (`Sid: UseCase<id>Results`) for inference-result writes on a Results_Bucket_Override outside `dda-inference-results-*`; a use case with empty Device_Read_Buckets and no out-of-pattern override has no statement. Maintained read-merge-write per use case; capped by `DEVICE_ACCESS_POLICY_MAX_BYTES`.
- **Device_Role_Template**: the repository's description of the Device_Role's S3 access — `DDAPortalComponentAccessPolicy` (`usecase-account-stack.ts`), the `GreengrassComponentS3Access` inline policy written by `station_install/setup_station.sh`, `station_install/create-edge-device-iam-role.sh`, `station_install/edge-device-iam-policy.json`, the `DDAWorkflowTuningSampleAccess` inline policy written by `deployments.py`, and (after this spec) the Device_Access_Document.
- **Hand_Attached_Policy**: a policy attached to a portal-managed role that no Device_Role_Template or CDK template produces.
- **Drift_Check**: a read-only script that lists a portal-managed role's inline and attached policies and reports every Hand_Attached_Policy, every use case with a deployment whose Device_Access_Document statement is missing, and, for portal Lambda roles, every unconditioned S3 object statement.
- **Enforcement_Acknowledgement**: the CDK context value `allowLegacyRoles=true` that a CLI deploy must pass when it deploys the compute stack with Registry_Enforcement unset (D7).
- **Runbook_Task**: a task that performs an account write, a deploy, or a device-affecting step (the ABAC probe and backfill, the portal deploy, the post-deploy verification's throwaway test resources — buckets, their tags and ABAC status, throwaway use cases and the component-bucket-policy and EventBridge writes their creation performs — the device-role evidence generation and policy detachment, the station-template verification on a lab device, landing on the trunk) — marked **RUNBOOK (owner-approved; formerly OWNER)** in `tasks.md`; these are the tasks earlier revisions marked OWNER, re-marked under the owner's recorded go-ahead. The owner approved these in advance; each is written as an executable runbook — exact commands, pre-checks with their expected output, the write, the verification, the rollback — and the implementation executes it only when every pre-check passes. A failed pre-check STOPS the task and asks the owner; the implementation never substitutes a guess for a pre-check.
- **Historical_Evidence_Window**: the device-role usage evidence read **backwards** from today — IAM service-last-accessed data over its available lookback (up to 400 days; **S3 management actions only**: the IAM User Guide's action-last-accessed table lists no object-level S3 action — `GetObject`, `GetObjectVersion`, `PutObject`, `PutObjectTagging`, `DeleteObject`, `ListBucket` are absent — and no resource dimension) and CloudTrail over its retention (90 days; `lookup-events` carries management events only — both the bucket dimension and the data-action dimension exist only where an S3 data-event trail or server access logging covers the device role's buckets) — rather than a future waiting period; the owner fixed the detachment timing as "immediately after the portal deploy, on this evidence". Evidence without a data-event source is recorded as "indeterminate: no bucket dimension and no data-action dimension" and never passes a bucket or action pre-check vacuously (Requirement 8.5).
- **Fresh_Registration**: the station installer provisioning a new, confirmed-free thing name on a device that carries no live Greengrass core — a dedicated spare, or a lab Jetson the owner explicitly names for re-provisioning (backed up first; restored or re-registered to its use-case device group afterwards). The installer always provisions at the fixed root `/aws_dda/greengrass/v2` (`setup_station.sh:1050`), so it cannot add a second core beside a live one (Requirement 8.3).

## Requirements

### Requirement 1: Use-case creation requires an explicit permission (I1, D1)

**User Story:** As a portal operator, I want use-case creation to require a permission that PortalAdmins hold, so that a use case — and the account grants its creation performs — cannot be created by any authenticated user.

#### Acceptance Criteria

1. WHEN a caller invokes `POST /usecases` without the Use_Case_Creator_Permission at the global scope, THE UseCases handler SHALL answer 403 with the Refusal_Envelope (`error_code: 'INSUFFICIENT_PERMISSIONS'`), write an `unauthorized_access` audit event (the audit table is the only table written: `log_audit_event` is a `put_item` on it, `shared_utils.py:343–359`), and perform no write to the use-cases or user-roles tables, no STS call and no Account_Grant.
2. WHEN a caller holding the Use_Case_Creator_Permission invokes `POST /usecases`, THE UseCases handler SHALL proceed exactly as it does today for that caller (creation, creator auto-assigned UseCaseAdmin, follow-on configuration) subject to Requirements 2 and 3.
3. THE UseCases handler SHALL evaluate the Use_Case_Creator_Permission through `rbac_manager.has_permission(user_id, 'global', Permission.CREATE_USECASES, user)`, so the decision is made by the same resolver, in both Registry_Enforcement states, as every other permission in the portal.
4. THE role matrix SHALL keep `Permission.CREATE_USECASES` on PortalAdmin only (D1).

### Requirement 2: Proof of control before any account grant (I1, D2)

**User Story:** As a portal operator, I want the portal to prove it can assume the use case's role in the named account before it grants that account anything, so that a request naming an account the caller does not control performs no grant.

#### Acceptance Criteria

1. WHEN `POST /usecases` is invoked with an `account_id` (multi-account body), THE UseCases handler SHALL, after the grammar of Requirement 3.1 and BEFORE any STS call, check that `account_id` is in the Trusted_Account_List, answering 400 with the Refusal_Envelope (`error_code: 'ACCOUNT_NOT_TRUSTED'`, message naming the remedy: add the account to `trustedUseCaseAccountIds` and redeploy the portal) otherwise; and SHALL then obtain Proof_Of_Control — a successful `sts:AssumeRole` on the supplied `cross_account_role_arn` (which the grammar pins to `arn:aws:iam::<account_id>:role/DDAPortalAccessRole`) with the supplied `external_id` — BEFORE the use-case record is written and BEFORE any Account_Grant.

WHEN Proof_Of_Control fails (AssumeRole denied, role not found, or the assumed account differs from `account_id`), THE UseCases handler SHALL answer 400 with the Refusal_Envelope (`error_code: 'ACCOUNT_CONTROL_NOT_VERIFIED'`, message naming the remedy: deploy `DDAPortalUseCaseAccountStack` in that account and supply its external id — correct because the account is already known to be trusted), write a `create_usecase` audit event with `result='failure'` and `reason='account_control_not_verified'` (or `'account_not_trusted'` for 2.1's refusal), and perform no write to the use-cases or user-roles tables and no grant (the audit row is the only write).
3. 4. WHEN `POST /usecases` is invoked with a single-account body (no `account_id`), THE UseCases handler SHALL derive the account from `sts:GetCallerIdentity` as today and SHALL require no AssumeRole and no Trusted_Account_List check (the grants target the portal's own account).
5. THE account rules SHALL run after the `UPDATE_USECASES` gate, the existing tuning-settings and additional-list validation and the record fetch, and **before** the bucket-config spec's attach validation (the Attach_Step) and `update_item`, so a body that changes both `account_id` and `s3_bucket` and fails Proof_Of_Control is refused with no eligibility probe. Account moves are API-only: the frontend's Edit modal is unchanged (it carries neither `external_id` nor `sagemaker_execution_role_arn`, so a modal-only move could never pass Proof_Of_Control), and the ADMIN_GUIDE SHALL document the move body (`account_id`, `cross_account_role_arn`, `external_id`, `sagemaker_execution_role_arn`).
   1. WHEN the body carries no Account_Field_Change — whether it omits the seven fields or echoes their stored values, as the frontend's Edit modal does on every save — THE handler SHALL process the request exactly as today, for Single_Account_Records and multi-account records alike (no grammar check on account fields, no STS call of any kind).
   2. WHEN the stored record is a Single_Account_Record, the merged `account_id` equals the portal account — **an absent merged `account_id` (a legacy record storing none, with a body supplying none) counts as the portal account**, since such a record's grants target the portal's own account — and `cross_account_role_arn` is not an Account_Field_Change, THE handler SHALL skip the role-ARN grammar, the Trusted_Account_List check and Proof_Of_Control for the use-case account (as on create) and SHALL apply only the grammar to the data-account triple, and only when one of its three fields is an Account_Field_Change and the merged `data_account_id` is set and differs from `account_id` (the data-account credentials are proven by the bucket-config spec's probe when `data_s3_bucket` changes, as in 2.3); WHEN `sagemaker_execution_role_arn` is an Account_Field_Change, THE handler SHALL also apply the Requirement 3.1 grammar to its merged value (account segment equal to the portal account), with no STS call.
   3. WHEN the stored record is a Single_Account_Record and the body moves the use case to another account (an Account_Field_Change of `account_id` to a value that differs from the portal account), THE body SHALL supply both `account_id` and `cross_account_role_arn` (else 400 `error_code: 'INVALID_ROLE_ARN'`), `external_id` defaulting to the stored value, and the merged `sagemaker_execution_role_arn` SHALL be in the new account (else 400 `error_code: 'INVALID_ROLE_ARN'`, message: supply sagemaker_execution_role_arn in account <new>), and THE handler SHALL run the grammar, the Trusted_Account_List check and Proof_Of_Control on the merged values before `update_item`.
   4. WHEN the stored record is not a Single_Account_Record and an Account_Field_Change of `account_id` makes the merged `account_id` equal the portal account, THE handler SHALL refuse with 400 (`error_code: 'INVALID_ACCOUNT_ID'`, message: a multi-account use case cannot be converted to single-account); a multi-account record that already stores the portal account and has it echoed back carries no change and falls under 2.5.1.

   6. WHEN the stored record is a Single_Account_Record and the body carries an Account_Field_Change of `cross_account_role_arn` (a value other than the stored one — an echoed stored `:root` ARN is not a change) while the merged `account_id` stays the portal account, THE handler SHALL refuse with 400 (`error_code: 'INVALID_ROLE_ARN'`, message: a single-account use case does not carry a cross-account role; supply `account_id` to move it) and perform no write, no `sts:AssumeRole` and no `sts:GetCallerIdentity`. 6. THE UseCases handler SHALL route `POST /usecases/verify-role` to `verify_role` (today the generic `POST` branch shadows it). `verify_role` SHALL first require the Use_Case_Creator_Permission through the same `has_permission` call as Requirement 1.3 (its only consumer is the onboarding wizard, which Requirement 1 makes PortalAdmin-only; a route that makes the portal attempt an AssumeRole with a caller-chosen ARN and external id is gated like the creation it precedes), answering 403 `{status: 'failed', error, error_code: 'INSUFFICIENT_PERMISSIONS'}` and an `unauthorized_access` audit event otherwise. THE handler SHALL share one Proof_Of_Control helper with the creation and update paths so they can never disagree. The frontend's call shape (`{role_arn, external_id}` with no `account_id`) SHALL be covered by a test in both Registry_Enforcement states that asserts `error` is present on every non-200 response.
7. THE Proof_Of_Control helper SHALL use a 900-second session, a fixed session name, SHALL never log or return the temporary credentials, and SHALL distinguish STS throttling or network failure (`reason='sts_unavailable'`) from denial; WHEN the create, update or verify-role path receives `sts_unavailable`, THE handler SHALL answer 503 with the Refusal_Envelope (`error_code: 'STS_UNAVAILABLE'`; on verify-role additionally `status: 'failed'`), audited as a failure with `reason='sts_unavailable'`, and perform no write to the use-cases or user-roles tables and no grant.
8. WHEN the permission check of Requirement 1.3 or 2.6 raises `RegistryUnavailable`, THE handler SHALL answer 500 `{'error': 'Authorization check failed'}` (the envelope the shared permission decorators already use, `shared_utils.py:1385/1421`) rather than the handler's generic 500, so a registry outage is distinguishable from a code failure in the logs and the response.

### Requirement 3: Account grants are validated, idempotent and bounded (I1)

**User Story:** As a portal operator, I want every account grant the portal writes to be well-formed, repeatable and reversible, so that bucket policies and event-bus permissions cannot grow without bound or hold statements for accounts no use case references.

#### Acceptance Criteria

1. THE UseCases handler SHALL validate `account_id` and `data_account_id` as exactly twelve ASCII digits; `cross_account_role_arn` as exactly `arn:aws:iam::<account_id>:role/DDAPortalAccessRole` and `data_account_role_arn` as exactly `arn:aws:iam::<data_account_id>:role/DDAPortalDataAccessRole` (the only names the account templates create and the only name the portal's own `sts:AssumeRole` grant permits — any other name could only ever fail at STS with a misleading error); and `sagemaker_execution_role_arn` (required for multi-account bodies, `usecases.py:1120`, later passed through `iam:PassRole`) as an IAM role ARN (`^arn:aws:iam::(\d{12}):role/[\w+=,.@/-]+$`) whose account segment equals `account_id` — on `PUT /usecases/{id}` on the **merged** values whenever any account field is an Account_Field_Change (so a move whose merged `sagemaker_execution_role_arn` is still in the old account is refused with `INVALID_ROLE_ARN`, Requirement 2.5.3/2.5.5); answering 400 (`error_code: 'INVALID_ACCOUNT_ID'` / `'INVALID_ROLE_ARN'`) otherwise, before any STS call. The stored account-root ARN of a Single_Account_Record SHALL never be run through the role-ARN grammar. **The same grammar, from the same two shared-layer validators, SHALL apply to the third writer of the data-account triple:** `POST /usecases/{id}/data/configure` (`data_management.configure_data_account`, `data_management.py:673–735`, UseCaseAdmin gate at 690) today copies `data_account_id`, `data_account_role_arn` and `data_account_external_id` from the body into `update_item` (fields 704–709, write at 716) with no check; it SHALL validate the triple on the body merged over the stored record before `update_item` — `data_account_id` twelve digits, `data_account_role_arn` exactly `arn:aws:iam::<merged data_account_id>:role/DDAPortalDataAccessRole` — refusing 400 `INVALID_ACCOUNT_ID` / `INVALID_ROLE_ARN` with the Refusal_Envelope, and SHALL refuse (400 `INVALID_ACCOUNT_ID`, message: supply `data_account_id`) a `data_account_role_arn` or `data_account_external_id` when no `data_account_id` is stored or supplied. A body that touches none of the three fields is processed as today (the bucket-config spec's Requirement 12.8 rules on `data_s3_bucket` are unchanged). No STS proof is added on this route (Requirement 2.3's rule: the data account is proven by the sibling's eligibility probe).
2. THE component-bucket policy writer (`update_component_bucket_policy_for_greengrass`) and the shared-components policy writer (`add_usecase_to_component_bucket_policy`) SHALL be idempotent: two calls for the same account produce one set of statements/principals, and the number of statements SHALL be bounded by the number of distinct use-case accounts.
3. WHEN the serialized component bucket policy would exceed `COMPONENT_BUCKET_POLICY_MAX_BYTES` (20,000 bytes — deliberately conservative under the 20,480-byte S3 limit, defined once in `shared_utils.py`), THE writer SHALL refuse the write with a logged warning and a `failed` status rather than attempt a `PutBucketPolicy` that S3 rejects.
4. WHEN `DELETE /usecases/{id}` succeeds and no other use case references the deleted use case's `account_id`, THE UseCases handler SHALL remove that account's statements from the component bucket policy and its EventBridge permission (best-effort, logged, returned in the response as `grants_removed`), SHALL leave them in place when another use case still references the account, and SHALL never remove the portal's own account's statements.
5. THE UseCases handler, the SharedComponents handler **and the bucket-config spec's `portal_owned_buckets()`** (which, as landed at `shared_utils.py:2296`, inlines the same `COMPONENT_BUCKET`-or-prefix-region-account derivation in `shared_utils.py`) SHALL resolve the Component_Bucket_Name through one shared-layer helper (`component_bucket_name()`: `os.environ.get('COMPONENT_BUCKET') or f"{os.environ.get('COMPONENT_BUCKET_PREFIX', 'dda-component')}-{os.environ.get('AWS_REGION', 'us-east-1')}-{os.environ.get('PORTAL_ACCOUNT_ID', '')}"` — the `shared_components.py:50–54` derivation exactly, every read defaulted, from the environment the CDK already provides to every handler; the UseCases function's environment carries no `COMPONENT_BUCKET` today, so an environment-only read would fail on every multi-account creation) — one definition, three consumers, so no two readers of the name can disagree; `portal_owned_buckets()` keeps its existing contract (it omits the component bucket when `PORTAL_ACCOUNT_ID` is unset and `COMPONENT_BUCKET` is empty): the helper stays a plain derivation that always returns a string with no unset failure path, and `portal_owned_buckets()` keeps its own guard — it calls `component_bucket_name()` only when `COMPONENT_BUCKET` or `PORTAL_ACCOUNT_ID` is set, else contributes nothing — so the sibling's existing `portal_owned_buckets` unit cases pass unchanged (asserted), including `test_portal_owned_buckets_prefix_derivation` (`test_usecase_bucket_config_units.py:287–296`), which deletes `AWS_REGION` and expects the `us-east-1` name. THE literal default bucket name at `usecases.py:1349` SHALL be deleted; and a unit test SHALL assert that, for a given region and account, the helper's result equals the name `compute-stack.ts:1068` grants the UseCases role on, and that with `AWS_REGION` unset it yields `dda-component-us-east-1-<account>`.
6. WHEN any Account_Grant write fails after Proof_Of_Control succeeded, THE UseCases handler SHALL behave as today (creation succeeds, the failure is returned in the response and audited) — Proof_Of_Control changes what is attempted, not how partial failures are surfaced.

### Requirement 7: Portal Lambda roles are scoped to portal-managed buckets by tag condition (I5, D5-B)

**User Story:** As a portal operator, I want the portal Lambda roles' S3 data-plane grant bounded to buckets that carry the Portal_Managed_Tag and are ABAC_Enabled, so that a handler defect cannot be used to reach every bucket the account can see, and so that registering a new bucket needs no redeploy.
