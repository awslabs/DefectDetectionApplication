# Bugfix Requirements Document

## Introduction

On August 6, 2026, dedicated AMD64 Build Job `06c9a7ac-6b65-49ee-acdd-db8bf6d0cc03` for `aws.edgeml.dda.LocalServer.amd64` was authorized and dispatched to Dedicated_Build_Server `srv-5b214096-91a9-41b7-9d62-cc03ba205c15`. It was submitted at 12:02:53 PM, started at 12:02:54 PM, and failed at 12:03:02 PM. Build Details reported only `The build agent SSM command ended with status 'Failed' before reporting a build result.` and `No log output was recorded for this build job.` Authorization succeeded, so this is a build execution and observability defect, not an RBAC defect.
This bugfix covers systematic diagnosis and correction of the Build_Job, SSM command, build-agent result, Build Log, terminal-state cleanup, and queue-promotion contract without presupposing the historical root cause. Static inspection establishes relevant gaps but not the incident cause: `build_events.py` consumes only the SSM event's command ID and status and has no permission or call to retrieve the final invocation; the job log points only to the SSM stdout stream; and the dispatcher defaults to `/opt/dda/DefectDetectionApplication` while fleet-launched dedicated servers clone to `/home/ubuntu/DefectDetectionApplication`.
RBAC authorization, role matrices, and builds/fleet navigation remain exclusively in the existing `build-fleet-rbac-visibility` spec and are explicitly out of scope. No production-code change, deployment, or live build is part of this requirements phase.

**Amendment (third defect facet — ephemeral runner storage exhaustion):** Read-only investigation of ephemeral `JP6` Build Job `bd91c5d8-ac7e-4125-becc-711860660f2e` (August 8, 2026; arm64, `m6g.4xlarge`, correct feature-branch `source_ref`, `config_snapshot` `volume_size_gb=100`, `max_runtime_hours=4`) established a further failure mode via the DynamoDB job record, SSM invocation `2068c6dc-e0a0-4abd-a66c-e410c81950f2`, and the CloudWatch build log. The runner lifecycle was clean and the build ran roughly 100 minutes, well under its runtime budget, but the JP6 target exports two large multi-stage docker images (`backend_tegra_gpu_enabled` and `backend_generic`; CUDA 11.4 + 12.6, TensorRT, Triton, cuDNN) concurrently via docker-compose. Docker is snap-installed, so all layer storage lives under `/var/snap/docker/common` on the single 100 GB gp3 root volume shared with the repository clone, buildkit cache, and `/tmp`. Both final layer-extraction steps failed with `no space left on device` (ENOSPC), the agent's local log tee itself hit ENOSPC, `gdk` exited 1, and the agent emitted a normal failed callback. A secondary observability defect compounded diagnosis: `scripts/portal-build-agent.sh` builds the durable error message via `tail -n 5 "$BUILD_LOG" | head -c 512`, which keeps the front of very long buildkit failure lines and drops the trailing root cause, so the durable DynamoDB error message and portal Build Details ended at `write /var/snap/docker/common/` and hid the actual cause; the full cause survived only in the CloudWatch stream. The approved user decision is to double the ephemeral runner volume default from 100 GB to 200 GB (config default and/or per-target sizing so JP6/arm64 receives at least 200 GB). Requirements 1.19–1.22, 2.20–2.23, and 3.13–3.15 below cover this facet.
## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN the observed authorized dedicated `AMD64` command reaches terminal SSM status `Failed` before its build-agent callback/result is recorded THEN the system marks the Build Job `failed` with a generic `AGENT_COMMAND_FAILED` message and the portal shows no recorded log output, concealing why the approximately eight-second execution failed
1.2 WHEN an agent SSM command reaches `Failed`, `TimedOut`, or `Cancelled` THEN the event consumer uses only the event's command ID and status and does not retrieve or persist the invocation's terminal `Status`, `StatusDetails`, `ResponseCode`, `StandardOutputContent`, `StandardErrorContent`, or available execution timestamps and identities
1.3 WHEN SSM provides stdout, stderr, or status details but the configured stdout CloudWatch stream is absent, empty, delayed, or incomplete THEN the Build Log API returns an empty event page and terminal Build Details can show only `No log output was recorded for this build job.`
1.4 WHEN raw command or agent output is considered for persistence or display THEN the current build-fleet path defines no common redaction contract that guarantees AWS credentials or tokens, repository credentials, passwords, authorization values, and other secrets are excluded from DynamoDB, API responses, portal output, Lambda/CloudWatch logs, and Audit_Log details
1.5 WHEN a dispatched build does not report a terminal callback/result THEN the generic command fallback does not fully distinguish command launch rejection, command execution failure, timeout, cancellation/interruption, successful command completion with a missing result, and Dedicated_Build_Server or ephemeral-runner lifecycle loss
1.6 WHEN an agent command reaches a terminal status but its SSM EventBridge notification is missing or delayed THEN no periodic reconciliation reads the recorded `ssm.command_id`, so the Build Job can remain non-terminal until another watchdog acts and the missing-callback/result condition is not diagnosed directly
1.7 WHEN an agent callback and SSM terminal notification are duplicated, delayed, concurrent, or delivered in either order THEN terminal absorption prevents outcome resurrection, but a later event cannot complete missing invocation diagnostics and diagnostic completeness depends on delivery order
1.8 WHEN any terminal path ends a dispatched job THEN status transition, `ended_at`, diagnostic/audit persistence, dedicated-server `running_build_job_id` release or ephemeral cleanup, oldest-eligible queue promotion, and duplicate-dispatch prevention are implemented across separate handlers and ticks without one tested invariant covering every terminal outcome
1.9 WHEN the dispatcher constructs a dedicated build-agent command THEN it assumes the configured repository path, script, shell tools, permissions, build target, EventBridge bus, source ref, AWS environment, and architecture contract are valid; the default dispatcher path differs from the fleet launch clone path, but no preflight validates that contract or proves this mismatch caused the historical failure
1.10 WHEN automated coverage exercises dispatch and event idempotence THEN it does not reproduce a terminal SSM `Failed` invocation containing stdout/stderr and no agent callback, demonstrate the current loss of those diagnostics, or cover the full target/mode matrix and cleanup/promotion invariants
1.11 WHEN a diagnostic test supplies secret-shaped values in invocation status details, stdout, or stderr THEN current tests do not prove those values are redacted from every durable and user-visible surface while preserving useful context
1.12 WHEN live verification is considered for this defect THEN starting a dedicated or ephemeral build can consume costly compute and publish artifacts, while the historical SSM, CloudWatch, and DynamoDB evidence may instead be inspectable read-only if still retained
1.13 WHEN the newly reported Build Job is marked failed for exceeding maximum runtime THEN the currently retained timeout evidence is insufficient to determine whether the job was making active progress, stalled or hung, legitimately waiting in a queue, delayed during provisioning, or actually beyond an active-execution safety ceiling, so it does not establish that extending the timeout or queueing the job is the correct remedy
1.14 WHEN a Build Job moves through queue wait, provisioning, and active execution THEN the current timeout evidence does not separately expose the duration and applicable budget of each lifecycle phase
1.15 WHEN a Build Job waits for an occupied Dedicated_Build_Server or an unfinished serialized predecessor THEN a maximum-runtime outcome can be reported without evidence proving that only active execution time, rather than legitimate queue wait, was charged to the execution budget
1.16 WHEN an active Build Job exceeds a simplistic elapsed wall-clock threshold THEN the current outcome does not establish whether meaningful progress and heartbeats remained fresh, whether the heartbeat became stale, whether progress stalled despite liveness, or whether a non-extendable hard safety ceiling was crossed
1.17 WHEN the runtime characteristics of target and execution-mode combinations differ THEN the current timeout evidence does not establish an evidence-supported hard-ceiling value for each combination, including JP5 and JP6 source builds that may legitimately take one to two hours or longer
1.18 WHEN a maximum-runtime, stale-heartbeat, or stalled-progress outcome occurs THEN current diagnostics do not necessarily expose the timing phase, configured budget and its source, observed duration, last heartbeat and meaningful progress, target and execution mode, and safely redacted supporting logs
1.19 WHEN an ephemeral `JP6` build exports its two large multi-stage docker images concurrently on a snap-docker runner whose layer storage, repository clone, buildkit cache, and `/tmp` share the single default 100 GB root volume THEN the system exhausts disk space (`no space left on device`) during final layer extraction and fails the build after approximately 100 minutes of costly compute, as evidenced by Build Job `bd91c5d8-ac7e-4125-becc-711860660f2e`
1.20 WHEN a build fails because the runner's disk is exhausted THEN the system classifies the outcome as a generic build failure (`BUILD_FAILED`) with no distinct disk-exhaustion error classification distinguishing it from source, compilation, or packaging defects
1.21 WHEN the build agent constructs the durable error message from long failure lines via `tail -n 5 "$BUILD_LOG" | head -c 512` THEN the truncation keeps the head of each long line and drops the decisive trailing cause, so the durable DynamoDB error message and portal Build Details end mid-path (for example at `write /var/snap/docker/common/`) and conceal `no space left on device`, leaving the root cause discoverable only in the CloudWatch stream
1.22 WHEN an ephemeral build is dispatched or fails THEN no dispatch preflight records available disk capacity for the build/docker storage path and failure diagnostics carry no disk usage evidence, so storage exhaustion cannot be confirmed or ruled out from the durable record
### Expected Behavior (Correct)

2.1 WHEN a recorded agent SSM command reaches any terminal status before a terminal build-agent callback/result is durably recorded THEN the system SHALL retrieve the final invocation when available and reconcile the command and callback evidence before finalizing the Build Job
2.2 WHEN final SSM invocation data is available THEN the system SHALL persist a bounded, structured diagnostic record associated with the Build Job and/or Build Log containing the command and instance identities, terminal status, status details, response code, available timestamps, stdout, and stderr after safe redaction; unavailable fields SHALL be identified as unavailable rather than fabricated
2.3 WHEN SSM provides useful diagnostics for a dispatched command failure THEN the Build Log API and portal SHALL present an actionable, safely redacted error and retained diagnostic output and SHALL NOT present only `No log output was recorded for this build job.`
2.4 WHEN a dispatched build terminates without an agent result THEN the system SHALL classify and expose stable safe error codes for command launch failure, command execution failure, timeout, cancellation/interruption, missing callback/result after command success, and infrastructure/server lifecycle failure, preserving the actual observed category instead of collapsing it into one generic failure
2.5 WHEN an agent command terminal notification is missing or delayed THEN the scheduled reconciliation path SHALL inspect the persisted command ID within a bounded interval, remain non-terminal for genuinely in-progress commands, and finalize a terminal or missing-result outcome without waiting for an unrelated runtime timeout
2.6 WHEN callbacks and command notifications are duplicated, delayed, concurrent, or reordered THEN the system SHALL converge on one deterministic terminal outcome and one merged redacted diagnostic record; later evidence MAY complete missing diagnostics but SHALL NOT overwrite a valid agent result, change an absorbed terminal status, or duplicate audit side effects
2.7 WHEN any launch failure, execution failure, timeout, cancellation/interruption, missing result, infrastructure loss, success, or publish outcome becomes terminal THEN the system SHALL set the correct status and `ended_at`, clear the owning server's busy/current-job state or perform the required ephemeral cleanup, promote the oldest eligible queued job, and prevent duplicate agent dispatch exactly once under retries and races
2.8 WHEN a dedicated `AMD64` build is prepared THEN the system SHALL validate the repository/working path, agent script existence and executability, required shell tools and environment, command argument/quoting contract, `AMD64` to `x86_64` target mapping, component identity, callback bus, and required AWS access before costly work; the correction SHALL address only causes supported by reproduced or retained evidence
2.9 WHEN equivalent contract checks and integration tests run for `AMD64_NVIDIA`, `JP5`, `JP6`, and ephemeral execution where applicable THEN the system SHALL prove their target mappings, invocation environments, callback/result reporting, diagnostics, and terminal cleanup remain valid while accommodating intentional architecture-specific differences
2.10 WHEN diagnostics contain AWS access keys, secret keys, session tokens, bearer/authorization tokens, repository credentials, passwords, signed URLs, or other configured secret patterns THEN the system SHALL redact the secret values before any DynamoDB, API, UI, Lambda/CloudWatch, Build Log, or Audit_Log write while retaining enough non-secret context to troubleshoot the failure
2.11 WHEN bug-condition exploration and later property-based tests generate SSM terminal statuses, available/missing invocation fields, stdout/stderr, callback presence and ordering, duplicate events, target/mode combinations, and queued followers THEN the tests SHALL first reproduce the current `Failed`-with-output/no-callback diagnostic loss and after the fix SHALL prove diagnostic preservation, redaction, terminal absorption, deterministic classification, exactly-once cleanup/promotion, queue ordering, and no duplicate dispatch for all generated cases
2.12 WHEN verification begins THEN safe mocked/unit/integration reproduction SHALL run before live verification; read-only inspection of retained historical SSM, CloudWatch, DynamoDB, and audit records MAY be used, but the system SHALL NOT deploy or start any chargeable build without explicit user approval
2.13 WHEN investigating the newly reported maximum-runtime failure THEN the system SHALL collect sufficient lifecycle, heartbeat, progress, and retained-log evidence to distinguish active execution, stalled or hung execution, legitimate queue wait, provisioning delay, and hard-ceiling expiry before selecting a remedy, and SHALL NOT infer that the timeout must be extended or the job must be queued from the failure label alone
2.14 WHEN a Build Job moves through queue wait, provisioning, and active execution THEN the system SHALL measure and report each phase separately, and queue wait or provisioning time SHALL NOT consume active execution runtime unless an explicit independent snapshotted queue-wait or provisioning budget applies to that phase
2.15 WHEN a Build Job waits for an occupied Dedicated_Build_Server or an unfinished serialized predecessor THEN the system SHALL keep the job queued in oldest-eligible order and SHALL NOT fail it under the active-execution maximum-runtime budget
2.16 WHEN an active Build Job continues to provide fresh correlated heartbeats and meaningful progress below its target-and-mode hard safety ceiling THEN the system SHALL NOT fail it solely because a simplistic wall-clock threshold elapsed; WHEN heartbeats become stale or heartbeats remain fresh while meaningful progress stalls THEN the system SHALL classify and report those as distinct failure conditions
2.17 WHEN runtime budgets are resolved for a Build Job THEN the system SHALL apply a non-extendable hard safety ceiling that is configurable by target and execution mode and snapshotted for that job; evidence that JP5 or JP6 source builds may legitimately take one to two hours or longer SHALL inform later configuration without mandating any particular ceiling before sufficient evidence is collected
2.18 WHEN a maximum-runtime, stale-heartbeat, or stalled-progress outcome occurs THEN the system SHALL expose the timing phase, configured budget and configuration source, observed duration, last heartbeat and meaningful progress, target and execution mode, and available safely redacted logs, with unavailable evidence identified rather than fabricated
2.19 WHEN validating any timeout correction THEN safe mocked and property-based validation SHALL precede any costly live build; changing production timeout configuration or launching a dedicated or ephemeral build SHALL require explicit user approval
2.20 WHEN an ephemeral runner volume size is resolved for a new Build Job THEN the system SHALL apply a raised default of 200 GB (double the prior 100 GB), snapshot the resolved size per job in `config_snapshot` as today, and leave previously created jobs' snapshots unchanged; per-target volume sizing MAY be supported provided the `JP6` target resolves to at least 200 GB
2.21 WHEN agent or build output contains ENOSPC/disk-exhaustion patterns (for example `no space left on device`) THEN the system SHALL classify the failure with a stable distinct error code (for example `RUNNER_DISK_FULL`) consistent with the classification philosophy of 2.4, instead of collapsing it into a generic build failure
2.22 WHEN a durable error message is derived from long failure lines THEN the system SHALL preserve the tail (root-cause end) of each captured line rather than truncating from the head, within the existing bounded-size and redaction limits, so that causes such as `no space left on device` survive into the durable record and portal Build Details
2.23 WHEN an ephemeral build is dispatched THEN preflight SHALL record the available disk capacity for the build/docker storage path, and WHEN a build fails THEN disk usage evidence SHALL be included in the failure diagnostics when available, with unavailable measurements identified rather than fabricated
### Unchanged Behavior (Regression Prevention)

3.1 WHEN a build agent reports normal building, publishing, success, build failure, or publishing failure events THEN the system SHALL CONTINUE TO apply the existing state-machine semantics, preserve successful result and partial-publish metadata, publish artifacts as before, and treat terminal states as absorbing
3.2 WHEN dedicated dispatch runs THEN the system SHALL CONTINUE TO enforce the DynamoDB single-job allocation lock, pre-dispatch `pgrep` verification, on-server `flock`, serialization watchdog, deferral cadence, and no-concurrent-build guarantees
3.3 WHEN cancellation is requested for a queued, running, provisioning, or terminal Build Job THEN the system SHALL CONTINUE TO apply the existing SSM stop, `pgrep` confirmation, interrupted/cancelled classification, conflict response, and fail-closed cancellation semantics
3.4 WHEN multiple jobs target a dedicated server or belong to one ordered request THEN the system SHALL CONTINUE TO preserve predecessor gates, original submission ordering, oldest-eligible queue promotion, and conditional-write protection against stale release or duplicate dispatch
3.5 WHEN users access build and fleet routes or navigation THEN the system SHALL CONTINUE TO use the existing role checks, permission matrices, authorization envelopes, and navigation rules without modification; all RBAC changes remain in `build-fleet-rbac-visibility`
3.6 WHEN clients use Build Jobs history, detail, logs, cancellation, or retry APIs THEN the system SHALL CONTINUE TO receive the existing response envelopes, field meanings, pagination tokens, retention behavior, and status values, with backward-compatible optional diagnostic additions only
3.7 WHEN supported targets are selected THEN the system SHALL CONTINUE TO map `JP5` and `JP6` to arm64 and `AMD64` and `AMD64_NVIDIA` to x86_64, retain their current component identities, and support both dedicated and ephemeral modes except where an existing validation intentionally restricts a combination
3.8 WHEN compute is interrupted, a server stops/terminates, provisioning fails, runtime expires, or serialization is violated THEN the system SHALL CONTINUE TO use the existing distinct status, retry eligibility, cleanup, notification, and audit semantics except for the added safe diagnostics and reconciliation required above
3.9 WHEN successful dedicated or ephemeral builds run THEN the system SHALL CONTINUE TO stream logs, emit callbacks, record published component versions and image references, retain logs, release/terminate compute, and promote queued work without material behavioral change
3.10 WHEN existing portal-build backend and frontend tests run THEN the system SHALL CONTINUE TO pass them unchanged; new exploration, integration, redaction, and property-based coverage SHALL be additive and SHALL require no live AWS build
3.11 WHEN any maximum-runtime, stale-heartbeat, or stalled-progress outcome becomes terminal THEN the system SHALL CONTINUE TO stop and clean up the affected execution, release its server allocation, promote the oldest eligible queued work, record the audit outcome, and prevent duplicate dispatch exactly once under retries and races while preserving serialization
3.12 WHEN any legacy or updated runtime deadline is evaluated THEN the system SHALL CONTINUE TO treat `now == deadline` as not expired and `now > deadline` as expired, and SHALL CONTINUE TO honor legacy snapshotted `max_runtime_hours` compatibility unless evidence supports a deliberate versioned change
3.13 WHEN an existing Build Job's `config_snapshot` records a volume size, instance type, or spot/on-demand choice THEN the system SHALL CONTINUE TO honor that job's snapshotted values, and new-job resolution of instance type and spot semantics SHALL CONTINUE TO behave as before except for the raised volume-size default and optional per-target sizing in 2.20
3.14 WHEN an ephemeral or dedicated build completes successfully within available disk capacity THEN the system SHALL CONTINUE TO stream logs, emit callbacks, publish artifacts, terminate or release compute, and record results without material behavioral change from the added disk preflight, disk diagnostics, or error-message tail preservation
3.15 WHEN build failures unrelated to disk exhaustion produce short or already-complete error lines THEN the system SHALL CONTINUE TO record their existing durable error messages, bounded sizes, and redaction behavior, with the tail-preserving truncation of 2.22 changing only which end of over-length lines is retained
