# Requirements Document

## Introduction

Every portal handler that reads or writes S3 on behalf of a use case does so with server-side credentials: the use case's cross-account role, its Data Account role, or (for single-account use cases) the portal Lambda's own execution role. Today the bucket those credentials are pointed at is taken from whatever `s3://` URI or `bucket` field the request carries. The shared client helper `get_s3_client_for_bucket` (`edge-cv-portal/backend/layers/shared/python/shared_utils.py:2095-2128`) reads the use case's `data_s3_bucket`, `data_account_id` and `account_id` only to choose which role to assume; nothing checks that the bucket belongs to the use case. Model validation and import, vLLM registration, training-manifest validation, manifest transformation, pre-labeled dataset validation, data-management folder browsing and upload URLs, and few-shot example references all follow that pattern. Two of those routes (`POST /models/validate`, `GET /usecases/{id}/data/folders`) require no role, the pre-labeled dataset module has no authorization at all, and labeling-job creation (`POST /labeling`), whose job record carries the few-shot references the worker later reads, has no role check on its general path.

This spec introduces **use-case bucket configuration**: every use case has an explicit, exact-name set of buckets it may use (its S3 bucket, its Data Account bucket, and an administrator-managed list of additional buckets), and every S3 access the portal performs on behalf of a use case is resolved through that set before any STS or S3 call. The portal's own buckets (the artifacts bucket and the Greengrass component bucket) are excluded from every set by rule — a record that names one, or a tag on one, does not admit it. Buckets the portal creates are tagged and recorded as portal-created and, when created for a known use case, added to that use case's additional buckets automatically. A bucket may only be attached to a use case when it is portal-created or carries the existing `dda-portal:managed=true` tag, and only when no other use case has it configured or claimed by tag — a claim outlives the use case it names, so a deleted use case's portal-created buckets stay its own until a PortalAdmin re-attaches one deliberately (a PortalAdmin may also share a configured bucket) — so configuring a use case cannot be used to point the portal at a bucket nobody handed to it or at another use case's storage. The S3 browse experience in the frontend marks buckets outside the set and offers UseCaseAdmins an "Allow for this use case" action, with the tag requirement explained when the bucket is not eligible.

Because several existing flows change behaviour, this spec carries an explicit customer-impact review (design "Customer impact") whose answer to "is this a breaking change?" is carried into the CHANGELOG and the verification notes, and a pre-deploy sizing script that counts the affected records before the deploy.

Everything here is portal-side (shared layer, Lambda handlers, one IAM addition on the UseCases Lambda role, the shared layer's vendored SDK, frontend, docs). No file under `src/`, `station_install/` or `hmi/` changes, so no LocalServer build and no on-device verification is owed.

### Out of scope

- **Role resolution changes.** `RBACManager.get_user_role`, `_legacy_role` and the `PORTAL_REGISTRY_ENFORCED` default stay as they are (Requirement 7 documents the production posture only). Retiring the legacy resolution order belongs to `portal-jwt-role-privilege-escalation`.
- **Who may create a use case, and proof of control over the roles a use case names.** `POST /usecases` keeps its current authorization; `cross_account_role_arn` / `data_account_role_arn` / `data_account_external_id` changes keep their current `UPDATE_USECASES` gate and are not verified by assuming the role. Both are decided in `portal-authorization-and-iam-scoping` (owner decisions D1, D2). This spec's eligibility rule (Requirement 10) is written so it composes with that decision: it checks the bucket, not the role.
- **Scoping the portal Lambda roles' S3 grant by tag** (`aws:ResourceTag/dda-portal:managed`) and the `GetBucketAbac` discovery grant. That is the follow-on IAM scoping spec; this spec only makes sure portal-created buckets are ready for it (tags written with the ABAC-compatible API, ABAC enabled at creation) and vendors the SDK both specs need.
- **Granting any Lambda role `sts:AssumeRole` on `DDAPortalDataAccessRole`.** The template grants AssumeRole only on `DDAPortalAccessRole` (`compute-stack.ts:546-553`); whether a live deployment can assume the Data Account role is UNVERIFIED and is measured before deploy (Requirement 14.3). The eligibility probe for a Data Account bucket fails closed when it cannot (Requirement 10.2); the grant itself is the follow-on's proof-of-control decision.
- **Re-checking stored `artifact_s3` buckets at compile or package time.** Previously imported models keep working (Requirement 8).
- **Additional buckets inside a separate Data Account.** `additional_s3_buckets` entries are buckets in the use case's own account (reached through `cross_account_role_arn`, or the execution role for single-account use cases). One Data Account bucket per use case (`data_s3_bucket`) is modelled, as today; a per-entry account model is the follow-on's (Requirement 1.7, design §1.5).
- **Sharing one bucket between use cases without a PortalAdmin.** A bucket already configured on use case A, or tagged `dda-portal:usecase-id` for A (whether or not A still exists), can be attached to use case B only by a PortalAdmin (Requirement 10.3). The residual that remains by design: a tagged bucket configured on *no* use case and carrying *no* claim is the administrator's opt-in pool and may be attached by any UpdateUsecases holder of any use case in that account; deleting a use case returns its administrator-tagged (unclaimed) buckets to that pool, because the portal removes no tags on deletion (the admin guide carries the manual step).
- **The grantees of the bucket policies `create_usecase` writes.** `update_component_bucket_policy_for_greengrass` (`usecases.py:620`) grants the caller-supplied `account_id` on the portal component bucket, and `update_data_bucket_policy_for_sagemaker` (`usecases.py:192`) grants the caller-supplied `sagemaker_execution_role_arn` on the Data Account bucket. Requirement 10 bounds *which bucket* the second one writes to (an eligible one); *who* is granted is proof-of-control work and is the follow-on's D2/I1.
- **Use case records written before this change.** Binding is membership and the attach rules (Requirement 10) apply when a value changes, so a record whose configured bucket would not pass them today keeps that bucket until someone changes it. Such records are identified once, before the deploy, by the sizing script's identifier mode and corrected by the operator through `PUT /usecases/{id}` (Requirement 14.4); no code path re-validates them.
- **Adjacent items noted while reading the handlers, tracked separately**: `POST /training/{id}/compile` skipping its role check when the body sets `auto_triggered`; `POST /shared-components/provision` registered without an authorizer; the Ground Truth branch of `POST /labeling` (`labeling.py:create_labeling_job` 331–400, no role check; it uses configured buckets only, so it is not a bucket-selection sink — the DDA branch *is* gated here, Requirement 4.6); the dormant `manifest_validator.py`; the dead `/transform-manifest` branch in `data_management.py`; `GET /s3-buckets` listing portal-account buckets without a role check; the device token-exchange role's hand-attached S3 policies.

## Glossary

- **Use_Case**: the DynamoDB record in `USECASES_TABLE` (`usecases.py`), with `s3_bucket`, optional `data_s3_bucket`, `cross_account_role_arn`, optional `data_account_role_arn`, and (new) `additional_s3_buckets`.
- **Allowed_Bucket_Set**: `allowed_s3_buckets(usecase)`: the exact-name set `{s3_bucket, data_s3_bucket, *additional_s3_buckets}` with empty values, names failing the Membership_Grammar and Portal_Owned_Buckets dropped.
- **Portal_Owned_Buckets**: `portal_owned_buckets()`: the portal artifacts bucket (`PORTAL_ARTIFACTS_BUCKET` — one bucket for the whole portal holding plugin sources, workflow packaging staging, test datasets, labeling annotations and previews under keys the portal chooses) and the Greengrass component bucket (`COMPONENT_BUCKET`, else `{COMPONENT_BUCKET_PREFIX}-{AWS_REGION}-{PORTAL_ACCOUNT_ID}`, the derivation `shared_components.py:53–54` uses). Never members of any Allowed_Bucket_Set, never attachable, reachable through no bucket-selected code path; the helper has no opt-in parameter (Requirement 2.10). "Portal_Bucket" below means the artifacts bucket specifically. The inference-results bucket is a use-case-account bucket and is not portal-owned.
- **Bare_Key_Reference**: a few-shot example reference that does not start with `s3://`. Two code paths used to resolve it against the Portal_Bucket; after this change it is refused at creation and resolves to nothing elsewhere (Requirement 2.7).
- **Additional_Buckets**: the new optional list attribute `additional_s3_buckets` on a Use_Case (buckets in the use case's own account). Written only through `UPDATE_USECASES`-gated paths and the portal's own bucket creation.
- **Membership_Grammar**: the exact-match-safe character class `^[A-Za-z0-9._-]{3,255}$` used for membership and URI parsing. It admits legacy bucket names (uppercase, underscores, up to 255 characters) and excludes `@`, `:`, `/`, whitespace and control characters; exactness comes from the string comparison, not from the grammar.
- **Bucket_Name_Grammar**: the S3 general purpose bucket naming rules as a regular expression: 3–63 characters, lowercase letters, digits, `.` and `-`, starting and ending with a letter or digit, no `..`, not formatted as an IPv4 address. Used only for names of buckets the portal is about to create.
- **Binding**: the check `assert_bucket_allowed(usecase, bucket, purpose)` that a bucket is in the Allowed_Bucket_Set, performed before any STS or S3 call.
- **Sink**: a code location where a bucket name that the caller influenced (directly in the request, or earlier through a persisted record) reaches an S3 or STS call made with portal-held credentials.
- **Refusal**: the HTTP 400 response a bound Sink returns for a bucket outside the Allowed_Bucket_Set (`error_code: bucket_not_allowed`) or for a bucket that may not be attached (`error_code: bucket_not_eligible`).
- **Portal_Created**: a bucket created by `POST /s3-buckets`; it carries the tags `dda-portal:managed=true` and `dda-portal:created-by=portal` (and `dda-portal:usecase-id=<id>` when created for a use case).
- **Managed_Tag**: the existing bucket tag `dda-portal:managed=true` that the portal's role templates and `data_management.list_buckets` already key on.
- **Eligible**: a bucket whose tags (read with the credentials the helper would use for it) include the Managed_Tag or the Portal_Created marker.
- **Unclaimed**: a bucket that is not `s3_bucket`, `data_s3_bucket` or an Additional_Buckets entry of any *other* Use_Case, and whose `dda-portal:usecase-id` tag (if present) names the target use case. A tag naming any other use case is a claim **whether or not that use case still exists** (a claim outlives the use case it names). A PortalAdmin may attach a claimed bucket (sharing, or re-homing a deleted use case's bucket).
- **Attach**: any operation that makes a bucket part of a Use_Case's Allowed_Bucket_Set: setting `s3_bucket` or `data_s3_bucket` at creation or update (`POST /usecases`, `PUT /usecases/{id}`, `POST /usecases/{id}/data/configure`), adding an Additional_Buckets entry through the API or the frontend, or the portal's own auto-add at bucket creation.
- **Clear**: sending `None`, `''` or a whitespace-only value for `data_s3_bucket`; it removes the Data Account bucket from the set and is neither grammar-checked nor probed. `s3_bucket` cannot be cleared.
- **Configured_Bucket**: `s3_bucket` or `data_s3_bucket`; "the configured buckets" means both.
- **Manifest_Reference**: a `source-ref` or `anomaly-mask-ref` (or other `*-ref`) S3 URI found inside a manifest's content.
- **UpdateUsecases holder**: a principal for whom `rbac_manager.has_permission(user_id, usecase_id, Permission.UPDATE_USECASES, user)` is true (UseCaseAdmin on that use case, or PortalAdmin).

## Requirements

### Requirement 1: Central bucket binding in the shared layer

**User Story:** As the portal, I want one predicate in one place that decides whether a bucket may be used on behalf of a use case, so that no handler can forget it and no two handlers disagree.

#### Acceptance Criteria

1. THE shared layer SHALL provide `parse_s3_uri(uri, *, require_key=True) -> (bucket, key)` that accepts only URIs of the form `s3://<bucket>/<key>` where `<bucket>` matches the Membership_Grammar, raising `InvalidS3Uri` (a `ValueError` subclass with `error_code = 'invalid_s3_uri'`) for anything else, including an uppercase scheme, a user-info or port component, an empty bucket, a URI longer than 2048 characters, and (when `require_key`) an empty key. `f"s3://{bucket}/{key}"` SHALL round-trip to the accepted input.
2. THE shared layer SHALL provide `portal_owned_buckets() -> frozenset[str]` equal to the Portal_Owned_Buckets (empty environment values omitted) and `allowed_s3_buckets(usecase) -> frozenset[str]` equal to the Allowed_Bucket_Set. Entries that fail the Membership_Grammar SHALL be dropped (logged at WARNING), never widened or normalised. Entries that are Portal_Owned_Buckets SHALL be dropped (logged at WARNING) even when the record names them, so no Portal_Owned_Bucket is ever a member of any Allowed_Bucket_Set.
3. THE shared layer SHALL provide `assert_bucket_allowed(usecase, bucket, purpose, *, actor=None, event=None)` that returns `None` when `bucket in allowed_s3_buckets(usecase)` and otherwise raises `BucketNotAllowed` (a `ValueError` subclass carrying `bucket`, `usecase_id`, `purpose`, `error_code = 'bucket_not_allowed'`) after writing an audit event with `action = 's3_bucket_refused'`, `result = 'denied'` and details `{bucket, purpose}` (never the object key). A bare `bucket` that fails the Membership_Grammar SHALL raise `InvalidBucketName` (`error_code = 'invalid_bucket_name'`) without an audit row.
4. Membership SHALL be an exact string comparison. No prefix, suffix, substring, account-id or case-insensitive match SHALL ever admit a bucket.
5. `get_s3_client_for_bucket(usecase, bucket_name, session_name)` SHALL call `assert_bucket_allowed` as its first statement, before role selection and before `assume_usecase_role`, and SHALL gain no parameter that bypasses it. For buckets in the Allowed_Bucket_Set the role it selects and the client it returns SHALL be byte-for-byte what they are today. The shared layer SHALL log `botocore.__version__` once at import so the deployed SDK version can be read from any function's log stream.
6. THE shared layer SHALL expose the role-selection step of the helper as a private function reused by the eligibility probe (Requirement 10), so the probe uses exactly the credentials the helper would use for that bucket without a way to obtain an unchecked client.
7. For an Additional_Buckets entry the role selected SHALL be the use case's `cross_account_role_arn` (the execution role for single-account use cases) and never the Data Account role; Additional_Buckets are buckets in the use case's own account.

### Requirement 2: Every caller-influenced sink is bound before I/O

**User Story:** As a UseCaseAdmin, I want every portal operation that touches S3 on my use case's behalf to stay inside the buckets configured for it, so that a request can never steer the portal's credentials at another bucket.

#### Acceptance Criteria

1. `training.validate_marketplace_manifest` and `training.validate_detection_manifest` SHALL parse the manifest URI with `parse_s3_uri` and bind its bucket before obtaining a client; `create_training_job` SHALL bind `dataset_manifest_s3` right after its role check and before any STS or S3 call, **regardless of `model_source`** (today only the marketplace path reads the manifest), returning the Refusal.
2. `training.transform_manifest` SHALL bind both the source bucket and the output bucket (explicit `output_manifest_uri`, or the source bucket when omitted) before any STS or S3 call and SHALL obtain the client used for `put_object` through `get_s3_client_for_bucket` for the output bucket (reusing the source client only when the buckets are equal).
3. `model_import.validate_model` and `model_import.import_model` SHALL bind the `model_s3_uri` bucket immediately after the existing `s3://` / `.tar.gz` shape checks and before any credential step. `validate_model_artifact` SHALL obtain its S3 client through `get_s3_client_for_bucket` (the hand-rolled client construction at `model_import.py:1034-1042` and the module-local `assume_usecase_role` at `model_import.py:794-815` are removed), so a refused bucket is never downloaded even by a future caller that skips the handler check. Consequence, stated and pinned by a unit test: for a use case with a separate Data Account, a model URI in `data_s3_bucket` is read with the Data Account role (the helper's choice, as every other sink), where today it is read with `cross_account_role_arn`; the design's Customer impact table carries this row.
4. `model_import.register_vllm_model` SHALL bind the `s3_model_artifact` bucket before its `head_object`; `model_import.evaluate_fit_check` SHALL bind the persisted `s3_model_artifact` bucket before its HEAD and, when refused, SHALL report `status: 'unverified'` exactly as it does for any other estimation failure.
5. `pre_labeled_datasets.validate_manifest` and `pre_labeled_datasets.create_dataset` SHALL bind the `manifest_s3_uri` bucket before any STS or S3 call and before persisting; `validate_manifest_file` SHALL require its `s3_client` argument (no fallback to a module client) and the module-level execution-role S3 client SHALL be removed; the segmentation mask probe SHALL use the use case's client for the mask bucket and SHALL skip the probe with a warning when the mask bucket is outside the Allowed_Bucket_Set (Requirement 6).
6. `data_management.list_folders`, `create_folder`, `get_upload_url` and `get_batch_upload_urls` SHALL bind the request-supplied `bucket` (after the fallback to the configured data bucket) before any credential step, and SHALL obtain their S3 client through `get_s3_client_for_bucket` for that bucket (replacing the `get_data_account_credentials` + `create_s3_client` pair), so the credential path follows the bucket as it does at every other Sink. Consequence, stated and pinned by a unit test: for a separate-Data-Account use case, `s3_bucket` and Additional_Buckets entries are reached with `cross_account_role_arn` where today the Data Account role is used for every bucket; `data_s3_bucket` and single-account use cases are unchanged. `get_data_account_credentials` remains for `list_buckets`.
7. Few-shot example references: `dda_labeling.create_dda_job` SHALL refuse, as validation errors, every `example_images` reference that is not an `s3://` URI parseable by `parse_s3_uri` (`error_code: invalid_s3_uri`, which covers Bare_Key_References) or whose bucket is outside the Allowed_Bucket_Set (`error_code: bucket_not_allowed`); `dda_labeling.rerun_prelabels` SHALL refuse with the Refusal when any stored few-shot reference of the job is not an in-set `s3://` URI; `dda_labeling._example_image_urls` SHALL skip, without presigning, any stored reference that is a Bare_Key_Reference (log WARNING naming the job id and kind) or an `s3://` reference whose bucket is outside the set (log WARNING naming the bucket, never the key), and SHALL no longer resolve anything against the Portal_Bucket; `dda_autolabel_worker._few_shot_ref_location` SHALL resolve a Bare_Key_Reference to `(None, None)` so the worker's existing "could not be resolved" `GenerationFailure` is raised for that example, and `_resolve_few_shot_images` SHALL continue to read `s3://` references through `get_s3_client_for_bucket` (unchanged signature). Because the worker catches `GenerationFailure` per task, a job with a refused or bare reference fails pre-label generation for every task (status `Failed`), as it does today when an example object has been deleted. The two docstrings and the worker test's comment that describe references as "portal artifacts bucket keys or full s3:// URIs" SHALL be rewritten to describe `s3://` URIs inside the use case's configured buckets.
8. `model_converter.convert_model` and `inspect_model_endpoint` SHALL bind through `is_trusted_model_source` as restated in Requirement 4.
9. Callers whose bucket comes from use-case configuration only (`s3_browse_utils.browse_s3_bucket`, the labeling, labeling-worker and auto-label workers, the labeling preview, `_create_detection_training_job`) SHALL need no new check and SHALL keep flowing through `get_s3_client_for_bucket`, so they are covered by Requirement 1.5. `create_usecase`'s Data Account bucket policy, CORS and tag operations SHALL run only after the bucket has passed eligibility (Requirement 10), which is the binding for those three writes.
10. For every Sink in 2.1–2.8, a request naming a bucket outside the Allowed_Bucket_Set SHALL produce no `sts:AssumeRole` call and no S3 call of any kind; and a request naming a Portal_Owned_Bucket SHALL be refused by every Sink, with no exception, including when the use case record names that bucket (Requirement 1.2).

### Requirement 3: Role requirements on model validation and inspection

**User Story:** As a portal operator, I want validating a model artifact to require the same role as importing it, because the two are one flow and validation performs the same privileged download.

#### Acceptance Criteria

1. `POST /models/validate` SHALL require `check_user_access(user_id, usecase_id, 'DataScientist')`, with the same arguments as `POST /models/import` (no `user_info`), so the two gates resolve identically for every principal in both `PORTAL_REGISTRY_ENFORCED` states.
2. `POST /models/inspect` (`model_converter.inspect_model_endpoint`) SHALL require `check_user_access(user_id, usecase_id, 'DataScientist')`, matching `POST /models/convert`.
3. A principal refused by either gate SHALL receive 403 and SHALL cause no `get_usecase_details`, STS or S3 call.
4. Tests SHALL pin the chosen `user_info` behaviour in both flag states (Requirement 15.6).

### Requirement 4: Pre-labeled dataset and labeling-job authorization, and converter trusted sources

**User Story:** As a portal operator, I want the pre-labeled dataset routes and labeling-job creation to check membership and role like every other handler, and the converter's trusted-source rule to use exact bucket names.

#### Acceptance Criteria

1. `GET /datasets/pre-labeled` (list) and `GET /datasets/pre-labeled/browse` SHALL require `check_user_access(user_id, usecase_id)` for the `usecase_id` named in the query string, answering 400 when it is absent and 403 when the check fails.
2. `GET /datasets/pre-labeled/{id}` SHALL read the record first (404 when absent) and then require `check_user_access(user_id, record['usecase_id'])`.
3. `POST /datasets/pre-labeled`, `POST /datasets/validate-manifest` and `DELETE /datasets/pre-labeled/{id}` SHALL require `check_user_access(..., 'DataScientist')` against the request's `usecase_id` (create, validate) or the record's `usecase_id` (delete), before any S3 or write.
4. `create_dataset` SHALL record `created_by` from the authenticated user using the shared `_display_identity(email, username, user_id)` convention, not from the request body.
5. `model_converter.is_trusted_model_source(model_s3_uri, usecase)` SHALL return true only when the parsed bucket is an exact member of `allowed_s3_buckets(usecase) ∪ TRUSTED_MODEL_BUCKETS`. The account-id substring rule (`TRUSTED_MODEL_ACCOUNTS`, `model_converter.py:105-110`) SHALL be removed; the environment variable, if still set, SHALL be ignored with one WARNING at import time.
6. `dda_labeling.create_dda_job` (reached from `POST /labeling` with `labeling_backend: DDA`, `labeling.py:274` → `241` → `dda_labeling.py:1594`, which has no authorization on its general path today) SHALL require `rbac_manager.has_permission(user['user_id'], usecase_id, Permission.CREATE_LABELING_JOBS, user)` — the `user_info`-threading form every other DDA labeling route obtains from `@rbac_check` — as soon as a non-empty `usecase_id` has been read from the body, answering 403 with an `unauthorized_access` audit row and making no S3, STS or DynamoDB write when the check fails, and 500 (never 403) when the registry is unavailable. With `PORTAL_REGISTRY_ENFORCED` off the Cognito `custom:role` claim is therefore honoured exactly as on the sibling labeling routes; with it on, a registry row is required. `CREATE_LABELING_JOBS` is held by DataScientist, UseCaseAdmin and PortalAdmin. The Ground Truth branch of `POST /labeling` is unchanged (Out of scope).

### Requirement 5: Refusal contract

**User Story:** As a frontend developer and as an API client, I want refusals to be machine-readable and self-explanatory.

#### Acceptance Criteria

1. Every Refusal SHALL be HTTP 400 with a JSON body containing `error` (human-readable message), `error_code` (`bucket_not_allowed`, `bucket_not_eligible`, `invalid_s3_uri` or `invalid_bucket_name`), `bucket`, `usecase_id` where known, and `remedy` (text naming what to do). The `error_code` tokens are lowercase snake_case by decision, departing from the SCREAMING_SNAKE codes of the trunk's `_workflow_error` / `error_response` envelopes: the same tokens serve as `reason` values (5.3), as audit-detail values (`s3_bucket_refused.details.reason`) and as the frontend's `bucketErrors.ts` branch keys, so one spelling travels unchanged from the shared layer to the UI; the handlers this spec touches do not use those envelopes, and the `usecase_not_found` named here is these handlers' own 404 body, not the workflow envelope's `USECASE_NOT_FOUND`.
2. For `bucket_not_allowed` the remedy SHALL say that a UseCaseAdmin can allow the bucket for this use case under Additional S3 buckets, or that the object can be placed in the use case's configured bucket; when the refused bucket is a Portal_Owned_Bucket, the remedy SHALL say that the portal's own buckets cannot be a target for this operation and cannot be allowed for a use case.
3. For `bucket_not_eligible` the body SHALL also carry `reason` (one of `portal_bucket`, `no_tags`, `tag_missing`, `tagging_unreadable`, `bucket_not_found`, `credentials_unavailable`, `account_mismatch`, `bucket_configured_on_other_usecase`, `too_many_buckets`) and the remedy SHALL name the action for that `reason` (per-reason table in design §1.2/§1.6): for `no_tags` / `tag_missing`, tagging with the S3 Control `TagResource` API, quoted as `aws s3control tag-resource --account-id <bucket owner account> --resource-arn arn:aws:s3:::<bucket> --tags Key=dda-portal:managed,Value=true` (the `s3api` namespace has no `tag-resource`); for `tagging_unreadable`, first tagging the bucket if it is not tagged (through the use case's role an untagged bucket also answers `AccessDenied`), else enabling ABAC on the bucket or granting `s3:GetBucketTagging` in its bucket policy, and on a single-account portal deployed with a data-bucket allowlist adding the bucket to that list and redeploying; checking the role/external id trust for `credentials_unavailable`; for `bucket_configured_on_other_usecase`, asking a PortalAdmin ("configured on, or tagged for, another use case"; the other use case's id is not returned) or, when the claiming use case no longer exists, asking a PortalAdmin or having an administrator remove the `dda-portal:usecase-id` tag; for `portal_bucket`, that the portal's own buckets cannot be allowed.
4. THE frontend SHALL branch on `error_code` (and `reason`) only, never on message text.
5. Handlers whose existing error mapping would turn a `BucketConfigError` into a generic 400 or 500 SHALL catch it first so the body in 5.1 is what the caller receives.

### Requirement 6: Manifest-internal references outside the set

**User Story:** As a data scientist, I want a manifest whose images live in another bucket to still be accepted, with a clear warning, because SageMaker's execution role decides at training time whether those images are readable.

#### Acceptance Criteria

1. WHEN a Manifest_Reference names a bucket outside the Allowed_Bucket_Set, the validating handler (`validate_marketplace_manifest`, `validate_detection_manifest`, `transform_manifest`, pre-labeled `validate_manifest_file`) SHALL skip the existence spot-check for that reference, SHALL add a warning naming the bucket (not the key) to the response's `warnings`, SHALL log it at INFO, and SHALL NOT fail the request.
2. No S3 or STS call SHALL be made for a skipped reference, and no `s3_bucket_refused` audit event SHALL be written for it (the request itself is not refused).
3. `create_training_job` SHALL surface validation `warnings` in its success response.

### Requirement 7: Role-resolution posture

**User Story:** As an operator, I want to know that production must run with registry enforcement on, without this feature changing how roles resolve.

#### Acceptance Criteria

1. `get_user_role`, `_legacy_role`, `registry_enforcement_enabled` and the CDK default SHALL be unchanged.
2. `deploy-infrastructure.sh` SHALL print a clearly marked warning when the enforcement value resolved for the deploy is not `true`, naming the backfill script and the `PORTAL_REGISTRY_ENFORCED=true` form.
3. The README deployment section and `ADMIN_GUIDE.md` SHALL state that production deployments run `PORTAL_REGISTRY_ENFORCED=true` after `backfill_portal_registry.py` has been run.

### Requirement 8: Existing records keep working

**User Story:** As a customer with models imported before this change, I want compile, package and deploy to keep working.

#### Acceptance Criteria

1. Binding SHALL apply at access time to the bucket the request names; `compilation.py`, `packaging.py` and `greengrass_publish.py` SHALL NOT re-check stored `artifact_s3` / `s3_model_artifact` buckets.
2. Eligibility (Requirement 10) SHALL be checked when a bucket is attached, never on every access; re-sending an unchanged value never probes.
3. A Use_Case record without `additional_s3_buckets` SHALL behave exactly as one with an empty list; a record whose `data_s3_bucket` is absent, `None` or `''` SHALL behave identically.
4. A Use_Case whose configured bucket has a legacy name (uppercase, underscore, longer than 63 characters) SHALL keep working: the Membership_Grammar admits it and `parse_s3_uri` parses URIs naming it.

### Requirement 9: Portal-created buckets are tagged, recorded and auto-added

**User Story:** As a UseCaseAdmin, I want a bucket the portal creates for my use case to be usable immediately, without manually adding it.

#### Acceptance Criteria

1. `POST /s3-buckets` SHALL validate `name` against the Bucket_Name_Grammar (400 `invalid_bucket_name`) and SHALL accept an optional `usecase_id`.
2. WHEN `usecase_id` is present, the handler SHALL load the use case (404 `usecase_not_found` when absent), SHALL require `rbac_manager.has_permission(user_id, usecase_id, Permission.UPDATE_USECASES, user)` (403 otherwise), SHALL require the use case to be single-account (`not is_cross_account_setup(usecase)`), answering 400 `bucket_not_eligible` with `reason: account_mismatch` otherwise, and SHALL require the current Additional_Buckets count to be below the cap (Requirement 12.3; `too_many_buckets` otherwise), all before creating anything.
3. WHEN `usecase_id` is absent, the handler SHALL require the caller to be a PortalAdmin (`caller_is_portal_admin(user)`), the permission the only current frontend caller (the use-case onboarding wizard's `S3BucketPicker`, `UseCaseOnboarding.tsx:339`) will need once use-case creation is PortalAdmin-only; this is documented as the resulting permission and is not widened. The wizard hides "Create new bucket" for non-PortalAdmins and renders the 403 by code as a fallback.
4. The handler SHALL supply the tags `dda-portal:managed=true` (the existing Managed_Tag key and value, reused from `tag_bucket_for_portal` and the role templates) and `dda-portal:created-by=portal`, plus `dda-portal:usecase-id=<usecase_id>` when known, **in the `CreateBucket` request itself** (`CreateBucketConfiguration.Tags`; the configuration dict is built for every region, us-east-1 included, carrying `LocationConstraint` only outside us-east-1), using clients built for the bucket's `region`. A `CreateBucket` failure therefore leaves nothing tagged. The ABAC-compatible `s3control.TagResource` operation is the **fallback only** (9.5); there is no `PutBucketTagging` fallback: the shared layer vendors a boto3/botocore whose service models carry `CreateBucketConfiguration.Tags`, `TagResource` and `PutBucketAbac` (Requirement 9.13), so the operations are always present.
5. After `create_bucket` succeeds, the handler SHALL first enable ABAC on the new bucket (`PutBucketAbac`, `Status: Enabled`; failure non-fatal, logged at WARNING, reported as `abac: 'failed'`), and SHALL then read the tags back with `GetBucketTagging` on the region-bound client, retrying a `NoSuchTagSet` or a set lacking the two portal keys up to three attempts one second apart. WHEN the keys are present the read tags are the eligibility evidence for the auto-add (10.6). WHEN they are still missing the handler SHALL make **one** `s3control.TagResource` call with the same tags — made after ABAC is on, the documented path for tagging an ABAC-enabled bucket — followed by one more read; the order (create-with-tags → ABAC → read → fallback) means no step depends on whether `TagResource` is accepted on a bucket whose ABAC is off.
6. WHEN the tags cannot be confirmed (the fallback `TagResource` fails, or the read after it still lacks the keys), the handler SHALL answer 500 `error_code: bucket_tagging_failed` naming the bucket (the bucket is not deleted), SHALL NOT auto-add it, and SHALL audit `create_s3_bucket` with `result: failure`. A unit test SHALL assert the call order and that every `Tags` argument — in `CreateBucketConfiguration` and in the fallback `TagResource` — is exactly the `dda-portal:*` keys.
7. WHEN `usecase_id` is present and tagging succeeded, the handler SHALL add the bucket to that use case's Additional_Buckets with the conditional write of Requirement 12.3 (which also requires the record to still exist), emit `s3_bucket_allowed` with `source: auto_add`, and return `added_to_usecase: true`. WHEN that attach cannot be made (record deleted meanwhile, another use case had the name configured before the bucket existed, or a DynamoDB error), the response SHALL still be 201 with `added_to_usecase: false` and `add_error: {error_code: 'usecase_not_found' | 'bucket_not_eligible' | 'usecase_update_failed', reason?, remedy}` (the bucket exists and is tagged; a UseCaseAdmin can allow it from Additional S3 buckets), and the audit row SHALL record `added_to_usecase: false`.
8. WHEN `create_bucket` reports `BucketAlreadyOwnedByYou`, the handler SHALL answer 409 `error_code: bucket_already_exists` and SHALL NOT tag, enable ABAC, record or attach anything. BEFORE calling `create_bucket`, the handler SHALL refuse a portal-owned name (`portal_bucket`) and SHALL run the Unclaimed configuration `Scan` of Requirement 10.3 for the name: a name another use case already has configured is refused with 400 `bucket_configured_on_other_usecase` for a non-PortalAdmin with nothing created, so the portal never creates and tags a bucket that another use case's record already points at.
9. A bucket that becomes `s3_bucket` or `data_s3_bucket` during use-case creation seconds after the portal created it SHALL pass eligibility: `create_usecase` calls the attach validator with `retry=True` for those two fields, so the probe retries a `NoSuchTagSet` or a tag set lacking both keys up to three attempts one second apart before concluding (Requirement 10.5), covering tag read-after-write. No other caller opts in.
10. A bucket SHALL never be in a use case's Allowed_Bucket_Set merely because the portal created it for a different use case; a bucket tagged `dda-portal:usecase-id=<A>` is not Unclaimed for use case B (Requirement 10.3).
11. The response SHALL include `portal_created: true`, `tags` (the keys written), `abac`, `added_to_usecase` and, when applicable, `add_error`.
12. The UseCases Lambda role SHALL be granted `s3:CreateBucket`, `s3:TagResource` and `s3:PutBucketABAC` (the spelling the vendored SDK's `PutBucketAbac` documentation gives the permission, and the one the follow-on spec uses) on `arn:aws:s3:::*`, on that role only. The `TagResource` statement carries `StringEquals aws:RequestTag/dda-portal:created-by = portal` **only if** the documentation lists `aws:RequestTag/${TagKey}` as applying to `s3:TagResource` (recorded with URL and date in the design and the verification notes, and verified with `iam simulate-principal-policy` before deploy) — the S3 User Guide does (it restricts the tags passed in `TagResource` and `CreateBucket`, which also covers the tags supplied at bucket creation, 9.4), so the statement **is conditioned**; had it not, the statement would carry no condition and the bound would be the handler, which writes only `dda-portal:*` keys (unit-tested either way). This is a CDK change; deploy therefore includes a CDK diff and the IAM preservation baselines are updated through the approved-additions record.
13. The shared layer SHALL vendor `boto3==1.43.101` and `botocore==1.43.101` (with `s3transfer`, `jmespath`, `python-dateutil`, `six`; installed with `--no-deps` so the already-vendored `urllib3 2.8.0` tree is byte-identical), and a unit test SHALL assert, with `sys.path` set to the layer's `python/` directory, that `get_service_model('s3').operation_names` contains `PutBucketAbac` and `GetBucketAbac` and `get_service_model('s3control').operation_names` contains `TagResource`, `UntagResource` and `ListTagsForResource`.

### Requirement 10: Bucket eligibility when attaching

**User Story:** As a portal operator, I want an administrator in AWS, not a portal user, to decide which buckets the portal may ever be pointed at, and I want a use case's storage to stay its own.

#### Acceptance Criteria

1. WHENEVER a bucket is Attached to a Use_Case (as `s3_bucket` or `data_s3_bucket` at creation; as `s3_bucket` or `data_s3_bucket` at update through `PUT /usecases/{id}` **or** `POST /usecases/{id}/data/configure` when the value changes; as an Additional_Buckets entry via the API or the frontend action; via the portal's auto-add), the portal SHALL read the bucket's tags with `GetBucketTagging` using the credentials the helper would use for that bucket (Requirement 1.6) and SHALL proceed only when the tags include the Managed_Tag or `dda-portal:created-by=portal`.
2. WHEN the tags do not qualify, or `GetBucketTagging` fails for any reason (`NoSuchTagSet`, `AccessDenied`, `NoSuchBucket`, STS failure, other errors), the Attach SHALL be refused with 400 `bucket_not_eligible` and the matching `reason` (Requirement 5.3), before any record is written. Eligibility fails closed, including when the portal's Lambda role cannot assume the Data Account role (`credentials_unavailable`).
3. WHENEVER a bucket is Attached, the portal SHALL also require it to be Unclaimed: one `Scan` of `USECASES_TABLE` (`s3_bucket = :b OR data_s3_bucket = :b OR contains(additional_s3_buckets, :b)`, excluding the target use case) returning no item, and no `dda-portal:usecase-id` tag naming a different use case — **whether or not that use case still exists** (one `get_item` on the claimed id decides only the remedy text: the sharing remedy for an existing use case, the stale-claim remedy naming the PortalAdmin and the tag-removal alternative for a deleted one). Otherwise the Attach SHALL be refused with 400 `bucket_not_eligible`, `reason: bucket_configured_on_other_usecase`, **unless** `caller_is_portal_admin(user)`, in which case it proceeds and the validator's result carries `shared_with_usecases: <count>` and, for a claim naming a deleted use case, `stale_claim: true`. **Every writer** — `create_usecase` (`s3_bucket`, `data_s3_bucket`, each additional entry), `update_usecase` (each changed configured bucket and each add), `configure_data_account` (`data_s3_bucket`) and the auto-add — SHALL then emit, after its write succeeds, one audit event `s3_bucket_allowed` with `resource_type = 'usecase'`, `resource_id = usecase_id`, details `{bucket, attribute: 's3_bucket' | 'data_s3_bucket' | 'additional_s3_buckets', source: 'api' | 'create' | 'configure' | 'auto_add'}` plus `shared_with_usecases` when greater than zero and `stale_claim: true` when set, and the request's attribution, so the override is recorded on every path that can use it, not only on the additional-list add. A `Scan` or `get_item` error SHALL propagate as 500, never as a refusal or an acceptance.
4. The check SHALL apply to multi-account use cases too (cross-account and Data Account roles). Because S3 evaluates the tag condition on `DDAPortalAccessRole`'s `GetBucketTagging` only on buckets with ABAC enabled, `ADMIN_GUIDE.md` SHALL document the onboarding order as tag the bucket, enable ABAC on it, then create the use case (today's Step 5 moves before Step 3 and gains the ABAC step).
5. `probe_bucket_eligibility(usecase_like, bucket, *, retry=False)` SHALL conclude every outcome on the first read and never sleep by default; WHEN called with `retry=True` it SHALL retry `NoSuchTagSet` and a tag set lacking both qualifying keys up to three attempts with one second between attempts before concluding `no_tags` / `tag_missing`, every other outcome still being concluded on the first attempt. Only `create_usecase` SHALL pass `retry=True`, and only for `s3_bucket` and `data_s3_bucket` (through the attach validator's `retry` parameter). On a `PermanentRedirect`/301 that botocore's region redirector did not resolve, the probe SHALL retry once with a client for the region named by the response's `x-amz-bucket-region` header and SHALL conclude `tagging_unreadable` when the header is absent or that attempt fails. The per-request add list (`additional_s3_buckets_add` on `PUT /usecases/{id}`, `additional_s3_buckets` on `POST /usecases`) SHALL be capped at ten names (400 `invalid_field` beyond it), so one request runs at most ten probes with no sleep — bounded well under the 29 s API Gateway integration timeout without a wall-clock deadline. A unit test with a `time.sleep` recorder SHALL show zero sleeps for a ten-name add of untagged buckets and at most two sleeps per configured bucket for `create_usecase`.
6. The portal's own auto-add (Requirement 9.7) SHALL use the tags it read back after creation in the same request (Requirement 9.5) as the eligibility evidence; the attach validator SHALL run no probe of its own for it.
7. `tag_bucket_for_portal` SHALL no longer write tags to customer buckets (its write branch is removed; it becomes the read-only confirmation for the Data Account bucket and keeps its result keys), so the portal performs no `PutBucketTagging` on any bucket it did not create.
8. Re-sending an unchanged `s3_bucket` / `data_s3_bucket` value SHALL NOT trigger a probe; a Clear of `data_s3_bucket` SHALL NOT trigger a grammar check or a probe; absent, `None` and `''` SHALL compare equal when deciding whether a value changed.
9. The design SHALL list every remaining way a caller can influence which bucket a use case is bound to and show how each is covered, and SHALL state the residual explicitly, including what deleting a use case releases.
10. A guard test SHALL walk every function under `edge-cv-portal/backend/functions/*.py` and `layers/shared/python/*.py` with `ast` and classify as a **writer** any function whose body contains a `put_item` / `update_item` / `batch_writer` / `transact_write_items` call **and** names `s3_bucket`, `data_s3_bucket` or `additional_s3_buckets` in a write-shaping position (dict-literal key, list/tuple/set element, subscript-store slice, `ExpressionAttributeNames` alias value, or a string literal that also contains an update-expression token). It SHALL assert the module-qualified writer set equals `{usecases.create_usecase, usecases.update_usecase, usecases._add_additional_bucket, usecases._remove_additional_bucket, data_management.configure_data_account}` and that the only call sites of `_add_additional_bucket` / `_remove_additional_bucket` are `usecases.update_usecase` and `usecases.create_s3_bucket`. The rule's own detection SHALL be checked against a fixture module holding one function of each matching shape and one read-only consumer that must not match. The guard detects any new function that **names** the attributes in a write-shaping position; a pass-through writer that never names them is outside what a literal rule can see, and the design states the allow-list convention (`updatable_fields`, `data_fields`) that reviewers hold new writers to. (On the unmodified tree the rule finds exactly `create_usecase`, `update_usecase` and `configure_data_account`; design §2.4.)
11. A Portal_Owned_Bucket SHALL be refused by the attach validator as its first step, with `reason: portal_bucket`, before any `Scan` or `GetBucketTagging`, whatever tags it carries and whoever the caller is (a PortalAdmin included); `POST /s3-buckets` SHALL refuse a portal-owned name before creating anything.

### Requirement 11: Frontend

**User Story:** As a UseCaseAdmin browsing S3 in the portal, I want to see which buckets my use case may use and allow an eligible one in place; as any user, I want a clear message instead of a raw error when a bucket is not allowed.

#### Acceptance Criteria

1. The Data Management page (`edge-cv-portal/frontend/src/pages/DataManagement.tsx`, bucket table and "Select Data Bucket" modal fed by `GET /usecases/{id}/data/buckets`) SHALL mark every bucket not in the use case's `allowed_s3_buckets` as "Not allowed for this use case", SHALL mark Portal_Created buckets, SHALL give the "Allowed" badge a tooltip stating that labeling jobs always use the use case's configured data bucket (an Additional_Buckets entry cannot be a labeling dataset), and SHALL show an "Allow for this use case" action on not-allowed buckets to UpdateUsecases holders **when `has_data_account_role` is false**; when it is true the buckets listed are in the separate Data Account and the page SHALL show "Buckets in a separate Data Account cannot be added here" instead of the action. When the use case has no `current_data_bucket`, the page SHALL default its selection to the first bucket with `allowed: true` (none when there is none) rather than the first listed bucket, so it never opens on a refusal.
2. The onboarding bucket picker (`S3BucketPicker.tsx`, fed by `GET /s3-buckets`) SHALL mark buckets that are not Eligible ("Not tagged for the portal") and Portal_Created ones; the marking is advisory (tag discovery is regional), selection stays possible, and the text SHALL say that the server decides when the use case is created. "Create new bucket" SHALL be hidden for non-PortalAdmins.
3. The "Allow for this use case" action SHALL call `PUT /usecases/{id}` with `additional_s3_buckets_add: [bucket]`; on 400 `bucket_not_eligible` it SHALL show the per-`reason` remedy (tag requirement with the `aws s3control tag-resource` form, ABAC, PortalAdmin sharing or re-homing, portal-owned bucket with no action); on 403 it SHALL say a UseCaseAdmin is required; on success it SHALL refresh the use case and the bucket list.
4. WHEN the server refuses browsing a bucket (`GET /usecases/{id}/data/folders` → 400 `bucket_not_allowed`), the page SHALL show the same marking and action instead of a raw error.
5. The use case Edit modal (`UseCases.tsx`) SHALL show the use case's current allowed buckets (configured and additional) and SHALL let UpdateUsecases holders remove an Additional_Buckets entry (`additional_s3_buckets_remove`) and add one by name, handling `bucket_not_eligible` and `invalid_bucket_name`. The modal's existing submission of `data_s3_bucket: ''` for use cases without a data bucket SHALL keep working (server-side Clear semantics, Requirement 10.8).
6. The pages that submit free-text S3 URIs (`pages/ImportModel.tsx`, `pages/PreLabeledDatasets.tsx`, `components/ManifestTransformer.tsx`, `pages/ManifestValidator.tsx`, `pages/RegisterLlm.tsx`) SHALL render a shared `BucketNotAllowedNotice` for `error_code: bucket_not_allowed` / `bucket_not_eligible` / `invalid_s3_uri` / `invalid_bucket_name`, with the "Allow for this use case" action for UpdateUsecases holders. `ImportModel.tsx`, which is reachable by every role (`App.tsx:136` mounts it without `RequireRole`), SHALL render a 403 from `POST /models/validate` as "Validating and importing models requires the DataScientist role on this use case".
7. UpdateUsecases visibility in the frontend SHALL come from `GET /users/me/usecases` (`user_role` per use case **or** `is_super_user`, both resolved by `RBACManager`), with the server remaining authoritative.
8. React component tests SHALL cover: marking of allowed / not-allowed / portal-created buckets; action visibility by role and by `has_data_account_role`; `error_code` / `reason` handling for `bucket_not_eligible`, `bucket_not_allowed` and 403; and refresh on success.

### Requirement 12: API for allowed and additional buckets

**User Story:** As an API client and as the frontend, I want to read the computed set and change the additional list through the existing use case endpoints.

#### Acceptance Criteria

1. `GET /usecases/{id}` SHALL return, on the `usecase` object, `allowed_s3_buckets` (sorted list) and `additional_s3_buckets` (list, `[]` when absent).
2. `PUT /usecases/{id}` SHALL accept the optional keys `additional_s3_buckets_add` and `additional_s3_buckets_remove` (lists of bucket names) under the existing `UPDATE_USECASES` gate; the raw key `additional_s3_buckets` SHALL be rejected with 400 `unsupported_field`. No new API Gateway route is added for this.
3. Every name SHALL be validated against the Membership_Grammar (400 `invalid_bucket_name`), each of `additional_s3_buckets_add` and `additional_s3_buckets_remove` SHALL carry at most ten names per request (400 `invalid_field` otherwise; the probe-latency bound of Requirement 10.5), the resulting list SHALL not exceed 100 entries (400 `bucket_not_eligible`, `reason: too_many_buckets`), and every added name SHALL pass Unclaimed and eligibility (Requirement 10, `retry=False`) before any write; when any entry fails, nothing is written and the response is the first failure's Refusal plus a `rejected` array holding one `{bucket, error_code, reason}` per failing name. Writes SHALL be per-entry atomic and never create a record: adds use `list_append` conditioned on `attribute_exists(usecase_id) AND (attribute_not_exists(#a) OR NOT contains(#a, :b))` with `ReturnValuesOnConditionCheckFailure='ALL_OLD'`, mapping a missing item to 404 `usecase_not_found` and a present name to `already_present`; removes use a read-compare-write conditioned on `attribute_exists(usecase_id) AND #a = :expected`, retried once and then 409 `concurrent_update`.
4. Each written add SHALL emit the attach audit event of Requirement 10.3 — `s3_bucket_allowed`, `resource_type = 'usecase'`, `resource_id = usecase_id`, details `{bucket, attribute: 'additional_s3_buckets', source: 'api'}` plus `shared_with_usecases` when a PortalAdmin attached a configured or claimed bucket and `stale_claim: true` when the claim named a deleted use case — and each written remove `s3_bucket_removed` with details `{bucket, attribute: 'additional_s3_buckets', source: 'api'}`, both with the request's attribution (actor). The same event shape is emitted by `create_usecase` (`source: 'create'`, for `s3_bucket`, `data_s3_bucket` and each `additional_s3_buckets` entry of 12.7), by `configure_data_account` (`source: 'configure'`) and by the auto-add (`source: 'auto_add'`); a changed `s3_bucket` / `data_s3_bucket` on `PUT /usecases/{id}` emits it with `source: 'api'` and the matching `attribute`.
5. The success response SHALL list `added`, `already_present`, `removed`, `not_present` and return the updated `allowed_s3_buckets`.
6. `GET /usecases/{id}/data/buckets` SHALL add `allowed` and `portal_created` to each bucket entry; `GET /s3-buckets` SHALL add `eligible` and `portal_created` booleans to each entry (no tag maps), derived from one Resource Groups Tagging `GetResources` call as `data_management.list_buckets` does today.
7. `create_usecase` SHALL accept an optional `additional_s3_buckets` list of at most ten names, validated, Unclaimed- and eligibility-checked like 12.3 (`retry=False`; only the two configured buckets use `retry=True`, Requirement 9.9), written with the record, each entry audited after `put_item` with `source: 'create'` (12.4).
8. `POST /usecases/{id}/data/configure` (`data_management.configure_data_account`) SHALL keep its route and `UseCaseAdmin` gate and SHALL apply the same Clear, grammar, Unclaimed and eligibility rules to a changed `data_s3_bucket` through the shared attach validator before its write (which is conditioned on `attribute_exists(usecase_id)`, 404 otherwise).

### Requirement 15: Tests
