# Design Document

## Overview

The portal accesses S3 on behalf of a use case through credentials it holds server-side. This design makes the set of buckets a use case may use an explicit, exact-name property of the use case record, and resolves every such access through that set before any STS or S3 call. The set is computed by one function in the shared layer (`allowed_s3_buckets`), enforced by one predicate (`assert_bucket_allowed`) that the shared client helper `get_s3_client_for_bucket` calls first, and repeated as an explicit pre-check in each handler so the caller gets a specific 400 with an `error_code` instead of a generic failure. The portal's own buckets — the artifacts bucket and the Greengrass component bucket — are outside the set **by rule**, not by default: `portal_owned_buckets()` names them, `allowed_s3_buckets` drops them even when a record names them, and the attach validator refuses them even when they are tagged. The artifacts bucket holds every use case's plugin sources, workflow staging, test datasets and labeling annotations under keys the portal chooses, and no bucket-selected code path may reach it — there is no opt-in anywhere; the few-shot example references that used to resolve a bare key against it are no longer a supported reference shape. Buckets the portal creates are tagged with the existing `dda-portal:managed=true` key plus a creation marker, ABAC is enabled on them, and when created for a known use case they are added to that use case's `additional_s3_buckets` list in the same request. Attaching any bucket to a use case (configured bucket or additional entry, through any of the record writers enumerated in §2.4) requires two things: the bucket carries the portal tag, read with the same credentials the portal would later use for it, and no other use case has it configured or claimed by tag — a claim outlives the use case it names, so a deleted use case's portal-created buckets stay its own until a PortalAdmin re-attaches one deliberately. The frontend's bucket pickers mark buckets outside the set and let UseCaseAdmins allow eligible ones in place.

Technology stack (locked): Python 3.11 Lambda handlers and the SharedLayer (`shared_utils.py`) with **boto3 1.43.101 / botocore 1.43.101 vendored into the layer** (the Lambda-managed runtime's bundled SDK is not relied on for the S3 ABAC/tag operations), DynamoDB conditional updates for the list attribute, S3 `CreateBucket` with `CreateBucketConfiguration.Tags` / `GetBucketTagging` / s3control `TagResource` (fallback) / S3 `PutBucketAbac` for tags, CDK (TypeScript) for the one IAM addition, React 18 + Cloudscape + vitest + fast-check for the frontend, pytest + moto + hypothesis for the backend (run through the Python 3.11 lane described in the verification notes). No new tables, no new API Gateway routes.

## 1. Shared layer: binding primitives (`layers/shared/python/shared_utils.py`)

### 1.1 Grammars and parser

```python
MEMBERSHIP_NAME_RE = re.compile(r'^[A-Za-z0-9._-]{3,255}$')          # membership + URI parsing
BUCKET_NAME_RE = re.compile(r'^(?!\d+\.\d+\.\d+\.\d+$)(?!.*\.\.)[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$')  # new names only

def is_valid_bucket_name(name) -> bool          # BUCKET_NAME_RE (POST /s3-buckets)
def is_membership_name(name) -> bool            # MEMBERSHIP_NAME_RE
def parse_s3_uri(uri: str, *, require_key: bool = True) -> Tuple[str, str]
```

Decision (two grammars): membership and parsing use the permissive, exact-match-safe `MEMBERSHIP_NAME_RE`. Buckets created before March 2018 in us-east-1 may carry uppercase letters, underscores and up to 255 characters; a use case whose *configured* bucket has such a name must keep working, and the strict grammar would drop that name from the set and refuse the use case's own bucket everywhere. Exactness is a property of the string comparison (§1.4), not of the grammar, so the permissive class loses nothing: it still excludes `@`, `:`, `/`, whitespace and control characters, so a URI can never smuggle a second host or a port into the compared string. The strict S3 rules apply only where the portal is about to *create* a bucket (`POST /s3-buckets`, §5.5).

`parse_s3_uri` requires `isinstance(uri, str)`, `len(uri) <= 2048` (so an oversized body cannot make the regex work hard), the literal lowercase prefix `s3://`, splits the remainder at the first `/`, requires the bucket to match `MEMBERSHIP_NAME_RE`, and requires a non-empty key when `require_key`. It does not call `urlparse` (whose `netloc` for `s3://bucket@other/key` is `bucket@other`), does not lowercase, strip, or percent-decode. Any failure raises `InvalidS3Uri`. The key is returned as-is; callers that need `.tar.gz` keep their existing suffix check after parsing.

`data_management.is_valid_bucket_name` (line 102) is not on any sink path and is left unchanged.

### 1.2 Exceptions and remedies

```python
class BucketConfigError(ValueError):

    def to_body(self) -> Dict  # {'error', 'error_code', 'bucket', 'usecase_id', 'purpose', 'reason', 'remedy'} minus None values

class InvalidS3Uri(BucketConfigError):       error_code = 'invalid_s3_uri'
class InvalidBucketName(BucketConfigError):  error_code = 'invalid_bucket_name'
class BucketNotAllowed(BucketConfigError):   error_code = 'bucket_not_allowed'
class BucketNotEligible(BucketConfigError):  error_code = 'bucket_not_eligible'

def bucket_config_error_response(exc: BucketConfigError, status: int = 400) -> Dict:
    return create_response(status, exc.to_body())
```

They subclass `ValueError` so the handlers whose `except ValueError` already maps to 400 keep working if a new call site forgets the explicit catch; the explicit catch (`except BucketConfigError as e: return bucket_config_error_response(e)`) is added before `except ValueError` at every handler named in §3 so the body is the Requirement 5 shape. `error_code` for a malformed *bare* bucket name is always `invalid_bucket_name`; for a malformed URI always `invalid_s3_uri`.

Ten constants. The tagging commands are the S3 Control forms: in AWS CLI 2.x the bucket tag write for the ABAC model is `aws s3control tag-resource` with `--account-id` (the `s3api` namespace has `put-bucket-tagging`, `put-bucket-abac` and `get-bucket-abac` but no `tag-resource`; verified on the CLI in the verification notes' Environment). The same operation is `create_s3_bucket`'s fallback tag write through boto3 (`s3control.tag_resource`, §5.5 step 5; its primary tag write is the `Tags` member of the `CreateBucket` request, step 3), so code and prose name one API. `put-bucket-tagging` still works on buckets without ABAC and the admin guide keeps it as the alternative (§9). The data-bucket-allowlist sentence exists because a deployment that sets `dataBucketAllowlist` (`compute-stack.ts:333–343`, bucket-level grant at 647–655) denies the execution role's `GetBucketTagging` on every other bucket, where neither ABAC nor a bucket policy is the cause; live deployments pass an empty allowlist, so the sentence is wording only.

### 1.3 Allowed set

```python
def portal_owned_buckets() -> FrozenSet[str]:
    """Buckets the portal owns for all use cases; never a member of any allowed set, never attachable."""
    artifacts = os.environ.get('PORTAL_ARTIFACTS_BUCKET', '')
    component = os.environ.get('COMPONENT_BUCKET') or (
        f"{os.environ.get('COMPONENT_BUCKET_PREFIX', 'dda-component')}-"
        f"{os.environ.get('AWS_REGION', 'us-east-1')}-{os.environ.get('PORTAL_ACCOUNT_ID', '')}"
        if os.environ.get('PORTAL_ACCOUNT_ID') else '')
    return frozenset(n for n in (artifacts, component) if n)

def allowed_s3_buckets(usecase: Dict) -> FrozenSet[str]:
    candidates = [usecase.get('s3_bucket'), usecase.get('data_s3_bucket'),
                  *(usecase.get('additional_s3_buckets') or [])]
    owned = portal_owned_buckets()
    allowed = set()
    for name in candidates:
        if not name or (isinstance(name, str) and not name.strip()): continue
        if not isinstance(name, str) or not MEMBERSHIP_NAME_RE.match(name):
            logger.warning("Ignoring configured bucket with invalid name on use case %s", usecase.get('usecase_id')); continue
        if name in owned:
            logger.warning("Ignoring portal-owned bucket configured on use case %s", usecase.get('usecase_id')); continue
        allowed.add(name)
    return frozenset(allowed)
```

Decision: entries failing the membership grammar are dropped rather than raising, because a corrupt record must never widen access and must not take the whole use case offline (its valid buckets keep working); with the permissive grammar this branch is reached only by names containing `/`, `:`, `@`, whitespace or control characters, which S3 never issued.

Decision: **the portal's own buckets are excluded by rule, not by default.** `portal_owned_buckets()` is computed from the environment every function on `sharedLayer` already carries (`PORTAL_ARTIFACTS_BUCKET`, `PORTAL_ACCOUNT_ID`, `COMPONENT_BUCKET_PREFIX` in `lambdaEnvironment`, `compute-stack.ts:725/730/758`; `AWS_REGION` is set by the Lambda runtime; `COMPONENT_BUCKET` is set explicitly on the functions that need it, 1828/2595) and mirrors the component-bucket derivation of `shared_components.py:53–54` (`{prefix}-{region}-{account}`; the CDK names the bucket the same way at 1813). It names two buckets:

- the **artifacts bucket** — one bucket for the whole portal holding per-use-case content: plugin sources and binaries (`plugin_builds.py:525–631`), workflow packaging staging (`workflow_packaging.py:2889`), workflow test datasets (`workflow_testing.py:338/487`, multipart image uploads), git-synced repository staging (`git_sync.py:1065`), segmentation annotations (`dda_labeling.py:2746–2757`), previews. If it were in a set, `GET /usecases/{id}/data/folders?bucket=<portal-artifacts>` would list all of it for any member of that use case, and the validate / transform / manifest sinks would read arbitrary keys from it for any DataScientist;
- the **component bucket** (`dda-component-<region>-<account>`) — the Greengrass artifact store every use-case account's devices read from (`shared_components.py:548–657` manages its bucket policy); a use case allowed to write into it could replace component artifacts.

Before this revision the exclusion held only while no record named these buckets and nobody tagged them: the CDK tags none of the portal's buckets (`storage-stack.ts` has no `Tags`), but a record written before this change can name the artifacts bucket (a development account's picker lists every account bucket), and a migration that tags every untagged configured bucket would have grandfathered it. Now a record that names a portal-owned bucket loses that entry from its set (WARNING per request; the sizing script counts such records and the runbook stops on them, §16 row 29), and the attach validator refuses a portal-owned bucket as its first step regardless of tags (§1.6 step 0). The inference-results bucket (`dda-inference-results-<account>` or the record's `inference_uploader_s3_bucket`, `captures.py:90`, `deployments.py:1501`) is **not** portal-owned: it lives in the use-case account and is reached with the use case's own role through a configuration-sourced path that this spec does not touch (§2.4); for a single-account use case it is a portal-account bucket like any other and may be attached if an administrator tags it.

Decision (bare-key few-shot references are not a supported reference shape): two paths today resolve a few-shot example reference that does not start with `s3://` to `(PORTAL_ARTIFACTS_BUCKET, <ref as given>)` — `dda_autolabel_worker._few_shot_ref_location` (428–439) reads it with the use case's helper client, and `dda_labeling._example_image_urls` (2234–2262) presigns it with the module-level execution-role client — with no prefix bound on the key. Nothing produces such references: the wizard has uploaded few-shot examples into the use case's data bucket and stored `s3://<data bucket>/labeling-examples/...` refs since the labeling backend was introduced (`CreateLabelingJob.tsx:1027–1059`, introducing commit found with `git log -S"labeling-examples"`), the labeling preview path already refuses any reference outside the dataset bucket (`_is_reference_in_scope` 4683, docstring 4912–4918), and the only writer of bare-key references in the tree is the worker's own test (`test_dda_autolabel_worker_few_shot.py:159`). An earlier revision kept the shape alive behind an `allow_portal_bucket` opt-in; that opt-in is removed. Bare keys are refused at job creation (`_validate_example_refs`, §3), resolve to nothing in the worker (the existing "could not be resolved to an S3 object" failure for that image), and are skipped by `_example_image_urls`. The invariant is therefore unconditional: no bucket-selected code path reaches the portal artifacts bucket. Jobs created before this change with bare-key references (the sizing script counts them, §16 row 17) lose those examples; the remedy is to recreate the job with examples uploaded through the wizard.

### 1.4 Assertion and audit

```python
def assert_bucket_allowed(usecase, bucket, purpose, *, actor=None, event=None) -> None
```

Order: (1) `bucket` must be a `str` matching `MEMBERSHIP_NAME_RE`, else `InvalidBucketName` (the `isinstance` check comes first, so a non-string body value is a 400 and never a `TypeError` → 500; no audit row: nothing was decided); (2) `bucket in allowed_s3_buckets(usecase)` → return; else refuse with `REMEDY_PORTAL_BUCKET` when `bucket in portal_owned_buckets()`, `REMEDY_NOT_ALLOWED` otherwise. There is no opt-in parameter of any kind: a portal-owned bucket can never be in the set (§1.3), so it is refused like any other bucket outside it, and the only difference is the remedy text. Refusal = `logger.warning("S3 bucket refused: usecase=%s bucket=%s purpose=%s")` (never a key), then `log_audit_event(user_id=(actor or {}).get('user_id') or 'system', action='s3_bucket_refused', resource_type='usecase', resource_id=usecase.get('usecase_id', 'unknown'), result='denied', details={'bucket': bucket, 'purpose': purpose}, identity=attribution_from(event, actor, usecase_id) if event else None)`, then `raise BucketNotAllowed(...)`. `log_audit_event` swallows its own failures, so audit loss never changes the decision. Exactly one audit row per refused request: handlers pre-check with the actor; the helper's own assertion (no actor) is reached only by a caller that skipped the pre-check.

Property 2 asserts for every additional entry that the role chosen is `cross_account_role_arn`, never `data_account_role_arn`.

### 1.6 Eligibility probe and attach validator

```python
@dataclass
class EligibilityResult:
    eligible: bool; reason: str; tags: Dict[str, str]; portal_created: bool; claimed_by: Optional[str]
    shared_with_usecases: int = 0     # filled by check_bucket_attachable when a PortalAdmin override admitted a shared/claimed bucket
    stale_claim: bool = False         # filled by check_bucket_attachable when the admitted claim named a deleted use case

def probe_bucket_eligibility(usecase_like: Dict, bucket: str, *, retry: bool = False) -> EligibilityResult
```

`usecase_like` is the record (or, at creation, the item about to be written, with the role fields already resolved). Steps: `_select_s3_role_for_bucket` → `assume_usecase_role` → `create_boto3_client('s3')` → `get_bucket_tagging(Bucket=bucket)`. Mapping, all fail-closed:

| Outcome | `eligible` | `reason` | Remedy |
|---|---|---|---|
| tags contain `dda-portal:managed=true` or `dda-portal:created-by=portal` | True | `eligible` | — |
| tags present, neither key qualifies (after the retries, when enabled) | False | `tag_missing` | `REMEDY_TAG` |
| `NoSuchTagSet` (after the retries, when enabled) | False | `no_tags` | `REMEDY_TAG` |
| `AccessDenied` / `403` | False | `tagging_unreadable` | `REMEDY_TAGGING_UNREADABLE` |
| `PermanentRedirect` / `301` with no `x-amz-bucket-region` header, or a failure on the one region retry (below) | False | `tagging_unreadable` | `REMEDY_TAGGING_UNREADABLE` |
| `NoSuchBucket` / `404` | False | `bucket_not_found` | `REMEDY_NOT_FOUND` |
| STS `assume_role` ClientError, or any other exception | False | `credentials_unavailable` | `REMEDY_CREDENTIALS` |

Cross-region buckets: botocore's S3 region redirector is the first line — a client built for the Lambda's region follows the `301` to the bucket's region transparently for most operations, so the ordinary case never reaches the probe's own handling. When a `ClientError` with code `PermanentRedirect` or `301` still surfaces, the probe reads `x-amz-bucket-region` from `e.response['ResponseMetadata']['HTTPHeaders']` and retries the read **once** with `create_boto3_client('s3', credentials, region=<that region>)` (`create_boto3_client(service_name, credentials, region=None)`, shared_utils 1624; the same credentials, no second STS call); a missing header or a failure of that second attempt concludes `tagging_unreadable` (the remedy's wording — the portal's role could not read the tags — is accurate for it). Unit case: redirect once, then success → `eligible` (task 1.4).

Outcomes decided by `check_bucket_attachable` itself, without a probe: `portal_bucket` (step 0, `REMEDY_PORTAL_BUCKET`), `bucket_configured_on_other_usecase` (steps 2 and 4, `REMEDY_OTHER_USECASE` or `REMEDY_STALE_CLAIM`), `account_mismatch` and `too_many_buckets` (the callers, before the validator). The probe is never run for a portal-owned bucket.

Retry (tag read-after-write) is **opt-in**: `probe_bucket_eligibility(usecase_like, bucket, *, retry=False)`. With `retry=True`, `NoSuchTagSet` and a tag set lacking both qualifying keys are retried up to **3 attempts with 1 s between attempts** (bounded 2 s added latency, only on those two outcomes) before concluding; with the default `retry=False` every outcome is concluded on the first read and the probe never sleeps. Only `create_usecase` passes `retry=True`, and only for `s3_bucket` and `data_s3_bucket`: the wizard runs `POST /s3-buckets` and `POST /usecases` seconds apart (`S3BucketPicker.tsx:73`, `UseCaseOnboarding.tsx:167`), bucket tagging reads are not guaranteed read-after-write consistent, and a bucket the portal has just tagged must not be reported `no_tags`. Every other caller probes buckets whose tags have been in place for longer than a second — `update_usecase` (changed configured buckets and each add), `configure_data_account`, the additional list at creation — and `create_s3_bucket`'s auto-add supplies `evidence` instead of probing (§5.5). **Latency bound, stated:** the per-request add list is capped at **10** names (`additional_s3_buckets_add`, §5.3 step 2; `additional_s3_buckets` at creation, §5.4), so the worst case for a `PUT /usecases/{id}` or `POST /usecases` is 10 probes × (one STS call + one tag read) with no sleep — well under the 29 s API Gateway integration timeout (the UseCases function's own timeout is 120 s, `compute-stack.ts:1064`, but its integration is a default `LambdaIntegration`, `api-gateway-stack.ts:191`, so 29 s is the limit that matters); `create_usecase` adds at most 2 × 2 s of sleep for its two configured buckets. A wall-clock deadline across the whole request was considered and rejected: it would need an eleventh refusal reason ("not probed: out of time") and the structural bound already suffices. `AccessDenied`, `NoSuchBucket`, the redirect case and credential failures are concluded without retry in both modes. `claimed_by = tags.get('dda-portal:usecase-id')`; `portal_created = tags.get('dda-portal:created-by') == 'portal'`. The probe logs the reason at INFO and never raises.

Why `tagging_unreadable` has its own remedy: `DDAPortalAccessRole`'s `s3:GetBucketTagging` is itself conditioned on `aws:ResourceTag/dda-portal:managed = true` (`usecase-account-stack.ts:470–488`), and S3 evaluates bucket-tag condition keys only on buckets with ABAC enabled (the compute-stack's own history at 631–641 records the regression that taught this; the S3 User Guide "Using tags with S3 general purpose buckets", https://docs.aws.amazon.com/AmazonS3/latest/userguide/buckets-tagging.html, states that `aws:ResourceTag/key-name` is evaluated only after ABAC is enabled on the bucket). Through the cross-account role the probe is therefore denied both on an *untagged* bucket and on a *tagged* bucket whose ABAC is off — exactly as the data path would be — which is why the remedy names both causes in order (tag it if untagged; enable ABAC or grant the read in the bucket policy if tagged). The probe behaves precisely like the sinks that follow it: a bucket it cannot read is a bucket the portal could not have used. If the ABAC premise turned out to be wrong (condition keys evaluated on every bucket), the only consequence is that the cross-account probe succeeds more often and the remedy's ABAC sentence is over-inclusive; no access decision widens.

```python
def check_bucket_attachable(*, target_usecase_id: Optional[str], usecase_like: Dict, bucket: str,
                            user: Dict, event: Optional[Dict], purpose: str,
                            evidence: Optional[EligibilityResult] = None,
```

The single attach validator every record writer calls (`create_usecase`, `update_usecase`, `create_s3_bucket` auto-add, `configure_data_account`). `retry` is passed through to the probe (step 3) and is `True` only from `create_usecase` for `s3_bucket` / `data_s3_bucket`. Order, all before any write:

0. **Portal-owned**: `bucket in portal_owned_buckets()` → `BucketNotEligible(reason='portal_bucket', remedy=REMEDY_PORTAL_BUCKET)` before the Scan and before the probe, whatever the bucket's tags say. The portal's own buckets are not attachable by anyone, PortalAdmin included. (Step 0 runs `isinstance(bucket, str) and bucket in …`, so a non-string reaches step 1.)
1. Grammar: `bucket` must be a `str` matching `MEMBERSHIP_NAME_RE`, else `InvalidBucketName` — a non-string body value (`null`, a number, a list) is a 400, never a `TypeError` → 500.
2. **Unclaimed (configuration)**: `usecases_table.scan(ProjectionExpression='usecase_id', FilterExpression='s3_bucket = :b OR data_s3_bucket = :b OR contains(additional_s3_buckets, :b)')` (paginated; the table is already scanned whole by `get_accessible_usecases`, shared_utils 1282). `others = {items' usecase_id} - {target_usecase_id}`. If `others` is non-empty and not `caller_is_portal_admin(user)` → `BucketNotEligible(reason='bucket_configured_on_other_usecase', remedy=REMEDY_OTHER_USECASE)`. A Scan error is an outage, not a decision: it propagates to the handler's generic `except Exception` and answers 500, like every other table error in these handlers.
3. Eligibility: `evidence` if the caller supplied one, else `probe_bucket_eligibility(usecase_like, bucket, retry=retry)`; not eligible → `BucketNotEligible(reason, remedy per table)`. Only `create_s3_bucket` passes `evidence` — an `EligibilityResult(eligible=True, reason='eligible', tags=<the tags it read back>, portal_created=True, claimed_by=tags.get('dda-portal:usecase-id'))` built from its own read-after-write `get_bucket_tagging` in the same request (§5.5 step 5; Requirement 10.6), so the auto-add never runs a probe of its own and never attaches a bucket whose tags were not confirmed.
4. **Unclaimed (tag claim)**: if `result.claimed_by` is set and `!= target_usecase_id`, the bucket is claimed by another use case and, unless `caller_is_portal_admin(user)`, the attach is refused with `bucket_configured_on_other_usecase`. One `usecases_table.get_item(Key={'usecase_id': claimed_by}, ProjectionExpression='usecase_id')` decides only the **remedy text**: an existing use case → `REMEDY_OTHER_USECASE`; a use case that no longer exists → `REMEDY_STALE_CLAIM` (the claim is still a claim). Decision (a claim outlives the use case it names): `delete_usecase` (1606–1621) deletes only the record — the buckets, their contents and their tags stay. Without this rule a deleted use case's portal-created buckets (tagged `dda-portal:usecase-id=<id>` by `POST /s3-buckets`, §5.5) would pass step 2 (configured on no use case) and step 4, and any UpdateUsecases holder — today any authenticated user through a self-created use case (§2.1) — could attach one and read and write its contents through every §3 sink. Treating the stale claim as a claim keeps that storage with a PortalAdmin decision, which is the same decision sharing already needs; the cost is one PortalAdmin step to re-home a deleted use case's bucket, and the remedy names the alternative (an AWS administrator removes the tag). The portal itself writes `dda-portal:usecase-id` on buckets it creates for a use case (§5.5), and `tag_bucket_for_portal` wrote it historically on Data Account buckets.
5. Return the result with `result.shared_with_usecases = len(others) + (1 if result.claimed_by and result.claimed_by != target_usecase_id and result.claimed_by ∉ others else 0)` and `result.stale_claim = True` when the admitted claim named a use case that no longer exists — both set only when the PortalAdmin override admitted a bucket that step 2 or step 4 would otherwise have refused (`0` / `False` on every other path). The validator returns them so that **every writer emits one and the same audit row** without recomputing anything.

**The attach audit row (one shape, four writers).** After its write has succeeded — never before — each writer calls `log_audit_event(user['user_id'], 's3_bucket_allowed', 'usecase', usecase_id, 'success', details, event=event)` once per attached bucket, with `details = {'bucket': name, 'attribute': 's3_bucket' | 'data_s3_bucket' | 'additional_s3_buckets', 'source': 'api' | 'create' | 'configure' | 'auto_add', **({'shared_with_usecases': result.shared_with_usecases} if result.shared_with_usecases > 0 else {}), **({'stale_claim': True} if result.stale_claim else {})}` and the request's attribution (the `event=` argument, as the handlers' other rows). `attribute` names the record field the bucket entered; `source` names the writer: `update_usecase` → `api` (each changed configured bucket after its `SET`, and each written add, §5.3 step 9); `create_usecase` → `create` (after `put_item`: `s3_bucket`, `data_s3_bucket` when set and not a Clear, each additional entry, §5.4); `configure_data_account` → `configure` (after its `update_item`, §5.6 step 5); `create_s3_bucket` → `auto_add` (after `_add_additional_bucket` returns `added`, §5.5 step 6). The PortalAdmin sharing override therefore has one destination on every path that can use it — a PortalAdmin re-pointing `s3_bucket` / `data_s3_bucket` onto a bucket configured on, or claimed by, another use case leaves a row with `shared_with_usecases` (and `stale_claim` when the claim named a deleted use case) exactly as an additional-list add does. One api test per writer pins the row (task 6.2).

Every refusal writes `s3_bucket_refused` with `details={'bucket', 'purpose', 'reason'}` before raising. `caller_is_portal_admin` may raise `RegistryUnavailable`; it is not caught here (the handlers' `except Exception` answers 500, never 403 — the shared helper's documented contract). What the override inherits, stated: `caller_is_portal_admin(user)` and `has_permission(…, user)` pass `user_info`, so with enforcement off `_legacy_role` honours the JWT claim (steps 1 and 4, shared_utils 1090–1092 and 1121–1124) for these gates exactly as it does for every other PortalAdmin and UPDATE_USECASES gate in the portal; the override is as strong as those gates and no stronger, and Requirement 7's production posture (enforcement on) is what makes it a registry decision. No code change follows from this.

Residual, stated: a tagged bucket configured on **no** use case and carrying **no** `dda-portal:usecase-id` claim may be attached by any UpdateUsecases holder (or use-case creator) — and not only within one account. The probe reads the tags with the role fields the attaching record names, and `GET /usecases/{id}` returns the whole record, role ARNs and external ids included, to anyone who can view that use case (`VIEW_USECASES` is Viewer-level; the follow-on spec's D8 keeps the rule that a global role applies to every use case under enforcement). The opt-in pool is therefore **every tagged, unconfigured, unclaimed bucket in any account whose use-case role fields the caller can read from `GET /usecases/{id}`** and copy onto a use case they administer. That pool is the administrator's opt-in and the documented meaning of the tag; the control over the role fields themselves — proof of control before a record may name a role — is the follow-on's D2 (§2.4, role-fields row), not this spec. Deleting a use case therefore releases its *administrator-tagged* buckets (configured buckets tagged by hand, with no claim) into that pool, while its *portal-created* buckets stay claimed; the portal removes no tags on deletion, and the admin guide tells administrators to remove the `dda-portal:*` tags (or the bucket) when a use case is deleted if its storage must not be re-attached (§9). Two use cases attaching the same unclaimed bucket in the same second can both pass step 2 (no transaction spans the Scan and the write); the result is a shared bucket a PortalAdmin would otherwise have had to approve, visible in the sizing script's shared-bucket count on re-run.

## 2. Decision: eligibility and unclaimed-ness on attach (Requirement 10)

### 2.1 The bypass that binding alone leaves open (evidence)

With binding alone the Allowed_Bucket_Set is whatever the record says, and the record is writable by paths a non-administrator holds:

- `POST /usecases` has no gate (`usecases.py:1101–1104`: "any authenticated user can create"); the creator is written a `UseCaseAdmin` row (1222–1231), which resolves under enforcement too (the global backfill row plus the use-case row; `_lookup_identity`, shared_utils 731–790). Omitting `account_id` makes `cross_account_role_arn = arn:aws:iam::<portal>:root` (1138–1143), which `assume_usecase_role` treats as "use the Lambda execution role" (1578–1584). The execution role's S3 data-plane grant is `arn:aws:s3:::*` by default (`compute-stack.ts:333–343`, 647–663).
- So, in the single-account mode (which `create_usecase` selects whenever `account_id` is omitted, 1113), a principal can create a use case, set `s3_bucket` to another use case's bucket, and every §3 sink — including `transform_manifest`'s `put_object` and the Data Management uploads — runs against that bucket with the execution role. An existing UseCaseAdmin can do the same with `PUT /usecases/{id}` (`s3_bucket`, `cross_account_role_arn`, `account_id` and the Data Account fields are all `updatable_fields`, 1563–1575), with `POST /usecases/{id}/data/configure` (`data_management.py:673–737`, writes `data_s3_bucket` and the Data Account role fields with no check beyond `UseCaseAdmin`), and across accounts by copying `data_account_role_arn` / `data_account_external_id` from `GET /usecases/{id}` of a use case they merely view onto their own use case (`DDAPortalDataAccessRole` grants S3 on `*` unconditionally, `data-account-stack.ts:55–100`).
- A tag requirement alone narrows this to *tagged* buckets — but in a single-account deployment every other use case's bucket that Data Management can show is tagged exactly so (`data_management.list_buckets` 229–240 keys on the tag; ADMIN_GUIDE tells administrators to tag), and every bucket this spec creates is tagged too. Nor is the reach bounded by the caller's own account: the role fields a record names decide which account the probe and the sinks read in, and those fields are readable from `GET /usecases/{id}` for every use case the caller can view, so what the tag rule alone would leave open is every tagged bucket in every account whose use-case role fields the caller can read (the residual §1.6 states once the Unclaimed rule has removed configured and claimed buckets from it; the follow-on's D2 is the control over the role fields).

Deferring `POST /usecases` to the follow-on (owner decision D1) narrows who can *create*, not what a UseCaseAdmin can *attach*; the follow-on's D2 exempts single-account records from proof of control, so the path would survive both specs. It must be closed here, at the attach.

### 2.2 The two rules and why both

**Eligibility (tag).** Evidence from AWS, not from the portal, that the bucket was handed to the portal: the `dda-portal:managed=true` tag that the role templates (`usecase-account-stack.ts:470–515`), `data_management.list_buckets`, `ADMIN_GUIDE.md` and `tag_bucket_for_portal` already treat as "this bucket is for the portal". It stops a use case from binding a bucket nobody handed to the portal at all.

**Unclaimed (configuration and `dda-portal:usecase-id`).** A bucket already configured on another use case — or tagged by the portal for another use case — is attachable only by a PortalAdmin. It stops a use case from binding *another use case's* storage, which the tag alone cannot express. The PortalAdmin override is what makes legitimately shared buckets possible, with an audit row recording the sharing.

### 2.3 Alternatives considered

- **Gate use-case creation (PortalAdmin only).** Decided elsewhere (`portal-authorization-and-iam-scoping`, D1) and not changed here; it narrows who can create but a UseCaseAdmin can still `PUT` `s3_bucket`/`data_s3_bucket`, so it does not replace either rule.
- **Scope the Lambda roles' S3 grant by tag.** The right long-term control (follow-on D5-B), but S3 evaluates `aws:ResourceTag` only on ABAC-enabled buckets, which requires a bucket backfill; this spec prepares for it (ABAC on portal-created buckets, vendored SDK) without depending on it. It also would not separate two tagged buckets from each other.
- **A portal-side registry of portal-created buckets (new table).** Rejected: the tag is already the system's marker, needs no CDK table, and is what IAM will key on.
- **Skip eligibility for multi-account use cases.** Considered because the documented onboarding order (`ADMIN_GUIDE.md` Step 3 "Create UseCase", Step 5 "Tag Customer's S3 Buckets") tags after creation. Rejected: (a) the Data Account role is unconditional inside the data account and its ARN/external id are readable from any use case a member can view, so "any bucket in that data account" would be reachable without eligibility; (b) through the tag-conditioned cross-account role the probe is denied exactly when the data path would be denied (untagged bucket, or tagged with ABAC off), so creating the use case first never bought the customer a working bucket; failing early with a reason-specific remedy is more useful than a use case that cannot reach its bucket. The documentation order is changed instead: tag, enable ABAC, then create (§9).
- **Refuse any bucket configured on another use case with no override.** Rejected: legitimately shared buckets exist (the sizing script counts them, §16) and must not break; the PortalAdmin override with an audit row is the narrowest shape that keeps them.
- **Require `dda-portal:usecase-id=<target>` for a non-PortalAdmin attach of a bucket configured on no use case** (the AWS administrator delegates each bucket to one use case at tagging time, closing the opt-in pool). Rejected: administrators would need the portal's use case ids in hand when they tag, which the onboarding guide's order (tag before the use case exists) makes impossible for the configured buckets; the opt-in pool is the price, it is measured before deploy (the "tagged buckets configured on no use case" count, §16 row 19), and the follow-on's D1 shrinks who can hold UpdateUsecases on a fresh use case.
- **Ignore a `dda-portal:usecase-id` claim once the use case it names has been deleted** (revision 3's rule: one `get_item`, stale → proceed). Rejected in this revision: it hands a deleted use case's portal-created buckets — contents included — to the first UpdateUsecases holder who attaches them, which contradicts Requirement 10's user story ("a use case's storage stays its own") and is exactly the shape the Unclaimed rule exists for. The claim now outlives the use case (§1.6 step 4); a PortalAdmin re-homes such a bucket deliberately, with the audit row recording `stale_claim: true`, or an administrator removes the tag. The opposite extension — have `delete_usecase` remove the use case's buckets' tags — was also considered and rejected: the portal would need `s3:UntagResource` on buckets it did not create, and deleting a use case must not silently change the eligibility of storage an administrator tagged by hand; the admin guide carries the step instead.
- **Exclude the portal's own buckets by convention only** (nothing tags them, no record should name them). Rejected in this revision: the exclusion is an invariant the sinks rely on (§1.3), and a convention is one migration or one mis-click in a development account away from failing; `portal_owned_buckets()` makes it a rule at the two places that decide membership and attachability.
- **Verify the Data Account role grant by adding `sts:AssumeRole` on `DDAPortalDataAccessRole` to the Lambda roles.** Not in this spec: the template grants AssumeRole only on `DDAPortalAccessRole` (`compute-stack.ts:546–553`), so whether any live deployment can assume the Data Account role is UNVERIFIED (every Data Account side-effect in `create_usecase` is wrapped in `try/except` and fails softly today, 1240–1333, so a dead path would be silent). The probe fails closed with `credentials_unavailable`; the sizing script measures the dependency before deploy (§14, `simulate-principal-policy`); the grant is the follow-on's proof-of-control decision (D2 assumes the use case's roles at creation and needs the same grant). If the measurement shows separate-Data-Account use cases exist and the simulation says denied, the owner is told before deploy (verification notes) that onboarding with a separate Data Account answers 400 until that grant exists — today it answers 201 with every Data Account step failed.

Writer guard (Requirement 10.10): `test_usecase_bucket_config_units.py::test_only_enumerated_writers_touch_bucket_attributes` walks every `FunctionDef` in `edge-cv-portal/backend/functions/*.py` and `layers/shared/python/*.py` with `ast`. A function is a **writer** when its body contains a call whose attribute or name is one of `put_item`, `update_item`, `batch_writer`, `transact_write_items` **and** names one of `s3_bucket`, `data_s3_bucket`, `additional_s3_buckets` in a *write-shaping position*: a dict-literal key, an element of a list/tuple/set literal (`updatable_fields`, `data_fields`), the slice of a subscript store (`item['data_s3_bucket'] = ...`), the value of an `ExpressionAttributeNames` alias (`{'#a': 'additional_s3_buckets'}`), or inside a string literal that also contains an update-expression token (`SET `, `REMOVE `, `list_append`, `contains(`, `attribute_not_exists(`). The rule is function-scoped because none of the current writers names the attribute in the write call itself: `create_usecase` builds `item` sixty lines before `table.put_item(Item=item)` (1155–1218), and `update_usecase` (1563–1589) and `configure_data_account` (704–720) build their `UpdateExpression` strings from field lists. It is position-scoped because a plain "any string literal anywhere in a function that also writes" rule matches twelve functions on the current tree (`compilation.start_compilation_job`, `training.create_training_job`, `workflow_packaging.package_workflow` and others that *read* `usecase['s3_bucket']` and write unrelated tables), which would force a loosened or allow-listed guard. **Self-check on the current tree (run while writing this revision):** the rule finds exactly `{usecases.create_usecase, usecases.update_usecase, data_management.configure_data_account}` and nothing else. After implementation the test asserts the module-qualified writer set equals `{usecases.create_usecase, usecases.update_usecase, usecases._add_additional_bucket, usecases._remove_additional_bucket, data_management.configure_data_account}`, and a second assertion (same AST walk, every `Call` whose attribute/name is `_add_additional_bucket` or `_remove_additional_bucket`) pins their call sites to `{usecases.update_usecase, usecases.create_s3_bucket}`. `create_s3_bucket` is a writer *by delegation*: it contains no DynamoDB write call of its own (the attach is `_add_additional_bucket`), so the two assertions together are the complete picture — five functions write the attributes, and the two list helpers are called from exactly two places. Any new function that **names** the attributes in a write-shaping position, or a new caller of the helpers, fails the test. What the rule cannot see, stated: a pass-through writer that never names an attribute (`for k, v in body.items(): expr += f"{k} = :{k}"`, or `put_item(Item=dict(body))`) is invisible to any literal-based rule; the guard relies on the module convention that every record writer shapes its write from an explicit allow-list (`updatable_fields` in `update_usecase`, `data_fields` in `configure_data_account`, the hand-built `item` in `create_usecase`), and a reviewer rejects a pass-through writer by hand. The guard pins the enumerated writers; the convention is what keeps the enumeration meaningful.

Attach-eligibility property (Requirement 15.3, Property 9): for any sequence of calls drawn from {`POST /usecases`, `PUT /usecases/{id}` with every updatable field, `POST /s3-buckets` with and without `usecase_id`, `POST /usecases/{id}/data/configure`, `DELETE /usecases/{id}` of a generated use case} by a principal that is not PortalAdmin, with a stubbed `GetBucketTagging` reporting any mix of untagged / unreadable / tagged / tagged-for-another-use-case / tagged-for-a-deleted-use-case buckets, the portal-owned names drawn into the mix, and a second pre-existing use case configured with bucket `A`: no resulting record contains an untagged or unreadable bucket or a portal-owned bucket in `allowed_s3_buckets`, no record other than the pre-existing one ever contains `A`, and a bucket whose `dda-portal:usecase-id` names a use case the sequence deleted is in no surviving record's set.

## 5. Use case record and API (`functions/usecases.py`, `functions/data_management.py`)

### 5.1 Storage and the two list helpers

`additional_s3_buckets` is a DynamoDB List of strings (not a String Set: boto3 returns sets as Python `set`, which `create_response`'s `json.dumps(default=decimal_default)` cannot serialise, and use-case records are serialised in many handlers). Absent attribute ≡ `[]`. Cap: 100 entries per use case (checked before any probe; `too_many_buckets`).

Two module-level helpers in `usecases.py`, the only code that writes the attribute (`now_ms = int(datetime.utcnow().timestamp() * 1000)`, the module's existing timestamp convention at 1135 and 1560):

```python
def _add_additional_bucket(table, usecase_id, name) -> Literal['added', 'already_present', 'usecase_not_found']:
    now_ms = int(datetime.utcnow().timestamp() * 1000)
    try:
        table.update_item(Key={'usecase_id': usecase_id},
            UpdateExpression='SET #a = list_append(if_not_exists(#a, :empty), :one), updated_at = :t',
            ConditionExpression='attribute_exists(usecase_id) AND (attribute_not_exists(#a) OR NOT contains(#a, :b))',
            ExpressionAttributeNames={'#a': 'additional_s3_buckets'},
            ExpressionAttributeValues={':empty': [], ':one': [name], ':b': name, ':t': now_ms},
            ReturnValuesOnConditionCheckFailure='ALL_OLD')
        return 'added'
    except ClientError as e:
        if e.response['Error']['Code'] != 'ConditionalCheckFailedException': raise
        return 'usecase_not_found' if not e.response.get('Item') else 'already_present'
```

The `attribute_exists(usecase_id)` conjunct is what prevents the upsert from materialising a phantom `{usecase_id, additional_s3_buckets}` record when the use case was deleted between the permission check and the write; `ReturnValuesOnConditionCheckFailure` (botocore 1.43 carries it) distinguishes "item gone" from "name already present" without a second read.

`_remove_additional_bucket(table, usecase_id, name)`: read the record (404 `usecase_not_found` if absent); if the name is absent ⇒ `not_present`; else write the filtered list with `ConditionExpression='attribute_exists(usecase_id) AND #a = :expected'`; on `ConditionalCheckFailedException` re-read and retry once, then 409 `{'error_code': 'concurrent_update'}`.

**`TagResource` statement shape is decided by evidence, not assumed.** Task 2.1 records, with the source URL and the date read, whether `aws:RequestTag/${TagKey}` (and `aws:TagKeys`) are listed as condition keys for `s3:TagResource`. If listed: `conditions: { StringEquals: { 'aws:RequestTag/dda-portal:created-by': 'portal' } }` — the role can only ever tag while asserting the portal marker, which is the only tag write the code performs — and `aws iam simulate-principal-policy` for the statement with and without the request tag is run and recorded before deploy. If not listed: the condition key would be absent from the request context, `StringEquals` would never match, and every tag write would be denied; the statement then carries **no condition** and the bound is the application layer: `create_s3_bucket` is the only tag writer for portal-account buckets and writes exactly the three `dda-portal:*` keys (unit-tested: every `Tags` argument — `CreateBucketConfiguration.Tags` and the fallback `tag_resource` — is asserted key-for-key). **Evidence gathered (verification notes, IAM evidence table; S3 User Guide "Using tags with S3 general purpose buckets", https://docs.aws.amazon.com/AmazonS3/latest/userguide/buckets-tagging.html, read 2026-10-13):** `aws:RequestTag/key-name` is documented as restricting the tag pairs passed during the `TagResource` **and** `CreateBucket` operations (its example policy 1.1 conditions `s3:CreateBucket` + `s3:TagResource` on `aws:RequestTag`), and `aws:TagKeys` is listed (example 1.3). The statement **is conditioned**, and the one condition covers both tag writes the handler can make — the tags supplied in the `CreateBucket` request (§5.5 step 3, for which S3 also requires `s3:TagResource`) and the fallback `TagResource` (step 5). The Service Authorization Reference page itself (`list_amazons3.html`) is script-rendered and could not be text-fetched; the user guide is the recorded source and the runbook's `simulate-principal-policy` is the live confirmation. The follow-on spec treats the same question identically (its design.md:301), so the two specs cannot disagree on the shape. The ABAC action is spelled **`s3:PutBucketABAC`** throughout — the stack, the CDK test and this document: the vendored botocore 1.43.101 `PutBucketAbac` documentation names the required permission `s3:PutBucketABAC` (the operation name keeps the service model's `PutBucketAbac` casing; IAM matching is case-insensitive, but the CDK test asserts the string, so one spelling is fixed here), and the follow-on spec uses the same spelling, so both specs name one action. `s3:PutBucketABAC` cannot be tag-conditioned (the key is not evaluated before ABAC is on); it is bounded the same way (called only on a bucket this handler has just created). ### 6.2 Vendored boto3/botocore in the shared layer

`compute-stack.ts:165` packages `backend/layers/shared` as-is (`Code.fromAsset`), so the layer ships whatever is committed under `layers/shared/python/` (`requests 2.34.2`, `urllib3 2.8.0`, `PyYAML`, `certifi`, … are vendored that way today; `build.sh` is a convenience, not the asset pipeline). The Lambda-managed `python3.11` runtime bundles its own boto3/botocore, which lags releases by months; `PutBucketAbac` and the bucket `TagResource` are recent additions, so relying on the runtime's copy would make every `POST /s3-buckets` fail at step 4 on a deployment whose runtime predates them, leaving an untagged bucket behind. Decision: vendor `boto3==1.43.101` and `botocore==1.43.101` — the version the 3.11 lane runs, in which the operation names were verified (`s3`: `PutBucketAbac`, `GetBucketAbac`; `s3control`: `TagResource`, `UntagResource`, `ListTagsForResource`) — plus their dependencies `s3transfer`, `jmespath`, `python-dateutil`, `six`, installed with `pip install --no-deps -t python/` so the already-vendored `urllib3 2.8.0` tree (pinned byte-for-byte by `test_preservation_dependency_out_of_scope.py` via `sha256_tree`) is not touched; botocore 1.43 accepts `urllib3 >= 1.25.4, < 3`. Size: ~22 MB (botocore) + ~1.3 MB (boto3) + ~1 MB (the rest) on disk — pure Python, compatible with the layer's `PYTHON_3_11` and `PYTHON_3_12` runtimes. `layers/shared/requirements.txt` gains the pins with a comment naming the two operations that need them. A vendored package on the layer path shadows the runtime's copy for every function on `sharedLayer` (42 functions; the one `jwtLayer`-only function is not an S3 caller). The owner has already approved this vendoring for the follow-on spec (its owner decision 4); doing it here, where the operations are first needed, means the follow-on composes with it rather than repeating it.

Unit test `test_shared_layer_sdk_operations.py`: with `sys.path[0]` set to `layers/shared/python`, import `botocore`, assert `botocore.__version__ == '1.43.101'`, and assert the five operation names above are in the respective `get_service_model(...).operation_names`. A future un-pin fails the lane.

Alternative considered and rejected: keep the runtime SDK, fall back to `put_bucket_tagging` (granting `s3:PutBucketTagging`) and skip ABAC with `abac: unsupported_sdk`. It keeps bucket creation alive on an old runtime, but silently turns "ABAC enabled at creation" — which the follow-on's tag-conditioned grant depends on — into a best-effort step whose failure the owner's CLI backfill would hide.

## 14. Testability

Unit-testable without AWS: `parse_s3_uri`, `portal_owned_buckets` (environment permutations: both set, only the prefix derivation, empty account id), `allowed_s3_buckets` (a record naming the artifacts bucket as `s3_bucket` and the component bucket as an additional entry yields the empty set, with the WARNING), `assert_bucket_allowed` (monkeypatched `log_audit_event` recorder), `_select_s3_role_for_bucket`, `probe_bucket_eligibility` (stub client; retry path with a fake `time.sleep`), `check_bucket_attachable` (stub table scan + stub probe + stub `get_item`: portal-owned refused at step 0 even when the stubbed tagging says `managed=true` and the Scan is never called; stale claim refused for a non-PortalAdmin with `REMEDY_STALE_CLAIM`, admitted for a PortalAdmin with `stale_claim: true` in the audit details), `BucketConfigError.to_body`, `is_trusted_model_source`, the vendored-SDK operation names, the writer guard (AST; its rule is itself checked by a fixture module containing one function of each shape — dict key, field list, subscript store, alias, update-expression string, and a read-only `usecase['s3_bucket']` consumer that must *not* match). Handler-level tests use the repo's monkeypatch harness (`test_model_import_fine_tunable.py` style): `check_user_access` stub per role, `get_usecase_details` returning a crafted record, recorders on `assume_usecase_role`, `boto3.client`, `get_usecase_client`, `get_s3_client_for_bucket` and every S3 method; assertions are "400 with `error_code` and all recorders empty" or "proceeds with the same role as before". Integration-style tests use the moto `aws_stack` fixture (real `shared_utils`, `test-usecases`, `test-user-roles`, `test-audit-log`, `test-portal-artifacts`) for the DynamoDB list semantics (including the `attribute_exists` condition with a deleted item), the audit rows, `create_usecase`/`update_usecase`/`create_s3_bucket`/`configure_data_account` end to end with a stubbed `get_bucket_tagging`/`tag_resource`/`put_bucket_abac` (moto's S3 supports `get_bucket_tagging`; `tag_resource` and `put_bucket_abac` are stubbed via `botocore.stub.Stubber` or a monkeypatched client factory). Property tests follow `test_property_import_source.py` / `test_property_portal_registry_roles.py`. Property 1's oracle is **hand-written from the record fields**, never `allowed_s3_buckets` itself: `oracle = {record['s3_bucket'], record.get('data_s3_bucket'), *record.get('additional_s3_buckets', [])} ∩ membership-grammar − {PORTAL_ARTIFACTS_BUCKET, COMPONENT_BUCKET}` with the two names read from the test environment, and the record generator draws the portal-owned names into `s3_bucket`, `data_s3_bucket` and the additional list with non-trivial probability, so the property exercises the exclusion instead of being vacuous for records that name those buckets. Property 8 and the `create_dda_job` gate test run under both flag states with three principals — a registry DataScientist, a claim-only DataScientist, and a Viewer — asserting validate = import for every principal and state, and for the labeling gate: claim-only admitted with the flag off, denied with it on and no registry row (both pinned). **The claim-only DataScientist is defined, not implied** (Requirement 15.6): JWT `custom:role = DataScientist`; a global row `{user_id, usecase_id: 'global', role: 'Viewer', status: 'enabled'}` — the provisioning row shape `backfill_portal_registry.py` and `user_admin.py` write (`status: 'enabled'` is what enforcement's `_lookup_identity` requires to resolve the user at all; the backfill mirrors a recognised claim, so this principal models a user whose Cognito claim was raised to DataScientist after provisioning, or whose claim the registry never mirrored — the one shape on which the two gate forms disagree) — and **no** row on the use case. Under enforcement that global Viewer row is what resolves (D8 of the follow-on: a global role applies to every use case), so the claim-only principal is a Viewer with the flag on and a DataScientist with it off, which is exactly the difference the two gate forms expose. **Harness assumption checked, not assumed:** whether moto 5.1.22 honours `ReturnValuesOnConditionCheckFailure='ALL_OLD'` on `UpdateItem` (returning the old item in the `ConditionalCheckFailedException` response, which §5.1's `_add_additional_bucket` reads to tell "item gone" from "name already present") is checked by a ten-line probe in the 3.11 lane at the start of the API task (task 4) and the answer recorded in `verification-notes.md`; if moto does not honour it, the api tests inject the condition failure through a monkeypatched `table.update_item` raising a `ClientError` with and without `Item` (the design already injects the 409 `concurrent_update` case this way), and the real-DynamoDB behaviour is exercised by runbook check 8 (`already_present`). The CDK statement test runs with `npm test` in `infrastructure/`. The `/users/me/usecases` dependency in the frontend is mocked at `apiService` as the existing page tests do.
