# Design Document

## Overview

This design turns the `car-assembly-check` requirements into one new workflow node type, two frontend sections, one Portal read, a per-deployment configuration of two LocalServer floors, five small offline scripts (one a shared Triage_File reader) plus one device-batch script, and a documented procedure (including the Portal Build Fleet build of the JP5 LocalServer from `main` after this spec's merge, with both floors of the demo deployment set to the version it publishes — no build-tooling change, §13) — on top of the RF-DETR-Seg pipeline that `rfdetr-seg-support` delivers and that this design never modifies. The centre of the design is the **Layout Check** node (`type_id = layout_check`): an executor binding whose pure logic lives in a new shared module `workflow_core/analytics/layout.py` beside `scene.py`, is evaluated on the device by `scene_analytics.apply_scene_analytics` right after the Detection_List is merged, is mirrored in the cloud test sandbox, and writes `layout.<nodeId>` into the Run_Metadata. The node compares each predicted instance mask (`mask_rle`, Canonical_RLE at source resolution, read from the capture record the marshal wrote) with a normalized polygon per class stored in the node's `expected_regions` parameter, using an intersection-over-union computed entirely on run-length intervals so a 4608 × 3288 frame never becomes a pixel array in pure Python. The verdict reaches device outputs through the existing dotted-path condition language (gating executor bindings — `mqtt_publish`, `digital_output`, `s3_upload` — never a `capture` sink), the device HMI through a new run-results section that re-uses the instance mask layer of `rfdetr-seg-support`, and — once the separate feature `results-tab-workflow-runs` uploads workflow-run artifacts to S3 — the Portal Results tab through the run-metadata JSON `{capture_id}.json` that lands beside the capture record in `<thing>/<wf>/<exec>/` (DD7; nothing of a workflow-engine run reaches S3 today, so the Portal surface is specified against that feature's layout and blocked until it lands). Grayscale preprocessing is a `custom_python_preprocess` node with a fixed OpenCV handler and needs no platform change. The `min_iou` threshold is calibrated twice — from the labels before deployment, then from the model's own predicted masks over a one-file-at-a-time batch of the whole labeled set on the device, exported from the run preview endpoint — before the production version is bound, and whenever the recalibration changes the threshold the batch is re-run on the recalibrated version so every measurement rests on the threshold the production version carries. The per-image ground truth comes from one source, the owner-confirmed Triage_File (DD18; 70 rows, confirmed 2026-11-25): the 48 photos first prepared are not all correct assemblies (11 are not), and 22 further device captures of wrong placements and missing pieces joined the labeling job — uploaded under the same prefixes on 2026-11-25 (O14 (a)); two jobs enumerate the 70: `r1` (`labeling-f85bdfc7`, created the same day; default-prompt pre-labels on 37 images, unusable per piece) and `r2` (**`labeling-485efbd9`**, `car-assembly-instances-r2`, created 19:43:59 UTC from the request the `r2` report prepared — the colour `prompt_overrides`, because the deployed Grounded-SAM worker proposes only the first label of the caption; its id read from the Portal's jobs table, never invented), and **`r2` is the Labeling_Job_Of_Record by owner decision O17 (A)** — `r1` is stopped, not deleted, after `r2`'s auto-label completed (§11; every path downstream is derived from `r2`, nothing else changes) — as examples of the same three classes (owner decision O13 (i)) and form the Fail_Set that proves the verdict fails when it should; only triage-confirmed correct images feed the reference layout and the false-fail side of the calibration. The classes are defined by shape — `front_fender` the nose piece, `rear_fender` the tab piece, `roof` the half-disc — and in the Training_Orientation (roof pocket at the top) a correct build has the tab piece in the LEFT pocket and the nose piece in the RIGHT (owner-confirmed convention; the labeling instructions state it for orientation only, the Reference_Layout embodies it). A stray piece at the image edge outside the car outline is left unlabeled by the owner's policy (decision O15 (i)), and at runtime the Layout_Check ignores any detected piece lying outside the car outline — the union of the Expected_Regions — so such a piece never changes the verdict, while a piece set down outside the outline instead of in its pocket leaves its class missing and the image fails (decision O19, DD23); the two known-good images that show the stray piece are therefore Known_Good (DD18). The device captures are rotated 180° relative to the training images (DD19), so the 22 were rotated like the 48 before upload and a production-camera workflow carries a `rotate-180` node ahead of the grayscale conversion. A colour-trained variant is trained from the same labels and compared with the grayscale model on the same held-out images and the same device (Requirement 11, owner decision O12 resolved); "monochrome + on-device grayscale" is the production default until that comparison confirms or revises it, and the production workflow version binds the winner. **The device is `mic-730ai`** (owner decision O6 (β), DD20): the demo account's Jetson AGX Xavier (`arm64_jp5`), the only enrolled device in the account of this use case that can be brought onto a Seg-capable LocalServer through the Portal. Greengrass component versions are per account and the deployed Seg floor names the lab lineage's numbers (rfdetr-seg-support M-11), so **by owner decision O18 (ii)** the Seg floor becomes per-deployment configuration — a second key of this spec's floor mechanism, with the committed literal as its default — and the demo deployment sets both floors to the version the demo Portal's Build Fleet publishes for this spec's merged `main` (DD9, DD20). **The demo `arm64JP5` lineage and `mic-730ai` are shared with another active actor** (requirements Facts, "shared lineage": a Portal Build Fleet build of `origin/main` without `layout_check` was published as `1.0.3` at 20:49 UTC on 2026-11-25 while this design was under review, the same actor then revised `mic-730ai` four times between 22:19 and 22:35 UTC to that build, and the Fleet publishes highest + 1), and the Portal's floors are minima — so the device move is a **Pinned_Revision** through the deployment API with the explicit version, never the UI's "Update to latest", and every recorded run is preceded by the **Installed_Version_Check** (`GET /system-health` → `localServerVersion`), which `batch_run.py` writes into every Result_Export and the offline scripts refuse to read without (DD22, §13). For the same reason both floors are **per-deployment configuration** (CDK context with an SSM fallback in the deploying account; `{}` as the Layout_Check floor's fail-closed default and the committed literal as the Seg floor's; DD9, §7), not code literals. The 70 photos came from a Basler camera on a JP7 Thor, and `mic-730ai` has no camera: the verification runs on the Static_Image_Camera and a folder batch of those photos, which needs no camera, and by owner decision O16 (a) no camera is mounted on `mic-730ai` for this use case (DD21). This design is implemented on `feature/car-assembly-check` (created from `origin/main` `e7547824`, the spec commit cherry-picked first) and delivered as a pull request to `main`; the Portal deploys, the Fleet build and the device steps come after the merge, and every live step needs the owner's go-ahead (§13; requirements Facts "Implementation branch").

Every decision below is final for the implementer. Where a requirement carries a decision for the user (the A/B sub-decisions O8–O10 and the winning criterion of Requirement 11.7), the design implements the recommended default and the section "Carried decisions" names exactly what changes if the user picks another option. **The owner resolved O1 (C), O15 (i), O16 (a), O18 (ii) and the new O19 (yes) after the spec commit (recorded 2026-11-27), and the design implements those choices**: the repository script for the reference capture (DD10), the stray piece left unlabeled with the two rows that show it Known_Good (DD18), a detected piece outside the car outline ignored at runtime (DD23), no camera on the Verification_Device (DD21), the Seg floor as a second per-deployment key and a Portal Build Fleet build (DD9, DD20). ## Decisions

**DD1 — The layout check is a new shared module `workflow_core/analytics/layout.py`, not an addition to `scene.py`.** `scene.py` is mirrored and pinned; adding a second, unrelated algorithm to it would move its hash for every reader and mix the counters' vocabulary with mask geometry. The new module follows the same contract (stdlib-only, no I/O, nothing raises, parsers return `(value, problems)`), exports exactly `parse_expected_regions`, `check_layout`, `attach_detection_ids`, `position_score`, `rle_intervals`, `interval_iou`, `run_metadata` and the constants named in "Interfaces", and is added to `MIRRORED_SHARED_MODULE_RELPATHS` of the mirror test together with the catalog and validator files it accompanies. Validator rules go into `validator/checks.py` (new codes `V14_LAYOUT_CONFIG_INVALID`, `W4_LAYOUT_NO_DETECTOR`; at `2b3abf34` the highest codes are `V13`/`W3`, so neither collides) and are re-exported from `validator/__init__.py`.

**DD2 — The node is generic: the keys of `expected_regions` are the classes it checks.** Hard-coding the three Piece_Classes into the platform would make a platform node carry a use case's vocabulary. The use case's value has exactly `front_fender`, `rear_fender`, `roof` (Requirement 4.1); the validator checks the map's shape (1–10 keys, valid polygons); `pass` means every configured class is `ok` (the three Piece_Classes here, never a hard-coded three); and a run that detects a class the map does not name reports it under `unexpected_classes` with `outcome = warning`, so an omitted class cannot pass silently (Requirement 5.3). The capture script emits every class it finds, so it cannot produce an incomplete map for a complete input. **The check rests on one assumption about the model:** its `class_label` follows a piece's *outline*, not its *position* in the frame — a detector trained on correct assemblies alone sees each class at one position only and could learn the position instead, in which case swapped fenders come back relabelled by position, both `ok`, and the verdict passes. The training data therefore includes the Fail_Set — pieces of every class away from their valid positions, labeled by shape (O13 (i), DD18) — and the Fail_Set Batch_Run of §13 and the swapped case of Requirement 10.2(b) are the test: a wrongly placed piece reported `ok` is the signal, and it stops the verification (the residual stop rule of O13).

**DD3 — Position_Score is computed on column-major run intervals; a pixel array is never built.** A Canonical_RLE is already a list of foreground intervals over the column-major index space `[0, width × height)`; the Expected_Region is rasterized into the same space one column at a time with a sweep over its edges, and IoU is the intersection length of two sorted interval lists divided by the union length. Cost for a near-convex 64-vertex polygon at 4608 columns: the sweep keeps 2–4 active edges per column (≈ 20 k float operations), the mask has ≈ 4,500 runs, the merge is linear — about 20–40 ms per piece in CPython on an Orin core (an estimate; measured in Requirement 10.4), 60–120 ms for three pieces, inside the 200 ms budget of Requirement 5.8; the pathological worst case (all 64 edges active in every column) is ≈ 300 k edge tests, still bounded. Pixel semantics: pixel `(x, y)` is foreground iff the number of polygon edges whose x-span covers its centre's x (`min_x ≤ x + 0.5 < max_x`, half-open; vertical edges never count) and whose crossing with the vertical line through the centre lies at or above the centre (`y_cross ≤ y + 0.5`) is odd — the even–odd rule stated with the same half-open convention on both axes that the column sweep of §1 uses, so the two agree on every centre, including centres lying exactly on a crossing. It is the rule a `cv2.fillPoly` of the integer-rounded polygon approximates; the oracle test evaluates this count per pixel centre on small frames and compares interval lists exactly, not against OpenCV. **Fallback if the budget is missed (Requirement 5.8):** `scene_analytics.py` gains a device-only `_position_score_numpy` with the same signature that vectorizes the **same** sweep (per column, the active edges' crossings are computed with array arithmetic and paired identically; the flattened intervals are the same integers), selected by a module flag only on the device, and the oracle fixtures pin `_position_score_numpy(...) == position_score(...)` exactly — the sandbox keeps the pure path, and because both paths emit identical intervals the device/sandbox identity invariant survives.

**DD4 — Frame size for the check comes from a header-only read of the capture record's input image, falling back to `metadata.frame`.** The masks are at the resolution of the frame `emltriton` processed, which is the image the capture record references under `deviceFleetAuxiliaryInputs[].data-ref` (the same reference `output_bindings._capture_record_source_dimensions` uses). That helper decodes the whole image with `cv2.imread` (`output_bindings.py:2208-2252`) — 100–200 ms for 15 MP — so the layout branch uses a new header-only reader `scene_analytics.capture_record_input_size(output_dir, capture_id)` (`PIL.Image.open(path).size`, no pixel decode, ≈ 1 ms), falls back to `tag_values["frame"]` (seeded for frame-feed runs once `stream_feed`'s binding tuple names `layout_check`), and reports `frame size unknown` as a warning outcome when neither exists. `needs_frame_size` and the counters' zone path are untouched, so zone users keep today's exact behaviour. The reader presupposes the one `capture` node on the frame path that DD17 fixes.

**DD5 — Detection_IDs are joined onto the raw entries by exact `(class_label, confidence, bounding_box)` equality.** `detections.read_detections` returns the marshal's raw entries (with `mask_rle`, without ids); `tag_values["detections"]` is the built list (ids, no masks). `attach_detection_ids(raw, built)` pairs them by the three fields the normalizer copies verbatim (`detections._normalize_entry` casts confidence and box to float; the join casts the raw values the same way), assigning each raw entry at most one id in built-list order; an unmatched raw entry gets `id = null` and a problem. Both the device and — for fixtures that carry raw entries — the sandbox call the same helper, so `flagged` carries the same ids every other consumer shows (detection-guided-bedrock-inspection Property 1). Edge case, harmless and pinned by a test: `_normalize_entry` maps a missing `class_label` to `""` while the join compares `label == str(class_label)` (`"None"`), so such an entry never joins — and never qualifies for any region (no region is keyed `None` or `""`), so it is neither flagged nor counted.

**DD6 — The executor hookup adds two optional keyword arguments, one call-site change and self-timing.** `scene_analytics.apply_scene_analytics(document, tag_values, frame_size=None, collector=None, output_dir=None, capture_id=None)`; `pipeline_executor._apply_scene_analytics` passes `output_dir=output_dir, capture_id=capture_id` (it already has both). `has_scene_analytics` becomes true for a `layout_check` binding so `_apply_scene_analytics` runs; `needs_frame_size` is unchanged (DD4). The layout branch reads the raw entries once per run with `detections.read_detections(output_dir, capture_id)` (the record was already read by `merge_detections`; a second read of a ≈ 100 KB file is cheaper than threading a cache through `merge_detections`' signature) and evaluates every `layout_check` binding in the same topological pass as counters and associations. The scene-analytics bindings are not timed today (`apply_scene_analytics` receives no duration sink; the output bindings are timed through `pipeline_executor._duration_sink`, `:2814-2825`, which is not threaded into the analytics step), so the layout branch wraps its own evaluation in `time.monotonic()` and calls `collector.record_invocation_duration(node_id, elapsed_ms)` (`node_status.py:330`, first value wins) — layout bindings only; the counters stay untimed (preservation). `pipeline_executor.py` is CSI-golden-pinned; its sha256 is rebaselined in the same commit (Requirement 12.1).

**DD7 — The Portal reads the verdict from the run-metadata JSON that `results-tab-workflow-runs` uploads beside the capture record; Requirement 8 is bound to that feature and blocked until it lands.** The executor persists the run metadata as `{output_dir}/{capture_id}.json` under `/aws_dda/captures/{workflow_id}/{execution_id}/` (`_persist_run_metadata`, `pipeline_executor.py:3486-3515`; `_WORKFLOW_CAPTURE_ROOT`, `:277`). Nothing uploads that folder today: the InferenceUploader watches `/aws_dda/inference-results` only, is not published in account 326334468650 and is not enabled for `reinvent` (requirements "Facts"), so the first revision's claim that it uploads the sibling was wrong. Three options were weighed: (a) bind Requirement 8 to `results-tab-workflow-runs`, whose FR-D1 uploads `{capture_id}.jpg`, `.jsonl`, `.json` and a `.run.json` sidecar to `<thingName>/<workflowId>/<executionId>/` and whose FR-P1–P3 make `captures.py` list workflow runs; (b) add a device-side upload to this spec; (c) drop the Portal surface. **(a) is chosen**: it keeps the Portal surface specified against the layout that will exist, costs no duplicate uploader (b would contradict O7 — no new DDA component, no IAM change — and duplicate a reviewed design), and makes the blocking explicit instead of silently dropping the surface (c); the first delivery's surfaces are the device ones (DD17, §5). In that layout the `.jsonl` and the `.json` are **always in the same folder** (no date folders), so the sibling key is simply `f"{key_base}.json"` — the run's `base` in that feature's `_group_keys_by_base`, the key its sidecar names as `artifacts.metadata` — and the first revision's basename fallback and midnight-straddle case disappear. One helper `_attach_layout(capture, s3, bucket, key_base, listed_keys, owner_args, detail)` performs one `get_object` on the existing bounded pool and sets `layout_summary` on **page** items (≈ 300 bytes per node: `pass`, per-class `status`/`iou`, `unexpected_classes`; a 50-capture page adds ≈ 15 KB and stays under the 200,000-byte Portal MCP shaping cap, `mcp_portal/shaping.py:33`, that `portal_data_captures_list` shares) and the full `layout` section on the **detail** (`key=` request, which lists nothing — `all_keys = {detail_key}`, `:238-250` — so the detail reads the key directly and treats `NoSuchKey` as absent); on a page the key is read only when the listing contains it. The helper is called from that feature's workflow-run assembly (`_capture_from_run`, its design §5.8) and from `_parse_capture` (the detail parse, which that feature keeps with its signature); legacy InferenceUploader captures have no such sibling and get `null`s, byte-identical otherwise. Because both `rfdetr-seg-support` (detail request, deployed) and `results-tab-workflow-runs` (three sources, not implemented) modify `captures.py`, Requirement 8 is implemented on a tree that contains both. Device-side the verdict is never written into the capture record (the marshal writes it mid-pipeline; the verdict exists only post-pipeline) — the run-metadata JSON is the one place the executor already persists metadata, and re-using it means no device contract change and nothing for the uploader to learn.

**DD8 — The Misplaced_Mask is rendered client-side from existing data; no new device artifact.** Both result views already decode `mask_rle` per instance (`rfdetr-seg-support` Req 10.6 HMI `InstanceMaskLayer`, Req 11.2 Portal `rleToImageData`). The views match `flagged` instances to mask entries by `class_label` and bounding box (the preview/detail entries carry no Detection_ID; the join of DD5 guarantees the box/label pair is unique per id) and draw them in the "misplaced" colour with the others dimmed, plus the non-`ok` Expected_Regions (carried in `layout.<nodeId>.expected_regions`, scaled by `frame`) as dashed SVG outlines. A `missing` piece shows only its outline.

**DD9 — The Layout_Check device code gets its own LocalServer floor (variant B, confirmed on 2026-11-24 and re-checked on 2026-11-25 at `c066b4c8`), and that floor is per-deployment configuration, not a code literal; by owner decision O18 (ii) the Seg floor becomes a second key of the same mechanism, its committed literal the default; variant A is recorded only as the alternative for a future rebuild.** The `layout_check` binding exists only in LocalServer builds that include `scene_analytics.py`'s layout branch and the vendored `layout.py`. Two variants: **A** — `workflow_packaging.py` sets the `has_rfdetr_seg_model` discriminator (rfdetr-seg-support Req 14.8(b)) also when the compiled document has a `layout_check` node, so `WORKFLOW_RFDETR_SEG_MIN_LOCAL_SERVER_VERSIONS` gates these workflows; correct iff the task-18 builds are made from a tree containing this spec's device code. **B** — a fourth floor `WORKFLOW_LAYOUT_CHECK_MIN_LOCAL_SERVER_VERSIONS`, discriminator `has_layout_check`, finding code `LAYOUT_CHECK_UNSUPPORTED_ARCH`, built like the Seg floor of DD8 in rfdetr-seg-support's design: `_parse_min_versions_map`, `min_local_server_version_for(..., layout_check=True)` taking the maximum with the other floors, the pre-submit gate, a coverage test. The observable check: the published `aws.edgeml.dda.LocalServer.*` versions recorded in rfdetr-seg-support `tasks.md` 18.1–18.6 and their source commit. **Variant B is confirmed**: at head `c066b4c8` (2026-11-25 05:07 UTC; worktree clean) 18.1–18.6 are done — lab `arm64JP6` **`1.0.85`** (`1.0.84` "published but unusable, do not deploy"), lab `arm64JP7` **`1.0.60`** (not hardware-verified; `1.0.59` unusable), lab `arm64JP5` `1.0.62`, lab `amd64` `1.0.56`, lab `amd64Nvidia` `1.0.5`, **demo `arm64JP5` `1.0.2`** (for `mic-730ai`), `arm64` not built — every image built from a commit of `feature/rfdetr-seg-support`, and `git grep -l layout_check HEAD` in that worktree exits 1; task 20.1 (`418b1faf`, changed in `36934d37`) carries the Seg floor literal `{arm64_jp5: '1.0.62', arm64_jp6: '1.0.85', x86_64: '1.0.56', x86_64_nvidia: '1.0.56'}` (`compute-stack.ts:860-865`) with `UNVERIFIED_RFDETR_SEG_ARCHES = {arm64_cpu, arm64_jp7}`, task 20.2 deployed it to both Portals, and 23.1 confirmed it. So the Seg floor names images without the `layout_check` binding, and riding that floor would let the gate approve a device that silently ignores the node. **Why not a literal (the second half of this decision):** the Seg literal's own defect, found live by that spec on the demo Portal (M-11): Greengrass component versions are **per account**, the one literal is deployed to two Portals, and its numbers are the lab lineage's — on the demo Portal `arm64_jp5: 1.0.62` is unreachable by a lineage that stood at `1.0.2` (at `1.0.3` since 20:49 UTC on 2026-11-25 — another actor's Fleet build of `origin/main`, requirements Facts "shared lineage"), so `mic-730ai` was refused with 409 `INCOMPATIBLE_LOCAL_SERVER`. A Layout_Check literal built the same way would need a different value per Portal and would be wrong on one of them whatever it said. Three ways to carry a per-deployment value were weighed: (a) a CDK context key passed with `-c` on every deploy — correct but fragile (a flag-less deploy resets it to the default, exactly the failure `detectorExportImage` had before its SSM fallback); (b) the Lambdas reading an SSM parameter at **runtime** — a new IAM grant and a cold-start read in two handlers for a value that changes once per build; (c) **a CDK context key with a synth-time SSM fallback in the deploying account** — the repository's own precedent (`bin/app.ts` `detectorExportImageDefault`: env, then SSM `/dda-portal/detector-export-image`, then nothing; an explicit `-c` always wins). **(c) is chosen**: context key `layoutCheckMinLocalServerVersions` (string or object → JSON string, the `llmModelImageLimits` handling), default filled by `context-helpers.layoutCheckFloorDefault(env, readSsm)` from the shell variable `LAYOUT_CHECK_FLOOR`, else the SSM String parameter **`/dda-portal/layout-check-min-local-server-versions`** of the deploying account **in the region the deploy resolves** — `bin/app.ts` `readSsmParameter` (`:35-47`) passes `--region` from `CDK_DEFAULT_REGION || AWS_REGION || AWS_DEFAULT_REGION || 'us-east-1'`, so the demo Portal's parameter is written and read with `us-west-2`, the deploying shell exports `AWS_REGION=us-west-2`, and the pre-deploy check of §13 step (3) reads the parameter back with `--region us-west-2` before the deploy (a shell resolving another region reads nothing, resolves `{}` and is stopped by the post-deploy check — fail-closed, but avoidable) —, else `{}`; **DD10 — Reference capture is the repository script (decision O1, option C — the owner's choice, recorded 2026-11-27); the polygon comes from the labeler's mask for the first reference; the threshold is calibrated from labels first and from predicted masks second.** `datasets/layout_reference.py` traces the largest connected component of each class's decoded mask (`cv2.findContours`, `RETR_EXTERNAL`, `CHAIN_APPROX_NONE`), simplifies it with `cv2.approxPolyDP` at the largest epsilon (searched geometrically from 0.5 px upward) that keeps IoU ≥ 0.98 against the source mask with ≤ 64 vertices, normalizes by the image size and prints the JSON. The labeled manifest (`--manifest`) is the default source because it does not depend on a trained model and is the ground truth the model is trained to reproduce; `--overlay` (the saved body of the device's `GET /workflows/executions/{id}/overlay`, whose `instances` carry `mask_rle` — rfdetr-seg-support Req 10.5(c) — with the frame size from the saved `GET …/metadata` body or `--size`) is supported for recapture after the fixture moves, when re-labeling is not wanted; a Portal capture detail is not an input because no workflow-engine run reaches the Portal today (DD7). `--calibrate` applies the shared `position_score` (the production rule) to either the labeled masks (`--calibrate <manifest>`) or the model's predicted masks (`--calibrate --results <Result_Export>`), with the Triage_File (`--triage`, DD18) splitting the images into the Known_Good_Set — whose scores give the distribution and the recommendation (the false-fail side) — and the Fail_Set — over which the same threshold must make every image fail with the triage-named pieces flagged or missing (the true-fail side, measured rather than only estimated by the synthetic rows). The synthetic margin rows stay: each fender against the other fender's region, and the roof against a **vertically flipped** copy of its region (an upside-down roof); a horizontally mirrored half-disc is itself, so that row would measure nothing. The production score is computed on a 96 × 96 mask grid (`RESOLUTION // 4` at 384) bilinearly upsampled to 4608 × 3288 and thresholded, whose IoU against the polygon is systematically lower and wider than the labelers' pixel-accurate masks, so a threshold derived from labels alone can false-fail a correct assembly; the predicted-mask pass over the whole Labeled_Set (§13) re-derives `min_iou` with the same margin rule before the production version is bound, and a change of threshold is followed by a re-run of the batch on the recalibrated version (§13 step 5) so the standing export's device verdicts carry the production threshold.

**DD14 — Scripts are pure and local; no AWS SDK calls.** All `datasets/` scripts read local files the user downloads (manifests, images, capture detail JSON, training metadata, Result_Exports) and write local files; existence checks use a local `--verify-dir`. **DD15 — Device batch runs are one file at a time, started by the device trigger API, correlated by construction.** A `folder_source` resolves the oldest matching file per run and consumes it after the run; nothing starts the next run (requirements "Facts"). `samples/car-assembly-check/batch_run.py`, running **on the device host** (where `/aws_dda/batch-input/` is the bind-mounted folder the container reads; the script's folder checks are local and it has no remote mode, §13), therefore drives the loop: for each source image, copy it into the folder (`shutil.copy`), `POST /workflows/registrations/{registration_id}/trigger`, poll `GET /workflows/executions/{execution_id}` every 0.5 s until `status ∉ {pending, running}` **and** the folder is empty, then export the run (metadata, node-status, execution, and the run preview `GET …/overlay` → `instances` with `mask_rle` and `detectionsTruncated`, rfdetr-seg-support Req 10.5(c)) into one record keyed by the source filename. The legacy `GET /workflows/{workflow_id}/results/{capture_id}` is not used: it resolves the id in the legacy `Workflow` table (404 for a `dda.workflow.*` registration) and reads the `InferenceResult` table that only the legacy Triton path writes, so for these runs it would carry no masks and the predicted-mask calibration would have no input (requirements "Facts"). Because exactly one file is in the folder per run, the run belongs to that file by construction — and nothing else could establish it: the capture record's input `data-ref` is `file://<capture_folder>/{capture_id}.jpg`, the frame the `capture` node wrote (`marshal_for_capture_template.py:465-469, 540-546`), not the staged source file, and no run-metadata field carries the source filename (`FolderFrame.original` is executor-internal, `pipeline_executor.py:376-388`). The Result_Export therefore records no "cross-check" basename (the first revision's `data_ref_basename` field would always have read `{capture_id}.jpg`), and the folder-empty refusal is the correlation's only guard. The alternative — an `mqtt_subscribe` trigger published 48 times — was rejected: `folder_source`'s `activation` port is inert ("edges into it are dropped at compile time", `catalog/nodes.py:346-349`), and the manual trigger route exists precisely for this. The loop's wait is bounded (`--timeout-s`, default 180 s per run, the harness's `workflow_output_s`); a timed-out or `failed` run is recorded with its `error` and the loop continues, so one bad run never loses the batch. The script knows nothing about ground truth unless given `--triage <csv>` (stdlib `csv`), in which case its summary line splits the counts by set — false-fails over the Known_Good_Set and false-passes over the Fail_Set — and nothing else changes; the per-piece agreement is the offline scripts' job (DD18).

**DD16 — The Grayscale_Node latency fallback is a whole-frame downscale at the frame source; `crop` is rejected.** The handler cannot resize (the bridge requires the output shape to equal the input shape), the catalog has no resize node, and a `crop` would change the pieces' scale and position in the model input relative to the uncropped training frames — exactly the parity the user required — so cropping would force re-deriving both image prefixes, the labels and the manifests from identically cropped images. A whole-frame downscale at the same field of view preserves parity: the trainer squashes every image to 384 × 384 whatever its source size, so the model input is the same picture resampled from a smaller source; masks come back at the delivered resolution; normalized Expected_Regions need no recapture. Mechanism: for the Static_Image_Camera, pin a downscaled copy of the colour original (Pillow `reduce(2)` → 2304 × 1644); for a camera on the Verification_Device, its binning/decimation setting (owner names it in O16; the Capture_Camera's Basler model very likely has neither, requirements "Facts"). If the camera cannot downscale, the measured time is recorded and accepted (the user's number is the total run time) and a `resize` node (`videoscale ! capsfilter`, the shape of `crop`'s descriptor) is recorded as a follow-up candidate.

**DD17 — The sample workflow has exactly one unconditional `capture` on the frame path and routes the verdict only through gated executor bindings.** `capture` compiles to `jpegenc ! emlcapture`, a GStreamer sink written during the pipeline; `conditional` gates executor bindings only and is collapsed out of the frame stream, and the Layout_Check runs post-pipeline — so a `capture` behind a `conditional` writes on every run and a pass/fail split of captures is unachievable. One `capture` is also required: without it no `{capture_id}.jsonl` record is routed (`detections.py:139-144`), the Portal Results tab shows nothing and DD4's reader has no `data-ref`. So: `source → gray → model → capture` is the frame path; `model → layout → verdict (conditional)` with `verdict.true → accept` and `verdict.false → reject`, both `mqtt_publish` in `payload_format = json` (two topics; both ports connected, so no W1 warning). The compiler collapses `layout`, `verdict`, `accept`, `reject` out of the stream, so the compiled pipeline is one linear segment ending in the capture sink and four executor bindings. The JSON template quotes every placeholder (a bare `{layout.layout.pass}` is not JSON and fails `MQTT_PAYLOAD_TEMPLATE_JSON`); a single-placeholder string renders with the native type, so `pass` is a boolean and `flagged` a list. No run id is in the template: `execution_id`/`capture_id` are capture-phase-only placeholders; the README documents a `phase = capture` publish of `{capture_id}` as the correlation option. `digital_output` (reject pulse on `layout.layout.pass == false`) and `s3_upload` on the `false` port are the documented production alternatives.

(c) is chosen. The helper reads columns by name; the join key is `filename` (the basename of a manifest `source-ref` or a Result_Export record's `file`); a row is **Known_Good** iff its `verdict` denotes a correct assembly and its `occluder` denotes none; **Fail_Set** iff it names misplaced or missing pieces (with or without an occluder); **Occluded_Correct** otherwise — a correct placement with an occluder, which carries no verdict expectation because the check has no class for whatever the occluder is and is reported in its own block wherever verdicts are compared (Requirement 1.7); `misplaced_pieces`/`missing_pieces` are lists of Piece_Class names split on `;`/`,`/whitespace; a `verdict` value the helper does not recognise, a piece name that is not a Piece_Class, a duplicate `filename`, a labeled image without a row and a row without an image are **listed, never guessed**, with the row's `confidence` and `notes` beside them, and the scripts exit 1 on any such listing. **The vocabulary is pinned from the confirmed file** (it exists since 2026-11-25 00:50 UTC; the owner confirmed the convention its verdicts rest on the same day): `KNOWN_GOOD_VERDICTS = ("correct",)`; `RECOGNISED_VERDICTS = ("correct", "incorrect", "incorrect_and_missing", "missing")`; `NO_OCCLUDER_VALUES = ("", "none")`, compared case-insensitively after stripping, because the file writes the **literal `none`** in 67 rows rather than an empty cell — a reader that tested only for emptiness would classify every row as occluded and leave the Known_Good_Set empty; any other `occluder` value (`hand` today) is an occluder and is not otherwise interpreted. ## Architecture

### 1. Shared pure logic: `workflow_core/analytics/layout.py` (Requirements 4.1, 5.2, 5.3)

New file in `edge-cv-portal/backend/layers/workflow_core/python/workflow_core/analytics/layout.py`, exported from `analytics/__init__.py` beside `scene`, mirrored to `src/backend/workflow_engine/vendor/workflow_core/analytics/layout.py`. Standard library only (`json`, `math`, `bisect`, `typing`). Nothing raises: every public function returns a result carrying `outcome` and `problems`, as `scene.count_detections` does.

**Parsing `expected_regions`** (`parse_expected_regions(text) -> (regions | None, problems)`): accepts the parameter as written (a JSON string) or an already-parsed dict. Rules, each producing one problem sentence: top level is a JSON object with 1–10 keys; each key a non-empty string ≤ 64 characters after strip; each value a list of 3–64 items, each item a list/tuple of two finite numbers in `[0, 1]`; consecutive duplicate vertices are dropped **cyclically** — the ring is read as closed, so a last vertex equal to the first (the GeoJSON habit of repeating the first vertex) is dropped too — and the 3–64 count is checked on what remains (the TypeScript port of §2 applies the same cyclic rule, so both report the same vertex count); the ring's signed area (shoelace) has magnitude ≥ 0.005 (0.5 % of the frame); the ring is simple — no two non-adjacent edges intersect (the package-private `scene._segments_intersect` is imported for the O(E²) ≤ 64² check, with the first and last edge treated as adjacent; same package, so no public surface is added to `scene.py`). Returns the normalized dict `{label: [(x, y), …]}` with vertices as floats.

**Rasterizing a region into column-major intervals** (`_region_intervals(polygon, width, height) -> List[Tuple[int, int]]`, private). The sweep lines are **vertical** (one per column, `X = cx = x + 0.5`), so a crossing is produced by an edge whose **x-span** covers `cx`: a horizontal edge (`y0 == y1`) is a valid crossing at `y = y0` for every column it spans, and a vertical edge (`x0 == x1`, zero width) never crosses a vertical line. Steps: scale vertices to pixels (`x × width`, `y × height`); build the edge list from consecutive vertex pairs (the ring closed), **skipping zero-width edges** (`min_x == max_x`) and keeping horizontal ones; sort edges by `min_x`; sweep columns `x = 0 … width − 1` with the one half-open rule on the x axis — an edge is **active iff `min_x ≤ cx < max_x`** (edges enter in `min_x` order; an edge is dropped once `cx ≥ max_x`; an endpoint exactly at `cx` therefore counts for the edge that starts there and not for the edge that ends there, so a vertex shared by two edges yields exactly one crossing or an empty pair, never an unpaired value); for each active edge compute the y of its intersection with `X = cx` by linear interpolation `y = y0 + (cx − x0) × (y1 − y0) / (x1 − x0)` (the divisor is non-zero because zero-width edges were skipped); sort the crossings and pair them `(y_a, y_b)` — for a simple polygon the count is even, since every active edge is counted once (the parser guarantees simplicity; should an odd count ever occur through float degeneracy, the unpaired last crossing is dropped and the function still returns — nothing in the module raises); convert each pair to the pixel rows whose **centres** satisfy the same half-open rule on the y axis, `y_a ≤ r + 0.5 < y_b`, i.e. `r0 = ceil(y_a − 0.5)`, `r1 = ceil(y_b − 0.5) − 1`, clipped to `[0, height − 1]`, and emit the flattened interval `[x × height + r0, x × height + r1 + 1)` when `r1 ≥ r0`. Intervals are emitted in ascending order by construction. Cost is `O(width × active_edges + E log E)`. **Pixel semantics (one rule, both axes half-open):** pixel `(x, y)` is foreground iff the number of edges with `min_x ≤ cx < max_x` whose crossing at `X = cx` satisfies `y_cross ≤ cy = y + 0.5` is odd — exactly what the sweep implements, so the brute-force oracle of the property test (DD3) is this count evaluated per pixel centre, and the test asserts interval-list **equality**, not an approximation. Worked check (pinned as a unit test): the rectangle `[[0.25, 0.25], [0.75, 0.25], [0.75, 0.75], [0.25, 0.75]]` on an 8 × 8 frame scales to x, y ∈ [2, 6]; its two vertical edges are skipped, its two horizontal edges are active for `cx ∈ {2.5, 3.5, 4.5, 5.5}` (columns 2–5) with crossings `y = 2` and `y = 6`, giving `r0 = ceil(1.5) = 2`, `r1 = ceil(5.5) − 1 = 5` — four intervals of length 4, the 16 pixels whose centres lie inside the rectangle, and no other.

**Decoding `mask_rle` into intervals** (`rle_intervals(rle, width, height) -> (intervals | None, problem)`): tokens → ints (any non-digit token → problem), counts alternate background/foreground starting with background, running sum must equal `width × height` (else problem), foreground runs become `[start, start + count)`. Same rules as `dda_manifest.rle_decode` and the device `mask_rle.decode`, without materializing the mask.

**IoU on intervals** (`interval_iou(a, b) -> float`): two-pointer merge of sorted interval lists summing overlap; union = `len(a) + len(b) − overlap`; `0.0` when the union is empty. `position_score(rle, width, height, polygon) -> (iou | None, problem)` composes the three.

**The outline rule (DD23)**: `interval_union(lists)` merges sorted interval lists into one sorted list of disjoint intervals (touching intervals merged); `interval_intersection_length(a, b)` is the two-pointer overlap sum `interval_iou` already computes; `outline_intervals(regions, width, height)` = `interval_union([_region_intervals(p, width, height) for p in regions.values()])`; `outline_overlap(mask, outline) -> float | None` = `interval_intersection_length(mask, outline) / Σ(end − start over mask)`, `None` for an empty mask.
**The check** (`check_layout(entries, frame_size, regions, min_iou=0.7, min_confidence=0.5, min_outline_overlap=0.1) -> dict`): `entries` are raw Detection_List entries in list form (`class_label`, `confidence`, `bounding_box`, optional `mask_rle`, `mask_area`, `mask_truncated`, and `id` when `attach_detection_ids` ran or the sandbox supplied it); `frame_size` a `(width, height)` pair or `{width, height}` dict or `None`. Steps: (1) if `regions` is `None` or not a dict → `outcome = error`, every piece `missing`, `pass = false`, problem "expected_regions is not usable"; (2) if `entries` is not a list → `outcome = warning` "no detections to check"; (3) if frame size is unknown or non-positive → `outcome = warning` "frame size unknown"; in cases 2–3 every piece is `missing`, `detections = []`; (4) otherwise, compute every region's intervals and the Car_Outline intervals once (`outline_intervals`); for each region label in insertion order: qualifying = entries with `str(class_label) == label` and `confidence ≥ min_confidence` (a non-numeric confidence counts as 0, the `scene._confidence_of` rule); for each qualifying entry decode its mask once (`rle_intervals`) — `None` when `mask_rle` is absent, truncated or inconsistent, in which case a problem names the id **and `outcome` becomes `warning`** (so the text reaches the node status, which carries problems only on `warning`/`error`) — and, when it decodes to at least one pixel, compute its `outline_overlap`; an entry with a measured `outline_overlap < min_outline_overlap` is appended to `ignored` (`id`, `class_label`, `confidence`, `bounding_box`, `outline_overlap`) and leaves the counting (DD23); every other qualifying entry is **counted** and gets its iou from the decoded intervals (`None` without a mask); status over the counted entries `missing` (0), `duplicate` (> 1, all flagged), else `ok` if `iou is not None and iou ≥ min_iou` else `misplaced` (flagged); a `min_outline_overlap` that is not a number in [0, 0.5] is replaced by `DEFAULT_MIN_OUTLINE_OVERLAP` with a problem and `outcome = warning`; (5) `unexpected_classes` = sorted distinct labels of qualifying entries not in `regions` (wherever they lie — the outline rule applies to configured classes only) → one problem, `outcome = warning`; (6) `pass = outcome == ok and all statuses == ok` over every configured class (the keys of `regions`; the three Piece_Classes in this use case — the function never assumes three). The piece-level `iou` is the best instance's iou or `None`, rounded to 4 decimals; `outline_overlap` is rounded to 4 decimals too, and `ignored` keeps the entries' input order. `run_metadata(result)` drops `outcome` and `problems` (the `scene.run_metadata` rule) and is what gets merged under `layout.<nodeId>`.

**Joining ids** (`attach_detection_ids(raw_entries, built_entries) -> List[dict]`): returns copies of `raw_entries` with `id` set from the first unused built entry whose `label == str(class_label)`, `confidence == float(confidence)` and `(x_min, y_min, x_max, y_max) == tuple(float(v) for v in bounding_box)`; `id = None` when none matches (recorded as a problem by `check_layout` when such an entry qualifies). Accepts `built_entries = None` (no ids at all). An entry without `class_label` normalizes to `label = ""` on the built side and compares as `"None"` on the raw side (DD5) — it stays unjoined and, having no region to qualify for, is ignored; the join test includes one.

### 8. Grayscale_Node (Requirement 6, DD11)

`samples/car-assembly-check/grayscale_handler.py` (the exact `code` parameter text):

```python
# ITU-R 601-2 luma (0.299 R + 0.587 G + 0.114 B), the weights Pillow's mode "L"
# used for the training set. Paste into a custom_python_preprocess node's "code";
# requirements empty, wall_clock_limit_s default. The bridge pins frames to RGB,
# so only the RGB branch runs on a device; the others keep the handler honest.
def process_frame(frame, metadata):
    fmt = (metadata.get("frame") or {}).get("format")
    if fmt == "GRAY8":
        return None  # already single-channel: pass through
    if fmt == "RGB":
        gray = cv2.cvtColor(frame, cv2.COLOR_RGB2GRAY)
        return cv2.cvtColor(gray, cv2.COLOR_GRAY2RGB)
    if fmt == "BGR":
        gray = cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY)
        return cv2.cvtColor(gray, cv2.COLOR_GRAY2BGR)
    raise ValueError("grayscale handler: unsupported frame format %r" % (fmt,))
```

`requirements` empty; `wall_clock_limit_s` default. A raised `ValueError` (for `RGBA` or anything else) fails the run with the node named (the bridge's existing error path), which is the intended behaviour for an unexpected format — silently passing colour to the grayscale model would be worse; it is unreachable while `BRIDGE_APPSINK_CAPS` pins `RGB`. The parity test (`edge-cv-portal/backend/tests/test_grayscale_handler_parity.py`, skipped without the local images) decodes three colour originals with Pillow (`ImageOps.exif_transpose` first, as the production report did) to RGB arrays, runs the handler, and compares with the monochrome JPEG decoded as RGB: `|diff| ≤ 2` for ≥ 99.9 % of pixels; a synthetic test asserts R = G = B, equal shape and dtype, and the per-format branches (the handler file is imported as a module with `cv2` and `np` injected, so the same text is tested that is pasted).

The summary line prints runs, passes, fails, errors; with `--triage` (stdlib `csv`, the set rules of DD18 and the `piece_counts` pattern copied inline, nothing else) it adds the false-fail list (Known_Good records with `pass == false`), the false-pass list (Fail_Set records with `pass == true`), the Occluded_Correct records with their verdicts (no expectation), the `duplicate` list (every record with a `duplicate` status, its set and class — expected only on a row whose `piece_counts` gives that class 2; otherwise an extra piece over the car, a stray piece the outline rule did not exclude, or a model error), the `ignored` list (every record with an instance ignored as outside the car outline, its set, class and Outline_Overlap — expected on a row with `unlabeled_stray > 0`; otherwise a spare piece the triage did not record or a false detection outside the outline; DD23), and lists files without a triage row. The re-derivation of each verdict with `check_layout` is done by `compare_variants.py` / `layout_reference.py --calibrate --results` (which import the shared module), not by `batch_run.py`, so the device-side script stays stdlib-only and trivially portable to the Jetson host.

**Pass/fail/missing staging (Requirement 10.2).** No camera is mounted on `mic-730ai` (owner decision O16 (a)): pin a Fail_Set image — the colour copy in the Training_Orientation — whose Triage_File row names misplaced pieces for (b) and one whose row names a missing piece for (c); for (e) (O19) a Known_Good image that shows the stray piece (`c3889f82` or `dc7bf42a`) — expected `pass = true`, the stray piece in `ignored` if the model detects it; an edited photo is used only if the owner asks and is marked synthetic in the notes. For (b) the notes record every detected instance's `class_label`, `confidence` and `bounding_box` from the run preview beside the verdict; a wrongly placed piece reported `ok` with the class of the position it occupies stops the verification (DD2, O13 residual).

**Result_Export** (`gray.json` and `color.json`; written by `batch_run.py`, read by `layout_reference.py --calibrate --results` and `compare_variants.py`): a JSON object `{"workflow_id", "registration_id", "device", "started", "local_server_version": "<localServerVersion read from GET /system-health before the first run>", "local_server_version_end": "<the same read after the last run>", "local_server_changed": false | true, "records": [...]}` — the two version strings and the flag are DD22's identity record (consumers require `--local-server-version <v>` and exit 1 when either string differs from it or the flag is true) — with one record per source image: `{"file": "<basename>", "execution_id", "capture_id", "status": "completed|failed|timeout|trigger_failed", "error": null | "<text>", "layout": <the layout.layout section or null>, "timings_ms": {"gray": 412, "model": 96, "layout": 38, "total": 1310}, "instances": [<the run preview's Detection_List entries, list form, with mask_rle>] | null, "detections_truncated": false | true | null}` (no `data_ref_basename`: the record's `data-ref` is always `{capture_id}.jpg`, DD15). `instances`/`detections_truncated` are the `instances`/`detectionsTruncated` of `GET /workflows/executions/{id}/overlay` (rfdetr-seg-support Req 10.5(c)); `timings_ms.<node>` come from `node-status` `durationMs` (absent → `null`); `total = finishedAt − startedAt` in ms.

**Triage_File** (`placement-triage.csv`, produced and confirmed by the owner; read by `assembly_triage.py`, DD18): a CSV with a header row and the eleven columns `filename, set, source_path, verdict, misplaced_pieces, missing_pieces, occluder, confidence, notes, piece_counts, unlabeled_stray`, one row per image of the Labeled_Set (70). Vocabulary as confirmed (pinned in the helper): `verdict ∈ {correct, incorrect, incorrect_and_missing, missing}`; `occluder ∈ {none, hand}` — the literal `none` (or an empty cell) means no occluder; `set ∈ {assembly48, anomaly, extra}`; `confidence ∈ {high, medium, low}`; piece lists `;`-separated (the reader also accepts `,` and whitespace); **`piece_counts`** exactly `front_fender=N;rear_fender=N;roof=N` (all three classes, non-negative integers — the number of instances of each class the labels must hold: seated, misplaced or hand-held pieces, never a stray piece outside the outline); **`unlabeled_stray`** a non-negative integer (pieces outside the car outline, never labeled). Consumer rules (the only ones this design fixes; the file's per-image contents are the owner's): `filename` joins to the basename of a manifest `source-ref` / a Result_Export `file`; Known_Good ⇔ `verdict = correct` **and** `occluder` ∈ `NO_OCCLUDER_VALUES` (the reader rule in force since owner decision O19: `STRAY_ROWS_ARE_KNOWN_GOOD = True` drops O15 (i)'s third conjunct `unlabeled_stray = 0`, because the check ignores a detected piece outside the car outline — DD18, DD23); Fail_Set ⇔ `misplaced_pieces` or `missing_pieces` is non-empty; Occluded_Correct ⇔ `correct` otherwise (no verdict expectation); the exact per-row count rule of Requirement 1.4 (`Triage.multiplicity_rule` = the parsed `piece_counts`); `set`, `source_path`, `confidence`, `notes` are printed, never interpreted; `piece_counts` is never derived from or checked against the other columns. A file lacking the two columns (the `.v1` backup) is refused.

**Reference capture output** (`layout_reference.py --out`): the `expected_regions` JSON exactly as pasted; stdout adds a table `label | vertices | iou` and, in `--calibrate`, `label | n | min | p5 | median | max | min(test) | swapped | flipped_roof | recommended_min_iou` over the Known_Good rows, with the source named (`labels` or `predicted`), followed by the Fail_Set true-fail listing (`file | set | expected pieces | verdict | pieces not flagged`, empty when the check holds; occluded images in their own block).

**Derived_Manifest**: byte-identical to the labeled manifest except each line's `source-ref` prefix; same line order.

## Invariants and who enforces them

- **The device result contract of rfdetr-seg-support is unchanged.** Enforced by this design writing nothing into the marshal, the base model, the capture record or the sidecar: the verdict lives only in Run_Metadata (executor) and the run-metadata JSON. Pinned by rfdetr-seg-support's device suites passing unmodified.
- **Run_Metadata never carries `mask_rle`.** Enforced by `run_metadata()` (shared module) which emits only `LAYOUT_METADATA_KEYS`, and by a test asserting no `mask_rle` substring in the merged metadata.
- **Device and sandbox produce the identical `layout.<nodeId>` for identical inputs.** Enforced by both calling the same mirrored module through `parse_expected_regions`/`check_layout`/`run_metadata` on raw-form entries (the device joins ids with `attach_detection_ids`; the sandbox receives ids on its entries and maps them with `_raw_form`); pinned by the mirror test and a shared fixture test (same raw-form inputs, equal output) in both suites. The numpy contingency of DD3 is pinned output-identical to the pure path, so the invariant survives it.
- **`flagged` ids are the Detection_IDs every other surface shows.** Enforced by `attach_detection_ids` joining on the fields `_normalize_entry` copies; pinned by a test over a synthetic record where ids are assigned by `build_detection_list` and matched back.
- **Workflows without `layout_check` are byte-identical in validation, compilation, execution and rendering.** Enforced by every new branch keying on the node type / binding name / metadata section; pinned by the existing goldens and suites passing unmodified. The counters' timing behaviour is unchanged (only layout bindings record a duration).
- **Position_Score equals the pixel-centre IoU.** Enforced by the interval algorithm; pinned by the brute-force oracle property test on frames ≤ 64 × 64 with random polygons and random masks.
- **The grayscale conversion on the device matches the training conversion** (ITU-R 601-2). Enforced by the fixed handler text; pinned by the parity test against the monochrome JPEGs.
- **Training input and inference input have the same field of view and conversion.** Enforced procedurally: the Grayscale_Node is always in the production workflow; the only admitted geometry change is a whole-frame downscale (DD16); `crop` is out of scope.
- **Exactly one `capture` on the frame path; verdict outputs only through gated executor bindings.** Enforced by the sample workflow (DD17) and the user-guide note; pinned by the sample's compile test (one `emlcapture` in the compiled segments, four executor bindings).
- **The production `min_iou` is derived from predicted masks, not labels alone, and every standing Result_Export carries its variant's production threshold.** Enforced procedurally by §13's order (the batch and recalibration precede the production binding, and a recalibration is followed by a re-run of the batch — for whichever variant is bound: §13 step 5 for grayscale, §12 step 3 for colour) and by `layout_reference.py --calibrate --results` exiting 1 on any would-be false-fail; recorded in `verification-notes.md`.
- **Only triage-confirmed correct images feed the Reference_Layout and the false-fail side; the Fail_Set is never silently treated as known-good.** Owned by the `datasets/` scripts through the one Triage_File reader (DD18): `layout_reference.py` refuses a non-Known_Good golden sample, the calibration splits its rows by set, `compare_variants.py` computes M3 per set, and unknown rows are listed rather than classified; the no-occluder values are `""` and `none` (the file's literal), so a reader that tested only for emptiness would misclassify every row; pinned by the scripts' tests with a fixture copied from the confirmed file. The Triage_File itself is owned by the owner (confirmed, never edited here; the withdrawn O15 (ii) edit and its reversal on 2026-11-27 were the owner's run's).
- **An instance is ignored only on a measured Outline_Overlap below the threshold (DD23).** Owned by `layout.check_layout`: an instance without a decodable, non-empty mask is always counted, an unknown frame keeps every piece `missing`, and `unexpected_classes` is computed over every qualifying instance wherever it lies, so missing information never removes an instance; pinned by the property test (every ignored instance has a measured overlap below the threshold; every `ok` class has exactly one counted instance with overlap ≥ the threshold and iou ≥ `min_iou`).
- **Ignoring cannot make a car pass that lacks a piece inside the outline.** Owned by the same function: ignoring only removes instances from the counting, and a class with no counted instance is `missing`, so `pass = false`; pinned by the "set down outside" case.
- **A Result_Export is read with the outline rule its records carry.** Owned by `layout_reference.py --calibrate --results` and `compare_variants.py`: verdicts are re-derived with the echoed `min_outline_overlap`, and an export echoing 0 is refused while rows with `unlabeled_stray > 0` are Known_Good (`STRAY_ROWS_ARE_KNOWN_GOOD = True`); pinned by the scripts' tests.
- **A `duplicate` on a Known_Good record never moves `min_iou`.** Owned by `layout_reference.py --calibrate --results`, which lists such records apart ("duplicate — not a calibration matter") and excludes them from the distribution and the recommendation, and by Requirements 4.6(b)/10.3, which route them to investigation instead of recalibration; pinned by the script's test on a synthetic Result_Export with a two-instance Known_Good record.
- **Training input and inference input share one orientation (DD19).** Enforced procedurally: the 22 were rotated into the Training_Orientation before upload (check recorded, Requirement 1.6), the production-camera workflow form carries `rotate-180`, the static-image forms carry none; the symptom (all pieces `misplaced`) is documented, and the production-camera form is checked once on a known-good physical assembly before its verdicts count (Requirement 6.5).
- **Predicted masks are read from the run preview, never from the legacy result history.** Enforced by `batch_run.py` using only the six `workflow_engine` routes (registration, trigger, execution, metadata, node-status, overlay); pinned by the stub-server test, which serves no `/results/` route.
- **The Portal verdict read never changes what the Portal shows for captures without a run-metadata sibling.** Enforced by `_attach_layout` adding only null fields when the key is absent; pinned by the legacy-capture test in `test_captures_layout.py`.
- **"Monochrome + on-device grayscale" stays the production default until Requirement 11 has run.** Enforced procedurally by §13 (the grayscale production version is bound first) and §12 step 5 (the winner is bound only after the criterion of Requirement 11.7 has been confirmed in `tasks.md` and the table written); recorded in `verification-notes.md`.
- **Every floor a device is gated against names a version its own account's lineage can reach.** Owned by the configuration layer: both floors are per-deployment configuration (DD9, §7; the Seg floor by owner decision O18 (ii)) — the demo deployment carries `arm64_jp5: <DEMO_JP5_VERSION>` for both, the version its own Fleet published (DD20); the lab deployment keeps the defaults (`{}`, and the committed literal whose numbers are the lab lineage's); validated at synth time (`parseMinVersionsFloor` throws on a bad shape) and pinned procedurally by the post-deploy check of §7 (each deployed value equals the configured one, or the tree's literal where none is configured) and by the infra tests' resolution paths for both keys. The pass-6 default (`arm64_jp6: 1.0.85` as "the device's" floor) violated this invariant: a lab-account version of an arch the demo account does not have.
- **The label count per class is exactly the row's `piece_counts`.** Owned by `assembly_triage.multiplicity_rule` (the parsed column, nothing derived) and `check_assembly_manifests.py --triage`; pinned by the reader's tests (format acceptance and rejection) and the check script's pass/fail cases (a duplicate on a swapped-fender row is listed, which the superseded `misplaced_pieces`-based rule could not do).
- **Batch runs correlate to files by construction.** Enforced by `batch_run.py` refusing to start a run while the folder is non-empty.
- **Every recorded number comes from the LocalServer build the notes name, `<DEMO_JP5_VERSION>` (DD22).** The Portal cannot own this: its floors are minima (`deployments.py:3655`) and the lineage is shared with another publisher. Owned in three layers — the **procedure** (the move is a Pinned_Revision that names the version; the Installed_Version_Check by hand before every case, stability and camera run; the coordination rule), **`batch_run.py`** (reads `GET /system-health` first and last, refuses to start on `--expect-local-server-version` mismatch, writes `local_server_version`/`local_server_version_end`/`local_server_changed` into every export) and the **offline consumers** (`layout_reference.py --calibrate --results`, `compare_variants.py` require `--local-server-version` and exit 1 on any disagreement before computing anything) — so an export from the wrong build can be produced only by hand-editing its header; pinned by the unit tests of both scripts.
- **One label set feeds the Grayscale_Model (and a Colour_Variant, if any).** Enforced procedurally by `rewrite_manifest_source_refs.py` (only `source-ref` changes) and verified by `check_assembly_manifests.py` before training; recorded in `verification-notes.md`.
