# Python 3.11 Security Upgrade Bugfix Design

## Overview

The DefectDetectionApplication (DDA) is built, tested, and run on Python 3.9,
which is end-of-life and no longer receives security patches. Every build of the
backend image therefore ships an unsupported interpreter whose CVEs cannot be
remediated. This is the defect: the system depends on (installs, selects, and
runs) Python 3.9.

The fix migrates the entire build/test/runtime/provisioning surface to a
supported Python 3.11 interpreter, with **no remaining Python 3.9 pin** that
affects how the application is built or run, and **no functional regression** in
the externally observable behavior of the application (camera/Aravis capture,
GStreamer pipelines, Triton inference, the FastAPI app and its endpoints,
defect-detection workflows, and the concurrent-camera-stream-viewing feature).

The fix is code-change-heavy and spans three layers, each with its own Python
selection strategy driven by the base image:

1. **Build orchestration** (`build-custom.sh`, `src/edgemlsdk/build.sh`) — the
   Python version is passed as data today (`-y 3.9` / `python=3.9` /
   `--build-arg PYTHON_VERSION`). We make the version a single source of truth
   and set it to 3.11.
2. **Image construction** (the three backend Dockerfiles and three edgemlsdk
   Dockerfiles) — these select/install Python and build native bindings
   (Triton Python backend via pybind11, Aravis/`gi`, the Panorama wheel). The
   Python install strategy differs per base image and is the bulk of the work.
3. **Provisioning + docs** (`setup-build-server.sh`, `station_install/*.sh`,
   `README*.md`, `test/README.md`) — host-side interpreter install/selection
   for DDA components, plus documentation.

The general strategy is: parameterize the Python version so it is set once;
choose the correct interpreter source for each base OS (deadsnakes PPA on
Ubuntu 20.04/22.04 apt-based images, from-source on the generic Ubuntu images
that already build Python from source); rebuild every native artifact that is
ABI-bound to `libpython` (Triton Python backend, PyGObject, pycairo) against
3.11; bump the handful of pinned Python packages that have no 3.11 wheel or fail
to build under 3.11; and preserve the distro-python coupling for `g-ir-scanner`
and the host model-conversion scripts that must NOT move to 3.11.

## Glossary

- **Bug_Condition (C)**: A `SystemArtifact` (build script, Dockerfile, runtime
  process, test invocation, install/provisioning script, or doc) that depends
  on, installs, selects, or runs the end-of-life Python 3.9 interpreter —
  formally `dependsOnPython(X, "3.9")`.
- **Property (P)**: After the fix, every buggy artifact depends on Python 3.11,
  no longer depends on 3.9, and runs a security-supported interpreter.
- **Preservation**: For every artifact that does NOT depend on Python 3.9, the
  fixed system behaves identically to the original. The externally observable
  application behavior is unchanged across JP5, JP6, and amd64 targets.
- **F / F'**: The original system built/run on Python 3.9 / the fixed system
  built/run on Python 3.11.
- **PYTHON_VERSION**: The single-source-of-truth build argument that selects the
  DDA interpreter version (`3.9` → `3.11`).
- **DDA interpreter**: The interpreter the application runs on (the one we
  switch `python3` to and set `CMD` to). Distinct from the **distro/system
  python** below.
- **distro/system python**: The interpreter that ships with the base image
  (3.8 on the JP5 / Ubuntu 20.04 base, 3.10 on the JP6 / Ubuntu 22.04 base).
  System tooling (`apt`, `g-ir-scanner`'s `_giscanner` C extension, host
  model-conversion scripts) is bound to it and MUST stay on it.
- **`gi` / GObject Introspection**: The PyGObject (`gi`) bindings used by
  Aravis/GStreamer. `gi` is the highest-risk coupling: the typelibs are
  generated by `g-ir-scanner` (a distro-python C extension) while the importable
  `gi` module is the pip-installed PyGObject built against the DDA interpreter.
- **Triton Python backend**: A pybind11/`libpython`-linked shared object that
  launches a Python stub process; it is ABI-bound to the exact `libpython`
  version it was compiled against (`PYBIND11_PYTHON_VERSION`).
- **Panorama wheel**: `panorama-1.0-py3-none-any.whl` — a `py3-none-any`
  (interpreter-agnostic) wheel that wraps the native `PanoramaSDK.deb`.

## Bug Details

### Bug Condition

The bug manifests whenever a build, runtime, test, or provisioning artifact
selects an end-of-life Python 3.9 interpreter. The artifact either installs
`python3.9`, switches `python3` to 3.9, fetches the 3.9 `get-pip.py`, sets
`PYTHON_EXECUTABLE`/`PYTHONHOME`/`libpython3.9.so`/`PYBIND11_PYTHON_VERSION=3.9`,
or invokes `python3.9 ...` directly — so the produced image, test run, or host
environment depends on an unsupported interpreter.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type SystemArtifact   // build script, Dockerfile, runtime
                                         // process, test invocation, install
                                         // script, or doc selecting an interpreter
  OUTPUT: boolean

  RETURN dependsOnPython(input, "3.9")
         // i.e. installs/selects/runs python3.9, or pins libpython3.9.so /
         //      PYTHON_EXECUTABLE=python3.9 / PYBIND11_PYTHON_VERSION=3.9 /
         //      PYTHONHOME=/usr/bin/python3.9, in a way that affects how the
         //      application is built or run
END FUNCTION
```

### Examples

- `build-custom.sh` calls `./build.sh -p $(uname -m) -u $IMAGE_VER -y 3.9 ...` →
  edgemlsdk and Triton are built against 3.9. Expected: built against 3.11.
- `src/edgemlsdk/build.sh` defaults `python=3.9` when `-y` is omitted. Expected:
  defaults to 3.11.
- `src/backend/Dockerfile.jp5` runs
  `apt-get install ... python3.9 python3.9-dev`, then
  `update-alternatives --set python3 /usr/bin/python3.9`, then
  `wget .../pip/3.9/get-pip.py`, then `CMD ["python3.9", "app.py"]`. Expected:
  installs/selects 3.11 and the container entrypoint runs `app.py` on 3.11.
- `src/edgemlsdk/Dockerfile.jp5` sets
  `Python3_LIBRARY=/usr/lib/libpython3.9.so` and builds Triton with
  `--extra-core-cmake-arg=PYBIND11_PYTHON_VERSION=3.9`. Expected: `libpython3.11.so`
  and `PYBIND11_PYTHON_VERSION=3.11`, producing a Triton Python backend that
  loads under 3.11.
- `test/backend-test/conftest.py` sets `os.environ["PYTHONHOME"] =
  "/usr/bin/python3.9"`. Expected: resolves to the 3.11 interpreter.
- `src/backend/edge_ml1_p_camera_management/install_edgemlsdk.sh` runs
  `python3.9 -m pip install ...` and installs the Panorama wheel under 3.9.
  Expected: installs into the 3.11 environment; the `py3-none-any` Panorama
  wheel imports under 3.11.
- Edge case (preserved, NOT buggy): `station_install/*.sh` and
  `patch_docker_host_prereqs.sh` deliberately run the host model-conversion
  scripts on the **system** `python3` (3.8/3.10), and the backend Dockerfiles
  point `g-ir-scanner` at the **system** python. These are distro-python
  dependencies, not Python-3.9 dependencies — they must remain unchanged.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Aravis/`gi` camera discovery, configuration, and capture must work exactly as
  on 3.9 (Req 3.1).
- GStreamer pipeline construction/execution and snapshot capture must produce
  the same output (Req 3.2).
- Triton Python-backend inference must load the model and return equivalent
  results (Req 3.3).
- The FastAPI app's endpoints (auth, user/group management, the full API
  surface) must return the same responses and status codes (Req 3.4).
- The concurrent-camera-stream-viewing feature (subscriptions, heartbeats,
  staleness, multi-viewer streaming) must behave per its existing spec (Req 3.5).
- Defect-detection workflows and triggers, including DIO outputs and the host
  model-conversion scripts, must produce the same results (Req 3.6).
- Each target (JP5 / JP6 / amd64) must still produce a working, packaged
  deployment artifact (Req 3.7).
- Existing TinyDB datastores, config files, and other persisted data must be
  read without migration errors (Req 3.8).

**Scope:**
All artifacts and behaviors that do NOT depend on the Python 3.9 pin must be
completely unaffected. This explicitly includes:
- The **distro/system python** and everything bound to it: `apt`/dpkg tooling,
  the `g-ir-scanner` `_giscanner` C extension shebang, and the host-side
  model-conversion Startup/Shutdown scripts that intentionally run on the
  system `python3` (3.8 on JP5, 3.10 on JP6).
- The native C/C++ dependency builds that are not Python-ABI-bound (OpenSSL,
  aws-crt/sdk/iot, Aravis core, Boost, c-periphery, FFmpeg, GStreamer system
  packages, CUDA 11.4 cudart staging on JP6).
- All application source code, data models, configuration, and the
  docker-compose service topology / profile selection.

**Note:** The expected correct behavior for buggy inputs is defined in the
Correctness Properties section (Property 1).

## Hypothesized Root Cause

The system was authored against Python 3.9 and the version is hard-coded (or
defaulted) at every layer. There is no single source of truth, so the pin is
scattered across shell defaults, Dockerfile `ENV`/`RUN`/`CMD` lines, Triton
cmake args, test config, and provisioning scripts. The migration must touch
each, and the difficulty concentrates in the places where 3.11 is not a drop-in:

1. **Interpreter availability differs per base image.** The JP5 backend base
   (`l4t-jetpack:r35.4.1`, Ubuntu 20.04 "focal") and the JP5 edgemlsdk base
   install `python3.9` directly from the focal `apt` repos; focal has **no**
   `python3.11`, so 3.11 requires the **deadsnakes PPA** (focal) — the same PPA
   the JP6 path already uses for 3.9. The generic backend/edgemlsdk Dockerfiles
   build **Python from source** (`Python-3.9.23.tgz`, `--enable-shared`); 3.11
   keeps that from-source approach (precedented — these images already compile
   OpenSSL and Python from source). The JP6 base
   (`l4t-jetpack:r36.3.0`, Ubuntu 22.04 "jammy") already adds deadsnakes for 3.9
   and can obtain 3.11 the same way.

2. **Native bindings are ABI-bound to `libpython`.** The Triton Python backend
   is compiled with `PYBIND11_PYTHON_VERSION=3.9` / `libpython3.9.so` and will
   not load under 3.11 unless rebuilt; PyGObject and pycairo are compiled
   against the interpreter headers.

3. **The `gi`/system-python coupling is fragile (highest risk).** Aravis is
   built with `-Dintrospection=disabled` on the Jetson Dockerfiles, and
   `g-ir-scanner` is force-pointed at the **distro** python (3.8 on JP5, a
   dynamically-detected 3.10 on JP6) because its `_giscanner` C extension is
   built for the distro python — not the DDA python. The importable `gi` is
   pip-installed PyGObject built against the DDA interpreter. Moving the DDA
   interpreter to 3.11 must NOT move the `g-ir-scanner` shebang.

4. **A few pinned Python packages predate 3.11.** `PyYAML==5.4.1` fails to build
   under Cython ≥3.0 (the well-known `AttributeError: cython_sources`), and
   `scikit-learn==1.0.2` has no cp311 wheels (3.11 wheels first shipped in
   scikit-learn 1.1). `dlr==1.10.0` is an old prebuilt runtime whose cp311
   arm64 wheel availability is unverified.

## Correctness Properties

Property 1: Bug Condition - Supported Python 3.11 interpreter everywhere

_For any_ artifact where the bug condition holds (`isBugCondition` returns true —
the artifact installs, selects, or runs Python 3.9), the fixed system SHALL
produce an equivalent artifact that depends on Python 3.11, no longer depends on
Python 3.9, and runs a security-supported interpreter — i.e. the built backend
image's `python3` and entrypoint are 3.11, the EdgeML SDK / Triton Python backend
are built against `libpython3.11` with `PYBIND11_PYTHON_VERSION=3.11`, the test
suite and provisioning select 3.11, and a full-repo audit finds no remaining 3.9
pin that affects how the application is built or run.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9**

Property 2: Preservation - No functional regression for non-3.9 artifacts

_For any_ artifact where the bug condition does NOT hold (`isBugCondition`
returns false), the fixed system SHALL produce the same result as the original
system, preserving all externally observable behavior: Aravis/`gi` capture,
GStreamer pipelines, Triton inference, the FastAPI endpoints, concurrent-camera
streaming, defect-detection workflows/triggers, the per-target packaged
artifacts, persisted TinyDB/config data, the distro-python tooling
(`apt`, `g-ir-scanner`, host model-conversion scripts), and the
non-Python-ABI native dependency builds.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8**

## Fix Implementation

### Single source of truth for the Python version

Introduce one authoritative `PYTHON_VERSION=3.11` and thread it everywhere, so
the version is set once and the `dependsOnPython(_, "3.9")` predicate is false
across the build graph.

- **`build-custom.sh`**: replace the two hard-coded `-y 3.9` invocations with a
  variable defined at the top, e.g. `PYTHON_VERSION="${PYTHON_VERSION:-3.11}"`,
  and pass `-y "$PYTHON_VERSION"` to `src/edgemlsdk/build.sh`. Add
  `--build-arg PYTHON_VERSION="$PYTHON_VERSION"` to **both** `docker-compose
  build` invocations (x86_64 `generic`-only branch and the
  `tegra`+`generic` branch). Update the in-image test block to invoke the
  interpreter by the parameterized version (see "in-image tests" below).
- **`src/edgemlsdk/build.sh`**: change the default `python=3.9` to
  `python=3.11`. (`-y` already forwards to the `PYTHON_VERSION` build-arg.)
- **`src/docker-compose.yaml`**: ensure each buildable service (`flask-app` and
  the edgemlsdk/tegra services) declares `args: [OS, PLATFORM, PYTHON_VERSION]`
  under `build.args` so the value reaches the backend Dockerfiles. (Verify and
  add `PYTHON_VERSION` to the build args list; today only `OS` is plumbed
  through `build-custom.sh`.)

### EdgeML SDK Dockerfiles (Triton Python backend + Panorama)

All three already accept `ARG PYTHON_VERSION`. The remaining work is to remove
the **hard-coded** `3.9` references that the ARG does not cover and to make 3.11
installable on each base.

- **`src/edgemlsdk/Dockerfile.jp5`** (Ubuntu 20.04 / focal):
  - Add the **deadsnakes PPA (focal)** before the Python install step, since
    focal `apt` has no `python3.11`:
    `add-apt-repository -y ppa:deadsnakes/ppa` (install
    `software-properties-common` first). Keep the existing
    `python${PYTHON_VERSION}` / `python${PYTHON_VERSION}-dev` /
    `-venv` / add `python${PYTHON_VERSION}-distutils` package list.
  - Replace the hard-coded `ln -s /usr/bin/python3.9 /usr/bin/python` with
    `/usr/bin/python${PYTHON_VERSION}`.
  - Replace the four `ENV` pins to use 3.11:
    `PYTHON_EXECUTABLE`, `Python3_EXECUTABLE` → `/usr/bin/python3.11`;
    `Python3_INCLUDE_DIR` → `/usr/include/python3.11`;
    `Python3_LIBRARY` → `/usr/lib/libpython3.11.so` (verify the actual
    `.so` path the deadsnakes package installs; deadsnakes typically provides
    `/usr/lib/x86_64-linux-gnu/libpython3.11.so` on amd64 and the aarch64
    equivalent — set the path from the build, do not assume).
  - In the **Triton build** (`python3.9 build.py ...`), replace the interpreter
    and every cmake arg: `python3.11 build.py`,
    `PYTHON_EXECUTABLE=/usr/bin/python3.11`,
    `PYTHON_INCLUDE_DIR=/usr/include/python3.11`,
    `PYTHON_LIBRARY=/usr/lib/libpython3.11.so` (+ `-D` variants),
    `PYBIND11_PYTHON_VERSION=3.11`.
- **`src/edgemlsdk/Dockerfile.jp6`** (Ubuntu 22.04 / jammy): identical edits;
  the deadsnakes PPA is already added, so only the package version
  (`python${PYTHON_VERSION}*`), the `ln -s .../python3.9` line, the four `ENV`
  pins, and the Triton `build.py` args/`PYBIND11_PYTHON_VERSION` change.
- **`src/edgemlsdk/Dockerfile`** (generic, builds from source): bump the
  source tarball to a 3.11 release (e.g. `Python-3.11.9.tgz`), keep
  `--enable-optimizations --enable-shared`, and update the
  `update-alternatives`, the four `ENV` pins
  (`/usr/local/bin/python3.11`, `/usr/local/include/python3.11`,
  `/usr/local/lib/libpython3.11.so`), the `ln -s /usr/bin/python3.9` line, the
  `python3.9 -c "import ssl..."` smoke checks, the Triton `build.py` invocation
  and cmake args, and the Ubuntu-18.04 `python3.6m` shim block (drive off the
  3.11 include dir). Keep the from-source approach — it is already the
  precedent here.

### Backend Dockerfiles (runtime image)

- **`src/backend/Dockerfile.jp5`** (Ubuntu 20.04 / focal):
  - Add the **deadsnakes PPA (focal)** before installing `python3.11`
    (`python3.11 python3.11-dev python3.11-venv python3.11-distutils`); focal
    apt has no 3.11 natively.
  - Switch `python3` to 3.11:
    `update-alternatives --install/--set /usr/bin/python3 ... /usr/bin/python3.11`.
  - Replace the pip bootstrap: `get-pip.py` for 3.11. The
    `https://bootstrap.pypa.io/pip/3.9/get-pip.py` version-specific URL must
    become the generic `https://bootstrap.pypa.io/get-pip.py` (3.11 is current,
    so the unversioned bootstrap is correct), or rely on the
    `python3.11-distutils` + `ensurepip` path.
  - Replace `python3.9 -m grpc_tools.protoc ...` → `python3.11 ...`,
    `CMD ["python3.9", "app.py"]` → `CMD ["python3.11", "app.py"]`,
    `python3.9 dlr_disable_phone_home.py` → `python3.11 ...`, and the
    `find / -name "libpython3.9.so.1.0"` diagnostic → 3.11.
  - **Preserve** the `g-ir-scanner` shebang hack pointing at the **system**
    python `/usr/bin/python3.8` — this is a distro-python dependency, not a 3.9
    dependency, and the `_giscanner` C extension is built for 3.8. Do NOT change
    it. (This is the core preservation point for Req 3.1.)
- **`src/backend/Dockerfile.jp6`** (Ubuntu 22.04 / jammy): deadsnakes is already
  added — change the installed package set to `python3.11*`, the
  `update-alternatives` target, the `get-pip.py` bootstrap, the `protoc`/`CMD`/
  `dlr` invocations, and the `libpython3.9` diagnostic. The `g-ir-scanner`
  detection already dynamically selects the **system** python (excludes the DDA
  version) — verify the exclusion still skips the DDA version after the bump
  (the current grep excludes `3.9`; update it to exclude `3.11` so it keeps
  selecting the distro 3.10).
- **`src/backend/Dockerfile`** (generic, builds from source): bump the
  `Python-3.9.23.tgz` build to a 3.11 release, update `update-alternatives`, the
  `protoc`/`CMD`/`dlr` invocations, and the `libpython3.9` diagnostics.

### Pinned dependency bumps for 3.11

In `src/backend/requirements.txt` (and the duplicated pins in
`install_edgemlsdk.sh`):

- **`pyyaml==5.4.1` → `6.0.1`** (required): 5.4.1 fails to build under
  Cython ≥3.0 on a fresh 3.11 build (`AttributeError: cython_sources`).
- **`scikit-learn==1.0.2` → `>=1.1.3,<1.2`** (required): 1.0.2 has no cp311
  wheels (3.11 wheels first shipped in scikit-learn 1.1). Update **both**
  `requirements.txt` and the two `python3.9 -m pip install scikit-learn==1.0.2`
  lines in `install_edgemlsdk.sh` (which also change to `python3.11`).
- **`dlr==1.10.0`** (verify, possible mitigation): confirm a cp311 aarch64 wheel
  exists; if not, pin to the nearest dlr release that provides one, or build
  from source. Note the JP6 image already relies on the Neo-bundled `libdlr.so`
  + staged CUDA 11.4 runtime, so the pip `dlr` package may only need to import.
- **`numpy==1.24.3`** (keep): supports 3.8–3.11. **`pydantic==2.1.1`** /
  `grpcio==1.56.2` / `grpcio-tools==1.51.1` (verify wheels): all nominally
  support 3.11; build the arm64 targets first and bump only if a wheel/build
  fails. `pycairo==1.23.0` / `PyGObject==3.42.2` build from source against the
  3.11 headers (supported).

### Test config and in-image tests

- **`test/backend-test/conftest.py`**: change
  `os.environ["PYTHONHOME"] = "/usr/bin/python3.9"` → the 3.11 path
  (`/usr/bin/python3.11` for JP5/JP6 deadsnakes installs;
  `/usr/local/bin/python3.11` / appropriate prefix for the from-source generic
  image — prefer deriving `PYTHONHOME` from `sys.base_prefix`/`sysconfig` so it
  is not hard-coded to a single layout).
- **`build-custom.sh` in-image test block**: replace `python3.9 -m pip install`
  and `python3.9 -m pytest` with the parameterized 3.11 interpreter.

### Provisioning scripts and docs

- **`setup-build-server.sh`**: replace the "Install Python 3.9" block (PPA path
  + 18.04 from-source path + `update-alternatives` to `python3.9`) with 3.11.
- **`station_install/setup_station.sh`**: replace the `python3.9`
  checks/install (`install_from_source`, `install_from_ppa`), the `PYTHON39`
  discovery, and the symlink/`update-alternatives` lines with 3.11.
  **Preserve** the explicit "do NOT change the system `python3`" logic and the
  host model-conversion `python3` (system) pip installs — those are distro-python
  by design (Req 3.6).
- **`station_install/patch_docker_host_prereqs.sh`**: the
  `for cand in /usr/local/bin/python3.9 /usr/bin/python3.9` candidate loop
  should target 3.11; keep `ensure_host_py_deps python3` (system python) intact.
- **Docs**: `README.md`, `README_main.md`, `test/README.md`,
  `TEST_COVERAGE_PLAN.md` — update the `python-3.9+` badges, the "Python 3.9"
  prose, and the `python3.9 -m pip/pytest` examples to 3.11.

### Ordering and risk

1. **EdgeML SDK image first** (it produces the Triton/Panorama artifacts the
   backend consumes). Build per target; confirm the Triton Python backend links
   `libpython3.11` and `PYBIND11_PYTHON_VERSION=3.11`.
2. **Dependency bumps** (`pyyaml`, `scikit-learn`, verify `dlr`) before the
   backend image build, since the backend `pip install -r requirements.txt`
   will otherwise fail on 3.11.
3. **Backend images** per target; the `g-ir-scanner`/distro-python preservation
   is the riskiest step — validate `gi` imports and an Aravis camera enumerates.
4. **Test config + in-image tests**, then **provisioning + docs**.
5. **Highest-risk areas to watch**: the `gi`/system-python coupling (Aravis
   capture), the Triton Python-backend rebuild (inference), and the `dlr`/Neo
   model-load path on JP6 (CUDA 11.4 runtime staging is unchanged but the
   interpreter that loads `libdlr.so` changes).

## Testing Strategy

### Validation Approach

Two phases: first surface counterexamples that demonstrate the dependency on
3.9 (and the breakage 3.11 would otherwise hit) on the unfixed tree, then verify
the fix removes every 3.9 dependency (Fix Checking) and preserves all observable
behavior (Preservation Checking). Because the artifacts are images and scripts,
"tests" are a mix of static audits, in-image checks, and runtime smoke tests on
each target.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE the fix and
confirm/refute the root-cause hypotheses. If refuted, re-hypothesize.

**Test Plan**: Audit the unfixed tree for `dependsOnPython(_, "3.9")` and attempt
the 3.11 build to observe the predicted failures (PyYAML/scikit-learn, Triton
ABI, deadsnakes availability, `gi` coupling).

**Test Cases**:
1. **Repo audit**: `grep -rn` for `3\.9`, `python3.9`, `libpython3.9`,
   `PYBIND11_PYTHON_VERSION=3.9`, `PYTHONHOME=.*3.9` across build scripts,
   Dockerfiles, install/provisioning scripts, test config, and docs — every hit
   is a counterexample where `isBugCondition` is true (will be non-empty on
   unfixed code).
2. **PyYAML build (3.11)**: `pip install pyyaml==5.4.1` under 3.11 with current
   Cython — expect `AttributeError: cython_sources` (will fail on unfixed pins).
3. **scikit-learn install (3.11)**: `pip install scikit-learn==1.0.2` under 3.11
   — expect no cp311 wheel / build failure (will fail on unfixed pins).
4. **Triton backend ABI**: inspect the built `triton-python-backend` for a
   `libpython3.9` link — expect it bound to 3.9 (counterexample for the rebuild
   requirement).
5. **Edge case — deadsnakes availability on focal**: confirm focal apt has no
   `python3.11` without the PPA (justifies the PPA decision for JP5).

**Expected Counterexamples**:
- Non-empty audit hits for 3.9 across all layers.
- PyYAML 5.4.1 / scikit-learn 1.0.2 fail to install on 3.11.
- Triton Python backend is `libpython3.9`-bound; possible causes: hard-coded
  cmake args, `ENV` pins, missing 3.11 interpreter on the base.

### Fix Checking

**Goal**: For all artifacts where the bug condition holds, the fixed system
produces an artifact that depends on 3.11 and not on 3.9.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := fixedSystem(input)
  ASSERT dependsOnPython(result, "3.11")
     AND NOT dependsOnPython(result, "3.9")
     AND isSecuritySupported(interpreterOf(result))
END FOR
```

Concretely:
- Post-fix repo audit for `3.9` returns no hit that affects how the app is built
  or run (Req 2.8).
- In each built backend image: `python3 --version` == 3.11, the `CMD`
  interpreter is 3.11, `grpc_tools.protoc` ran under 3.11 (Req 2.3).
- The Triton Python backend links `libpython3.11` and was built with
  `PYBIND11_PYTHON_VERSION=3.11` (Req 2.4); the Panorama wheel imports under 3.11
  (Req 2.5).
- The in-image test suite runs to completion under 3.11; `PYTHONHOME` resolves to
  3.11 (Req 2.6).
- Provisioned build server / station expose 3.11 for DDA components (Req 2.7).

### Preservation Checking

**Goal**: For all artifacts where the bug condition does NOT hold, the fixed
system produces the same result as the original.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT originalSystem(input) = fixedSystem(input)
END FOR
```

**Testing Approach**: Property-based testing is recommended where the behavior is
expressible over a generated input domain (e.g. FastAPI endpoint request/response
equivalence and the concurrent-camera-stream session/heartbeat/staleness logic),
because it explores many inputs automatically and catches edge cases that
example tests miss. For image/runtime behavior, use runtime smoke tests on each
target. Capture baseline behavior on the **unfixed** (3.9) system first, then
assert the fixed (3.11) system matches.

**Test Plan**: Observe 3.9 behavior for the unchanged surface, then re-run on
3.11 and compare.

**Test Cases**:
1. **Aravis/`gi` capture preservation**: on unfixed code confirm `import gi`,
   `gi.require_version('Aravis', ...)`, camera enumeration and capture work;
   verify identical on 3.11. Confirm the `g-ir-scanner` shebang still points at
   the distro python (3.8 JP5 / 3.10 JP6) and was not changed (Req 3.1).
2. **GStreamer pipeline preservation**: build/run a streaming + snapshot pipeline
   and compare output to the 3.9 baseline (Req 3.2).
3. **Triton inference preservation**: load a model through the rebuilt Python
   backend and compare inference results to the 3.9 baseline (Req 3.3).
4. **FastAPI endpoint preservation**: run the existing backend unit tests
   (auth, user/group management, the API surface) under 3.11; responses/status
   codes match the 3.9 baseline (Req 3.4).
5. **Concurrent-camera-stream preservation**: exercise subscriptions, heartbeats,
   staleness, and multi-viewer streaming per the existing spec (Req 3.5).
6. **Workflow/trigger preservation**: DIO outputs and host model-conversion
   scripts (still on the system `python3`) produce the same results (Req 3.6).
7. **Per-target packaging preservation**: JP5, JP6, and amd64 each produce a
   working packaged artifact (Req 3.7).
8. **Persisted-data preservation**: an existing TinyDB datastore/config from a
   3.9 deployment is read without migration errors under 3.11 (Req 3.8).
