# Requirements Document

## Introduction

The DDA portal's labeling feature offers an Auto_Labeler that generates Pre_Labels for dataset images before human review. Today the Auto_Labeler supports two model families: SAM (`sam`), which produces class-agnostic segmentation regions with no notion of what the user wants detected, and Bedrock vision models (`bedrock:<model_id>`), which answer only Classification and bounding-box ObjectDetection prompts and cannot produce masks. SAM pre-labels have proven low-value in practice because they segment everything indiscriminately rather than the defects the user cares about.

This feature adds a prompt-guided LLM auto-labeling mode: the job creator selects an image-capable LLM (a Bedrock vision model such as Amazon Nova Pro or Claude, extensible to other model identifiers) and writes a Detection_Prompt describing what to detect. For each dataset image the LLM returns a structured JSON document containing Coordinate_Guidance (bounding boxes and/or polygons locating the prompted objects), which the system converts into the modality-appropriate Pre_Label — mask regions for Segmentation jobs, bounding boxes for ObjectDetection jobs. The existing review flow is preserved unchanged: team labelers see the Pre_Label in the annotation canvas and correct it before submitting, or (in skip-verification mode) an admin reviews and accepts/rejects the results. Accepted/submitted annotations flow into the existing DDA_Manifest generation, whose format (SageMaker Ground Truth-compatible JSON Lines with rendered PNG masks for Segmentation) remains unchanged so training consumption is unaffected.

## Glossary

- **Portal**: The edge-cv-portal web application (AWS Lambda + DynamoDB + S3 backend with a React frontend).
- **Labeling_Job**: A DDA-backend labeling job record in the LabelingJobs table, created through the job creation wizard and processed by the labeling worker.
- **Job_Creator**: The Portal user creating a Labeling_Job (holds the create-labeling-jobs permission; skip-verification jobs additionally require the UseCaseAdmin or PortalAdmin role).
- **Auto_Labeler**: The subsystem that generates Pre_Labels for dataset images: the SQS fan-out in dda_labeling_worker.py plus the per-image consumer dda_autolabel_worker.py.
- **LLM_Auto_Label_Model**: An image-capable large language model selected for prompt-guided auto-labeling, identified by a model identifier (a Bedrock model ID such as one for Amazon Nova Pro or Claude).
- **Model_Catalog**: The list of LLM_Auto_Label_Model choices the Portal presents in the job creation wizard.
- **Detection_Prompt**: Job-creator-supplied natural-language text describing the objects or defects the LLM_Auto_Label_Model is asked to locate in each image.
- **Coordinate_Guidance**: The structured JSON document returned by the LLM_Auto_Label_Model for one image, containing geometric localization of detected objects (bounding boxes and/or polygons in pixel coordinates) with a class name per detection.
- **Guidance_Parser**: The component that parses and validates the LLM_Auto_Label_Model's raw text output into Coordinate_Guidance.
- **Mask_Converter**: The component that converts validated Coordinate_Guidance into the Pre_Label geometry for the job's modality (RLE mask regions for Segmentation; bounding boxes for ObjectDetection).
- **Pre_Label**: The per-image machine-generated annotation stored in the portal artifacts bucket and referenced by the task item's prelabel_s3_key, presented to reviewers as a starting point.
- **Label_Set**: The job's ordered list of class names (fixed to normal/anomaly for Classification; 1-10 user-defined classes otherwise).
- **Labeler_Interface**: The annotation canvas served to Labeling_Team members, which loads the Pre_Label as an editable starting annotation.
- **Admin_Review**: The skip-verification review flow where a UseCaseAdmin/PortalAdmin accepts or rejects each auto-labeled result before manifest generation.
- **DDA_Manifest**: The JSON Lines output manifest written to the use case's output bucket (SageMaker Ground Truth-compatible attributes; Segmentation entries reference rendered PNG masks), consumed unchanged by training.
- **RLE**: The run-length-encoded mask region representation already used by SAM Pre_Labels and Segmentation annotations (`{regions: [{class, rle}], image_width, image_height}`).

## Requirements

### Requirement 1: LLM model selection at job creation

**User Story:** As a Job_Creator, I want to choose an image-capable LLM as the auto-label model when creating a labeling job, so that pre-labels are generated by a model that understands what I ask it to detect instead of segmenting everything indiscriminately.

#### Acceptance Criteria

1. WHEN the Job_Creator enables auto-labeling in the job creation wizard, THE Portal SHALL present the Model_Catalog of LLM_Auto_Label_Model choices alongside the existing SAM option.
2. THE Model_Catalog SHALL identify each LLM_Auto_Label_Model by a non-empty human-readable display name and a non-empty model identifier.
3. THE Portal SHALL offer LLM_Auto_Label_Model choices for the Segmentation, ObjectDetection, and Classification modalities.
4. IF the Model_Catalog cannot be loaded when the Job_Creator enables auto-labeling, THEN THE Portal SHALL present an indication that the Model_Catalog is unavailable and SHALL accept a free-text model identifier entry for the LLM_Auto_Label_Model selection.
5. WHEN a Labeling_Job is submitted with an LLM_Auto_Label_Model whose identifier is empty, exceeds 256 characters, or contains whitespace or control characters, THE Portal SHALL reject the job creation request with an error identifying the invalid model parameter, and SHALL persist no Labeling_Job record or associated task records.
6. WHEN a Labeling_Job with an LLM_Auto_Label_Model is persisted, THE Portal SHALL store the selected model identifier on the Labeling_Job record.
7. WHEN a Labeling_Job with an existing auto-label configuration (SAM, or the existing Bedrock classification/detection mode) is created, THE Portal SHALL process the job through the pre-existing auto-label path with no change to its stored job configuration, Pre_Label generation behavior, or review flow.

### Requirement 2: Detection prompt input

**User Story:** As a Job_Creator, I want to write a prompt describing what the LLM should detect, so that the pre-labels target the defects relevant to my use case.

#### Acceptance Criteria

1. WHEN the Job_Creator selects an LLM_Auto_Label_Model, THE Portal SHALL prevent job submission until a Detection_Prompt of between 1 and 2000 characters is provided, and SHALL indicate that a Detection_Prompt is required.
2. THE Portal SHALL accept a Detection_Prompt of between 1 and 2000 characters, where a Detection_Prompt consisting only of whitespace characters is treated as empty.
3. IF a Labeling_Job is submitted with an LLM_Auto_Label_Model and a missing or empty Detection_Prompt (including a whitespace-only Detection_Prompt), THEN THE Portal SHALL reject the job creation request identifying the missing Detection_Prompt, and SHALL persist nothing.
4. IF a Labeling_Job is submitted with an LLM_Auto_Label_Model and a Detection_Prompt exceeding 2000 characters, THEN THE Portal SHALL reject the job creation request identifying the Detection_Prompt length violation, and SHALL persist nothing.
5. WHEN a Labeling_Job with an LLM_Auto_Label_Model is persisted, THE Portal SHALL store the Detection_Prompt on the Labeling_Job record character-for-character as entered by the Job_Creator.
6. WHERE a job uses skip-verification mode with an LLM_Auto_Label_Model, THE Portal SHALL continue to require the existing per-label prompts and SHALL include both the Detection_Prompt and the per-label prompts in the model request, with each prompt's text preserved unaltered.

### Requirement 3: Coordinate guidance generation

**User Story:** As a Job_Creator, I want the selected LLM to return structured coordinate guidance for each image, so that its detections can be turned into editable pre-labels.

#### Acceptance Criteria

1. WHEN the Auto_Labeler processes an image for a job with an LLM_Auto_Label_Model, THE Auto_Labeler SHALL send the model exactly one request for that image, containing the image data, the Detection_Prompt, the job's Label_Set, the image's pixel dimensions, and instructions to respond with a JSON document of Coordinate_Guidance expressed in pixel coordinates relative to those dimensions.
2. THE Coordinate_Guidance format SHALL support between 0 and 100 detections per image, where each detection is a bounding box or a polygon carrying exactly one class name from the Label_Set and pixel coordinates.
3. IF the image's pixel dimensions cannot be determined from the image data, THEN THE Auto_Labeler SHALL record a Pre_Label generation failure for that image identifying the unsupported image content, and SHALL NOT invoke the LLM_Auto_Label_Model for that image.
4. IF a model invocation does not return a response within 120 seconds or returns an error, THEN THE Auto_Labeler SHALL record a Pre_Label generation failure for that image with a failure reason that distinguishes timeout from model error, and SHALL make no further invocation attempts for that image.
5. WHEN a Pre_Label generation failure occurs for one image, THE Auto_Labeler SHALL continue processing every remaining image of the job, with the failure of one image leaving the processing outcome of every other image unchanged.
6. WHEN a model invocation returns a response within 120 seconds, THE Auto_Labeler SHALL pass the model's raw response text to the Guidance_Parser for validation.

### Requirement 4: Guidance parsing and validation

**User Story:** As a Portal operator, I want the LLM's output strictly validated before it becomes a pre-label, so that malformed model output never corrupts annotations or manifests.

#### Acceptance Criteria

1. WHEN the LLM_Auto_Label_Model responds, THE Guidance_Parser SHALL extract the first parseable JSON document from the response text, tolerating surrounding prose and code fences, and selecting the first candidate in reading order when multiple parseable JSON documents exist.
2. IF the response contains no parseable JSON document, THEN THE Guidance_Parser SHALL record a Pre_Label generation failure for that image identifying the unparseable output.
3. IF the extracted JSON document does not match the expected Coordinate_Guidance structure (a collection of detections, each carrying exactly one class name and exactly one geometry that is either a bounding box or a polygon), THEN THE Guidance_Parser SHALL record a Pre_Label generation failure for that image identifying the structural mismatch.
4. THE Guidance_Parser SHALL reject Coordinate_Guidance containing a class name that does not exactly match a Label_Set entry (comparison is case-sensitive after trimming leading and trailing whitespace from the class name), recording a Pre_Label generation failure identifying the offending class.
5. THE Guidance_Parser SHALL reject Coordinate_Guidance containing a bounding box with non-numeric coordinates, non-positive width or height, or extent outside the image's pixel bounds (a bounding box is within bounds when x >= 0, y >= 0, x + width <= image_width, and y + height <= image_height), recording a Pre_Label generation failure identifying the malformed geometry.
6. THE Guidance_Parser SHALL reject Coordinate_Guidance containing a polygon with fewer than 3 vertices, non-numeric vertex coordinates, or any vertex outside the image's pixel bounds (a vertex is within bounds when 0 <= x <= image_width and 0 <= y <= image_height), recording a Pre_Label generation failure identifying the malformed geometry.
7. IF Coordinate_Guidance contains more than 100 detections for one image, THEN THE Guidance_Parser SHALL reject the Coordinate_Guidance, recording a Pre_Label generation failure identifying the detection count limit exceeded.
8. IF any detection in a Coordinate_Guidance document is rejected, THEN THE Guidance_Parser SHALL reject the entire document, SHALL produce no Pre_Label for that image, and SHALL record a single Pre_Label generation failure for that image.
9. WHEN Coordinate_Guidance contains zero detections, THE Guidance_Parser SHALL accept it as a valid empty result.
10. FOR ALL valid Coordinate_Guidance documents, parsing the serialized document SHALL produce a guidance object whose detections have identical class names, geometry types, and coordinate values to the original (round-trip property).

### Requirement 5: Conversion to modality pre-labels

**User Story:** As a Job_Creator, I want the LLM's coordinate guidance converted into the pre-label geometry my job's modality needs, so that segmentation jobs get mask regions and detection jobs get boxes.

#### Acceptance Criteria

1. WHERE the job modality is Segmentation, THE Mask_Converter SHALL convert each Coordinate_Guidance detection into exactly one RLE mask region carrying the detection's class name (a polygon rasterized to its filled interior; a bounding box rasterized to its filled rectangle), without merging regions across detections that share a class name.
2. WHERE the job modality is Segmentation, THE Mask_Converter SHALL emit the Pre_Label in the existing segmentation Pre_Label format (regions with class and RLE, plus image_width and image_height matching the source image's pixel dimensions).
3. WHERE the job modality is ObjectDetection, THE Mask_Converter SHALL emit each Coordinate_Guidance detection as exactly one bounding box carrying the detection's class name in the existing detection Pre_Label format, with bounding-box detections emitted with their validated coordinates unchanged and polygon detections converted to the axis-aligned bounding box spanning the minimum and maximum of their vertex coordinates.
4. WHERE the job modality is Classification, THE Auto_Labeler SHALL emit the Pre_Label in the existing classification Pre_Label format, deriving the label from the Coordinate_Guidance (one or more detections means the anomaly class; zero detections means the normal class of the binary Label_Set).
5. WHEN validated Coordinate_Guidance contains zero detections and the job modality is Segmentation or ObjectDetection, THE Mask_Converter SHALL emit a Pre_Label containing zero regions or zero bounding boxes in the modality's existing Pre_Label format, treated as a successful generation.
6. THE Mask_Converter SHALL emit every mask region and bounding box entirely within the image's pixel bounds (no emitted geometry extends below 0 or beyond image_width or image_height).
7. IF conversion of an image's Coordinate_Guidance fails, or a detection rasterizes to an empty mask region or converts to a bounding box with zero width or height, THEN THE Mask_Converter SHALL record a Pre_Label generation failure for that image with the failure reason and SHALL write no partial Pre_Label for that image.

### Requirement 6: Pre-label storage and task resolution

**User Story:** As a Portal operator, I want LLM pre-labels stored and tracked exactly like existing pre-labels, so that the downstream labeler and review flows work without modification.

#### Acceptance Criteria

1. WHEN an LLM Pre_Label is generated successfully, THE Auto_Labeler SHALL write the Pre_Label to the portal artifacts bucket at the existing per-task pre-label location before marking the task resolved, and SHALL then mark the task's prelabel_status Available with the task's prelabel_s3_key referencing the written Pre_Label.
2. IF the write of a generated Pre_Label to the portal artifacts bucket fails, THEN THE Auto_Labeler SHALL mark the task's prelabel_status Failed with a failure reason identifying the storage failure, and SHALL NOT mark the task Available.
3. WHEN LLM Pre_Label generation fails for an image, THE Auto_Labeler SHALL mark the task's prelabel_status Failed with the failure reason recorded on the task record, and SHALL NOT set a prelabel_s3_key reference for that task.
4. THE Auto_Labeler SHALL resolve each task's prelabel_status (the transition from Pending to Available or Failed) at most once, with any duplicate queue delivery for an already-resolved task leaving the task's prelabel_status, failure reason, and stored Pre_Label reference unchanged.
5. WHILE a task's prelabel_status is Pending (neither Available nor Failed), THE Portal SHALL withhold the task from labeler presentation, exactly as for existing auto-label models.
6. WHERE the job uses skip-verification mode, THE Auto_Labeler SHALL count each task's first resolution (whether Available or Failed) exactly once toward the job's per-task completion counter, and SHALL mark the job review-ready when the count of resolved tasks equals the job's image count, with duplicate queue deliveries contributing no additional counts.

### Requirement 7: Preserved review and correction flow

**User Story:** As a labeler or admin, I want to review and correct the LLM's guesses in the same interface I use today, so that adopting LLM auto-labeling requires no retraining of reviewers.

#### Acceptance Criteria

1. WHEN a Labeling_Team member opens a task whose LLM Pre_Label is Available, THE Labeler_Interface SHALL load the Pre_Label as the editable starting annotation, exactly as for existing auto-label models.
2. WHEN a Labeling_Team member opens a task whose Available LLM Pre_Label contains zero annotation elements (a valid empty Coordinate_Guidance result), THE Labeler_Interface SHALL present the image with an empty editable annotation for annotation from scratch.
3. THE Labeler_Interface SHALL allow the labeler to modify, delete, and add annotation elements before submission, exactly as for existing auto-label models.
4. IF a submitted annotation fails the existing per-modality completeness rules, THEN THE Labeler_Interface SHALL reject the submission with a message identifying the unmet completeness rule and SHALL retain the labeler's in-progress annotation for correction.
5. WHEN a task with a Failed LLM Pre_Label is presented to a labeler in a team job, THE Labeler_Interface SHALL present the image without a Pre_Label for annotation from scratch, and the submitted annotation SHALL be validated by the same per-modality completeness rules as any other task.
6. WHERE the job uses skip-verification mode with an LLM_Auto_Label_Model, THE Admin_Review SHALL list every image of the job with its succeeded/failed Pre_Label generation status; for each succeeded image THE Admin_Review SHALL present the Pre_Label and accept/reject decision controls, exactly as for the existing Bedrock skip-verification flow.
7. WHERE the job uses skip-verification mode, WHEN an image's Pre_Label generation has Failed, THE Admin_Review SHALL display that image with its failure status and SHALL exclude it from the accepted results.
8. WHEN a Labeling_Team member submits an annotation for a task with an LLM Pre_Label, THE Portal SHALL record the result as human-annotated, exactly as today.
9. WHEN an Admin_Review accepts an LLM Pre_Label result in skip-verification mode, THE Portal SHALL record the result as machine-annotated, exactly as today.

### Requirement 8: Manifest compatibility

**User Story:** As an ML engineer, I want manifests from LLM-auto-labeled jobs to be byte-format-identical to today's manifests, so that training pipelines consume them without changes.

#### Acceptance Criteria

1. WHEN a job with an LLM_Auto_Label_Model completes (every team task submission is received, or the skip-verification Admin_Review is finalized), THE Portal SHALL generate the DDA_Manifest through the existing manifest generation path, including rendered PNG masks for Segmentation and the existing per-modality manifest attributes.
2. THE DDA_Manifest generated from an LLM-auto-labeled job SHALL pass the existing manifest validation gate without transformation, for each of the Segmentation, ObjectDetection, and Classification modalities.
3. WHEN Segmentation annotations originating from LLM Pre_Labels are serialized, THE Portal SHALL render their RLE regions to PNG masks using the existing job-wide color map, producing a pixel-identical mask to that rendered for an equivalent annotation of any other origin.
4. THE DDA_Manifest generated from an LLM-auto-labeled job SHALL contain the same entry structure and attribute names as a DDA_Manifest generated from a job of the same modality without an LLM_Auto_Label_Model, with no LLM-specific attributes added to any entry.
5. WHEN generating the DDA_Manifest for a skip-verification job with an LLM_Auto_Label_Model, THE Portal SHALL include one entry per accepted image and SHALL exclude rejected images, identically to the existing Bedrock skip-verification flow.
6. WHEN generating the DDA_Manifest for a team job with an LLM_Auto_Label_Model, THE Portal SHALL include one entry per submitted annotation, including annotations for tasks whose Pre_Label generation failed and were labeled from scratch.

### Requirement 9: Authorization and auditability

**User Story:** As a Portal administrator, I want LLM auto-labeling governed by the existing permission model and audit trail, so that the new capability introduces no new access paths.

#### Acceptance Criteria

1. THE Portal SHALL authorize creation of Labeling_Jobs with an LLM_Auto_Label_Model by the existing labeling job creation permission, with skip-verification jobs additionally requiring the UseCaseAdmin or PortalAdmin role, identically to today.
2. IF a user without the labeling job creation permission submits a Labeling_Job with an LLM_Auto_Label_Model, THEN THE Portal SHALL reject the request with an error identifying the missing permission, and SHALL persist nothing.
3. IF a user without the UseCaseAdmin or PortalAdmin role submits a skip-verification Labeling_Job with an LLM_Auto_Label_Model, THEN THE Portal SHALL reject the request with an error identifying the missing role, and SHALL persist nothing.
4. WHEN a Labeling_Job with an LLM_Auto_Label_Model is created, THE Portal SHALL include the selected model identifier and the auto-label mode in the existing job_created audit event details.
5. WHEN the Auto_Labeler reads a dataset image, THE Auto_Labeler SHALL use the existing cross-account access mechanism, and IF cross-account access fails, THEN THE Auto_Labeler SHALL fall back to single-account direct access.
6. IF both cross-account access and single-account direct access fail for an image, THEN THE Auto_Labeler SHALL record a Pre_Label generation failure for that image with the access failure reason.
7. THE Auto_Labeler SHALL send each model request with the image and prompt content only, transmitting no dataset credentials or portal secrets to the model.

### Requirement 10: Failure visibility

**User Story:** As a Job_Creator, I want to see how LLM auto-labeling performed on my job, so that I can judge whether the model and prompt are working.

#### Acceptance Criteria

1. WHEN the Job_Creator views a Labeling_Job with an LLM_Auto_Label_Model, THE Portal SHALL display the selected model identifier and the full stored Detection_Prompt on the job detail view.
2. WHEN a task's LLM Pre_Label generation fails, THE Portal SHALL retain the failure reason on the task record, truncated to at most 1024 characters, for the lifetime of the task record.
3. WHEN the Job_Creator views a Labeling_Job with an LLM_Auto_Label_Model whose Pre_Label generation has resolved for at least one task, THE Portal SHALL display the count of tasks with prelabel_status Available and the count of tasks with prelabel_status Failed on the job detail view.
4. WHEN the Job_Creator views a task whose prelabel_status is Failed, THE Portal SHALL display that task's retained failure reason.
5. IF every image of a job with an LLM_Auto_Label_Model fails Pre_Label generation, THEN THE Portal SHALL NOT transition the job to a failed or terminal state, and SHALL present every task for team labeling from scratch (team jobs) or present every task in Admin_Review with its Failed status (skip-verification jobs, with the existing finalize gating rejecting a review with zero accepted results).
