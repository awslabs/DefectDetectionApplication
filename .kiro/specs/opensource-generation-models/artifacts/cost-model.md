## 3. Cost formulas (Req 4.3)

- **Always-on:** `instances × 730 h × rate`, where `instances = max(concurrency,
  ceil(images_month ÷ (730 × 3600 ÷ measured_latency)))`. Persistent capacity, so
  volume only matters when throughput (not concurrency) binds.
- **On-demand:** `rate × (images_month × measured_latency + bursts ×
  (cold_start + 300 s)) ÷ 3600`, capped at the always-on cost for the same shape
  (a scale-to-zero deployment can never rationally cost more than leaving it on).
- **Cold start** = estimated provisioning + **measured** `model_load_seconds`:
  SageMaker 360 s + load, EC2 stop/start 120 s + load, ECS/EKS 450 s + load. The
  provisioning terms are documented estimates (no endpoint was created — task 4.4
  skipped); the load terms are Phase C measurements (FLUX 4.2–4.4 s, Hunyuan-2.1
  18.9 s, FLUX.2 38.1 s, PixArt 376–554 s).
- **Bedrock baseline:** `images_month × $/image`. No capacity cost, no cold start.

## 5. Reading the grid

1. **Always-on self-hosting never beats the Bedrock baseline below ~41,000
   images/month.** One always-on g6e.2xlarge costs $1,637/month = 40,918 Nova
   Canvas images; one ml.g6e.2xlarge endpoint = 51,100 images. At `dev-light`
   (1,100 images) always-on self-hosting is **37× more expensive per image** than
   Nova Canvas.
2. **On-demand self-hosting beats the baseline at every profile — for FLUX.1.**
   FLUX.1-Fill-dev on SageMaker async: $0.049/image at `dev-light`, $0.035 at
   `steady-team`, $0.029 at `production-sustained`, against $0.04 flat for Nova
   Canvas. FLUX.1-schnell is cheaper still ($0.037 / $0.022 / $0.017) because it
   is 1.8× faster.
3. **At production volume the ranking inverts to favour self-hosting outright.**
   150,000 images/month: Nova Canvas $6,000, FLUX.1-Fill-dev async $4,406, EC2
   stop/start $3,492, FLUX.1-schnell stop/start $1,960. The self-hosted saving is
   $1.6k–4.0k/month — real, but small relative to the engineering cost of owning
   a GPU serving stack, which this model does not price.
4. **FLUX.2 [dev] is the worst value at every profile** ($0.10–0.17/image, 2.6–4.3×
   Nova Canvas) *and* cannot do mask inpainting. HunyuanImage-2.1 is mid-priced
   ($0.05–0.11) and text-to-image only.
5. **PixArt is by far the cheapest per image** ($0.003–0.02) but is text-to-image
   only, so it cannot serve the pipeline's primary path at any price.
6. **The `dev-light` on-demand rows are near the EBS floor.** $37/month compute for
   FLUX.1-Fill-dev stop/start sits alongside ≈$16/month of gp3 for a 200 GB
   weights volume — include storage before quoting a dev-environment number
   ($37 → ≈$53). SageMaker async has no equivalent idle-storage charge (weights
   live in S3, ≈$1.4/month for 60 GB).
7. **Measured-latency caveat, in the self-hosted rows' favour.** All FLUX latencies
   were measured under `enable_model_cpu_offload`; 36.7 s is an upper bound. A
   resident-bf16 deployment on ml.g6e.4xlarge ($3.76/hr) at, say, 15 s/image would
   cost less per image than the ml.g6e.2xlarge rows despite the higher hourly
   rate. That shape was not measured, so it is not in the grid.

Tradeoff read:

- **The saving is enormous and the latency price is a one-off per burst.** Below
  `production-sustained`, on-demand saves 90–98 % of the always-on bill. The user
  pays 2.4–8.2 minutes on the first request of a session and measured
  per-image latency thereafter. For a human-in-the-loop preview workflow (the
  portal shows previews for approval), that is the right trade for dev.
- **EC2 stop/start buys the shortest cold start** (2.4–4.0 min for FLUX) because the
  weights never leave the EBS volume; SageMaker async costs ~4 extra minutes but
  removes all orchestration and queues the request instead of failing it.
- **At `production-sustained` the trade narrows sharply** — on-demand still saves
  42–70 % for FLUX/Hunyuan but only **6 %** for FLUX.2 [dev], because the instance
  is busy almost continuously and scale-to-zero has nothing left to reclaim. At
  that volume, choose always-on for predictable latency.
- **PixArt's cold start is dominated by measured model load** (376–554 s for the
  T5-XXL encoder), not by provisioning — the one case where the model, not the
  hosting option, sets the cold-start cost. It was measured on a 16 GiB host with
  swap; a ≥32 GiB host should improve it substantially, but that was not
  re-measured.

## 8. Bedrock baseline caveats (Req 4.4) — read before quoting the baseline

The baseline is priced with **published list prices**, deliberately, because
neither Bedrock inpainting path is straightforwardly usable on this account today:

1. **Nova Canvas is lifecycle `LEGACY` in us-east-1 and is not invokable on this
   account.** Verified read-only:

   ```
   $ aws bedrock get-foundation-model --model-identifier amazon.nova-canvas-v1:0 --region us-east-1
   → modelLifecycle: {"status": "LEGACY", "legacyTime": "2026-03-30", "endOfLifeTime": "2026-09-30"}
   ```

   `InvokeModel` against it is rejected on this account (the legacy-model
   `ResourceNotFoundException` path the portal already classifies). So the $0.04
   figure is a **price comparison, not an available option** — and the model
   reaches end of life 2026-09-30, i.e. the baseline disappears within the
   implementation window.
2. **The live incumbent is `us.stability.stable-image-inpaint-v1:0`** (Bedrock
   inference profile, `ACTIVE` in us-east-1 — confirmed via
   `aws bedrock list-inference-profiles`). That is the working Bedrock inpainting
   model the self-hosted options must actually beat. Its per-image price is **not
   published in the Pricing API for us-east-1** (a full `AmazonBedrock` product
   sweep returned no Stability image-service SKUs), so it is *not* used as the
   arithmetic baseline; confirm it on the Bedrock pricing page before making a
   commitment. In the $0.03–0.08/image band that Bedrock image models occupy, the
   conclusions in §5 do not change: always-on self-hosting still loses below
   ~40k images/month, and on-demand FLUX.1 still wins at `steady-team` and above.
3. **Titan Image Generator is retired** and is not a baseline option, though
   `MODEL_CATALOG` in `synthetic_core.py` still lists
   `amazon.titan-image-generator-v2:0` alongside `amazon.nova-canvas-v1:0` — a
   detail the registry migration should clean up
   (`model-registry-proposal.md`).

**Sensitivity:** at $0.03/image the break-even for one always-on g6e.2xlarge rises
to 54,600 images/month; at $0.08 it falls to 20,500. The on-demand FLUX.1-schnell
rows stay cheaper than the API baseline across that whole band at every profile.

## 9. What this model does not price

- Engineering and operational cost of owning a GPU serving stack (container build,
  weights lifecycle, patching, on-call). At `steady-team` volumes the self-hosted
  saving is ~$150–270/month — under one engineering hour per month.
- Reserved/Savings Plans (SageMaker Savings Plans reach ~64 % off; would improve
  always-on rows materially) and Spot (unsuitable for latency-sensitive serving,
  and Phase C deliberately used on-demand for determinism).
- Multi-model packing — one endpoint serving both FLUX.1-schnell and Fill-dev,
  which the measured 4.2–4.4 s load times make plausible and which would halve the
  always-on cost of running both.
- Cost Explorer reconciliation: unavailable for this exploration (tag not activated
  as a cost allocation tag; see `benchmark-results/README.md`). The **ledger** —
  USD 11.11 of the 500 Cost_Cap — is the authoritative actual-spend record, and it
  is the empirical anchor for the hourly rates used above.
