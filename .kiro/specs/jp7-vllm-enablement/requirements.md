# Requirements Document

## Introduction

The jetpack7-support feature delivered the JetPack 7 (Jetson Thor) LocalServer image (`src/backend/Dockerfile.jp7`: CUDA 13.0.2 devel Ubuntu 24.04 arm64 base, cuDNN 9.14 / TensorRT 10.14 exact pins, single CPython 3.11 interpreter, Thor `sm_110`) but shipped it deliberately vLLM-free: the Dockerfile carries a JP5-style disabled hook (`VLLM_ENABLE=0`, empty `VLLM_SPEC`/`VLLM_INDEX_URL`), the portal's vLLM architecture gating excludes `arm64_jp7` (the catalog adds `ARCH_ARM64_JP7` to `DEVICE_ARCHITECTURES` but NOT to `VLLM_ARCHITECTURES`), and the README documents vLLM as disabled on JP7 pending a Thor/cu130 wheel source.

No prebuilt vLLM wheel exists for Thor/CUDA 13 in the form this image needs. The JP6 enablement (jp6-vllm-enablement) used prebuilt `vllm==0.10.2+cu126` cp310 wheels from `pypi.jetson-ai-lab.io` — that index publishes nothing for Thor/cu130/cp311, and vLLM's own released wheels target x86_64 CUDA 12.x (community reports confirm Thor requires a from-source build with `sm_110` arch flags). This feature therefore BUILDS THE vLLM WHEEL FROM SOURCE inside the JP7 image build, via a new build script following the established `install_onnxruntime_gpu.sh` pattern (per-JetPack pins, CUDA architecture selection, prerequisite checks, wheel install, import/functional verification), and flips the JP7 vLLM layer to enabled-by-default with an opt-out. vLLM requires a matching PyTorch: PyTorch publishes an official cu130 wheel index (`https://download.pytorch.org/whl/cu130`) with aarch64 SBSA wheels that the NVIDIA developer community uses on Thor; the design must verify a cp311 aarch64 cu130 torch wheel exists for the chosen torch version, and if none does, building torch from source joins the scope. JP7 has no interpreter split (cp311 only), so this enablement is structurally simpler than JP6's dual-interpreter work.

Once the image ships vLLM, the portal's vLLM architecture gating gains `arm64_jp7`: the workflow_core catalog's `VLLM_ARCHITECTURES` (layer + vendored copy), the `vllm_supported_architectures()` functions in `packaging.py`, `greengrass_publish.py`, and `model_import.py`, the `vllm_fit_check.py` device memory profile, and the frontend vLLM gating surfaces. The chosen vLLM source version must keep the classic `AsyncLLMEngine`/`AsyncEngineArgs`/`SamplingParams` API surface that `vllm_runtime/manager.py` is written against, verified by an in-build gate. Known constraints: JP5/JP6 vLLM behavior stays byte-unchanged; the source build is hours-long and memory-heavy on arm64 (ccache and parallelism caps required; one build at a time per `.kiro/steering/builds.md`, on the Ubuntu 24.04 arm64 build server); any `Dockerfile.jp7` change requires rebaselining the preservation goldens in the same change; on-hardware validation on a Thor device mirrors the JP6 spec's Smoke_Model/Realistic_Model manual procedures.

## Glossary

- **JP7_Image**: The LocalServer JetPack 7 (`arm64_jp7`) container image built from `src/backend/Dockerfile.jp7` (base `nvcr.io/nvidia/cuda:13.0.2-devel-ubuntu24.04` arm64, digest-pinned; cuDNN 9.14 / TensorRT 10.14 exact pins; Thor `sm_110`).
- **DDA_Interpreter**: The single CPython 3.11 interpreter (deadsnakes) inside the JP7_Image that runs the DDA backend (`app.py` with the in-process Companion_Runtime) — there is no JP6-style interpreter split on JP7.
- **vLLM_Layer**: The build-arg-gated vLLM install layer in `Dockerfile.jp7`, currently `VLLM_ENABLE=0` with empty `VLLM_SPEC`/`VLLM_INDEX_URL`, changed by this feature to an enabled-by-default from-source build.
- **vLLM_Build_Script**: The new from-source vLLM wheel build script under `src/backend/` (e.g. `edge_ml1_p_camera_management/install_vllm_gpu.sh`), invoked by the vLLM_Layer, following the `install_onnxruntime_gpu.sh` pattern: pinned versions with env-var overrides, CUDA architecture selection, prerequisite checks, wheel production and install, and post-install verification.
- **vLLM_Version_Pin**: The default vLLM source version (git tag) the vLLM_Build_Script builds — selected at design time as a version that (a) supports CUDA 13 / Thor `sm_110` source builds and (b) retains the Classic_Engine_API; overridable via env var.
- **Torch_Pin**: The default pinned PyTorch version and wheel source for the JP7_Image — a cp311 aarch64 cu130 wheel from the PyTorch_cu130_Index if the design verifies one exists for the chosen version, otherwise a from-source torch build.
- **PyTorch_cu130_Index**: The official PyTorch wheel index `https://download.pytorch.org/whl/cu130`, which publishes CUDA 13.0 wheels including aarch64 SBSA builds.
- **Thor_Arch**: CUDA compute capability `sm_110` (`11.0a` family), the Jetson Thor GPU architecture the vLLM kernels must be compiled for.
- **Classic_Engine_API**: The vLLM API surface `vllm_runtime/manager.py` uses: `AsyncEngineArgs(**engine_args)`, `AsyncLLMEngine.from_engine_args`, `engine.generate(prompt, sampling_params, request_id)` yielding cumulative request outputs, `SamplingParams(**params)`, `shutdown_background_loop`, and the `errored` attribute.
- **Capability_Probe**: The `app.py` startup check `importlib.util.find_spec("vllm")` that activates the Companion_Runtime and Text_Generation_API router only when the vllm package is importable.
- **Companion_Runtime**: The device `vllm_runtime` package (`VllmRuntimeManager` + `VllmRuntimeServer`) that loads Triton_vLLM repositories and serves generate calls, written against the Classic_Engine_API.
- **Text_Generation_API**: The device FastAPI router (`endpoints/text_generation.py`) exposing non-streaming generate and SSE streaming over loaded vLLM models.
- **Portal_vLLM_Gating**: The complete set of portal locations that decide which Target_Architectures support vLLM: `VLLM_ARCHITECTURES` in `edge-cv-portal/backend/layers/workflow_core/python/workflow_core/catalog/nodes.py` and the vendored `src/backend/workflow_engine/vendor/workflow_core/catalog/nodes.py`; `vllm_supported_architectures()` in `edge-cv-portal/backend/functions/packaging.py` (plus its `VLLM_ARCH_TO_TARGET` map), `greengrass_publish.py`, and `model_import.py`; `DEVICE_MEMORY_PROFILE_BYTES` in `edge-cv-portal/backend/functions/vllm_fit_check.py`; and the frontend vLLM gating surfaces (`edge-cv-portal/frontend/src/pages/deployments/vllmArchGate.ts` and the `components/vllm-publish/` publish flow).
- **Build_Server**: The Ubuntu 24.04 arm64 build server that runs JP7 component builds, one build at a time per `.kiro/steering/builds.md`.
- **Docker_Preservation_Goldens**: The JP7 baselines pinned by the preservation gate: `test/backend-test/backend_jammy_pkgs/baselines/backend_Dockerfile.jp7.sha256.txt` and `test/backend-test/security/baselines/docker_baseline_backend_Dockerfile.jp7_masked.txt`, plus the digest-equality check between `src/backend/Dockerfile.jp7` and `src/edgemlsdk/Dockerfile.jp7` (`test_jp7_digest_equality.py`).
- **Security_Audit_Gates**: The audit gates run inside `build-custom.sh`, including the Docker non-ECR base image audit and the dependency/supply-chain CVE audit.
- **Smoke_Model**: facebook/opt-125m — a tiny HuggingFace model for a fast end-to-end smoke of the full register→package→publish→deploy→generate pipeline, mirroring the JP6 enablement.
- **Realistic_Model**: A mid-size HuggingFace instruct model (per the JP6 spec's convention, e.g. Qwen/Qwen2.5-7B-Instruct) exercising a realistic workload on the Thor device, with engine_configuration sized at design time for the Thor target's memory.
- **On_Hardware_Validation_Procedure**: A documented manual test procedure executed on a physical Jetson Thor JP7 device, following the repo convention that on-hardware steps are documented rather than automated.

## Requirements

### Requirement 1: vLLM Wheel Built from Source by a Reusable Build Script

**User Story:** As a build operator, I want a dedicated script that compiles a vLLM wheel from source for Thor/CUDA 13/cp311 inside the JP7 image build, so that the image ships a working vLLM despite no prebuilt wheel existing for this platform.

#### Acceptance Criteria

1. THE vLLM_Build_Script SHALL exist under `src/backend/` and follow the `install_onnxruntime_gpu.sh` pattern: pinned default versions, prerequisite checks that fail fast with a named missing prerequisite, wheel production, wheel install into the DDA_Interpreter, and post-install verification.
2. THE vLLM_Build_Script SHALL default the vLLM source version to the vLLM_Version_Pin and SHALL accept env-var overrides for the vLLM version, the CUDA architecture list (default Thor_Arch), the CUDA home path, and the parallel build job count.
3. WHEN the vLLM_Build_Script runs, THE vLLM_Build_Script SHALL compile the vLLM CUDA kernels for the Thor_Arch, produce a wheel whose tags declare cp311 compatibility and the aarch64 platform, and install that wheel into the DDA_Interpreter.
4. THE vLLM_Build_Script SHALL cap the default parallel build job count at the lesser of the available processor count and a memory-safety ceiling of 6 jobs (the `install_onnxruntime_gpu.sh` cap for memory-heavy arm64 CUDA compiles), overridable via the parallel-build-jobs env var of criterion 2.
5. WHERE ccache is available in the build environment, THE vLLM_Build_Script SHALL configure the build to compile through ccache so that a repeated build reuses prior compilation results.
6. WHEN the vLLM_Build_Script completes the wheel install, THE vLLM_Build_Script SHALL verify under the DDA_Interpreter that `import vllm` succeeds and that every Classic_Engine_API symbol is present — `AsyncEngineArgs`, `SamplingParams`, and the `from_engine_args`, `generate`, and `shutdown_background_loop` attributes of `AsyncLLMEngine` — and SHALL exit nonzero naming the missing symbol if any symbol verification fails.
7. IF `import vllm` fails during the post-install verification, THEN THE vLLM_Build_Script SHALL exit nonzero immediately with the import error, without proceeding to the individual symbol checks.
8. IF a build prerequisite is missing (CUDA toolkit at the expected path, the torch installation the vLLM build compiles against, or required build tools), THEN THE vLLM_Build_Script SHALL exit nonzero before starting the long compile, naming the missing prerequisite.
9. WHEN the vLLM_Build_Script produces the wheel, THE vLLM_Build_Script SHALL stage a copy of the built wheel at a single fixed directory inside the image outside the build tree before cleaning the build tree, so a successful hours-long build is preserved for inspection and reuse.
10. WHEN the wheel install and the staging of criterion 9 complete, THE vLLM_Build_Script SHALL remove its source checkout and build tree from the image.
11. IF the vLLM compile exits with an error or produces no cp311 aarch64 wheel, THEN THE vLLM_Build_Script SHALL exit nonzero with an error identifying the failed step or the absent wheel, without installing any partial artifact into the DDA_Interpreter.
12. IF ccache is not available in the build environment, THEN THE vLLM_Build_Script SHALL proceed with the build without compiler caching and SHALL NOT exit nonzero on account of ccache absence.

### Requirement 2: Matching PyTorch for cu130/cp311/aarch64

**User Story:** As a build operator, I want the JP7 image to carry a PyTorch build that matches CUDA 13, CPython 3.11, and aarch64, so that the from-source vLLM build compiles against it and the Companion_Runtime's torch-dependent paths work on the device.

#### Acceptance Criteria

1. THE JP7_Image SHALL install the Torch_Pin into the DDA_Interpreter in a `Dockerfile.jp7` layer ordered before the vLLM_Layer, and WHEN the vLLM_Layer completes, THE torch version installed in the DDA_Interpreter SHALL be identical to the Torch_Pin version — the vLLM build SHALL NOT replace, upgrade, or downgrade the installed torch.
2. THE design SHALL verify whether a cp311 aarch64 cu130 wheel exists on the PyTorch_cu130_Index (or a verified NVIDIA Thor/SBSA index) for a torch version compatible with the vLLM_Version_Pin, and SHALL record in the design document the verified wheel identity as the exact torch version, the wheel's cp311/aarch64/cu130 platform tags, and the source index it was verified on; IF no such wheel exists, THEN THE feature SHALL build torch from source for cu130/cp311/aarch64 with the Thor_Arch, following the same script conventions as Requirement 1 (pinned versions with env-var overrides, prerequisite checks that fail fast naming the missing prerequisite, parallelism caps, and post-install verification).
3. WHEN the JP7_Image build completes with the Torch_Pin installed, THE build's import verification gate SHALL confirm under the DDA_Interpreter that `import torch` succeeds and that torch reports a CUDA 13.x build; IF either check fails, THEN THE JP7_Image build SHALL fail naming the failed check.
4. WHEN the vLLM_Layer and Torch_Pin installs complete, THE JP7_Image build SHALL verify that the DDA_Interpreter's dependency environment remains functionally consistent: every package the DDA backend imports at startup SHALL remain importable under the DDA_Interpreter, the numpy and transformers versions in the final image SHALL satisfy the version constraints of the existing application dependency set, and the DDA_Interpreter's dependency resolution check SHALL report zero broken or conflicting requirements for packages the DDA backend uses.
5. IF the vLLM_Version_Pin's dependency metadata demands a torch version different from the Torch_Pin, THEN THE vLLM_Build_Script SHALL build against the installed Torch_Pin using vLLM's existing-torch mechanism, SHALL NOT install the metadata-demanded torch version, and THE design SHALL record the verified vLLM/torch version pairing in the design document.
6. THE JP7_Image SHALL pin every CUDA-dependent wheel in the vLLM dependency chain that the vLLM_Version_Pin requires (torch, and as demanded by the pinned vLLM version: torchvision, triton, xformers, or their vLLM-pinned equivalents) to exact versions from a verified source — the PyTorch_cu130_Index, a verified NVIDIA cu130 arm64 index, or a from-source build — and THE design SHALL record in the design document the verified source and exact version for each such wheel; a CUDA-dependent wheel in this chain SHALL NOT be resolved as an unpinned transitive install from default PyPI.
7. IF any dependency consistency check in criterion 4 fails, THEN THE JP7_Image build SHALL fail with the failing package named in the build output, and the built image SHALL NOT be treated as a valid JP7_Image artifact.
8. WHEN the JP7_Image runs on a Thor device, THE DDA_Interpreter SHALL report `torch.cuda.is_available()` as true, verified as part of the On_Hardware_Validation_Procedure.

### Requirement 3: JP7 vLLM Layer Enabled by Default with Verification Gates

**User Story:** As an edge device operator, I want a plain JP7 image build to produce a vLLM-capable image by default, with build-time gates proving the install works, so that deployed LLM models serve on Thor devices without special build flags.

#### Acceptance Criteria

1. THE vLLM_Layer SHALL default `VLLM_ENABLE` to `1` in `Dockerfile.jp7`, and WHEN the JP7_Image is built with `VLLM_ENABLE=1`, THE vLLM_Layer SHALL invoke the vLLM_Build_Script (with the Torch_Pin install as its companion step) in place of the current prebuilt-wheel `pip install` body, retaining `VLLM_ENABLE=0` as the opt-out defined in criteria 3.7 and 3.10.
2. WHEN the JP7_Image is built with `VLLM_ENABLE` set to `1`, THE vLLM_Layer SHALL invoke the vLLM_Build_Script gated solely on the `VLLM_ENABLE` value: no other build arg — including an empty or absent `VLLM_SPEC` or `VLLM_INDEX_URL` — SHALL cause the vLLM_Layer to skip or alter the invocation, and the legacy `VLLM_SPEC`/`VLLM_INDEX_URL` build args SHALL either be removed from `Dockerfile.jp7` or accepted without effect on the vLLM_Layer's gating.
3. WHEN the JP7_Image build completes successfully with default build args, THE built image SHALL contain the from-source vLLM wheel installed into the DDA_Interpreter such that `import vllm` succeeds under the DDA_Interpreter; IF the build reports failure, THEN the build's artifacts SHALL NOT be treated as a vLLM-capable image regardless of partially completed layers.
4. WHERE the JP7_Image is built with `VLLM_ENABLE=1`, THE `Dockerfile.jp7` GPU-dependent import check gate SHALL verify the final image state under the DDA_Interpreter for each of: vllm importability, torch importability, and the presence of every Classic_Engine_API symbol the Companion_Runtime uses (`AsyncEngineArgs`, `AsyncLLMEngine.from_engine_args`, `SamplingParams`, `shutdown_background_loop`, and the `errored` attribute), as separate checks so that a check failure fails the build with the build log naming the specific failing package or symbol.
5. WHEN a JP7_Image containing vLLM starts on a Thor device, THE Capability_Probe SHALL execute during `app.py` startup, find the vllm package, and activate the Companion_Runtime and the Text_Generation_API router, such that the Text_Generation_API routes are registered on the running backend.
6. THE vLLM_Version_Pin SHALL expose the Classic_Engine_API, verified during design against the pinned version's source and enforced at build time by the gates in Requirements 1.6 and 3.4.
7. WHEN the JP7_Image is built with `VLLM_ENABLE=0`, THE vLLM_Layer SHALL install no packages (neither the vLLM wheel nor the Torch_Pin companion install), and THE vLLM-specific import gate checks of criterion 3.4 SHALL be skipped with a build-log message stating the skip and the `VLLM_ENABLE` value.
8. IF the vLLM_Build_Script exits nonzero during a build with `VLLM_ENABLE=1`, THEN THE JP7_Image build SHALL fail with the vLLM_Build_Script's error output present in the build output, and SHALL NOT fall back to any alternative vLLM install path.
9. THE vLLM_Layer (including the Torch_Pin companion install step) SHALL be ordered after the onnxruntime GPU build layer in `Dockerfile.jp7`, so that a vLLM build failure or a vLLM-only change does not invalidate the cached onnxruntime GPU build layer and the two hours-long compiles remain independently cacheable.
10. WHEN a JP7_Image built with `VLLM_ENABLE=0` starts on a device, THE Capability_Probe SHALL find no vllm package and THE backend SHALL complete the pre-feature startup sequence without activating the Companion_Runtime or the Text_Generation_API router.

### Requirement 4: Portal vLLM Architecture Gating Gains arm64_jp7

**User Story:** As a portal user, I want `arm64_jp7` accepted everywhere the portal gates vLLM by architecture, so that I can package, publish, fit-check, and deploy vLLM models and llm_inference workflows to Thor devices.

#### Acceptance Criteria

1. THE Portal_vLLM_Gating SHALL include `arm64_jp7` in every vLLM-supported architecture set: `VLLM_ARCHITECTURES` in the workflow_core catalog layer and its vendored copy, and `vllm_supported_architectures()` in `packaging.py`, `greengrass_publish.py`, and `model_import.py`, with the catalog layer's `VLLM_ARCHITECTURES` and the vendored copy's `VLLM_ARCHITECTURES` containing identical membership after the change.
2. THE `VLLM_ARCH_TO_TARGET` map in `packaging.py` SHALL map `arm64_jp7` to the packaging target name `jetson-xavier-jp7`, matching the target name the existing `arm64_jp7` (non-vLLM) packaging path already uses, so that every architecture returned by `vllm_supported_architectures()` has an entry in `VLLM_ARCH_TO_TARGET`.
3. THE `vllm_fit_check.py` `DEVICE_MEMORY_PROFILE_BYTES` SHALL gain an `arm64_jp7` entry whose value is an exact byte figure recorded in the design document, strictly less than the Thor developer kit's 128 GB nameplate unified memory and derated the way the existing `arm64_jp6` entry derates the Orin's 32 GB to 30 GiB, and WHEN a Fit_Check evaluates `arm64_jp7`, THE Fit_Check SHALL produce a finding for `arm64_jp7` using that entry instead of skipping it as an unprofiled architecture.
4. WHEN a vLLM model is registered or published through the portal after this feature's gating change is deployed, THE published component's supported architectures SHALL include `arm64_jp7` alongside the pre-existing JP5/JP6 entries.
5. WHEN a deployment targets a device recorded as `arm64_jp7` with a vLLM-bearing component whose supported set includes `arm64_jp7`, THE backend vLLM architecture gate and its frontend twin (`vllmArchGate.ts`) SHALL both pass the device.
6. THE frontend vLLM gating surfaces (the `vllmArchGate.ts` twin and the `components/vllm-publish/` publish flow) SHALL treat `arm64_jp7` as a supported architecture in both gate evaluation and every display of a supported-architecture set, and THE existing property tests for these surfaces SHALL be extended to cover `arm64_jp7` and pass.
7. THE `arm64_jp4` exclusion, the `JP5_VLLM_ENABLED = False` flag, and the JP5/JP6 entries of every gating set SHALL remain unchanged.
8. WHEN a deployment targets a JP5 or JP6 device after this feature, THE portal gating verdicts for those devices SHALL be identical to pre-feature behavior, as demonstrated by the pre-existing JP5/JP6 gating test expectations passing unmodified.
9. WHEN a workflow containing an `llm_inference` node is packaged for `arm64_jp7` after this feature's gating change is deployed, THE packaging validation SHALL accept it with zero `V6_LLM_ARCH_UNSUPPORTED` findings.
10. IF a deployment targets a device recorded as `arm64_jp7` with a vLLM-bearing component whose supported set does not include `arm64_jp7` (such as a component published before this feature), THEN THE backend vLLM architecture gate and its frontend twin SHALL both reject the device, indicating that the component's supported architectures do not include the device's architecture.

### Requirement 5: Build System, Baselines, and Documentation Stay Consistent

**User Story:** As a maintainer, I want every existing build gate, baseline, and document updated in the same change, so that the enablement lands without breaking the preservation gates or leaving stale documentation.

#### Acceptance Criteria

1. WHEN `Dockerfile.jp7` is changed by this feature, THE Docker_Preservation_Goldens SHALL be recaptured in the same change: `backend_Dockerfile.jp7.sha256.txt` updated to the sha256 of the final `src/backend/Dockerfile.jp7` content and `docker_baseline_backend_Dockerfile.jp7_masked.txt` updated to the masked form of that same content, such that the preservation gate tests pass against the recaptured baselines and a diff of the recaptured masked baseline against its pre-feature version contains only the lines introduced by the vLLM_Layer, Torch_Pin, and verification-gate changes of Requirements 1–3.
2. THE digest-equality check between `src/backend/Dockerfile.jp7` and `src/edgemlsdk/Dockerfile.jp7` (`test_jp7_digest_equality.py`) SHALL pass after this feature's changes.
3. THE JP5, JP6, JP4, and x86 backend Dockerfiles and their baselines SHALL be byte-identical to their pre-feature content, and THE JP5/JP6 vLLM install behavior SHALL be unchanged, verified by zero diff lines in those Dockerfiles and baselines and by no reference to the vLLM_Build_Script from any non-JP7 Dockerfile.
4. WHEN the Security_Audit_Gates run inside `build-custom.sh` after this feature's changes, THE Security_Audit_Gates SHALL all exit successfully with zero unresolved findings, including the Docker non-ECR base image audit and the dependency/supply-chain CVE audit evaluating the vLLM_Version_Pin, the Torch_Pin, and every CUDA-dependent wheel pinned per Requirement 2.6.
5. IF any Security_Audit_Gate fails on the new vLLM or torch dependencies, THEN THE feature SHALL be blocked from landing until the failure is resolved by changing the flagged dependency version or source — gate failures SHALL NOT be resolved by overriding the gate, adding suppressions for the new dependencies, or weakening the audit rules.
6. WHEN the device backend test suite under `test/backend-test/` and the portal backend, workflow_core layer, and frontend test suites run after this feature's changes, THE suites SHALL pass with zero test failures, with any gating-set test expectations updated to include `arm64_jp7` as intended by Requirement 4, and with no pre-existing test deleted, skipped, or weakened to achieve the pass.
7. THE README's "JetPack 7 (JP7) Devices" section SHALL be updated to state that vLLM is enabled on JP7 via a from-source build, replacing the "vLLM is disabled" limitation, such that a search of the README after this feature's changes finds zero remaining statements that vLLM is disabled or unsupported on JP7.
8. THE README's JP7 documentation SHALL state the expected JP7 build duration impact of the from-source vLLM build as a bounded time range derived from a measured Build_Server build during validation, SHALL document the `VLLM_ENABLE=0` opt-out and its effect on the built image, and SHALL note that JP7 builds run on the Build_Server one at a time.
9. THE design SHALL record the build-baseline treatment of the vLLM_Build_Script — either registered with a sha256 baseline in the backend build baseline suite (the `install_aravis.sh.sha256.txt` convention) or untracked (the `install_onnxruntime_gpu.sh` treatment) — and THE backend build baseline suite SHALL pass after the feature's changes with that treatment applied.

### Requirement 6: On-Hardware Validation on a Thor Device

**User Story:** As a QA engineer, I want a documented on-hardware validation procedure covering a fast smoke-test model and a realistic model on a Jetson Thor JP7 device, so that the default-enabled vLLM path is proven end-to-end before release.

#### Acceptance Criteria

1. THE feature SHALL provide an On_Hardware_Validation_Procedure covering the Smoke_Model through the complete pipeline on a Thor JP7 device: registration through the portal's Register LLM flow with a HuggingFace source, packaging for `arm64_jp7`, publish, deployment, READY status propagation observable on the portal's deployment view, a non-streaming generate round trip through the Text_Generation_API that returns non-empty generated text, and an SSE streaming session through the Text_Generation_API that delivers incremental output events and terminates with a completion event.
2. THE On_Hardware_Validation_Procedure SHALL cover the Realistic_Model through the same pipeline stages with an engine_configuration (gpu_memory_utilization and max_model_len) whose exact values are recorded in the design, sized for the Thor target's memory consistently with the `arm64_jp7` device memory profile established in Requirement 4.
3. THE On_Hardware_Validation_Procedure SHALL document the Register LLM portal steps for each model: navigating to the Models page's "Register LLM" action, selecting the HuggingFace source and entering the model ID, the exact engine settings values to enter for that model (gpu_memory_utilization and max_model_len), submitting the form, and the expected resulting model record — the `LLM (vLLM)` type badge and a supported-architectures set that includes `arm64_jp7`.
4. THE On_Hardware_Validation_Procedure SHALL include executing an `llm_inference` workflow node against a deployed model on the JP7 device and verifying that non-empty generated text appears in the node's inference metadata output.
5. THE On_Hardware_Validation_Procedure SHALL include verifying vision-model coexistence on the JP7 device: a previously supported vision model (ONNX or Triton-served) and a vLLM model loaded simultaneously, with a vision inference request and a vLLM generate request each returning a successful response while both models remain loaded.
6. THE On_Hardware_Validation_Procedure SHALL specify, for each stage (register, package, publish, deploy, load, generate, stream, workflow, coexistence), an expected outcome stated as an observable condition (a portal status, an API response content, or a device log entry) and the failure triage steps for that stage, such that a tester can reach a binary pass/fail verdict per stage.
7. THE On_Hardware_Validation_Procedure SHALL include verifying, under the DDA_Interpreter inside the deployed container on the Thor device, that `torch.cuda.is_available()` returns true and that a vLLM engine load completes with the model reaching loaded status on the Thor GPU, and its triage steps SHALL distinguish container-image problems from host driver-stack problems.
