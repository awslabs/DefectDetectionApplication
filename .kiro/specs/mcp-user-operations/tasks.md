# Implementation Plan: MCP Account-Lifecycle Tools (`mcp-user-operations`)

## Overview

This plan implements `design.md` (revision 4, design review APPROVED with 0 HIGH, 0 MEDIUM and 3 NIT findings; accepted by the owner at the design gate; task 1.2 brings it to revision 5) for the four Phase-4 tools of the Portal_MCP_Server's `admin` view: `portal_admin_account_create` (`M`), `portal_admin_account_disable`, `portal_admin_account_enable` and `portal_admin_account_delete` (`M!`, `confirm=account_username`). The work is portal-only: four `ToolSpec` rows, three optional `ToolSpec` fields (`self_protect_arg`, `resource_id_arg`, `error_detail_key`), the `EmailLookup` tuple with the `refresh` keyword and `refresh_email` in `principal.py`, the Self_Protection_Rule as pipeline step 5b in `pipeline.py` (`call_tool`, which the MCP server and the Portal assistant both run: owner decision 2a, design revision 5), the detail-key join in `errors.py`/`shaping.py`, the envelope `resource_id` rule in `audit.py`, the regenerated exports, the tests of the design's Testing Strategy, the documentation, one scoped deploy, one live exercise against throwaway identities and one release. No handler, route, frontend, layer, IAM statement or edge file changes (N1–N3); `mcp_edge.DELIVERED_PHASES` stays `(1, 2, 3)`.

The plan follows the mcp-servers phase shape (entry criteria → the owner's destructive-list sign-off → delivery → deploy and live exercise with the Mutating_Switch on only for the Exercise_Window → release → final checkpoint), labelled **Phase 4** of the Portal_MCP_Server because the rows carry `phase=4` and `DELIVERED_PHASES` becomes `(1, 2, 3, 4)`. The task numbers are this spec's own (1–8); the phase label continues the mcp-servers numbering. Two code commits carry the phase, in the order the design's Phasing table gives: the **authoring commit** (task 2: rows, fields, pipeline, exports, tests, harness, the ADMIN_GUIDE table rows; `DELIVERED_PHASES` stays `(1, 2, 3)`, so the rows are authored, exported and tested but neither listed nor accepted) and, after the owner's sign-off, the **delivering commit** (task 4: `DELIVERED_PHASES = (1, 2, 3, 4)`, version `1.2.0 → 1.3.0`, the version pins, the documentation prose). The sign-off list is generated from `catalog_tools.json`, which holds the rows only once they are authored, so the authoring commit precedes the gate and the delivering commit follows it (Requirement 4.6: signed off before the rows are delivered).

Three owner gates, each a numbered question when reached, as in the mcp-servers phases: **gate 1** the destructive-list sign-off (task 3), **gate 2** the deploy and the live exercise with its Exercise_Window (task 5), **gate 3** the release push, PR and merge (task 7). Every live AWS write of this plan sits behind one of them; the spec-authoring run that produced the three documents made no code change, no AWS call and no push.

Property-based tests use Hypothesis, at least 100 examples (`@settings(max_examples=100, deadline=None)`), tagged `**Feature: mcp-user-operations, Property {number}: {property title}**`, as the design's Correctness Properties section specifies; a property that extends a mcp-servers property test adds its clauses to that test's file, as the design's Testing Strategy assigns.
