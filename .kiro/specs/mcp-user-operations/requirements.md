# Requirements Document

## Introduction

This spec adds the four account-lifecycle operations of the Portal's User Manager to the Portal_MCP_Server as MCP tools: create a Portal account, disable it, enable it, and delete it. The mcp-servers spec (Phases 1–3, complete) delivered every other administration tool of the `admin` view — the account listing, the account-level role change, Use_Case role assignment and removal, the audit-log query and the edge account sync — and placed these four in no phase. Backlog 31 of its design records the owner's decision (2026-11-02, at the Phase-3 destructive-list sign-off) that they become a follow-up spec which defines their classification, `confirm` targets, permissions and tests, and that the account-lifecycle half of the route-registration test changes in the same commit that adds them.

The REST side already exists. The routes `POST /admin/users`, `POST /admin/users/{username}/disable`, `POST /admin/users/{username}/enable` and `DELETE /admin/users/{username}` are registered on the Portal_API (mcp-servers Backlog 2, resolved 2026-10-26) and are served by the User_Admin_Handler (`edge-cv-portal/backend/functions/user_admin.py`), whose behaviour is specified by the `portal-user-manager` spec (Requirements 5, 7, 12, 13 and 14) and the `portal-jwt-role-privilege-escalation` spec (Requirement 3). What remains is the MCP side: four catalog rows, their RBAC and audit treatment, the catalog mirrors and tests, the documentation, one scoped deploy, one live exercise and one release.

Everything the mcp-servers spec established applies unchanged and is not re-specified here: the Portal_MCP_Server's authentication (User_Pool access tokens validated in the Lambda), its request pipeline (lookup → validation → `confirm` → the Mutating_Switch → the pre-dispatch RBAC check → Lambda dispatch → shaping → audit), the tool classes and the `confirm` convention (Requirement 5 there), Property 6 (marked audit entries per completion), the error-category vocabulary (D21), the naming convention (D22), the `status_tool` rule (D32), the catalog machinery (`ToolSpec`, `tools_for_view`, the exports) and the catalog-honesty suites. This document states what the four tools must do and what must hold around them; the design document settles the tool-by-tool contract, the RBAC decision table, the audit rows, the catalog and documentation changes with the exact recount delta, the live-exercise plan and the correctness properties.

## Baseline (as read from the code at `0861addb`)

Portal_MCP_Server (`edge-cv-portal/backend/functions/mcp_portal/`):
- `__version__ = '1.2.0'`, `DELIVERED_PHASES = (1, 2, 3)` ("the only phase gate: a catalog spec whose phase is not listed here is neither listed nor accepted"), `VIEWS = ('data', 'models', 'devices', 'workflows', 'admin')`. `MCP_SERVER_VERSION = '1.2.0'` in `edge-cv-portal/infrastructure/lib/mcp-stack.ts`. The deployed stack runs with `MCP_MUTATING_TOOLS_ENABLED=false` (CDK context `mcpMutatingToolsEnabled`, default false).
- The `admin` view holds 15 tools: 8 read-only Phase-1 tools and 7 mutating Phase-3 tools. The `/admin/users` family consists of `portal_admin_accounts_list` (`GET /admin/users`, read-only, Phase 1) and `portal_admin_account_role_change` (`PUT /admin/users/{username}/role`, mutating, Phase 3); both declare `manage_users` at the `global` scope, `resource_type='account'`, backend key `userAdmin`, handler module `user_admin`, and the role-change tool addresses the account as `account_username` (→ path `username`), because `username` and `email` are claim-named argument names the catalog rejects. The destructive rows of the view (`portal_admin_usecase_delete`, `portal_admin_role_remove`, `portal_admin_edge_sync_device_sync`) use `confirm_arg('Repeat <argument>.')` with `confirm_target='<argument>'`; a missing or mismatched `confirm` is `confirmation_required`.
- `CATALOG` holds 183 portal tools (`portal_models_delete` is absent by owner decision; its absence test stands). `tools/list` on the aggregate endpoint returns 89 tools with the switch off and 183 with it on.
- The envelope rule (`audit.py`): the MCP layer writes one `mcp_tool_call` entry for every pre-dispatch outcome other than a denial or an availability failure (those write their own marked entries), for every post-dispatch non-2xx except a 403 from a handler that audits its own denials, and for a 2xx only when the handler writes no entry of its own (`handler_audits=False`). A handler that audits on some branches only is pinned `handler_audits=False` in `test_mcp_handler_audit_flags.py` (`PINNED_AUDIT_FLAGS`, with its reason), so the envelope always records the call.

User_Admin_Handler (`user_admin.py`), as the `portal-user-manager` spec specifies and the code implements:
- Every route runs behind `require_portal_admin`: the caller's effective role must be PortalAdmin (decided by the RBAC_Layer from the Portal_Identity_Registry, never from the token's `custom:role`); a denial answers 403 and writes an `unauthorized_access` audit entry; an unreadable registry answers 500 and writes `authorization_unavailable`.
- `create_account` (`POST /admin/users`, body `{username, email, role}`): validates the three fields and the email shape (non-empty local part, `@`, a domain containing a dot) and the role against `PORTAL_ROLES` (PortalAdmin, UseCaseAdmin, DataScientist, Operator, Viewer, DataLabeler) before any User_Pool call (400); records the audit entry `account_create` before the effect; creates the account with the User_Pool's own invitation email and temporary password (the Portal never holds the password); writes the account's global Portal_Identity row; answers 201 `{message, username, email, role}`; a duplicate username is 409 with nothing created; other User_Pool failures 502 with no partial record; a registry write that fails after the account exists is 502 "account was not provisioned" with the partial state audited; a failed pending-audit write is 500 "action not applied" with the User_Pool untouched.
- `disable_account` / `enable_account` (`POST /admin/users/{username}/disable|enable`): a missing account is 404; an account already in the requested state is a 200 no-op `{username, enabled, changed: false}` with no User_Pool change, no audit entry and no sync staging; disabling the last remaining enabled PortalAdmin is 409 with a `rejected` audit entry written before any change (the Last_PortalAdmin_Guard); otherwise the audit entry `account_disable`/`account_enable` is recorded before the effect, the User_Pool flag is changed, the account's global Portal_Identity row `status` is set (which is what stops an already-issued token from holding privilege on its next request), the account's record in every device staged set that contains it is marked pending for the Account_Sync_Service, and the entry is finalized; a registry update that fails after the User_Pool change is 502 "<verb> incomplete" with the partial state audited.
- `delete_account` (`DELETE /admin/users/{username}`): a missing account is 404 with nothing modified; deleting the last remaining enabled PortalAdmin is 409 with a `rejected` audit entry; otherwise the audit entry `account_delete` (carrying the account's email and role) is recorded before the effect, the User_Pool account is deleted, its Portal_Identity rows and its edge credential record are removed, every device staged set that contains it is marked disabled and deleted for the next sync, and the entry is finalized; a cleanup that fails after the User_Pool deletion is 502 "partial deletion" naming what is retained for a later attempt.
- Routes that handle credential material and stay excluded from MCP (mcp-servers Requirement 5.5): `POST /admin/users/{username}/password` and `POST /admin/users/{username}/forgot-password`. No route exists for resending an invitation or for MFA management.

Tests and mirrors (baselines the tasks document must carry forward): `tests/mcp` 3,827 passed; trunk backend suite 49; CDK 44 suites / 527 tests; the IAM preservation synth gate 40; the 16.3 docs check PASS (portal 183, edge 73, 256 documented rows); the design recount 161 rows (portal 184 = 87/53/44; edge 73 = 47/9/17). The hosted-UI login automation for throwaway identities used by the Phase-2 and Phase-3 live exercises (owner decision B2) exists and can be reused.

## Glossary

Terms defined by the mcp-servers requirements keep their meaning here: Portal, Portal_API, User_Pool, Portal_Role, Permission, RBAC_Layer, Portal_Identity_Registry, Use_Case, Audit_Log, Attribution_Fields, Account_Sync_Service, MCP_Client, Portal_MCP_Server, MCP_Tool, Read_Only_Tool, Mutating_Tool, Tool_Catalog, Principal, MCP_Audit_Marker. New or narrowed terms:

- **Account**: A User_Pool account (a Cognito user of `dda-portal-users`) together with its global Portal_Identity row and, where present, its edge credential record and its records in device staged sync sets. Addressed by its username.
- **Account_Lifecycle_Tool**: One of the four MCP_Tools this spec adds: `portal_admin_account_create`, `portal_admin_account_disable`, `portal_admin_account_enable`, `portal_admin_account_delete`.
- **User_Admin_Handler**: The existing Lambda handler `user_admin.py` (backend key `userAdmin` in the MCP dispatch map), the Portal's User Manager backend and the writer of the Portal_Identity_Registry.
- **Admin_View**: The `admin` view of the Tool_Catalog, served at `…/mcp/admin`; its tools are also served on the aggregate endpoint `…/mcp`.
- **Destructive_Tool**: A Mutating_Tool with `destructiveHint` true (`M!` in the mcp-servers tables) that requires the `confirm` argument.
- **Mutating_Switch**: The server-level setting `MCP_MUTATING_TOOLS_ENABLED` (CDK context `mcpMutatingToolsEnabled`, default false) that lists and accepts Mutating_Tools only while on.
- **Last_PortalAdmin_Guard**: The User_Admin_Handler's rule that the Portal retains at least one enabled PortalAdmin account: a disable, deletion or role change that would remove the last one is rejected with 409 and a `rejected` audit entry.
- **Self_Protection_Rule**: The rule, new in this spec and evaluated by the Portal_MCP_Server before dispatch, that a Principal cannot disable or delete its own Account through MCP.
- **No_Op_Completion**: A disable or enable call whose target is already in the requested state: the handler answers 200 with `changed: false` and writes no audit entry.
- **Delivery_Phase**: The integer `phase` of a catalog row, gated by `DELIVERED_PHASES`. Phases 1–3 are delivered; this spec adds Phase 4.
- **Catalog_Mirrors**: Every artefact that must agree with `CATALOG`: `catalog_tools.json` and `catalog_routes.json`, the ADMIN_GUIDE tool tables (checked by the 16.3 docs check), the design catalog tables (checked by the recount), and the honesty suites under `edge-cv-portal/backend/tests/mcp/` and `edge-cv-portal/infrastructure/test/`.
- **Throwaway_Identity**: A User_Pool account created for one live exercise, with a registry row naming its role, and deleted at the end of the same exercise.
- **Exercise_Window**: The interval during which the deployed `EdgeCVPortalMcpStack` runs with the Mutating_Switch on for a live exercise; it starts with a scoped deploy on the owner's go and ends with the scoped deploy that restores the switch to false.

## Requirements

### Requirement 1: Account-Lifecycle Tools in the Admin View

**User Story:** As a PortalAdmin working in an AI assistant, I want to create, disable, enable and delete Portal accounts through MCP tools, so that account administration through an assistant carries the same guardrails and audit trail as the User Manager page.

#### Acceptance Criteria

1. THE Portal_MCP_Server SHALL add exactly four Account_Lifecycle_Tools to the Admin_View of the Tool_Catalog: `portal_admin_account_create` wrapping `POST /admin/users` (`user_admin.create_account`), `portal_admin_account_disable` wrapping `POST /admin/users/{username}/disable` (`user_admin.disable_account`), `portal_admin_account_enable` wrapping `POST /admin/users/{username}/enable` (`user_admin.enable_account`), and `portal_admin_account_delete` wrapping `DELETE /admin/users/{username}` (`user_admin.delete_account`), each with `domain='admin'`, `backend='userAdmin'`, `handler_module='user_admin'` and `resource_type='account'`.
2. THE tool names SHALL follow D22 and the `account` stem of the existing `/admin/users` family (`portal_admin_accounts_list`, `portal_admin_account_role_change`) and of Backlog 31; the `user` stem (`portal_admin_users_list`, `portal_admin_user_permissions_get`, `portal_admin_role_assign`/`_remove`) addresses Portal_Identity role rows by `user_id` and SHALL NOT be used for Account operations. (Assumption: the run brief's working names `portal_admin_user_*` are replaced by these names for that reason; the owner may object at the requirements gate.)
3. THE Portal_MCP_Server SHALL implement each Account_Lifecycle_Tool by dispatching the registered route to the User_Admin_Handler with the Principal's verified claims, exactly as the existing `userAdmin` rows do, and SHALL perform no state change of its own: no direct call to the User_Pool, the Portal_Identity_Registry, the edge credential table or the Account_Sync_Service, and no change to the User_Admin_Handler, the `user-admin-api-stack.ts` routes or the frontend.
4. THE Account_Lifecycle_Tools SHALL be served on the aggregate endpoint and on the Admin_View, and a `tools/call` naming one of them on the `data`, `models`, `devices` or `workflows` view SHALL be refused `Unknown tool` as every out-of-view call is.
5. THE following SHALL NOT be added by this spec: tools for `POST /admin/users/{username}/password` and `POST /admin/users/{username}/forgot-password` (credential material, mcp-servers Requirement 5.5); resend-invitation and MFA-management tools (no Portal_API route exists for either); a second form of the role change, role assignment, role removal, account listing or edge sync (all exist since Phases 1 and 3); bulk or multi-account operations; any edge (LocalServer) tool or change.

### Requirement 2: Caller — PortalAdmin Only

**User Story:** As a Portal administrator, I want the account tools usable only by a PortalAdmin acting at the account level, so that no Use_Case role and no assistant acting for one can change who has Portal access.

#### Acceptance Criteria

1. THE Tool_Catalog SHALL declare `permissions=('manage_users',)` and `scope='global'` on each Account_Lifecycle_Tool, and THE Portal_MCP_Server SHALL evaluate that declaration through the RBAC_Layer before dispatch, as for every other tool; `manage_users` is held by PortalAdmin only, so the declared role set equals the set the User_Admin_Handler admits (`require_portal_admin`), and the per-row handler set recorded in `test_mcp_catalog_permissions.py` SHALL be `{PortalAdmin}` for all four.
2. IF the Principal's effective account-level role is not PortalAdmin — a UseCaseAdmin, DataScientist, Operator, Viewer or DataLabeler, a Principal with no Portal_Identity row, or a Principal whose Use_Case rows name PortalAdmin while its global row does not — THEN THE Portal_MCP_Server SHALL answer `not_authorized`, SHALL not dispatch, and SHALL record exactly one `unauthorized_access` Audit_Log entry carrying the MCP_Audit_Marker.
3. WHILE the Principal's own global Portal_Identity row carries `status` disabled, THE Portal_MCP_Server SHALL treat the Principal as holding no role (as the RBAC_Layer does under registry enforcement) and SHALL deny every Account_Lifecycle_Tool; the token's `custom:role` claim SHALL grant nothing.
4. IF the Portal_Identity_Registry cannot be read during the check, THEN THE Portal_MCP_Server SHALL answer `authorization_unavailable`, SHALL not dispatch, and SHALL record one `authorization_unavailable` entry, matching the handler's own 500 behaviour.
5. WHERE `PORTAL_REGISTRY_ENFORCED` is off, THE Portal_MCP_Server SHALL resolve the role as it does for every other `global`-scoped tool (the documented D29 behaviour accepted at the Phase-1 sign-off, item (e)); this spec adds no resolution rule.
6. THE Account_Lifecycle_Tools SHALL take no `usecase_id` argument and SHALL offer no argument, header or mode that changes the Principal, elevates the role, or addresses an account on another Principal's behalf.

### Requirement 3: Self-Protection and the Handler's Guards

**User Story:** As a PortalAdmin, I want an assistant acting for me to be unable to lock me out or to remove the Portal's last administrator, so that a misunderstanding in a conversation cannot cost the Portal its administration.

#### Acceptance Criteria

1. WHEN `portal_admin_account_disable` or `portal_admin_account_delete` names the Principal's own Account — `account_username` equals any identifier the User_Pool resolves to the calling Principal, that is its username or its email sign-in alias — THE Portal_MCP_Server SHALL refuse the call before dispatch (the Self_Protection_Rule), SHALL invoke no handler, SHALL answer the error category `conflict` with a message stating that a principal cannot disable or delete its own account, and SHALL record exactly one marked Audit_Log entry for the refusal. (Assumption: `conflict` is proposed because the handler's Last_PortalAdmin_Guard, the sibling rule, also answers 409; the design may argue for `invalid_input`. No new error category is added.)
2. THE Self_Protection_Rule SHALL be evaluated after the pre-dispatch RBAC check and before dispatch, so a non-PortalAdmin naming itself is still answered `not_authorized`, and SHALL apply whatever the value of `confirm`.
3. THE Self_Protection_Rule SHALL apply to disable and delete only: `portal_admin_account_enable` and `portal_admin_account_create` naming the Principal's own username SHALL be dispatched and answered by the handler (an enable of an already-enabled account is a No_Op_Completion; a create of an existing username is 409).
4. THE Portal_MCP_Server SHALL NOT re-implement the Last_PortalAdmin_Guard: WHEN the User_Admin_Handler rejects a disable or deletion with 409 because the target is the last remaining enabled PortalAdmin, THE Portal_MCP_Server SHALL answer `conflict` carrying the handler's reason text, and the handler's `rejected` audit entry SHALL be the record of the attempt (marked, as every handler entry written under MCP is).
5. THE Portal_MCP_Server SHALL mirror, not re-implement, every other invariant the User_Admin_Handler enforces, by mapping the handler's answer to the shared error vocabulary: 400 (field validation, email shape, unknown role) → `invalid_input`; 404 (no such account) → `not_found`; 409 (duplicate username on create) → `conflict`; 500 and 502 (User_Pool failure, failed pending-audit write, partial provisioning, incomplete disable or enable, partial deletion) → `backend_failure`; and a No_Op_Completion → a successful result whose `changed: false` is returned to the caller unchanged.
6. WHEN the User_Admin_Handler answers a partial-state 502 whose `message` carries a recovery step ("delete the account and retry", "retry the disable", "removed on a subsequent attempt"), THE tool result's message SHALL carry that text (scrubbed as every backend message is), not only the short `error` label, so the caller learns what remains to be done.
7. THE Account_Lifecycle_Tools SHALL add no effect and skip no effect of the handler: the invitation email the User_Pool sends on create, the Portal_Identity row writes, the device sync staging and the edge credential record removal happen exactly as they do for the User Manager page, and the tools SHALL add no restriction beyond the Self_Protection_Rule (for example, creating a PortalAdmin account or disabling an account other than the caller's is allowed when the handler allows it), per mcp-servers Requirement 1.3.

### Requirement 4: Classification, Confirmation and the Mutating Switch

**User Story:** As a Portal administrator, I want account creation marked as state-changing and account disable, enable and delete marked as destructive with an explicit confirmation, all behind the deployment-level switch, so that an assistant cannot change an account's standing in a single unconsidered step or on a deployment that has not opted in.

#### Acceptance Criteria

1. THE Tool_Catalog SHALL classify `portal_admin_account_create` as a Mutating_Tool that is not destructive and not idempotent (`classification=MUTATING`, `destructive=False`, `idempotent=False`; annotations `readOnlyHint` false, `destructiveHint` false, `idempotentHint` false; rendered description ending in `MUTATING.`).
2. THE Tool_Catalog SHALL classify `portal_admin_account_disable`, `portal_admin_account_enable` and `portal_admin_account_delete` as Destructive_Tools (`classification=MUTATING`, `destructive=True`, `confirm_target='account_username'`, `idempotent` left at its default) whose rendered descriptions end in `MUTATING, DESTRUCTIVE — requires confirm=account_username.`; enable is destructive because it re-grants Portal privilege and, at the next sync, local login on every device whose staged set holds the account.
3. THE three Destructive_Tools SHALL carry the `confirm` property exactly as the existing destructive rows do (`confirm_arg('Repeat account_username.')`, type string, not listed in `required`), and IF `confirm` is absent or differs from `account_username`, THEN THE Portal_MCP_Server SHALL answer `confirmation_required`, SHALL not dispatch, and SHALL record one marked Audit_Log entry.
4. THE four Account_Lifecycle_Tools SHALL be gated by the Mutating_Switch: WHILE it is off, THE Portal_MCP_Server SHALL omit them from `tools/list` on every endpoint and SHALL answer `mutating_tools_disabled` (with one marked entry) to any call; the switch's default SHALL stay false, and the deployed stack SHALL run with it off outside an Exercise_Window.
5. THE four rows SHALL name `portal_admin_accounts_list` as their `status_tool` (the family has no single-account read tool; the listing carries `enabled`, `role`, `email` and the account's presence), and a post-dispatch `timeout` or `backend_failure` SHALL carry `effect: "unknown"` and that `status_tool`, per D32.
6. THE destructive list of this spec — the three Destructive_Tools, with `portal_admin_account_create` listed beside them as the mutating non-destructive tool — SHALL be signed off by the owner before the rows are delivered, as every phase's destructive list was.

### Requirement 5: Every Call Audited

**User Story:** As a Portal administrator, I want every account tool call — allowed, refused or failed — in the existing Audit_Log with the MCP marker and the target account named, so that I can reconstruct who changed which account through which assistant.

#### Acceptance Criteria

1. WHEN an Account_Lifecycle_Tool call completes with any outcome, THE Audit_Log SHALL hold at least one entry for it, every such entry SHALL carry the MCP_Audit_Marker (`channel='mcp'`, `mcp_tool`, `mcp_server` naming the server and its version, `mcp_client`, `mcp_request_id`) and the Attribution_Fields (`username`, `email`, `source_ip`, `user_agent`, `identity_source`), and no completion SHALL leave an unmarked entry (Property 6).
2. WHEN a call succeeds and the handler writes its own entry, THE record SHALL be the handler's entry as the User Manager writes it, marked through the request audit context and not duplicated by the MCP layer: `action` `account_create` (details `email`, `role`, `created_user_id`, `registry_entry`), `account_disable` / `account_enable` (details `enabled`), or `account_delete` (details `email`, `role`), each with `resource_type='user_account'`, `resource_id` = the target username, `user_id` = the caller's `sub`, and `result` finalized from `pending` to `success`.
3. WHEN a disable or enable call is a No_Op_Completion, THE Audit_Log SHALL still receive exactly one marked entry for the call (the MCP `mcp_tool_call` envelope, `result='success'`, `details.status` 200), because the handler writes none on that branch; the design SHALL use the existing branch-conditional mechanism (`handler_audits=False` pinned with its reason) or state an equivalent, and a changed disable or enable MAY therefore leave the handler's entry plus the envelope, the documented exception to the `max(k, 1)` count.
4. WHEN a call ends before dispatch in `invalid_input`, `confirmation_required`, `mutating_tools_disabled` or the Self_Protection_Rule's `conflict`, THE Audit_Log SHALL receive exactly one `mcp_tool_call` envelope with `result='failure'` and `details.error_category` naming the category; WHEN it ends in `not_authorized` or `authorization_unavailable`, THE record SHALL be the one `unauthorized_access` or `authorization_unavailable` entry of Requirement 2.
5. WHEN a dispatched call is answered with a non-2xx status, THE Audit_Log SHALL receive the `mcp_tool_call` envelope (`result='failure'`, `details.status`, `details.error_category`) and, where the handler wrote one, the handler's own `failure` or `rejected` entry, both marked.
6. THE `mcp_tool_call` envelope of every Account_Lifecycle_Tool SHALL carry in `details` the fields `tool`, `status`, `duration_ms`, `error_category` (on failure) and the target `account_username`, plus `role` for `portal_admin_account_create` (through `audit_args`), and its `resource_id` SHALL be the target username rather than `collection`; the design SHALL state how the username reaches `resource_id` for a tool whose target argument does not end in `_id`.
7. THE audit-before-effect ordering of the handler SHALL be preserved: IF the handler's pending audit write fails, THEN the action is not applied (the handler's 500), the tool answers `backend_failure`, and THE Portal_MCP_Server SHALL not retry the dispatch (D32, one attempt).
8. THE existing sanitization (`sanitize_audit_details`) SHALL apply to every detail recorded; no argument of the four tools carries credential material (the User_Pool generates and delivers the temporary password itself), and no tool result, audit detail or log line SHALL contain a password, temporary password or token.
9. WHEN a PortalAdmin queries `portal_admin_audit_logs_query` with `channel='mcp'` and `mcp_tool` set to one of the four names, THE result SHALL contain the entries of Requirements 5.2–5.5 for that tool; these entries are the evidence of the live exercise (Requirement 9).

### Requirement 6: Tool Contracts

**User Story:** As a user of an MCP client, I want each account tool to take exactly the inputs the User Manager form takes, validate them before anything runs, and return what the Portal returns, so that I can drive account administration without reading the REST API.

#### Acceptance Criteria

1. THE input schema of `portal_admin_account_create` SHALL have exactly the properties `account_username` (required; → body `username`), `account_email` (required; → body `email`) and `role` (required; → body `role`; an enum of the six Portal_Role values in `PORTAL_ROLES` order), with `additionalProperties: false`; the names `username` and `email` are claim-named and SHALL NOT be argument names.
2. THE `account_username` property of all four tools SHALL carry the catalog's path-parameter identifier pattern (no `/`, not `.` or `..`, 1–256 characters), on the create tool as well, so that every account the create tool can create is addressable by the three path-parameter tools; IF a value fails the pattern, THEN the answer is `invalid_input` naming the property.
3. THE `account_email` property SHALL be a string of at most 254 characters whose schema pattern is no looser than the handler's rule where a pattern can express it (a non-empty local part, one `@`, a domain containing a dot); the handler's own check stays authoritative and its 400 maps to `invalid_input`.
4. THE input schemas of `portal_admin_account_disable`, `portal_admin_account_enable` and `portal_admin_account_delete` SHALL have exactly the properties `account_username` (required; → path `username`) and `confirm`, with `additionalProperties: false`.
5. WHEN a call succeeds, THE tool result SHALL be the handler's response body shaped as an object: create → `username`, `email`, `role`, `message` with `resource_id` = the created username; disable and enable → `username`, `enabled`, `changed`, `message`; delete → `username`, `email`, `role`, `deleted`, `message`; no result SHALL contain a password or temporary password.
6. THE rendered description of each tool SHALL state what it does and its consequences in the D35 format (base sentence, `Touches: account`, classification): create states that the User_Pool sends an invitation email with a temporary password to `account_email`; disable states that the account loses Portal privilege on its next request and is marked disabled on synced devices at the next sync; enable states the reverse; delete states that the account, its Portal registry rows and its edge credential record are removed and that synced devices drop it at the next sync.
7. THE Account_Lifecycle_Tools SHALL offer no pagination arguments and no `usecase_id`, and THE Portal_MCP_Server SHALL forward every argument other than `confirm` to the route (`confirm` is server-consumed), so the catalog argument test holds.

### Requirement 7: Catalog Honesty and the Mirrors

**User Story:** As the repository owner, I want the four rows held to the handlers and reflected in every mirror by the same suites that hold the other 183 rows, so that the catalog, its exports, the documentation tables and the design tables cannot disagree.

#### Acceptance Criteria

1. ## Non-Negotiable Constraints

The constraints C1–C8 of the mcp-servers requirements apply unchanged (existing credentials only; no new identity store; no secrets in configuration; RBAC on every call; audit on every action; steering compliance; additive and reversible; the security posture). This spec adds:

- **N1 No REST change.** `user_admin.py`, `user-admin-api-stack.ts`, the shared layer's audit and RBAC code and the frontend are not modified; the trunk backend suite count stays at its baseline.
- **N2 No edge change.** No file under `src/`, `test/backend-test/`, `station_install/` or the recipes changes; no component build; no device access.
- **N3 No new infrastructure permission.** No IAM statement, no dispatch-map key (`userAdmin` exists), no new CDK resource; the only CDK diff is the MCP Lambda asset and its `MCP_SERVER_VERSION` value, plus the switch value during the Exercise_Window.
- **N4 No credential material.** No password, temporary password, verifier or token crosses the MCP boundary in an argument, result, audit detail or log line; the password and forgot-password routes stay excluded.
- **N5 Switch off by default.** The Mutating_Switch default stays false; it is turned on only for an Exercise_Window on the owner's go and restored at its end; every live write of this spec (deploy, exercise, push) is owner-gated by number.
- **N6 One source per row.** Each of the four rows is authored once in `catalog.py` and once in this spec's design table; every mirror is regenerated or updated in the same commit.
- **N7 Public wording.** Neutral tone in every committed file (Requirement 10.5); the hygiene gate runs on every commit.

## Proposed Answers to the Open Points (for the requirements gate)

1. **Scope and non-scope.** Four tools — `portal_admin_account_create`, `portal_admin_account_disable`, `portal_admin_account_enable`, `portal_admin_account_delete` — wrapping the four registered `/admin/users` routes in the `admin` view. Not in scope: password set and forgot-password (credential material), resend invitation and MFA (no routes), role change / role assign / role remove / accounts list / edge sync (exist), bulk operations, any REST, frontend or edge change.
2. **Names.** The `account` stem, as in `portal_admin_accounts_list`, `portal_admin_account_role_change` and Backlog 31; the brief's working names `portal_admin_user_*` are not used because the `user` stem addresses Portal_Identity role rows by `user_id`.
3. **Caller.** `manage_users` at the `global` scope — PortalAdmin only, decided pre-dispatch by the RBAC_Layer; every Use_Case role, a missing row and a disabled row are denied `not_authorized` with one marked `unauthorized_access` entry; registry outage → `authorization_unavailable`.
4. **Self-protection.** A Principal cannot disable or delete its own account (by username or by its email alias): refused by the Portal_MCP_Server before dispatch, category `conflict`, one marked entry; the Last_PortalAdmin_Guard stays the handler's and its 409 maps to `conflict` with the handler's reason — mirrored, not re-implemented.
5. **Classes and confirm.** Create = mutating, not destructive, not idempotent; disable, enable, delete = destructive with `confirm=account_username` in the exact existing convention (`confirm_arg`, `confirm_target`, `confirmation_required`); `status_tool` = `portal_admin_accounts_list` for all four.
6. **Mutating switch.** All four behind `MCP_MUTATING_TOOLS_ENABLED`: not listed and `mutating_tools_disabled` while off; default stays false; on only for the Exercise_Window.
7. **Audit payload.** Every completion ≥ 1 marked entry (marker: `channel`, `mcp_tool`, `mcp_server`, `mcp_client`, `mcp_request_id`; attribution: `username`, `email`, `source_ip`, `user_agent`, `identity_source`); success = the handler's `account_create`/`account_disable`/`account_enable`/`account_delete` entry (`user_account`, `resource_id` = username, details `email`/`role`/`created_user_id`/`registry_entry` or `enabled`); refusals and failures = the `mcp_tool_call` envelope (`tool`, `status`, `duration_ms`, `error_category`, `account_username`, `role` on create; `resource_id` = username); the no-op disable/enable gets the envelope through the existing `handler_audits` pin; denials = one `unauthorized_access`.
8. **Catalog honesty.** Rows in `catalog.py`, exports regenerated, the two route tests flipped from "absent" to "present" in the same commit, every honesty suite over the rows, view tests (admin and aggregate only; `Unknown tool` elsewhere), RBAC matrix, guardrails and Property 6 extended; ADMIN_GUIDE admin table 15 → 19 and docs check at 187 portal tools; the rows live in this spec's design table, the mcp-servers design is annotated only, and the recount expectation becomes mcp-servers unchanged + 4.
9. **Versioning.** `phase=4` on the rows, `DELIVERED_PHASES` → `(1, 2, 3, 4)` in the delivering commit, `__version__` and `MCP_SERVER_VERSION` `1.2.0` → `1.3.0`; no separate gate constant; edge unchanged.

## Decisions Left to the Design

- How the Self_Protection_Rule compares the target with the Principal (the username and email the server already knows for the caller, or a target lookup) and the final error category (`conflict` proposed).
- The mechanism that gives a No_Op_Completion its one marked entry (`handler_audits=False` pinned with a reason, as the four existing branch-conditional rows are, or an equivalent).
- How the handler's `message` reaches the caller on partial-state 502s (Requirement 3.6) without changing the error text of other tools' results.
- How `resource_id` becomes the target username on the envelope for an argument not ending in `_id` (Requirement 5.6), and whether the envelope's `resource_type` stays `account` (as the existing `/admin/users` rows) or becomes the handler's `user_account`.
- The exact `account_email` schema pattern, the test-count deltas, the live-exercise identities and sequence, and the exact recount and docs-check numbers after the change.

- A single-account read tool (`portal_admin_account_get`); the listing serves as the `status_tool`.
- Edge (LocalServer) tools, builds or device verification; the edge MCP server keeps `DELIVERED_PHASES = (1, 2, 3)`.
- `portal_models_delete` (mcp-servers Backlog 1; a separate owner decision) and every other open mcp-servers backlog item.
- Changes to the audit-log query's indexing (mcp-servers Backlog 30) or the audit UI.
- Any implementation, deploy, AWS call, device access, push or commit in the spec-authoring run that produces this document.
