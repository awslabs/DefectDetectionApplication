# Design Document: MCP Account-Lifecycle Tools (`mcp-user-operations`)

## Overview

This design adds the four account-lifecycle operations of the Portal's User Manager to the Portal_MCP_Server as Phase-4 tools of the `admin` view: `portal_admin_account_create`, `portal_admin_account_disable`, `portal_admin_account_enable` and `portal_admin_account_delete`. Each is one more `ToolSpec` row of the existing declarative catalog, dispatched through the existing Lambda-to-Lambda pipeline to the registered `/admin/users` routes of the User_Admin_Handler (`user_admin.py`), so the handler's PortalAdmin gate, validation, audit-before-effect ordering, Last_PortalAdmin_Guard, Portal_Identity writes and device-sync staging run unchanged (mcp-servers D4, D5, D6). The design settles what the mcp-servers design left to this spec (its Backlog 31): the rows and their classification (create `M`; disable, enable and delete `M!` with `confirm=account_username`), the PortalAdmin-only permission (`manage_users` at the `global` scope), the audit rows per outcome, and one new pre-dispatch rule, the Self_Protection_Rule (a Principal cannot disable or delete its own Account through MCP), evaluated between the RBAC check and dispatch by the shared tool pipeline (`mcp_portal/pipeline.py:call_tool`), which the MCP server and the Portal assistant both run.

Four small, generic additions to the `mcp_portal` package carry the four rows: a `ToolSpec.self_protect_arg` field read by a new step 5b of the request pipeline (`pipeline.py:call_tool`), which reads the caller's email address from the User_Pool on the very call it decides (a `refresh` keyword on `principal.lookup_email`, whose result becomes an `EmailLookup(email, failed)` tuple so that a failed lookup is told from an account that has no email attribute, and step 5b fails closed only when a retry can help), a `ToolSpec.resource_id_arg` field read by the envelope's `resource_id` rule (`audit.py`), and a `ToolSpec.error_detail_key` field read by the backend-status mapping (`errors.py`, `shaping.py`) so the handler's recovery text on a partial-state 502 reaches the caller. Everything else is catalog data, exports, tests and documentation. The four rows carry `phase=4`; `mcp_portal.DELIVERED_PHASES` becomes `(1, 2, 3, 4)` and the server version `1.2.0` → `1.3.0` in the commit that delivers them, which keeps `DELIVERED_PHASES` the only phase gate. The portal catalog grows from 183 to 187 delivered tools (the design tables of the two specs together describe 188 portal tools in 165 rows, `portal_models_delete` still deferred); the edge MCP server does not change. The delivery follows the mcp-servers phase shape: entry criteria, the owner's destructive-list sign-off, a scoped deploy of `EdgeCVPortalMcpStack`, one live exercise against throwaway identities inside a bounded Exercise_Window with the Mutating_Switch on, and the release. This is the fifth revision. Revision 5 (tasks.md task 1.2, before any code) applies the three NIT findings of the review that approved revision 4: a budget guard before the step-5b read, `principal.sub` as a third exact comparison of the Self_Protection_Rule, and the official `mcp` Python SDK client as the live exercise's only client. It also applies owner decision 2a (2026-11-04): step 5b sits in `pipeline.call_tool`, so the MCP server and the Portal assistant both enforce the rule. That placement follows the tree the implementation starts from, `3fa572f5` (the merge of PR #128, which brought the Portal assistant's Phase 1, PR #126, onto `main`), where steps 3–9 of the pipeline moved from `server.py:on_call_tool` into `pipeline.call_tool`; the pipeline research bullet below is re-read at that commit, and tasks.md task 1.1 records every other citation and baseline re-verified there. The responses to the four design reviews are the last sections; the requirements document (approved at its gate) is the baseline for every decision below.

### Technology stack (locked)

Unchanged from the mcp-servers spec, with no new dependency: Python 3.11 on Lambda with the `mcp` SDK 2.3.0, `jsonschema` (Draft 2020-12), `boto3`/`botocore` and the SharedLayer (`shared_utils`); the catalog as frozen `ToolSpec` dataclasses; the CDK stack in TypeScript (`aws-cdk-lib`); tests with pytest, Hypothesis and moto under `edge-cv-portal/backend/tests/mcp/`, and jest for the infrastructure; `python -m mcp_portal.catalog --export-routes` for the two JSON exports.

- **The pipeline today** (at `3fa572f5`). `server.py:on_call_tool` runs 1 authenticate and 2 lookup (unknown, undelivered or out-of-view → `-32602 Unknown tool`), builds the call's `McpContext` (`server.py:190–192`) and runs steps 3–9 as `pipeline.call_tool(spec, args, principal, ctx, *, mutating_enabled, view, server_version, event_name)` (`pipeline.py:166`) on a worker thread (`anyio.to_thread.run_sync`); `call_tool` is synchronous and imports no `mcp` SDK symbol. It runs 3 validate (schema, then `confirm`; `validation_failure` and `confirmation_failure` live in `pipeline.py`, and `server.py` re-exports them), 4 gate (`mutating_tools_disabled` unless the caller's `mutating_enabled`), 5 authorize (`authz.authorize`, which writes the denial entry itself and returns the Identity_Source), 6 dispatch (`dispatch.invoke`, one `Invoke` attempt after its own budget check, read timeout 20 s), 7–9 shape (`shaping.shape`), audit (`audit.write_envelope`) and log. `finish(failure, dispatched, status, shaped, event, identity_source)`, a closure in `call_tool`, is the one exit that writes the envelope and the telemetry line (`mcp_tool` on the MCP server; the caller's `event_name` names it); a denial or an unavailability returns its `ToolOutcome` without it; every `ToolFailure` that `dispatch.invoke` returns (`timeout`, `throttled`, the transport and payload `backend_failure`s) goes through `finish(response, dispatched=True, status=None, …)`, so the envelope's `details.status` is `null` for all of them while the result's `status` carries the failure's own value (`429` on `throttled`, `null` otherwise). The Portal assistant (`assistant/turn.py`) calls `pipeline.call_tool` in-process with a `Principal` from `principal_from_claims` (the ID token's `cognito:username` and `email` claims; `lookup_email` only when the `email` claim is missing), an `McpContext` with `channel='assistant'`, `mutating_enabled` from its own actions switch and `event_name='assistant_tool'`. It offers a mutating row only when the row is not destructive or is on its destructive allow-list (`assistant/tools.py:mutating_allowed`), and that list is empty (owner decision 3a), so of the four Phase-4 rows only `portal_admin_account_create` can reach it once delivered (owner decision 4a). `dispatch._remaining_ms()` reads `dispatch.LAMBDA_CONTEXT`, which only the MCP Lambda's handler sets (`handler.py:110`), so in the assistant worker it is `None` and the dispatcher's budget check does not apply; the worker's role holds no `cognito-idp` permission (`assistant-stack.ts`). `Principal` (`principal.py`) carries `sub`, `username` (the access token's `username` claim; `cognito:username` in the assistant) and `email` from `lookup_email`, a per-container cache over `cognito-idp:AdminGetUser` keyed by `sub` (in the assistant, usually the ID token's `email` claim). The address travels to every audit entry of the call from one place: `McpContext.principal_email`, which the caller of `call_tool` sets (the MCP server from `principal.email` when it builds the context after step 2, `server.py:190–192`), is carried by `marker_event` and the dispatched event's `mcp` block (`audit.py:96–97`, `dispatch.py:142–143`), and `shared_utils.attribution_from` reads `mcp.principal_email` as the email candidate for the envelope and for every entry the handler writes on that call (`shared_utils.py:385`); the telemetry line carries no email (`telemetry.FIELDS`). `lookup_email` yields the literal `'unknown'` on **two** paths: when `AdminGetUser` raised (WARNING; **not cached**, so the next call re-attempts the lookup), and when it succeeded but the account has no `email` attribute or an empty one (**cached**, like any other successful lookup; `test_mcp_authz.py::test_account_without_email_is_unknown` pins the value). The pool requires `email` at sign-up, but `AdminCreateUser` does not enforce required attributes, so an account without an email attribute is possible; the Self_Protection_Rule must tell the two paths apart (A4). The cache (`_EMAILS`, 1,024 entries, oldest evicted first) has no expiry, so a cached address is stale from the moment the account's own `email` attribute changes until the entry is evicted or the container is replaced; the Self_Protection_Rule therefore does not read it (A4). The MCP Lambda's role already holds `cognito-idp:AdminGetUser` on the pool (`mcp-stack.ts`, statement `ReadPrincipalEmail`), the one permission the lookup needs; the module's `cognito-idp` client is configured with a 2 s connect and 5 s read timeout and two attempts.

### Design decisions

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| A1 | Names and stem | `portal_admin_account_create` / `_disable` / `_enable` / `_delete` (D22; the `account` stem of `portal_admin_accounts_list`, `portal_admin_account_role_change` and Backlog 31) | The `user` stem (`portal_admin_users_list`, `portal_admin_user_permissions_get`, `portal_admin_role_assign`/`_remove`) addresses Portal_Identity role rows by `user_id`; these tools address User_Pool accounts by username (Requirement 1.2) |
| A2 | Delivery as Phase 4 of the existing server | The rows carry `phase=4`; the delivering commit sets `mcp_portal.DELIVERED_PHASES = (1, 2, 3, 4)`, `__version__ = '1.3.0'` and `MCP_SERVER_VERSION = '1.3.0'` (`mcp-stack.ts:113`); no second gate constant | `DELIVERED_PHASES` is documented as the only phase gate; `tools_for_view`, the call lookup, `catalog_tools.json`, the docs tables, the docs check, the harness and the undelivered-tool protocol case all key on a numeric phase per tool, so a fourth value fits every mirror, while a second constant would add a second gate to each (Requirement 8.1). New tools without a changed contract are a minor bump, as `1.0.0 → 1.1.0 → 1.2.0` were (8.2) |
| A3 | Caller | `permissions=('manage_users',)`, `scope='global'` on all four, evaluated pre-dispatch by `authz.authorize` as for every row | `manage_users` is held by PortalAdmin only, so the declared role set equals the set `require_portal_admin` admits (Requirement 2.1); the handler's own gate still runs after dispatch (D5, defence in depth); the recorded handler set in `test_mcp_catalog_permissions.py` is `{PortalAdmin}` for all four |
| A4 | **Self_Protection_Rule mechanism** | A new field `ToolSpec.self_protect_arg: Optional[str]` (set to `'account_username'` on the disable and delete rows) and a new pipeline step **5b** in `pipeline.call_tool` (revision 5, owner decision 2a: the pipeline the MCP server and the Portal assistant share), after `authorize` and before `dispatch`. For a spec with the field set, step 5b first applies the dispatcher's budget rule (the remaining Lambda time known and below `MIN_DISPATCH_BUDGET_MS` → the pre-dispatch `timeout` with `BUDGET_MESSAGE`, without the read), then reads the caller's email address from the User_Pool **on this call**: `principal.refresh_email(principal)`, that is `lookup_email(sub, username, refresh=True)`, which skips the per-container cache read, makes the `AdminGetUser` call, writes the cache on success and returns an `EmailLookup(email, failed)` named tuple (Data Models). It then decides, in this order: `args[self_protect_arg]` equal to the Principal's `username` or to its `sub` → refused `ToolFailure('conflict', 'a principal cannot disable or delete its own account', status=409)`; the lookup failed (`AdminGetUser` raised; nothing cached) → refused `ToolFailure('backend_failure', "the caller's account email could not be resolved, so the self-protection rule cannot be evaluated; retry")`; the lookup returned an address and the target equals it → the same `conflict`; otherwise — no match, or the account has no email attribute (`'unknown'` with `failed` False), so no alias exists — the call proceeds to dispatch. All three comparisons are exact string equality. A refusal invokes nothing; `finish(…, dispatched=False)` writes one marked envelope. `Principal` is unchanged: `Principal.email` stays the step-1 value (cached, used for the attribution fields and `portal_admin_whoami`) and is **not** what step 5b compares against; enable, create and every other row make no second lookup | The identifiers the User_Pool resolves to the caller are the `username` claim (D3, verified) and the account's **current** `email` attribute. That it resolves no third one, the `sub`, is a reading of the Cognito documentation of the admin calls' `Username` parameter that the repository cannot show, so the premise is unverified; the `sub` comparison makes it not matter: a target equal to the caller's `sub` (the `account_username` pattern admits one) is refused whichever identifiers the pool resolves, with no read and no new message (design review of revision 4, finding 2). The server's cached copy of the latter (`principal.email`) is stale from the moment the caller's own email attribute changes, and a disable or delete addressed by the new alias would pass a cached comparison and reach the handler — the outcome Requirement 3.1 (a SHALL over "any identifier the User_Pool resolves to the calling Principal") exists to prevent (design review of revision 2, finding 2). Reading the address on the call closes that path at the cost of one `AdminGetUser` per disable or delete call — a rare, destructive, PortalAdmin-only operation — through the IAM statement the attribution lookup already holds (`ReadPrincipalEmail`, no IAM change, N3). The requirements left the comparison basis to the design ("the username and email the server already knows for the caller, or a target lookup"): a fresh read of the caller's own address is the first option made exact, and it keeps the User_Pool call about the caller, not the target. Requirement 1.3's "no direct call to the User_Pool" is read as the enumeration of the state changes the sentence forbids ("SHALL perform no state change of its own: no direct call to …"): the lookup is a read of the caller's own attributes, the same read step 1 already makes on every call, and the target lookup the requirements themselves leave open would be a read of the same kind (the owner can object to this reading at the design gate). The username and `sub` comparisons come first so that a self-disable by either is refused `conflict` even while the pool cannot be read. Exact comparison is the pool's own rule: `dda-portal-users` is created without `signInCaseSensitive`, whose CDK default is case-sensitive, so a differently-cased string names another account or none and the handler answers for it (pinned by a jest assertion, Testing Strategy, and observed once live, row 7 of the exercise). Fail-closed on a **failed** lookup because the alias is unknown at that moment, while the failure is transient and uncached, so "retry" is meaningful. Not fail-closed on a missing attribute because such an account has no alias to compare and would otherwise be refused permanently with a retry message that never helps (design review of revision 1, finding 1); the tuple, rather than a distinct cached sentinel such as `''`, keeps `Principal.email`, `portal_admin_whoami`, the attribution fields and the two pinned `'unknown'` tests unchanged. The alternative of keeping the cached comparison and accepting the stale-alias case as a documented limitation (option (b) of the review) was not taken: it would leave a SHALL partially met for the sake of one read that costs nothing new. `conflict` (409) because the sibling rule, the Last_PortalAdmin_Guard, also answers 409 and because the refusal is a state conflict of the request with the caller's own standing, not an invalid property (Requirement 3.1; the `status=403` precedent of the pre-dispatch `not_authorized` result carries the status the handler would have answered). The budget guard (design review of revision 4, finding 1) applies `dispatch.invoke`'s own rule one step earlier: in every case it refuses, the dispatcher would have refused the call at step 6 anyway (the remaining time only decreases), so no outcome that would have reached the handler changes, and after a slow, uncached step-1 lookup it removes the second User_Pool wait that could outlast the 29 s Lambda timeout and lose the envelope. Step 5b sits in `pipeline.call_tool` rather than in `server.py:on_call_tool` (owner decision 2a) so that the rule holds for every caller of the pipeline; in the Portal assistant, which no destructive Phase-4 row reaches today (its destructive allow-list is empty, owner decision 3a), `_remaining_ms()` is `None`, so the guard does not apply (nor does the dispatcher's check), and the worker role cannot read the pool, so the rule fails closed there (Backlog 7) |

## Architecture

Nothing new is deployed: the four tools are rows of `mcp_portal.catalog.CATALOG`, served by the existing `EdgeCVPortalMcpStack` Lambda on `/mcp` and `/mcp/admin`, and dispatched with `lambda:InvokeFunction` to the existing `UserAdminHandler` (backend key `userAdmin`, already in the SSM dispatch map, D30) with a REST-proxy-shaped event whose `requestContext.authorizer.claims` is the verified access-token payload and whose `event['mcp']` block carries the marker (D4, D6). The handler writes its own audit entries through `attribution_from(event, acting_user)`, so they carry the marker without any handler change.

### Request pipeline with the new step (`server.py:on_call_tool` steps 1–2, `pipeline.py:call_tool` steps 3–9)

1. **Authenticate** — unchanged (`server.py`; the Portal assistant builds its Principal from the REST authorizer's ID-token claims).
2. **Lookup** — unchanged: a Phase-4 name is `Unknown tool` while `4 ∉ DELIVERED_PHASES`, and on the `data`, `models`, `devices` and `workflows` views always (`spec.domain != view`) (`server.py`; the assistant offers only the delivered rows its switch and destructive allow-list admit).
3. **Validate** — unchanged (this step and every later one run in `pipeline.call_tool`): `jsonschema` (`invalid_input` naming the property), then for the three `M!` rows `confirm == args['account_username']` (`confirmation_required`).
4. **Gate** — unchanged: `mutating_tools_disabled` while the Mutating_Switch is off (the four are also absent from `tools/list`).
5. **Authorize** — unchanged: `authz.authorize` evaluates `manage_users` at `'global'`; `Denied` → `not_authorized` with the one marked `unauthorized_access` entry; `Unavailable` → `authorization_unavailable` with its entry.
5b. **Self-protection (new; in `pipeline.call_tool`, so the MCP server and the Portal assistant both run it, owner decision 2a).** Only when `spec.self_protect_arg` is set, in this order. First the budget guard: when `dispatch._remaining_ms()` is not `None` and below `MIN_DISPATCH_BUDGET_MS` (24 s), `finish(ToolFailure('timeout', BUDGET_MESSAGE), dispatched=False, identity_source=identity_source)` without the read, which is the refusal `dispatch.invoke` would give at step 6 (Error Handling). Then `lookup = refresh_email(principal)` — `principal.refresh_email`, that is `lookup_email(principal.sub, principal.username, refresh=True)`: no cache read, one `AdminGetUser`, the cache written on success; called directly, because `call_tool` is synchronous and already runs on the worker thread `server.on_call_tool` hands it to, where `authz.authorize` and `dispatch.invoke` run too (in the assistant, on the Turn's own thread) — then `failure = self_protection_failure(spec, args, principal, lookup)`, a pure function beside `validation_failure` and `confirmation_failure` in `pipeline.py`: `None` when `spec.self_protect_arg` is unset, and `None` when `args.get(spec.self_protect_arg)` is absent or not a string (unreachable after step 3, which has already required the property; the function never raises); else, in this order: the target equal to `principal.username` or to `principal.sub` → `ToolFailure('conflict', SELF_PROTECTION_MESSAGE, status=409)`; `lookup.failed` → `ToolFailure('backend_failure', EMAIL_UNRESOLVED_MESSAGE)`; `lookup.email != 'unknown'` and the target equal to `lookup.email` → the same `conflict`; otherwise `None` (this last branch includes the account without an email attribute: `lookup.email == 'unknown'` with `failed` False, no alias to compare). All three comparisons are exact string equality; `principal.email`, the cached step-1 value, is not consulted. A failure returns `finish(failure, dispatched=False, identity_source=identity_source)`: one `mcp_tool_call` envelope (`result='failure'`, `details.status` `null`, `details.error_category`, `resource_id` = the target through A8) attributed through `marker_event` with the Identity_Source step 5 resolved, one telemetry line (`mcp_tool`; `assistant_tool` in the assistant), nothing invoked; the tool result carries `status: 409` on the `conflict` (the status the handler's sibling guard answers) and `null` on the `backend_failure` and on the budget `timeout`.
6. **Dispatch** — unchanged (`build_backend_event`, `invoke`).
7–9. **Shape, audit, log** — unchanged except that `shaping.shape` passes `spec.error_detail_key` to `map_backend_status` (A7) and `audit._resource_id` consults `spec.resource_id_arg` (A8).

The sequence for a successful `portal_admin_account_disable`: client `tools/call` → steps 1–5 pass → 5b finds the time budget sufficient, reads the caller's current address with one `AdminGetUser` and finds the target equal to none of the caller's username, `sub` and address → `Invoke(UserAdminHandler, {httpMethod: POST, resource: /admin/users/{username}/disable, path: /admin/users/<encoded>/disable, pathParameters: {username}, body: '{}', requestContext.authorizer.claims, mcp: {...}})` → the handler's `require_portal_admin` admits the PortalAdmin → `_set_account_enabled` writes the pending `account_disable` entry (marked), disables the pool account, sets the registry row `status`, marks the staged sets, finalizes the entry → 200 `{message, username, enabled: false, changed: true}` → the shaper returns the body with `resource_id` = `body.username` → `audit.write_envelope` writes the envelope too, because the row is pinned `handler_audits=False` (A10) → the `mcp_tool` line → `CallToolResult(structured_content={result, resource_id})`.

## Tool-by-tool contract

Common to all four: `tools/call` on `/mcp` or `/mcp/admin` only; the result on success is `CallToolResult(content=[TextContent(json)], structured_content={result: <body>, resource_id: <body.username>})`; every error is `CallToolResult(is_error=True, content=[TextContent("<category>: <message>")], structured_content={category, message, request_id, status, effect?, status_tool?})` (D21). The result's `status` is the handler's HTTP status on a dispatched call that returned one, `409` on the Self_Protection_Rule's refusal, `403` on `not_authorized`, `429` on `throttled`, otherwise `null` (`timeout`, the transport and payload `backend_failure`s, the unresolved-email refusal, and every other pre-dispatch refusal). The envelope's `details.status` is a different field: the dispatched handler status, or `null` when nothing was dispatched or the dispatch itself failed — so the step-5b refusal reads `409` in the result and `null` in the envelope, and `throttled` reads `429` in the result and `null` in the envelope. A post-dispatch `timeout` or transport `backend_failure` reads "the operation may have been applied; call portal_admin_accounts_list before retrying" with `effect: "unknown"` and `status_tool: "portal_admin_accounts_list"` (D32); a handler status (400–502) carries no `effect` key. The rendered description is `f"{description} Touches: account. {classification_text}"` (D35).

### `portal_admin_account_create`

- **Input schema** (`additionalProperties: false`): `{"account_username": {"type": "string", "pattern": "^(?!\\.{1,2}$)[A-Za-z0-9._:@+=-]{1,256}$", "maxLength": 128, "description": "The new account's username (not an email address; the account's email goes in account_email)."}, "account_email": {"type": "string", "maxLength": 254, "pattern": "^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$", "description": "The account's email address; the User_Pool sends the invitation there."}, "role": {"type": "string", "enum": ["PortalAdmin", "UseCaseAdmin", "DataScientist", "Operator", "Viewer", "DataLabeler"], "description": "The account-level Portal role."}}`, `required: ["account_username", "account_email", "role"]`.
- **Dispatch event**: `httpMethod: 'POST'`, `resource` and `path: '/admin/users'`, `pathParameters: null`, `queryStringParameters: null`, `body: '{"username": …, "email": …, "role": …}'` (`param_map={'account_username': 'username', 'account_email': 'email'}`; `role` under its own name; all three travel in the body because the method is POST and none fills a path parameter).
- **Success**: 201 → `result = {message, username, email, role}`, `resource_id = username`. No password, temporary password or token appears: the handler's body carries none (857–862).
- **Error mapping**: schema → `invalid_input` naming the property; `confirm` supplied → `invalid_input` "confirm is not an argument of portal_admin_account_create"; 400 `Invalid account request` → `invalid_input` "Invalid account request: <message>"; 409 → `conflict` "username already exists: An account with the username <u> already exists"; 500 `Audit log unavailable` → `backend_failure` "Audit log unavailable: The action was not applied"; any other 500 (`{error: 'Internal server error'}`, the handler's catch-all) → `backend_failure` "Internal server error"; 502 `account was not created` → `backend_failure` "account was not created" (the handler's mapping for every User_Pool failure other than a duplicate username, including an `account_email` that is already the verified email of another account — the pool's `email` alias is unique — and an email-shaped `account_username`; the body carries no `message`, so A7 adds nothing and nothing is created); 502 `account was not provisioned` → `backend_failure` "account was not provisioned: The Cognito account <u> was created but its portal registry entry was not written, so it has no portal access; delete the account and retry"; 403 (a race with a role change after the pre-dispatch check) → `not_authorized` "Access denied: PortalAdmin role required", no envelope (the handler's `unauthorized_access` entry is the record).
- **Audit**: success → the handler's `account_create` entry only (`handler_audits=True`; details `username`, `email`, `role`, `created_user_id`, `registry_entry` — `finalize_audit_event` merges the pending `{email, role}` with the final set, so the finished entry has these five keys, the four Requirement 5.2 names among them); every failure → the envelope with `details.account_username` and `details.role`, plus the handler's finalized `failure` entry where the handler got that far.
- **Edge cases**: an `account_email` that another account already holds as its verified email → the pool's alias-uniqueness error (`AliasExistsException`; `email` is an alias attribute and `create_account` sets `email_verified=true`) → 502 → `backend_failure` "account was not created", nothing created (the live exercise pre-checks the address it uses for this reason, Live exercise plan); an email-shaped `account_username` is schema-valid (the pattern admits `@`) and refused by the User_Pool, which does not accept an email-format username in a pool with the email alias → 502 → `backend_failure` "account was not created" (the argument description names the fix: the address goes in `account_email`); a value the pattern excludes (`/`, a non-ASCII letter) → `invalid_input` — such an account is created in the User Manager page, not through MCP; `account_username` equal to the caller's own username → dispatched → 409 `conflict` (Requirement 3.3); creating a `PortalAdmin` is allowed (Requirement 3.7).

### `portal_admin_account_disable`

- **Input schema**: `{"account_username": {"type": "string", "pattern": "^(?!\\.{1,2}$)[A-Za-z0-9._:@+=-]{1,256}$", "description": "The account username, or its email sign-in alias."}, "confirm": {"type": "string", "maxLength": 256, "description": "Repeat account_username."}}`, `required: ["account_username"]`.
- **Dispatch event**: `POST`, `resource: '/admin/users/{username}/disable'`, `path: '/admin/users/<quote(value, safe="")>/disable'` (an email alias travels as `alice%40example.com`), `pathParameters: {username: <value>}` (raw; the handler `unquote`s it, 674–687), `body: '{}'`; `confirm` is server-consumed and never forwarded.
- **Success**: 200 → `result = {message, username, enabled: false, changed: true}` or, for an already-disabled account, `{message, username, enabled: false, changed: false}` (the No_Op_Completion, returned unchanged); `resource_id = username`.
- **Error mapping**: `confirm` absent or ≠ `account_username` → `confirmation_required` "portal_admin_account_disable is destructive; pass confirm=account_username"; the Self_Protection_Rule → `conflict` (409) "a principal cannot disable or delete its own account" (the target equals the caller's username or `sub`, or the address step 5b has just read from the User_Pool); the budget guard before the step-5b read → `timeout` "insufficient time budget to start the backing operation; retry" (`status: null`, nothing ran); the step-5b `AdminGetUser` failed on this call → `backend_failure` "the caller's account email could not be resolved, so the self-protection rule cannot be evaluated; retry" (`status: null`, nothing ran; a target equal to the caller's username or `sub` is still `conflict`); 404 → `not_found` "User not found"; 409 `Disable rejected` → `conflict` "Disable rejected: <u> is the last remaining enabled PortalAdmin account; the portal must retain at least one enabled PortalAdmin"; 500 → `backend_failure` "Audit log unavailable: The action was not applied", or "Internal server error" from the handler's catch-all; 502 `action failed` → `backend_failure` "action failed"; 502 `disable incomplete` → `backend_failure` "disable incomplete: The account <u> was disabled in the user pool but its portal registry entry was not updated, so its portal access is unchanged; retry the disable".
- **Audit**: changed → the handler's `account_disable` entry (details `{enabled: false}`) **and** the envelope (pinned `handler_audits=False`); no-op → the envelope only (`result='success'`, `details.status` 200); the guard's 409 → the handler's `rejected` entry and the envelope; every pre-dispatch refusal → the envelope only.
- **Edge cases**: the target is already disabled → no-op (also the safe outcome of a client retry after a `timeout`); the target is the caller by username, by `sub` or by its current email alias → refused before dispatch; the caller has no email attribute → compared by username and `sub` only, then dispatched; the caller's own `email` attribute changed since the container cached it → the rule compares against the address read on this call, so a disable addressed by the **new** alias is refused `conflict` and one addressed by the **former** address is dispatched (the pool no longer resolves it to the caller: the handler answers 404, or acts on the other account that now holds the address), while every attribution of that call — the envelope's `email` field **and** the `email` field of the entries the handler writes on it — still shows the cached step-1 value (the call's `McpContext.principal_email` is set once from `principal.email` by `server.on_call_tool` and is not rebound by step 5b in `pipeline.call_tool`; it reaches the handler's entries through the event's `mcp` block and `attribution_from`; the `mcp_tool` log line carries no email), and the refreshed address serves from the next call on, because step 5b wrote the cache (Data Models, "The email lookup result and the fresh read"); the target is the last enabled PortalAdmin → the handler's 409; a slow guard count or staged-set scan beyond the 20 s read timeout → `timeout` with `effect: unknown`.

### `portal_admin_account_enable`

- **Input schema**: as disable.
- **Dispatch event**: as disable with `resource: '/admin/users/{username}/enable'`.
- **Success**: 200 → `{message, username, enabled: true, changed: true}` or the no-op `{…, enabled: true, changed: false}`; `resource_id = username`.
- **Error mapping**: `confirmation_required`; 404 → `not_found`; 500 → `backend_failure`; 502 `action failed` → `backend_failure`; 502 `enable incomplete` → `backend_failure` with "… retry the enable". No `conflict` outcome: the Self_Protection_Rule does not apply and the handler has no guard on enable.
- **Audit**: as disable (`account_enable`, details `{enabled: true}`; the envelope always).
- **Edge cases**: the caller's own account named → dispatched; it is enabled (the caller holds a valid token), so the handler answers the no-op; the account's standing on synced devices changes only at the next sync (the handler marks the staged sets).

### `portal_admin_account_delete`

- **Input schema**: as disable.
- **Dispatch event**: `DELETE`, `resource: '/admin/users/{username}'`, `path: '/admin/users/<encoded>'`, `pathParameters: {username}`, `body: null` (no body argument and the method carries none).
- **Success**: 200 → `{message, username, email, role, deleted: true}`; `resource_id = username`.
- **Error mapping**: `confirmation_required`; the Self_Protection_Rule → `conflict` (409) (username, `sub`, or the address read on this call); the budget guard before the step-5b read → `timeout` (pre-dispatch, `status: null`); the step-5b `AdminGetUser` failed on this call → `backend_failure` (pre-dispatch, `status: null`); 404 → `not_found` "User not found: The account <u> was not found"; 409 `Deletion rejected` → `conflict` "Deletion rejected: <u> is the last remaining enabled PortalAdmin account; …"; 500 → `backend_failure` "Audit log unavailable: The action was not applied" (or the catch-all "Internal server error"); 502 `deletion failed` → `backend_failure` "deletion failed"; 502 `partial deletion` → `backend_failure` "partial deletion: The account <u> was deleted but its portal registry entry and its verifier record was not removed; it will be removed on a subsequent attempt" (the leftover list as the handler words it).
- **Audit**: success → the handler's `account_delete` entry only (details `{email, role}`); the partial-cleanup 502 → the handler's entry finalized `success` with `partial_cleanup` **and** the envelope (`result='failure'`, `details.status` 502), both marked; the guard's 409 → the handler's `rejected` entry and the envelope; pre-dispatch refusals → the envelope only.
- **Edge cases**: a second delete of the same account → 404 `not_found` (nothing modified); the caller's own account → refused before dispatch; the last enabled PortalAdmin → the handler's 409; the deleted account's existing MCP session keeps the tools that need no permission until its access token expires (the documented behaviour of the token verifier), while every permission-gated tool is denied from the next call on because its registry rows are gone.

Invariant: `failed` ⇒ `email == 'unknown'`, and `failed` ⇒ nothing was written to the cache by that call. The three states step 5b distinguishes in the tuple `refresh_email` returns (its decision compares the username and the `sub` first, which need no read): an address (`failed` False) — compare it too; `'unknown'` with `failed` False (the lookup succeeded, the account has no email attribute) — nothing more to compare; `'unknown'` with `failed` True — refuse `backend_failure`, and a retry re-attempts the lookup because nothing was cached. The cache (`_EMAILS`, keyed by `sub`, 1,024 entries, per container, no expiry) keeps serving step 1 as today — the attribution fields and `portal_admin_whoami` may show a stale address until a refresh or a miss replaces the entry — and is never the basis of a self-protection decision.

**Attribution on the call that refreshes.** `McpContext.principal_email` is set once by the caller of `pipeline.call_tool` (on the MCP server, from `principal.email` when `server.on_call_tool` builds `mcp_ctx`), and step 5b does not rebind the `ctx` that `call_tool` receives: on the one disable or delete call that performs the fresh read, the envelope's `email` field and the `email` field of every entry the handler writes on that call (both come from `attribution_from` over `mcp.principal_email`) carry the step-1 address, and the next call's step 1 reads the entry step 5b wrote to the cache. The alternative — rebinding `ctx = dataclasses.replace(ctx, principal_email=lookup.email)` in `call_tool` after a successful read with an address, which the `finish` closure and the step-6 `build_backend_event` call would both pick up — was considered and not taken: it adds a branch to the pipeline whose only effect is the attribution of one call, it needs a rule for a read that returns `'unknown'` while the cache holds an address, and the staleness it would remove is the attribution-only property of the cache recorded as Backlog 6. The stale-cache test asserts both fields (Testing Strategy, Property 2 row).

## Correctness Properties

### Property 1: Phase-4 catalog well-formedness

### Property 2: Self-protection decision

*For any* Principal (`username` and `sub` arbitrary identifiers; its cached `email` an arbitrary address or `'unknown'`), any fresh lookup result `lookup = EmailLookup(email, failed)` (an arbitrary address with `failed` False, `('unknown', False)`, or `('unknown', True)`), any schema-valid `account_username` and any `confirm`, and each of the four tools under the switch on and a PortalAdmin registry row: for disable and delete, `self_protection_failure(spec, args, principal, lookup)` returns a `conflict` failure (status 409) iff `account_username == principal.username` or `account_username == principal.sub` or (not `lookup.failed` and `lookup.email != 'unknown'` and `account_username == lookup.email`), a `backend_failure` (status `null`) iff `lookup.failed` and the target is neither the username nor the `sub`, and `None` otherwise — so the decision never depends on `principal.email` (a target equal to the cached address but not to the fresh one is `None`; one equal to the fresh address but not to the cached one is `conflict`), an account without an email attribute (`('unknown', False)`) is compared by username and `sub` only, and a target equal to the literal string `unknown` is dispatched; comparison is exact (a case variant of the username, the `sub` or the address is `None`); for enable and create it always returns `None`; it returns `None` and does not raise for an argument object without the property or with a non-string value; through `on_call_tool`, and through a direct `pipeline.call_tool` with the Portal assistant's context (`channel='assistant'`; owner decision 2a), `lookup_email` is called with `refresh=True` exactly once for a disable or delete that reaches step 5b when the budget allows, and never when the budget guard refuses it (`timeout` with `BUDGET_MESSAGE`), for enable, create or a call refused before step 5b; ## Security considerations

- **C1–C8 and N1–N7.** Existing credentials only (the MCP access token; the handler receives claims, never the token — D4); no new identity store; no secret in configuration (the owner's email address lives in the run's state, not in the repository); RBAC on every call (pre-dispatch and in the handler); audit on every action (the audit table); additive and reversible (rows gated by `DELIVERED_PHASES` and the switch); no REST, frontend, edge or IAM change (N1–N3); no credential material in any argument, result, audit detail or log line (N4: the schemas have no password property, the handler's bodies carry none, `sanitize_audit_details` and `errors.scrub` apply, the `mcp_tool` line never logs arguments); the switch default stays `false` and every live write is owner-gated (N5); one source per row (N6); neutral wording and the hygiene gate on every commit (N7).
- **What the Self_Protection_Rule relies on.** The caller's `username` and `sub` are verified token claims; the caller's `email` is read from the User_Pool by the MCP Lambda's own role (`ReadPrincipalEmail`, `cognito-idp:AdminGetUser` on the pool) on the call that decides — step 5b never reads the per-container cache, so the address compared is the one the pool resolves at that moment. The comparison uses nothing the client supplied except the target string. The rule fails closed when that read failed on the call (and only then: an account without an email attribute has no alias and is compared by username and `sub`). In the Portal assistant the same step runs (owner decision 2a), but the worker role holds no `cognito-idp` permission, so there the read fails and the rule refuses every target other than the caller's username or `sub` with the retryable `backend_failure`; no assistant call reaches that state today, because no destructive Phase-4 row is on the assistant's allow-list (owner decision 3a; Backlog 7). It does not replace the handler's guards and adds no restriction beyond itself (Requirement 3.7).
- **What the rule does not claim.** It governs the MCP channel and the Portal assistant (both run `pipeline.call_tool`); a follow-up may add the same rule to the User Manager (Backlog 1). A PortalAdmin can still disable or delete any other account the handler allows, including another PortalAdmin, subject to the handler's Last_PortalAdmin_Guard.
- **Alias addressing.** Addressing an account by its email alias is the User_Pool's own resolution; the handler's audit entries and results record the string the caller used. The audit table therefore holds the alias on such calls; `portal_admin_accounts_list` shows the canonical username beside the email, so a reader can join them.
- **Enforcement off.** The D29 behaviour applies unchanged (RBAC decision table); the deployed portal runs enforced.
