# Requirements Document

## Introduction

Station Quick Setup lets a portal user register a new edge station from the Edge CV Portal and receive a single one-line shell command to run on the target device. Today an operator must clone the DefectDetectionApplication GitHub repository on the station, resolve AWS credentials manually, and invoke `station_install/setup_station.sh <region> <thing_name>` by hand. With this feature, the user adds a device in the portal, fills in basic information (device name and device group), and the portal generates a setup command containing a short-lived Setup_Token (expiring within 90 minutes). Running that command on the station downloads a Setup_Bundle customized to the portal deployment it was generated from (use case account, region, and endpoints) and provisions the station end to end, with no GitHub repository checkout required on the device.

## Glossary

- **Portal**: The Edge CV Portal (edge-cv-portal) web application, consisting of a React frontend, Lambda-backed REST API, and CDK-managed infrastructure.
- **Portal_Backend**: The Lambda functions and API Gateway endpoints that serve the Portal's REST API.
- **Use_Case**: A portal-managed tenant record (dda-portal-usecases) holding the cross-account role ARN, external ID, account ID, and region of the AWS account where edge devices are provisioned.
- **Station**: A physical or virtual edge device (for example a Jetson or x86 host) that runs the DDA Greengrass stack after provisioning.
- **Station_Operator**: The person with shell access to the Station who runs the Setup_Command on the device.
- **Setup_Token**: A single-use, time-limited opaque credential generated by the Portal_Backend, bound to one Device_Registration, used to authorize download of the Setup_Bundle and retrieval of Provisioning_Credentials.
- **Setup_Command**: The one-line shell command (curl piped to bash, or equivalent) displayed by the Portal that the Station_Operator runs on the Station.
- **Setup_Bundle**: The self-contained set of installation artifacts served by the Portal_Backend, derived from `station_install/setup_station.sh` and its supporting files, parameterized for a specific Device_Registration.
- **Device_Registration**: The portal-side record of a pending Station, holding the device name, Device_Group, Use_Case, creating user, token metadata, and setup status.
- **Device_Group**: The IoT Thing Group the Station's Greengrass core device joins during provisioning (the existing script uses a fixed group name; this feature makes the group selectable).
- **Provisioning_Credentials**: The AWS material the Station needs to complete Greengrass provisioning (for example temporary scoped credentials or pre-created IoT certificates), delivered to the Station in exchange for a valid Setup_Token.
- **Quick_Setup_Endpoint**: The unauthenticated-by-JWT HTTPS endpoints of the Portal_Backend that serve the Setup_Bundle and Provisioning_Credentials to Stations presenting a Setup_Token.
- **Setup_Status**: The lifecycle state of a Device_Registration: `pending`, `in_progress`, `completed`, `expired`, or `failed`.

## Requirements

### Requirement 1: Register a Device from the Portal

**User Story:** As a portal user with device-management permission, I want to add a new device in the portal by entering a device name and selecting a device group, so that station setup is driven from the portal rather than from a repository checkout.

#### Acceptance Criteria

1. WHEN a user with the manage-devices permission submits a device registration with a device name, Device_Group, and Use_Case that pass the validations in criteria 2, 3, 8, and 9, THE Portal_Backend SHALL create a Device_Registration with Setup_Status `pending`.
2. IF a device registration is submitted with a device name or a new Device_Group name that does not match the pattern `[a-zA-Z0-9:_-]{1,128}` (valid IoT Thing and Thing Group name), THEN THE Portal_Backend SHALL reject the request with a validation error identifying each invalid field and SHALL NOT create a Device_Registration.
3. IF a device registration is submitted with a device name that already exists as an IoT Thing in the Use_Case account, or that matches the device name of an existing Device_Registration in the same Use_Case, THEN THE Portal_Backend SHALL reject the request with a conflict error identifying the conflicting device name and SHALL NOT create a Device_Registration.
4. IF a device registration is submitted by a user without the manage-devices permission for the selected Use_Case, THEN THE Portal_Backend SHALL reject the request with an access-denied error and SHALL record an audit event.
5. IF the audit event for a rejected device registration cannot be recorded, THEN THE Portal_Backend SHALL fail the entire registration operation with an error.
6. WHEN a Device_Registration is created, THE Portal_Backend SHALL record the creating user, Use_Case, device name, Device_Group, and creation time in the Device_Registration.
7. WHEN a user with the manage-devices permission initiates a device registration for a Use_Case, THE Portal SHALL present the list of existing IoT Thing Groups from the Use_Case account for Device_Group selection.
8. WHEN a device registration is submitted with a new Device_Group name instead of an existing IoT Thing Group, THE Portal_Backend SHALL accept the new Device_Group name as the Device_Group of the Device_Registration.
9. IF a device registration is submitted with the device name, Device_Group, or Use_Case missing or empty, THEN THE Portal_Backend SHALL reject the request with a validation error identifying each missing field and SHALL NOT create a Device_Registration.
10. IF the Portal_Backend cannot verify device name uniqueness in the Use_Case account (for example, the cross-account role cannot be assumed or the IoT Thing lookup fails), THEN THE Portal_Backend SHALL reject the registration with an error indicating that uniqueness verification failed and SHALL NOT create a Device_Registration.

### Requirement 2: Generate the One-Line Setup Command

**User Story:** As a portal user, I want the portal to give me a single one-line command after I add a device, so that I can copy it and run it on the station without any other preparation.

#### Acceptance Criteria

1. WHEN a Device_Registration is created, THE Portal_Backend SHALL generate a Setup_Token and SHALL return, in the registration response, a Setup_Command that embeds the Setup_Token and the Quick_Setup_Endpoint URL of the Portal deployment that generated it.
2. THE Setup_Command SHALL consist of a single shell line of at most 2048 characters, executable on an Ubuntu station with no prior DDA installation, whose only prerequisites are curl (or wget), bash, and sudo access.
3. THE Setup_Command SHALL reference only HTTPS URLs.
4. WHEN the Setup_Command is generated, THE Portal SHALL display the Setup_Command with a copy-to-clipboard control that places the complete Setup_Command on the clipboard in a single user action, and SHALL display the token expiration date and time.
5. WHEN a user with access to the Device_Registration requests a new Setup_Command for a Device_Registration whose Setup_Status is not `completed`, THE Portal_Backend SHALL invalidate any prior Setup_Token for that Device_Registration before issuing a new Setup_Token and SHALL return an updated Setup_Command, so that at most one Setup_Token is valid per Device_Registration at any time.
6. THE Setup_Command SHALL require no GitHub credentials, repository clone, or manual file transfer on the Station.
7. IF Setup_Token generation or storage fails during Device_Registration creation, THEN THE Portal_Backend SHALL fail the registration operation with an error indicating that the Setup_Command could not be generated and SHALL NOT persist a Device_Registration without a valid Setup_Token.
8. IF a new Setup_Command is requested for a Device_Registration whose Setup_Status is `completed`, THEN THE Portal_Backend SHALL reject the request with an error indicating the registration is already completed and SHALL NOT issue a new Setup_Token.

### Requirement 3: Setup_Token Security Properties

**User Story:** As a security-conscious platform owner, I want the setup link to carry a token that expires within 90 minutes and cannot be reused, so that a leaked command has a bounded blast radius.

#### Acceptance Criteria

1. WHEN a Setup_Token is generated, THE Portal_Backend SHALL set the token expiration to at most 90 minutes after generation time.
2. WHEN a Setup_Token is generated, THE Portal_Backend SHALL derive the token value from a cryptographically secure random source with at least 128 bits of entropy.
3. IF a request presents a Setup_Token after the token expiration time, THEN THE Quick_Setup_Endpoint SHALL reject the request with an expiration error and SHALL mark the Device_Registration Setup_Status as `expired` if the Setup_Status is `pending`.
4. IF a request presents a Setup_Token that has already been consumed by a completed credential exchange, or that has been invalidated by Setup_Command regeneration or Device_Registration deletion, THEN THE Quick_Setup_Endpoint SHALL reject the request with an invalid-token error.
5. IF a request presents a Setup_Token that does not correspond to any Device_Registration, THEN THE Quick_Setup_Endpoint SHALL reject the request with an invalid-token error identical in response structure and content to the invalid-token error returned for consumed or invalidated tokens, so that the response does not distinguish unknown tokens from tokens tied to existing registrations.
6. THE Portal_Backend SHALL store only a one-way hash of each Setup_Token value at rest.
7. WHEN a Setup_Token is validated, THE Quick_Setup_Endpoint SHALL bind all resulting operations to the single Device_Registration associated with the Setup_Token.
8. IF a Setup_Token validation fails for any reason (expired, consumed, invalidated, unknown, or check-evaluation failure), THEN THE Portal_Backend SHALL record an audit event containing the failure reason, the source IP of the request, and the request timestamp.
9. IF more than 10 requests with invalid Setup_Tokens are received from the same source IP within a 5-minute window, THEN THE Quick_Setup_Endpoint SHALL reject subsequent requests from that source IP for at least 5 minutes.
10. IF any Setup_Token security check (expiration, reuse, invalidation, or existence) cannot be evaluated, THEN THE Quick_Setup_Endpoint SHALL reject the request rather than proceed with an unverified token.

### Requirement 4: Serve the Customized Setup Bundle

**User Story:** As a station operator, I want the setup command to download an installer already customized to the portal deployment and to my device's registration, so that I do not have to supply region, thing name, or endpoints myself.

#### Acceptance Criteria

1. WHEN a request presents a valid Setup_Token, THE Quick_Setup_Endpoint SHALL serve a Setup_Bundle parameterized with the Device_Registration's device name, Device_Group, the Use_Case's AWS region, and the Quick_Setup_Endpoint URL of the serving Portal deployment, so that the Setup_Bundle can perform the credential exchange (Requirement 5) and status reporting (Requirement 6) without any operator-supplied values.
2. THE Setup_Bundle SHALL be derived from the repository's `station_install/setup_station.sh` provisioning logic so that a Station provisioned through Quick Setup reaches the same observable end state as one provisioned by running `setup_station.sh <region> <thing_name>` from a repository checkout of the same version, where end-state equivalence is verified by: a Greengrass core device registered under the device name in the Use_Case's AWS region, the Greengrass runtime installed and running as a system service, the station software prerequisites installed, and the device tagged for portal management per Requirement 6.5, with the Device_Group membership per criterion 6 as the only intended difference.
3. THE Setup_Bundle SHALL include all supporting files needed for provisioning so that the Station requires no access to the GitHub repository.
4. WHEN a Portal deployment completes successfully, THE Portal infrastructure SHALL package the Setup_Bundle source artifacts from the repository's `station_install` directory as part of that deployment, and THE Quick_Setup_Endpoint SHALL serve only bundle artifacts packaged by the most recently completed successful Portal deployment.
5. WHEN the Setup_Bundle is served, THE Quick_Setup_Endpoint SHALL include a cryptographic integrity checksum computed over the exact bundle content served.
6. WHEN the Station runs the Setup_Bundle, THE Setup_Bundle SHALL join the Station's Greengrass core device to the Device_Group recorded in the Device_Registration instead of the fixed `DDA_transition_EC2_Group`, and SHALL create the Device_Group as an IoT Thing Group in the Use_Case account when no group with that name exists.
7. IF joining the Device_Group fails during provisioning, THEN THE Setup_Bundle SHALL treat the provisioning run as failed per Requirement 7.7.
8. WHEN the Setup_Command downloads the Setup_Bundle, THE Setup_Command SHALL verify the downloaded bundle content against the provided integrity checksum before executing any part of the bundle.
9. IF the checksum verification fails, THEN THE Setup_Command SHALL NOT execute any part of the bundle, SHALL report an error indicating the integrity failure, and SHALL exit with a non-zero exit code.
10. IF the Setup_Bundle artifacts from a completed Portal deployment are not available when a valid Setup_Token is presented, THEN THE Quick_Setup_Endpoint SHALL reject the request with an error and SHALL NOT serve a partial bundle or artifacts from an incomplete deployment.

### Requirement 5: Provisioning Credentials Without Operator AWS Login

**User Story:** As a station operator, I want the setup process to obtain the AWS material it needs using only the setup token, so that I do not need to configure AWS credentials or log in on the station.

#### Acceptance Criteria

1. WHEN the Setup_Bundle executes on the Station and presents a valid Setup_Token, THE Quick_Setup_Endpoint SHALL return Provisioning_Credentials that authorize every provisioning operation the Setup_Bundle performs in the Use_Case account for the registered device name, so that provisioning completes without any other AWS credentials configured on the Station.
2. THE Provisioning_Credentials SHALL NOT authorize provisioning operations for any device name other than the registered device name of the Device_Registration bound to the Setup_Token, and SHALL NOT authorize operations beyond those the Setup_Bundle performs during provisioning.
3. WHEN Provisioning_Credentials are issued, THE Portal_Backend SHALL set their validity period to at most the remaining lifetime of the Setup_Token, measured at the time of issuance.
4. WHEN Provisioning_Credentials are issued for a Setup_Token, THE Portal_Backend SHALL mark the Setup_Token as consumed atomically with the issuance, so that at most one credential issuance occurs per Setup_Token and any subsequent or concurrent credential request presenting the same Setup_Token is rejected with an invalid-token error.
5. WHEN the credential exchange succeeds, THE Portal_Backend SHALL set the Device_Registration Setup_Status to `in_progress`.
6. WHEN provisioning finishes on the Station, whether provisioning succeeds or fails, THE Setup_Bundle SHALL remove Provisioning_Credentials from the Station's persistent storage so that no file on the Station contains Provisioning_Credentials secret material after the Setup_Bundle exits.
7. IF Provisioning_Credentials cannot be issued after a Setup_Token has been successfully validated, THEN THE Quick_Setup_Endpoint SHALL return an error indicating the issuance failure and THE Portal_Backend SHALL NOT mark the Setup_Token as consumed, so that the Setup_Bundle can retry the credential exchange within the remaining Setup_Token lifetime.
8. THE Setup_Bundle SHALL exclude Provisioning_Credentials secret material from its terminal output and from the installation log on the Station.

### Requirement 6: Setup Status Visibility in the Portal

**User Story:** As a portal user, I want to see whether the station I registered has completed setup, so that I know when the device is ready and can retry if something went wrong.

#### Acceptance Criteria

1. WHEN the Setup_Bundle completes provisioning successfully on the Station, THE Setup_Bundle SHALL report completion to the Quick_Setup_Endpoint, and THE Portal_Backend SHALL set the Device_Registration Setup_Status to `completed`.
2. WHEN the Setup_Bundle terminates with a provisioning error, THE Setup_Bundle SHALL report the failure with an error summary to the Quick_Setup_Endpoint, and THE Portal_Backend SHALL set the Device_Registration Setup_Status to `failed` and store the error summary truncated to at most 1024 characters.
3. WHEN the devices view is loaded or refreshed, THE Portal SHALL display each existing Device_Registration with its stored Setup_Status, and WHILE the Setup_Status is `pending` or `in_progress`, THE Portal SHALL display the token expiration time alongside the Setup_Status.
4. WHEN a Device_Registration has Setup_Status `expired` or `failed`, THE Portal SHALL offer regeneration of the Setup_Command per Requirement 2.5.
5. WHEN a Station provisioned through Quick Setup registers as a Greengrass core device, THE Setup_Bundle SHALL apply the `dda-portal:managed=true` tag so that the device appears in the existing Portal device listing.
6. WHEN a user with the manage-devices permission deletes a Device_Registration whose Setup_Status is not `completed`, THE Portal_Backend SHALL invalidate the associated Setup_Token and remove the Device_Registration.
7. IF a status report cannot be authenticated as originating from the Setup_Bundle of the targeted Device_Registration, or targets a Device_Registration whose Setup_Status is already `completed`, THEN THE Quick_Setup_Endpoint SHALL reject the report with an error and SHALL leave the Device_Registration Setup_Status unchanged.
8. IF a status report cannot be delivered to the Quick_Setup_Endpoint, THEN THE Setup_Bundle SHALL retry delivery up to 3 attempts in total, and IF all attempts fail, THEN THE Setup_Bundle SHALL print a message on the Station indicating that the setup status could not be reported to the Portal, without altering the provisioning outcome.
9. IF a deletion request targets a Device_Registration whose Setup_Status is `completed`, THEN THE Portal_Backend SHALL reject the request with an error indicating that completed registrations cannot be deleted, and SHALL leave the Device_Registration unchanged.

### Requirement 7: Station-Side Setup Experience

**User Story:** As a station operator, I want the one-line command to give clear progress and error output, so that I can tell whether setup worked without portal access.

#### Acceptance Criteria

1. WHEN the Setup_Command starts on the Station, THE Setup_Bundle SHALL verify, before making any system changes, that the Station meets the prerequisites of the provisioning logic: a supported Ubuntu release, a supported CPU architecture, at least 2 GB of free disk space on the root filesystem, root privileges, and the presence of each command-line tool the provisioning logic requires before it can install the remaining dependencies.
2. IF one or more prerequisite checks fail, THEN THE Setup_Bundle SHALL print each unmet prerequisite, SHALL make no system changes, and SHALL exit with a non-zero exit code.
3. WHEN the Setup_Bundle begins execution, THE Setup_Bundle SHALL create the installation log file, SHALL print the log file location to standard output, and SHALL record the output of every provisioning step in that log file.
4. WHEN each provisioning step starts, THE Setup_Bundle SHALL print the name of that step to standard output.
5. IF the Quick_Setup_Endpoint rejects the presented Setup_Token as expired or invalid, THEN THE Setup_Bundle SHALL print an instruction to regenerate the Setup_Command from the Portal and SHALL exit with a non-zero exit code.
6. WHEN the Setup_Bundle completes all provisioning steps successfully, THE Setup_Bundle SHALL print the device name, Device_Group, AWS region, and the location of the installation log file, and SHALL exit with exit code zero.
7. IF a provisioning step fails, THEN THE Setup_Bundle SHALL stop at that step without attempting subsequent provisioning steps, SHALL print the name of the failed step and the log file location, and SHALL exit with a non-zero exit code.
8. WHEN the Setup_Bundle is re-run on a Station where a previous run partially completed and the re-run completes successfully, THE Setup_Bundle SHALL leave the Station in the same end state as a single successful run on a fresh Station.

### Requirement 8: Audit and Observability

**User Story:** As a portal administrator, I want every quick-setup action audited, so that I can trace who created devices and which stations redeemed tokens.

#### Acceptance Criteria

1. WHEN a Device_Registration is created or deleted, a new Setup_Token is issued for a Device_Registration, or a Device_Registration changes Setup_Status, THE Portal_Backend SHALL record an audit event containing the action type, the acting principal (the authenticated portal user for user-initiated actions, or the Device_Registration bound to the presented Setup_Token for Station-reported actions), the Use_Case, the device name, the action outcome (success or failure), and the event timestamp.
2. WHEN a Setup_Token is redeemed at the Quick_Setup_Endpoint for the Setup_Bundle or Provisioning_Credentials, THE Portal_Backend SHALL record an audit event containing the device name, the Use_Case, the requested resource (Setup_Bundle or Provisioning_Credentials), the source IP of the redeeming request, the redemption outcome (success or failure), and the event timestamp.
3. THE Portal_Backend SHALL exclude Setup_Token values and Provisioning_Credentials secret material from all log output, audit event payloads, and error responses.
4. IF the audit event for a Setup_Token redemption cannot be recorded, THEN THE Quick_Setup_Endpoint SHALL reject the redemption request with an error and SHALL NOT serve the Setup_Bundle or Provisioning_Credentials.
5. THE Portal_Backend SHALL retain quick-setup audit events for at least 90 days and SHALL support retrieval of audit events filtered by device name and by time range.
