# ── CUDA 11.4 cudart provider (for the Neo/DLR model runtime) ──────────────
# SageMaker Neo's NVIDIA/TensorRT path maxes out at cuda-ver 11.4, so DDA models
# are compiled against CUDA 11.4. The Neo artifact bundles its own libdlr.so
# which dynamically links libcudart.so.11.0 (RUNPATH
# /usr/local/cuda-11.4/targets/aarch64-linux/lib). JetPack 6 only ships CUDA
# 12.6 (libcudart.so.12), so the model would fail to load with
# "libcudart.so.11.0: cannot open shared object file". We pull just the CUDA
# 11.4 runtime lib from NVIDIA's official NGC l4t-cuda image at BUILD time
# (nothing is committed to the repo) and stage it at the exact RUNPATH the
# bundled libdlr.so expects. That path is NOT shadowed by the runtime
# `-v /usr/local/cuda:/usr/local/cuda` host mount (which mounts /usr/local/cuda,
# not /usr/local/cuda-11.4), so it resolves without disturbing the host CUDA 12.
# A CUDA 12.6 driver is backward-compatible with the CUDA 11.x runtime, so the
# 11.4 cudart works against JetPack 6's GPU driver.
# ── TensorRT 8 provider (for the Neo/DLR model runtime) ─────────────────────
# The Neo-compiled model's bundled libdlr.so ALSO DT_NEEDs libnvinfer.so.8
# (TensorRT 8), on top of libcudart.so.11.0. JetPack 6 ships TensorRT 10
# (libnvinfer.so.10), so a DLR model fails to load with
# "libnvinfer.so.8: cannot open shared object file". TensorRT 8's own
# transitive DLA/tegra deps (libnvdla_compiler.so, libcudla.so.1, libnvos.so,
# libcuda.so.1) are already present on the JetPack 6 device at runtime (the
# L4T driver libs), so only the TRT 8 userspace stack must be supplied. Pull
# the matched CUDA-11.4-linked TRT 8.5 + cuDNN 8 + cuBLAS 11 libraries from
# the JetPack 5 image (r35.4.1) at BUILD time — their sonames (.so.8 / .so.11)
# never collide with the base image's TRT 10 / cuDNN 9 / cuBLAS 12, so the
# TRT10 (ONNX Runtime) and CUDA 12 (torch/vLLM) paths are undisturbed.
# Re-declare after FROM so the build arg is available in the build stage.

# ── vLLM engine for the companion Triton_vLLM_Runtime ──────────────────────
# (jp6-vllm-enablement, Requirements 1.1, 1.2, 1.4–1.7) Default-enabled layer
# installing the pinned prebuilt Jetson AI Lab wheel vllm==0.10.2+cu126 for
# the DDA interpreter (PYTHON_VERSION=3.10 — the jp6/cu126 wheels are
# cp310-only, which is why the backend runs 3.10 on JP6). The index is used
# as --extra-index-url so pure-python transitive deps (transformers,
# tokenizers, …) resolve from PyPI while the +cu126 local-version wheel
# (vllm) can only be satisfied by the Jetson index — PyPI never hosts
# local-version specifiers, so the pin cannot be hijacked upstream. torch is
# pinned to 2.8.0 (the version vllm 0.10.2 pairs with) and MUST come from the
# Jetson index: both indexes host a "torch-2.8.0" wheel of the SAME version
# string, but PyPI's is a manylinux_2_28_aarch64 CPU-only build (no
# libtorch_cuda.so — vLLM model loads then die with "libtorch_cuda.so: cannot
# open shared object file") while the Jetson wheel is a linux_aarch64 CUDA
# 12.6 build. When both indexes are consulted pip prefers PyPI's manylinux
# wheel, so torch is installed in its own step with --index-url pointing ONLY
# at the Jetson index (no PyPI fallback), before the vllm step resolves the
# rest. That step uses --no-deps: the Jetson index hosts only the CUDA wheels,
# NOT torch's pure-python runtime deps (filelock, sympy, networkx, jinja2,
# fsspec, typing-extensions), so resolving deps against the Jetson-only index
# fails with "No matching distribution found for filelock". Installing the
# torch wheel alone here and letting the vllm step below (which carries
# --extra-index-url PyPI) backfill those pure-python deps keeps the CUDA torch
# wheel un-hijackable while still satisfying torch's imports.
# Pinning also avoids PyPI's newer aarch64 torch (>=2.13), which pulls
# the nvidia-*-cu13 dependency family whose nvidia-cusparselt-cu13 ships no
# aarch64 wheel, failing the pip-check verification gate below. The
# "numpy>=1.26,<2" co-constraint caps the numpy that vllm/torch pull below
# 2.0, protecting the cp310 ABI surface of scikit-learn<1.2 and opencv in the
# same environment (requirements.txt itself is untouched — shared with
# JP5/x86). The layer sits after all app-dependency layers so pip resolves
# against the final environment, and before the aravis build so a
# wheel-resolution failure aborts early. transformers is co-pinned to <5:
# left floating, pip resolves transformers 5.x from PyPI, whose tokenizer
# API drops `all_special_tokens_extended` — vllm 0.9.3's TokenizerGroup
# still reads it, so every model load fails on-device with
# "GPT2Tokenizer has no attribute all_special_tokens_extended" (observed on
# jp6-orinagx with transformers 5.14.1). The >=4.51.1 floor is vllm 0.9.3's
# own minimum. triton (the OpenAI GPU-kernel compiler, NOT the NVIDIA
# inference server) is installed from the Jetson index in a follow-up step:
# the Jetson vllm wheel does not declare it as a dependency, but vLLM's CUDA
# execution path imports it at engine init — without it every model load
# fails on-device with "No module named 'triton'" (observed on jp6-orinagx).
# The build-host verification below cannot catch that miss: with no GPU
# driver vLLM reports UnspecifiedPlatform and never takes the CUDA path, so
# the import-time probe passes regardless. Hence the explicit find_spec
# check in the verification gate. Failure is loud: no `|| true`, a
# failed install fails the image build with the pip error in the log. Build
# with VLLM_ENABLE=0 (or an empty VLLM_SPEC) to skip the layer; app.py's
# capability probe (importlib.util.find_spec("vllm")) then runs the
# pre-feature startup sequence exactly.
# vllm is pinned to 0.9.3+cu126, NOT 0.10.2+cu126: the index's 0.10.2 wheel
# aborts the whole process (std::bad_alloc inside torch operator registration
# while dlopen'ing vllm/_C.abi3.so — a wheel/torch ABI incompatibility against
# the index's current torch-2.8.0 build). The 0.9.3 wheel from the same wheel
# batch registers its ops cleanly against torch 2.8.0 and carries the same
# classic V0 API surface (AsyncEngineArgs/SamplingParams/AsyncLLMEngine) that
# vllm_runtime/manager.py targets. The full-import verification gate below
# exists precisely to catch this class of breakage at build time.
ARG VLLM_ENABLE=1
ARG VLLM_SPEC="vllm==0.9.3+cu126"
ARG VLLM_INDEX_URL="https://pypi.jetson-ai-lab.io/jp6/cu126"
# Classic V0 engine: vllm_runtime/manager.py targets AsyncLLMEngine; V1 is the
# default engine selection since vLLM 0.8, so pin the V0 path explicitly.
ENV VLLM_USE_V1=0
# The Jetson CUDA torch wheel is a plain linux_aarch64 build (not manylinux):
# unlike PyPI's manylinux wheel it does NOT vendor openblas and dynamically
# links the JetPack system libopenblas.so.0. Install it (small, pure-C runtime
# lib — no python packages, so no py3compile concern) before torch, or
# `import torch` dies with "libopenblas.so.0: cannot open shared object file".
RUN apt-get update && \
    apt-get install -y --no-install-recommends libopenblas0 && \
    rm -rf /var/lib/apt/lists/*
RUN if [ "$VLLM_ENABLE" = "1" ] && [ -n "$VLLM_SPEC" ]; then \
        if [ -n "$VLLM_INDEX_URL" ]; then \
            pip install --no-cache-dir --index-url ${VLLM_INDEX_URL} --no-deps "torch==2.8.0"; \
        fi && \
        pip install --no-cache-dir \
            ${VLLM_INDEX_URL:+--extra-index-url ${VLLM_INDEX_URL}} \
            ${VLLM_SPEC} "torch==2.8.0" "numpy>=1.26,<2" "transformers>=4.51.1,<5" && \
        if [ -n "$VLLM_INDEX_URL" ]; then \
            pip install --no-cache-dir --index-url ${VLLM_INDEX_URL} "triton==3.6.0"; \
            # torchvision is required by transformers' AutoVideoProcessor for
            # vision-language models (Qwen2.5-VL preprocessing); without it
            # every VL model load fails on-device with "AutoVideoProcessor
            # requires the Torchvision library" (observed on the JP6 Orin AGX,
            # edge-vlm-image-inference rollout). Pinned to 0.23.0 — the
            # torchvision release paired with torch 2.8.0 (a floating install
            # resolves 0.26.x, which requires torch 2.9 and breaks at import
            # in _meta_registrations). --no-deps for the same reason as the
            # torch step: the Jetson wheel must not be displaced by PyPI. \
            pip install --no-cache-dir --index-url ${VLLM_INDEX_URL} --no-deps "torchvision==0.23.0"; \
        fi; \
    else \
        echo "vLLM layer skipped (VLLM_ENABLE=${VLLM_ENABLE}, VLLM_SPEC='${VLLM_SPEC}')"; \
    fi
# ── VL (vision-language) model enablement fixes ─────────────────────────────
# (edge-vlm-image-inference rollout; every fix below was verified live on the
# JP6 Orin AGX by hot-patching the running container until a Qwen2.5-VL-7B
# AWQ load + image generate succeeded end-to-end. Text-only models never
# exercise these paths, which is why the gaps went unnoticed until now.)
#   1. Triton JIT toolchain wiring: loading a VL model makes triton JIT-compile
#      its cuda_utils shim, which needs cuda.h on its include path and a ptxas
#      binary in its backend bin dir. The Jetson triton wheel ships neither;
#      both exist in the image's CUDA 12.6 toolkit — link them in. Without
#      this every VL load fails with "fatal error: cuda.h: No such file or
#      directory" and then "Cannot find ptxas".
#   2. ViT attention backend: vllm 0.9.3's get_vit_attn_backend hardcodes
#      XFORMERS when flash-attn is unavailable, but no cp310 CUDA xformers
#      wheel exists for Jetson (the index's wheel is cp312-built; its CUDA
#      extensions cannot load, failing with "No operator found for
#      memory_efficient_attention_forward"). Patch the two XFORMERS fallback
#      selections to TORCH_SDPA — qwen2_5_vl.py fully supports SDPA, and the
#      DECODER attention is unaffected (it uses the wheel's bundled
#      vllm-flash-attn, the same path text-only models use today). The sed is
#      guarded: zero replacements fail the build so a future vllm bump that
#      changes the file is caught here instead of on-device.
RUN if [ "$VLLM_ENABLE" = "1" ] && [ -n "$VLLM_SPEC" ]; then \
        TRITON_NV=/usr/local/lib/python3.10/dist-packages/triton/backends/nvidia && \
        CUDA_INC=$(find /usr/local/cuda*/targets/aarch64-linux/include -name cuda.h | head -1) && \
        PTXAS=$(find /usr/local/cuda*/bin -name ptxas | head -1) && \
        test -n "$CUDA_INC" && test -n "$PTXAS" && \
        mkdir -p ${TRITON_NV}/include ${TRITON_NV}/bin && \
        ln -sf "$CUDA_INC" ${TRITON_NV}/include/cuda.h && \
        ln -sf "$PTXAS" ${TRITON_NV}/bin/ptxas && \
        VISION_PY=/usr/local/lib/python3.10/dist-packages/vllm/model_executor/models/vision.py && \
        grep -q "selected_backend = _Backend.XFORMERS" "$VISION_PY" && \
        sed -i "s/selected_backend = _Backend.XFORMERS/selected_backend = _Backend.TORCH_SDPA  # jetson: no cp310 CUDA xformers wheel; SDPA verified on-device/g" "$VISION_PY" && \
        grep -q "jetson: no cp310 CUDA xformers wheel" "$VISION_PY"; \
    else \
        echo "VL enablement fixes skipped (VLLM_ENABLE=${VLLM_ENABLE}, VLLM_SPEC='${VLLM_SPEC}')"; \
    fi
# Post-install verification (gated to mirror the install condition):
#   1. the installed vllm distribution is exactly ${VLLM_SPEC}'s version —
#      the +cu126 local-version wheel from the Jetson index (metadata check);
#   2. FULL `import vllm` + the classic V0 API surface vllm_runtime/manager.py
#      targets. On the driverless build host a healthy wheel degrades
#      gracefully (WARNING about libcuda.so.1, no GPU init), while a
#      torch-ABI-broken wheel (e.g. the index's 0.10.2+cu126 against
#      torch-2.8.0) hard-aborts with std::bad_alloc during vllm._C operator
#      registration — exactly the crash that took down the backend on-device,
#      so the abort failing this RUN is the gate working;
#   3. torch imports and is a CUDA build (torch.version.cuda set AND
#      libtorch_cuda.so shipped — catches the PyPI CPU-only manylinux wheel
#      shadowing the Jetson CUDA wheel);
#   4. the app's startup dependency surface survives the vllm/torch
#      transitive installs (catches a numpy/torch clobber);
#   5. pip's resolver reports no broken requirements.
# Any miss fails the build.
RUN if [ "$VLLM_ENABLE" = "1" ] && [ -n "$VLLM_SPEC" ]; then \
        python3 -c "import importlib.metadata as md; want='${VLLM_SPEC}'.split('==')[1]; got=md.version('vllm'); assert got == want, 'vllm dist mismatch: got %s, want %s' % (got, want); print('vllm dist', got, 'OK')" && \
        python3 -c "import vllm; from vllm import AsyncEngineArgs, SamplingParams; from vllm.engine.async_llm_engine import AsyncLLMEngine; print('vllm', vllm.__version__, 'classic API OK')" && \
        python3 -c "import importlib.metadata as md; v=md.version('transformers'); assert int(v.split('.')[0]) < 5, 'transformers %s too new for vllm 0.9.x (needs <5)' % v; import transformers.tokenization_utils_base as b; assert hasattr(b.PreTrainedTokenizerBase, 'all_special_tokens_extended'), 'tokenizer API missing all_special_tokens_extended'; print('transformers', v, 'tokenizer API OK')" && \
        python3 -c "import triton; print('triton', triton.__version__, 'OK (vLLM CUDA-path kernel compiler)')" && \

# ── CUPTI/NVTX staging for the Jetson CUDA torch wheel ──────────────────────
# At runtime docker-compose bind-mounts the HOST's /usr/local/cuda over the
# container's. The image's /usr/local/cuda is a symlink to /usr/local/cuda-12.6
# and the mount resolves through it, so the ENTIRE image toolkit (cuda-12.6
# included) is shadowed by the host's — which ships only the runtime libs, not
# dev extras like CUPTI. The Jetson CUDA torch wheel (kineto profiler) dlopens
# libcupti.so.12 at CUDA init, so vLLM model loads died on-device with
# "libcupti.so.12: cannot open shared object file" while the same image passed
# every build-host check (no mount there). Stage CUPTI + NVTX (+ the nvperf
# libs CUPTI lazily dlopens when profiling) at a mount-proof path and register
# it with the loader. The conf file is 00- prefixed so it sorts FIRST in
# /etc/ld.so.conf.d glob order: ldconfig keeps one cache entry per soname
# (first wins), and the default cuda conf entries point into the shadowed
# /usr/local/cuda tree. Host/driver libs are unaffected — these five libs are
# simply absent from the host toolkit.
RUN mkdir -p /opt/nvidia/cuda-extras/lib && \
    cp -a /usr/local/cuda-12.6/targets/aarch64-linux/lib/libcupti.so* \
          /usr/local/cuda-12.6/targets/aarch64-linux/lib/libnvToolsExt.so* \
          /usr/local/cuda-12.6/targets/aarch64-linux/lib/libnvperf_host.so \
          /usr/local/cuda-12.6/targets/aarch64-linux/lib/libnvperf_target.so \
          /opt/nvidia/cuda-extras/lib/ && \
    echo "/opt/nvidia/cuda-extras/lib" > /etc/ld.so.conf.d/00-cuda-extras.conf && \
    ldconfig && \
    ldconfig -p | grep -F "libcupti.so.12 (libc6,AArch64) => /opt/nvidia/cuda-extras/lib/libcupti.so.12" || \
    (echo "ERROR: staged libcupti.so.12 does not win the loader cache" && ldconfig -p | grep -i cupti && exit 1)

# ── /usr/local/cuda: symlink -> real mount-point directory ──────────────────
# docker-compose bind-mounts the HOST's /usr/local/cuda here. In the base
# image /usr/local/cuda is a symlink chain to /usr/local/cuda-12.6, and Docker
# resolves the chain when creating the mount — so the host toolkit used to
# shadow the ENTIRE image toolkit, cuda-12.6 included. With torch/vllm built
# against CUDA 12.6, an older host toolkit (e.g. JetPack 6.0's 12.2 libcudart,
# which lacks cudaGetDriverEntryPointByVersion) then broke model loads:
# "libc10_cuda.so: undefined symbol: cudaGetDriverEntryPointByVersion,
# version libcudart.so.12". Replacing the symlink with a real, empty directory
# makes the mount land AT /usr/local/cuda and stop there: host libs stay
# visible exactly where JP4/JP5-era code expects them, while the image's
# /usr/local/cuda-12.6 toolkit remains reachable. docker-compose.yaml puts
# /usr/local/cuda-12.6/targets/aarch64-linux/lib FIRST on LD_LIBRARY_PATH
# (tegra service) so torch resolves the 12.6 runtime it was built against;
# driver libs (libcuda.so.1, libnvrm*) live in the tegra dirs / NVIDIA runtime
# injection, not in the toolkit lib dir, so the host driver keeps winning.
RUN rm /usr/local/cuda && mkdir /usr/local/cuda && \
    ldconfig && \
    ls /usr/local/cuda-12.6/targets/aarch64-linux/lib/libcudart.so.12 >/dev/null && \
    echo "cuda mount-point conversion OK"
