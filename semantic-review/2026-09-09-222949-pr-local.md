# Exit-75 lock-held deferral for the portal build dispatcher

The change teaches the build fleet backend that SSM ResponseCode 75 from `scripts/portal-build-agent.sh` is the agent's documented lock-held deferral, not a hard failure. `classify_attempt` gains an additive, *undecided* `BUILD_LOCK_HELD` row in its terminal-`Failed` branch; the dispatcher's settlement path routes that marker into a new `defer_lock_held_job`, which requeues the job at the head of its queue (original `created_at`, `deferred_at` recorded, runner/allocation kept, no terminal ledger) under a bounded safety valve. Defect B is addressed with conditional one-writer-wins attempt claims (the dedicated claim now rides inside the `queued -> building` transition; the ephemeral send loop gets `claim_execution_attempt`), a job-id-based `find_command_by_comment` returning `CommandMatch`, and a cancel-or-proven-dead resend gate placed after the visibility bound.

The classification half is preservation-safe. The settlement half carries the risk: the deferral is reachable only from the building/publishing reconciliation path, the re-dispatch loop it creates has no lock-holder verification, and the resend gate's "proven never executed" predicate returns True for the evidence shape the incident produced.

**Watch for:** the deferral never fires for an ephemeral job still in `provisioning`, which is the common exit-75 shape, leaving the job wedged with a live runner (confirmed); the re-dispatch re-runs the agent command's `git checkout --force` preamble *outside* the build lock, rewriting tracked files (including `gdk-config.json`, which `portal-build.sh` writes) under the build that legitimately holds the lock (confirmed); `prior_command_proven_never_executed` returns True for a terminal `Failed`/`Undeliverable` invocation with no `ExecutionStartDateTime`, the incident's command `1b538196` shape, so a resend goes out with no cancellation (confirmed); the bounded valve is evaluated only inside `defer_lock_held_job`, so a job that stops being re-dispatched has no bound and no watchdog backstop (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The rc-75 row sits after the preflight and ENOSPC evidence rows and before the generic fallthrough, inside the `Failed`-only arm, so `TimedOut`/`Cancelled`, agent authority 1, cancellation, hard ceiling, and infrastructure loss all decide as before, and every non-75 code still reaches `COMMAND_EXECUTION_FAILED`.

The deferral is wired into exactly one caller: `reconcile_running_command`, which `command_reconciliation` invokes only for jobs in `AGENT_RUNNING_STATUSES` (`building`, `publishing`). An ephemeral agent that exits 75 does so at the script's Step 1, before it emits `phase=building`, so its job is still `provisioning`: no deferral, no failure, and `ssm.command_id` stays set so the send gate blocks re-dispatch. That job is wedged with a running runner. The incident itself is covered only because an orphan command had already moved the job to `building`.

The requeue mirrors `PREDISPATCH_DEFER` faithfully and deliberately keeps the runner binding, so the deferred ephemeral job re-dispatches onto the same instance. What it does not carry over is the pre-dispatch pgrep verification that protects the dedicated path, and the agent command mutates the shared repo tree before it ever reaches `flock`.

The bounded valve only runs when another exit-75 arrives. Nothing else bounds the requeued state: the runtime watchdog filters to `building`/`publishing`, and `queue_wait_ms` is frozen once `dispatched_at` exists, so neither the queue-wait nor the provisioning budget can expire for a deferred job. When the valve does fire it settles terminally with `cleanup_required=True`, which terminates the ephemeral runner, delaying the original incident harm by the window rather than removing it. The window comes from `build_planner.max_runtime_ms`, which ignores the `runtime_budgets` target/mode overrides the real hard ceiling uses, and it is wall-clock from the first exit-75 deferral, so pgrep-deferral time and build time both consume it.

The claim work is the strongest part of the change. Folding the dedicated claim into the `queued -> building` transition removes a window rather than adding a mechanism, and no prior behavior is lost. `claim_execution_attempt` mirrors `claim_resend`'s precedent correctly for the two states that occur in practice, with one soft edge: `attribute_not_exists(execution_attempt.attempt_id)` also passes when an `execution_attempt` map exists without an `attempt_id`.

The resend gate closes less than it claims. Its docstring states that `Undeliverable` is not proof of non-execution, then the implementation treats terminal delivery status plus a missing `ExecutionStartDateTime` as exactly that proof. Both arms also fail open on SSM API errors, because `retrieve_invocation` collapses throttling and every other `ClientError` into the same `None` that means "no invocation exists". Separately, the new job-id matching can attach a previous deferral cycle's already-settled exit-75 command instead of resending, which re-defers the job and leaves the genuinely-sent command orphaned; `lock_deferral.last_command_id` is recorded but never used to exclude it.

1. **Deferral unreachable in `provisioning`** — `command_reconciliation` only calls `reconcile_running_command` for `building`/`publishing`, and the agent exits 75 before emitting `phase=building`, so an ephemeral lock-held deferral never requeues; the job wedges in `provisioning` with `ssm.command_id` set and a live runner. Treat missing execution evidence on a delivery-failed invocation as indeterminate, or always cancel-and-confirm before any resend.
4. **Resend gate fails open on SSM errors** — `retrieve_invocation` returns `None` for throttling/`AccessDenied`/5xx as well as `InvocationDoesNotExist`, so `cancel_command_confirmed` reads "no invocation" and returns True. Distinguish "does not exist" from "could not read" and treat the latter as wait.
5. **Stale prior-command attach** — past the visibility bound, a previous deferral cycle's exit-75 command is found by job id, shows execution evidence, and gets attached, re-deferring the job while the current attempt's real command stays orphaned. Exclude commands already settled on the job (`lock_deferral.last_command_id`, prior `execution_attempt.command_id`).
6. **Valve only advances on another exit-75; no external backstop** — `defer_lock_held_job` is the sole evaluator, the runtime watchdog skips `queued`/`provisioning`, and `queue_wait_ms` is frozen by the existing `dispatched_at`. A job that stops being re-dispatched holds its runner indefinitely. Add a deadline check on the requeued state itself.
7. **Valve window uses the wrong budget and the wrong clock** — `lock_deferral_window_ms` calls `build_planner.max_runtime_ms`, ignoring the `runtime_budgets` overrides `effective_budget` resolves, and measures wall-clock from the first exit-75 deferral, so pgrep-deferral and build time consume it and a legitimate later deferral can hard-fail immediately. Use `effective_budget(job).hard_runtime_ms` and count deferral pressure, not elapsed wall time.
8. **Valve exit re-creates the incident harm** — the exhausted path settles FAILED with `cleanup_required=True`, so the termination watchdog terminates a runner that may still be running the lock-holder build. Confirm no build processes before planning ephemeral cleanup on this path.
9. **Re-dispatch treats "no `terminated_at`" as runner liveness** — a spot-reclaimed or externally terminated instance is never replaced with fresh compute, and the requeued job can sit in `provisioning` unbounded behind the `instance_ssm_online` gate. Verify instance state before reusing the runner, or fall through to provisioning.
10. **Classification keys on the response code alone** — an inner tool exiting 75 with a lost `failed` phase event now loops through deferrals (each cycle a full rebuild) and finally settles as `BUILD_LOCK_HELD`. Consider requiring the agent's deterministic lock marker text alongside rc 75.
11. **`claim_execution_attempt` condition edge** — `attribute_not_exists(execution_attempt.attempt_id)` also passes for an `execution_attempt` map (or NULL attribute) that lacks `attempt_id`, letting a claim overwrite it; the loser's log line always blames "a concurrent tick" even when the refusal came from the local live-attempt pre-check.
12. **Attempt bookkeeping after a prior-attempt attach** — `_attach` revives a settled attempt id from `terminal` to `sent` while keeping the current attempt's `claimed_at`/`sending_at`, so the attempt's clocks describe a different dispatch than the command it now points at. Record the adopted binding explicitly instead of overwriting identity in place.
13. **Coverage gaps in the frozen suites** — no dedicated-mode deferral (the allocation-kept clause of Req 2.1), no re-dispatch cycle, no valve exhaustion, no provisioning-status exit 75, no cancel-during-deferral, and the resend gate is exercised only in the `InProgress` shape.

### Where the deferral is actually reachable

`defer_lock_held_job` has exactly one caller, inside `reconcile_running_command`, and `command_reconciliation` reaches that function only through `elif status in AGENT_RUNNING_STATUSES`, which is `{building, publishing}`. The EventBridge path in `build_events.reconcile_command_evidence` gates its own terminal application on the same set, and `decide_ssm_fallback` documents the policy ("a queued/provisioning job has no agent outcome to lose").

For a dedicated job that is fine: the dispatcher transitions `queued -> building` before the SendCommand, so an rc-75 invocation always lands on a `building` job. For an ephemeral job it is not. `portal-build-agent.sh` takes `flock` in Step 1 and exits 75 there, well before the `phase=building` emission at line 430, so nothing ever moves the job out of `provisioning`. The resulting state:

```
status            = provisioning
ssm.command_id    = <the exit-75 command>     -> ephemeral send gate skips the job
execution_attempt = sent (not `sending`)      -> ambiguous-send recovery skips it
runtime watchdog  = building/publishing only  -> no timeout
```

No deferral, no failure, no re-dispatch, and the runner keeps billing. The incident job was covered only because the orphaned first command had already emitted `phase=building`. With Defect B's double-send now largely closed, the remaining ephemeral exit-75 producers (a leftover build on a reused runner, the root-owned-lock/bad-fd pattern) all land in `provisioning`. The exploration test seeds `status=STATUS_BUILDING`, so the suite cannot see this.

### The re-dispatch loop versus the build it deferred for

`provision_ephemeral` gains a branch that requeues onto the existing runner instead of provisioning new compute, gated on `is_reverification_due(deferred_at)`. Naming the 5-minute pre-dispatch cadence is right, but the cadence is only half of what the dedicated path does: `verify_and_start_dedicated` runs `VERIFY_BUILD_PROCESS_COMMANDS` through `decide_predispatch` and refuses to dispatch while a build process exists. The ephemeral re-dispatch has no equivalent — it sends the agent precisely because the lock was held five minutes ago.

That matters because the lock is not the first thing the command touches. `agent_command` composes a root prologue and then a build-user body whose Source_Sync preamble runs before the agent script:

```
SSM command
  root: chown -R ubuntu:ubuntu <repo_dir>; chown lock; chgrp docker.sock
  ubuntu: git fetch --prune origin
          git checkout --force -B <ref> origin/<ref>     <-- rewrites tracked files
          bash scripts/portal-build-agent.sh ...
                 Step 1: exec 9>lock; flock -n 9 || exit 75   <-- lock taken HERE
```

So every deferral cycle force-checks-out the tree the lock holder is building in. `portal-build.sh` writes `gdk-config.json` (a tracked file) at line 239 to select the component name for the target; a concurrent `checkout --force` restores the committed content underneath the running build. That is the failure mode `.kiro/steering/builds.md` describes as corrupting model versioning, arriving from the dispatcher rather than from two operators. The agent's own Step 2 sync is correctly inside the lock; only the dispatcher-side preamble is not.

The dedicated path is protected by its pgrep gate, so this is specific to the new ephemeral re-dispatch.

### Bounding the deferral

`defer_lock_held_job` checks `now > first_deferred_at + lock_deferral_window_ms(job)` on entry, so the valve is consulted only when a *new* exit-75 settlement arrives. Every other way the deferred state can persist is unbounded.

The requeued job is `queued` with a live runner. `runtime_timeout_watchdog` filters on `RUNNING_WATCHDOG_STATUSES` before calling `decide_runtime_timeout`, so the queue-wait and provisioning branches of `decide_timing` — which do handle those statuses — are never evaluated in the tick. Even if they were, `queue_wait_ms` ends at `timing.queue_ended_at` or `dispatched_at`, and the deferral deliberately leaves the earlier `dispatched_at` in place, so the measured wait is frozen at its pre-dispatch value and no queue-wait budget can expire for a deferred job.

If the re-dispatch transitions to `provisioning` but the send does not happen (`instance_ssm_online` false because the runner was spot-reclaimed or is impaired), the job leaves `queued`, so the deferral branch no longer applies, and `provisioning` has no watchdog either. The liveness test for reusing the runner is `runner.get('terminated_at')` being absent, which only the dispatcher's own termination sets, so an externally terminated instance still looks reusable and the job never provisions replacement compute.

The window value is also not the one the docstring reasons about. `lock_deferral_window_ms` calls `build_planner.max_runtime_ms(config_snapshot)`, which reads only `max_runtime_hours` (default 4h). The ceiling the *holder* actually runs under comes from `build_reconciliation.effective_budget`, which resolves `runtime_budgets[target][mode]` and `runtime_budgets[target].default` first. A target configured with an 8-hour `hard_runtime_hours` and no snapshot `max_runtime_hours` yields a 4-hour valve against an 8-hour build. And because the window is wall-clock from the first exit-75 deferral, a dedicated job that defers via the pgrep path for five hours (a healthy wait that never touches `lock_deferral`) hard-fails on the very next exit-75 it sees, since `now` is already past `first_deferred_at + window`.

When the valve fires, the code falls through to the generic terminal path, which plans `plan_job_ledger(job, cleanup_required=True)` for ephemeral jobs. `termination_watchdog` keys on terminal status alone — it does not consult the ledger — so the runner is terminated. By the deferral's own premise the lock holder may still be building on it. The runtime watchdog solves the same problem with `send_shell_command(STOP_BUILD_COMMANDS)` followed by `reconcile_compute_cleanup`'s pgrep confirmation; this path has no equivalent.

### Conditional claims

Moving the dedicated claim inside the `queued -> building` transition loses nothing: the previous shape wrote status first and then `bootstrap`/`execution_attempt`/`preflight` through an unconditional `update_job_fields`, and both writes were already unreachable when the transition lost its condition. It also removes the intermediate state where a job is `building` with no attempt. `dedicated_bootstrap_gate` returns a non-None note on every proceeding path, so no `None` reaches the extra map.

`claim_execution_attempt`'s condition is correct against DynamoDB nested-path semantics for the two shapes that matter — attribute absent, and attribute present with an `attempt_id` — and the settled-supersede arm (`attempt_id` equality plus `dispatch_state = terminal`) is genuinely one-writer-wins, since the winner's write changes the `attempt_id` the loser's condition names. The gap is the third shape: an `execution_attempt` that exists but has no `attempt_id` (or is a NULL attribute) satisfies `attribute_not_exists`, and the claim overwrites it. `new_execution_attempt` always sets the id, so this arises only from a partial or legacy record, but the condition asserts less than the docstring claims.

One diagnostic wrinkle: the local pre-check `if prior_id and dispatch_state != DISPATCH_TERMINAL: return False` fires before any write, yet the caller logs "lost the execution-attempt claim to a concurrent tick". Skipping a send because a live attempt exists and losing a race are different situations to debug.

### The resend gate

The gate runs after the visibility bound, so no cancellation is issued for a command the job might still be waiting on. The predicate underneath it is the problem:

```python
if invocation.get('ExecutionStartDateTime') \
        or invocation.get('Status') not in SSM_TERMINAL_STATUSES:
    return False  # executed (or still executing): attach, never resend
return match.list_status in SSM_TERMINAL_STATUSES
```

`bugfix.md` describes command `1b538196` as "marked by SSM 'Failed/Undeliverable', rc −1, no recorded execution start" while it was in fact executing and holding the lock. That is `Status='Failed'` (terminal) with no `ExecutionStartDateTime`, so this function returns True — "proven never executed" — and the caller skips `cancel_command_confirmed` entirely and resends. The docstring names this exact shape as something not to trust. The exploration test's fixture uses `Status='InProgress'` with `ExecutionStartDateTime` set, exercising only the `False` branch.

Both arms also fail open on API trouble. `retrieve_invocation` returns `None` for every `ClientError`, logging only when the code is not `InvocationDoesNotExist`/`InvalidCommandId`. A throttled `GetCommandInvocation` therefore yields `never_executed is None`, which routes to `cancel_command_confirmed`; there `CancelCommand` succeeds (a cheap API), the follow-up read fails the same way, `invocation is None`, and the function returns True on the reasoning that the command never reached the instance. Under SSM throttling — plausible when every job's tick does `ListCommands` plus `GetCommandInvocation` — the gate authorizes a resend over a live command.

The job-id matching introduces a third path. `find_command_by_comment` returns any command whose comment parses to the same job id, preferring exact, then non-terminal, then most recent. After a lock-held deferral, the job legitimately has a prior attempt whose command is terminal `Failed` with rc 75. If a later attempt's send is ambiguous and its own command is not visible in the 50-command window, the fallback match is that old command; `prior_command_proven_never_executed` sees its execution evidence, returns `False`, and `_attach` binds the job to a command that settled hours ago. The next tick reconciles it, classifies rc 75 again, and defers again, burning a deferral cycle and the valve budget while the attempt's actually-sent command stays orphaned. `defer_lock_held_job` already records `lock_deferral.last_command_id`; nothing consumes it.

`_attach` also rewrites identity in place: for a non-exact match it replaces `attempt_id` and `command_comment` while keeping the current attempt's `claimed_at`/`sending_at`, and it moves an id that was previously settled `terminal` back to `sent`. Heartbeat and progress sequences in `timing` are not attempt-scoped on this path (only the deferral clears them), so the adopted attempt inherits the current attempt's clocks and the previous attempt's sequence history.

### Classification and cross-lambda behavior

`is_lock_held_response_code` rejects bools before ints, which matters because `True == 1` in Python, and it accepts numeric strings the same way the diagnostic builder does.

Keying on the response code alone has one consequence: the agent ends with `exit "$BUILD_EXIT_CODE"`, so any inner tool exiting 75 surfaces as rc 75. The agent emits a `failed` phase event first and that event moves the job terminal, so the misread only occurs when the event is lost — in which case the job cycles through full rebuild attempts until the valve expires and settles as `BUILD_LOCK_HELD` rather than failing on the real cause.

`build_events.reconcile_command_evidence` shares the classifier but has no deferral wiring, so an rc-75 EventBridge delivery records the diagnostic and leaves the job nonterminal; the dispatcher's next tick performs the requeue. That is a latency cost only, and the deferral's `'reconciliation': None` write clears the state the events path left behind. `legacy_ssm_fallback` (jobs with no resolvable instance identity) still hard-fails an rc-75 command, which is unavoidable without invocation evidence.

### What the frozen suites do not reach

Coverage of the classification matrix is thorough: every authority row, both evidence rows against all response codes, `STABLE_ERROR_CODES` membership, comment round-trips, `claim_resend`'s four outcomes, the pre-dispatch defer shape, the termination watchdog, and the lock-ownership heal text.

Not covered: the `provisioning`-status exit 75 (the settlement test seeds `building`); the dedicated post-dispatch deferral, including the "allocation kept" clause of Req 2.1; the `provision_ephemeral` re-dispatch branch and therefore the whole defer/re-dispatch cycle; valve exhaustion and the terminal path it falls into; the `queued`-with-live-runner state against the rest of the tick (cancellation, sweeps, watchdogs); `cancel_command_confirmed` at all; and the resend gate's `True`/`None` branches, which are the ones that authorize a send.

Note on verification: no pytest is installed on this host, so the suites were read, not executed.
