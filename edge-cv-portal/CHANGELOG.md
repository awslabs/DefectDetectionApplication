### Added - Layout Check node, per-deployment LocalServer floors and the car-assembly-check use case (2026-11-27)

A **Layout Check** node (`layout_check`, Post-processing) checks that each listed class of an instance-segmentation model is detected exactly once in its own region of the frame, so a station can tell whether every piece of an assembly sits where it belongs.

- **The node.** `expected_regions` maps each class label to a polygon of 3 to 64 normalized points (1 to 10 classes); a class is `ok` when its mask overlaps its region with an IoU of at least `min_iou` (default 0.7), otherwise `misplaced`, `missing` or `duplicate`. Detections below `min_confidence` (0.5) are not counted, and a detection with less than `min_outline_overlap` (0.1) of its mask inside the union of the regions is ignored and listed under `ignored`. The verdict is written to the run metadata as `layout.<nodeId>.pass`, `.pieces.<class>.status`/`.iou`, `.flagged`, `.unexpected_classes` and `.ignored`, so a Conditional can route on `layout.<nodeId>.pass == false`. One shared module computes it for LocalServer, the cloud test sandbox and the validator, which adds V14 (invalid configuration) and W4 (no Model Inference node upstream); the Workflow Builder mirrors both checks.
- **Device.** LocalServer evaluates the node in its scene-analytics pass, and the station HMI shows a Layout Check section per run with the misplaced pieces highlighted on the frame. The device code is unit-tested only; it has not yet been verified on hardware.
- **Per-deployment LocalServer floors.** Packaging refuses a `layout_check` workflow for an architecture without a Layout Check floor entry (`LAYOUT_CHECK_UNSUPPORTED_ARCH`), and deployment refuses a device whose installed LocalServer is below it (`INCOMPATIBLE_LOCAL_SERVER`, with `details.layout_check_min_local_server_versions`). The floor comes from the CDK context key `layoutCheckMinLocalServerVersions`, else the shell variable `LAYOUT_CHECK_FLOOR`, else the SSM parameter `/dda-portal/layout-check-min-local-server-versions`; its default `{}` refuses every `layout_check` workflow. The RF-DETR-Seg floor becomes the second key of the same form (`rfdetrSegMinLocalServerVersions`, `RFDETR_SEG_FLOOR`, `/dda-portal/rfdetr-seg-min-local-server-versions`); its default stays the committed literal, so a deployment that sets nothing behaves as before.
- **The car-assembly-check use case.** Scripts in `datasets/` for the triage file, the `source-ref` rewrite between image variants, the manifest checks, the reference capture and `min_iou` calibration, and the grayscale/colour comparison; `samples/car-assembly-check/` holds the sample workflows, the grayscale handler and the device batch driver `batch_run.py`. User guide: 8.4 (the node), 8.9 (the worked example), 4.2 (one labeling job for several image variants) and 13.4 (feature floors).
- **Documentation.** The build script's existing `COMPONENT_VERSION_OVERRIDE` is documented in the README build section and `.kiro/steering/builds.md`; the script is not changed.
### Added - Settings: images per auto-label worker run (2026-11-26)

Since 2026-11-25 the Grounded-SAM worker runs one Grounding DINO pass per label, so an image takes about 2.5 s plus 4.5 s per label. The auto-label worker gets up to 5 images per run and labels them one after the other within its 300 s timeout. With the up to 140 s a Grounded-SAM cold start can take, 5 images of a 7-label job need about 310 s. A run that reaches 300 s is stopped, and the queue gives its images to a new run twice more. Images still without a pre-label then stay **Pending**: labelers never see them, and a skip-verification job never becomes review-ready.

- **Images per worker run.** A new **Auto-Labeling** tab on the Settings page (PortalAdmin) sets how many images of its batch a worker run labels, from 1 to 5. The worker reads the value at the start of every run, so a save applies to the next run with no deploy. The run sends the other records of its batch back to its own queue as new messages, which other runs pick up at once, and labels any record it could not send back itself. 3 fits a 10-label Grounded-SAM job even with a 140 s cold start. The value applies to every auto-label model.
- **Nothing saved, nothing changes.** With no saved value, an unreadable settings item, or a stored value that is not a whole number from 1 to 5, a run labels every record of its batch, as before. Each run logs the value it used and its record counts, for example `Auto-label images per run: none (default); records 5, processed 5, re-queued 0`.
- **Settings API.** `GET` and `PUT /data-accounts/autolabel-configuration`, a reserved id on the existing PortalAdmin-only routes, so no API Gateway route is added. `PUT {"images_per_run": 3}` saves 3 as the settings item `autolabel.images_per_run`, `{"images_per_run": null}` deletes the item, and any other value is answered with 400. Saves are audit-logged as `update_autolabel_configuration`, denied attempts as `unauthorized_access`.
- **Infrastructure.** `DdaAutolabelWorker` gets `AUTOLABEL_QUEUE_URL` and permission to send messages to `dda-portal-autolabel-queue`. The 300 s timeout, the batch size of 5, the 300 s visibility timeout, the 3 receives before the dead-letter queue and the 240 s bound per Grounded-SAM image are unchanged.
- **Docs.** User guide [19.5 Auto-Labeling](../docs/user-guide/19-settings.md#195-auto-labeling); General and Deployment switches are renumbered to 19.6 and 19.7. The **Auto-label model** row of 4.2 points to the setting.
- **Not changed.** Images that a timed-out run did not finish still stay `Pending`: a retried batch labels every record again, the dead-letter queue is not read, and **Re-run pre-labels** only retries `Failed` tasks. A lower **Images per worker run** makes such a timeout less likely but does not recover tasks that are already stuck.

### Fixed - Grounded-SAM pre-labels for the second and later labels of a job (2026-11-25)
The Grounded-SAM worker joined all of a job's prompts into one Grounding DINO caption (`p1. p2. p3.`) and ran the model once per image. The model the worker ships, the onnx-community `grounding-dino-tiny-ONNX` export, builds the per-phrase text attention mask and position ids with a loop that was unrolled for a one-phrase caption when the model was exported, so only the first prompt was encoded as a phrase. Every token of a later prompt attended only to itself, and no such prompt reached the 0.35 box threshold (the best of 135 words tried in those slots scored 0.29). A multi-label job therefore only got proposals for its first label: all 37 proposals of the three-label job labeling-f85bdfc7 were named `front_fender`.
- **One Grounding DINO pass per label.** Each pass gets a one-phrase caption (`p1.`), which the export encodes correctly, and its detections go to that pass's label. The image is preprocessed once for all passes. Per-label NMS, the cap of 20 detections per image across all labels, the box and text thresholds and the SAM pass (one image embedding, one mask per kept box) are unchanged, as are the model files, the worker's Dockerfile and the response format.
- **Single-label jobs are unchanged**, byte for byte: their one pass uses the caption the worker sent before. On the real models, the responses for 4 single-label prompt maps on 6 images are identical before and after the fix (24 of 24).
- **Multi-label jobs change for every label.** Each prompt is now scored on its own, so the first label's scores change too, and the same region can be proposed under two labels because NMS stays per label. With front_fender = "rounded nose piece", rear_fender = "square tab piece" and roof = "half disc" on 6 car-assembly photos, the proposals per label go from 7 / 0 / 0 to 7 / 11 / 10, every label on all 6 images (the worker run locally on the deployed model files).
- **Latency and cost.** Each label after the first adds one Grounding DINO pass, about 4.5 s and about $0.0009 per image (the worker's 10,240 MB, plus the autolabel worker waiting on it). A three-label image takes about 16 s instead of about 7 s, and a ten-label image about 48 s, inside the 240 s bound of the autolabel worker and the preview and the worker's 300 s timeout. There is still one worker invocation per image.
- **Known limit.** The export also treats `?` as a phrase break, so the words after a `?` inside a prompt are still read one by one. The prompt guardrail still rejects periods.
- **Rollout.** The next Portal deploy rebuilds the worker image with the same model files. Pre-labels and previews generated after it use one pass per label; stored pre-labels are not regenerated.

### Added - RF-DETR-Seg instance segmentation (2026-11-23)

The Portal and LocalServer support **RF-DETR-Seg**, Roboflow's instance-segmentation member of the RF-DETR family (rfdetr 1.10.1): one mask per detected object beside its box and class, from labeling through training, import, packaging, device inference and results. All six published sizes (nano 312, small 384, medium 432, large 504, xlarge 624, 2xlarge 768) are available; the licence position is stated in the README's "Instance segmentation (RF-DETR-Seg)" section.

- **Labeling.** A fourth task type, **Instance Segmentation** (`InstanceSegmentation`, DDA labeling only): labelers draw one polygon per object; pre-labels come from SAM, Grounded-SAM or a prompt-guided LLM. The job's output is an instance-segmentation manifest (`instance-segmentation` with a box and an RLE mask per annotation, plus the class map).
- **Training.** **RF-DETR (Roboflow)** with model type **Instance Segmentation (masks + boxes)** trains `train_rfdetr_seg.py` on SageMaker from that manifest (`model_type: instance_segmentation`, `detection_arch: rf_detr_seg`): size, resolution (a multiple of the size's block, 12 or 24, in 240–1152), score and mask thresholds, the **Output** mode and a base model (a published checkpoint or a prior RF-DETR-Seg model). The job reports the two mask metrics (`test:mask-mAP50`, `test:mask-mAP50-95`) beside the box metrics. The rfdetr trainer requirements now pin `transformers`, which detection training on the current trainer image depends on.
- **Import.** Smart Import converts an RF-DETR-Seg `.pth` checkpoint to ONNX in the detector conversion job (box, class and mask-overlap parity on the export runtime and the fleet's oldest runtime) and imports an RF-DETR-Seg ONNX graph (three outputs: boxes, class logits, mask logits) through the **Instance Segmentation (RF-DETR-Seg)** tile, with required class names, both thresholds and the Output mode; `segmentation` + `rf_detr` for such a graph is accepted as a deprecated alias of the new type in semantic mode.
- **Packaging and devices.** Every RF-DETR-Seg model is packaged in **instance** mode (stage type `rf_detr_instance_segmentation`; the device records `mask_rle`, `mask_area` and `class_index` per detection, writes the composite mask and a filled overlay, keeps the list under a 4 MiB ceiling, stores the detections with the result history, and the HMI draws the masks) or as a **semantic overlay** (`rf_detr_semantic_segmentation`, the segmentation record); the mode can be changed when packaging. The device's results export can write an instance-segmentation manifest (`manifest_format=instance`). A per-architecture RF-DETR-Seg feature floor gates packaging and deployment of workflows that use such a model (`RFDETR_SEG_UNSUPPORTED_ARCH` until the architecture's LocalServer build is entered). Device contract: `docs/multi-runtime-inference.md` §24.
- **Results.** The captures listing and the Results viewer show the per-object masks of instance captures (`has_masks` and `mask_area` on the listing, the masks fetched per capture), and the device's instance-manifest export is read by the Portal as an instance-segmentation manifest with the masks intact, so exported results can seed a new Instance Segmentation labeling job.
- **MCP.** `portal_models_training_create` and `portal_models_convert` accept `instance_segmentation` / `rf_detr_seg` with the mask threshold and Output mode; captures listed through MCP carry `has_masks` and `mask_area`, never the per-instance mask. The Portal MCP server version is **1.4.0**. On the device, every edge tool returning detections drops `mask_rle` and keeps boxes and `mask_area`.
- **Switch.** The feature is on by default and can be turned off at deploy time with the CDK context `enableRfDetrSeg=false` (`PORTAL_RFDETR_SEG_ENABLED` on the Training, Model Converter and Packaging functions; `rfDetrSegEnabled` in the frontend `config.json`): the Seg pickers and tile are hidden and RF-DETR-Seg requests answer 403. Existing paths — YOLO and RF-DETR detection, the Marketplace classification and segmentation training, the three existing labeling task types, the detection and anomaly device records — are unchanged.

### Added - Build Fleet: optional NAT gateway for the build instances (2026-11-23)

Build instances reach GitHub, container registries, Systems Manager and the other AWS endpoints through the build VPC's internet gateway. In an account where VPC Block Public Access blocks internet gateway traffic in ingress-only mode, they lose that path: dedicated build servers go offline in Systems Manager (ConnectionLost), and builds cannot run. Ingress-only mode still allows traffic through a NAT gateway, so the Build Fleet stack can now add one.

- **A CDK context flag, off by default.** `buildFleetNatGateway` adds one NAT gateway with its own Elastic IP in the build VPC's second public subnet, and points the first subnet's default route at it; every build instance launches in the first subnet. The second subnet keeps its internet gateway route. There is no new subnet and no inbound rule. A deploy without the flag changes nothing.
- **Turning it on and off.** `BUILD_FLEET_NAT_GATEWAY=true ./deploy-infrastructure.sh` turns it on and `BUILD_FLEET_NAT_GATEWAY=false` turns it off; `infrastructure/deploy_portal_fixes.sh` takes the same variable. With the variable unset, both scripts keep the deployed state (the Build Fleet stack's `BuildNatGatewayId` output), and they stop when they cannot read it. A hand-run `cdk deploy` must pass `-c buildFleetNatGateway=true` while the gateway is on.
- **Cost and availability.** About $36.50 a month for the gateway and its Elastic IP, plus $0.045 per GB processed and $0.01 per GB each way between the two Availability Zones (us-east-1 prices). The build instances then depend on the gateway's Availability Zone as well as their own. See [Build Fleet NAT gateway](ADMIN_GUIDE.md#build-fleet-nat-gateway).
- **Execution policy.** `iam/portal-cfn-execution-network-policy.json` allows `ec2:CreateNatGateway` and `ec2:AllocateAddress` only with the `dda-portal:managed` tag in the request, and `ec2:DeleteNatGateway` and `ec2:ReleaseAddress` only on resources that carry it. The portal tags both new resource types at creation. An account set up with `iam/setup-account.sh portal` before this change must run it again before turning the gateway on. The permissions boundary is unchanged.

### Fixed - Synthetic data: generation passes longer than the worker's 15-minute limit (2026-11-22)

A variation costs about 25 s (20 s of model time plus 3–5 s of image work: resize, restore to the source size, PNG upload), so a pass of 10 source images × 5 variations needs about 20 minutes against the generation worker's 900 s Lambda limit. Pass 2 of session 6115b94c ran 43 of its 50 tasks and hit the limit; Lambda's default asynchronous retry policy (two retries, the function had no explicit setting) re-ran the whole plan from the start twice, producing 130 failed previews for 50 tasks with the same seeds, and because the worker only reported **Awaiting review** after the last task the session stayed in **Generating** with **Regenerate** disabled.

- **The worker continues across invocations.** It checks its remaining time before each variation and, when under 2 minutes remain, hands the rest of the plan to a continuation invocation of itself. Every preview record now carries its task index, and a continuation runs only the variations without a record, so a plan larger than one invocation completes without a second click and no task runs twice. A per-pass worker token rejects a duplicate or retried worker event: it runs nothing and writes nothing.
- **Lambda retries of the worker are off** (`MaximumRetryAttempts 0`; worker events older than 2 minutes are discarded). The worker is idempotent per task and reports a dead pass through the session, so a retry could only re-run or duplicate work.
- **A dead pass reads Failed, not Generating.** A pass whose worker stopped without reporting (its deadline plus a 3-minute grace has passed) is moved to **Failed** with the reason — the pass, how many preview records were written for how many planned — when the session is next opened. Previews already generated stay reviewable; **Regenerate** starts a new pass. A worker that cannot start its continuation, or has no time left for a single variation, fails the pass the same way instead of leaving it running.
- **`POST /synthetic/sessions/{id}/generate` answers 409** while a pass is genuinely running (the Portal already disables **Regenerate** then); a stale pass is superseded by the new one.
- **Unchanged.** The default **Resize to fit the model, then restore the original size**, the aspect-matched Amazon image-variation outputs and the JPEG output for scaled-down Stability sources stand. The frontend is unchanged: the progress bar keeps counting across invocations.
- **Session 6115b94c.** Opening it moves it from **Generating** to **Failed** with the reason; **Regenerate** runs pass 3 across two worker invocations to **Awaiting review** with 50 previews.

### Fixed - Synthetic data: Stability response size for resized source images (2026-11-22)

After the 2026-11-21 fix below, a generation pass over 4608×3288 source images against Stability Stable Image Inpaint sent each image at 3636×2594 (9,431,784 pixels, inside the model's limits) and the request was accepted, but every variation of pass 2 of session 6115b94c failed with `ValidationException: {"detail":"Response payload size 18982136 bytes exceeds the maximum allowed size of 16777216 bytes. Please try adjusting the seed, using a different input image, or requesting JPEG output_format"}` (payloads 18,982,136 to 20,276,590 bytes). The worker requested the default PNG output, and a PNG of a 9.4-megapixel photograph (1.5–1.6 bytes per pixel, base64-encoded inside the response) does not fit under Stability's 16 MiB response limit.

- **JPEG output for downscaled sources.** A Stability source scaled *down* to the model's pixel limit is now requested with `output_format: "jpeg"`, the remedy the error names, at the same fitted size. A JPEG of the same image is about 0.3 bytes per pixel, so the response stays far under the limit (the real-model check with the live 4608×3288 sample returned payloads of 3,578,819 and 3,618,531 bytes for two seeds, 21 % of the cap, where the same request with PNG output was refused at 20,012,462 bytes). The generated image is scaled back to the source size and stored as PNG, as before, so the staged and integrated files keep their format and dimensions; the model's JPEG encoding is the only difference from the intended output of the earlier fix, and the first output at all for these sources.
- **Unchanged.** In-limit sources and sources scaled *up* to the model's minimums keep PNG output byte-for-byte. Amazon Nova Canvas and Titan Image Generator v2 have no output-format parameter and their outputs (at most 4,194,304 and 1,982,464 pixels) stay far below any such limit. The default **Resize to fit the model, then restore the original size** and the aspect-matched Amazon image-variation sizes stand.
- **Known limit.** An in-limit Stability source between about 7.8 and 9.4 megapixels is still sent as-is with PNG output and can hit the same response limit depending on its content, as before.

### Added - Configuration overrides can set a Bedrock node's model request fields (2026-11-21)

`WorkflowNodeOverrides` can now set a **Bedrock Inference** node's `additional_model_request_fields`, so turning a Claude model's thinking on or off on one device no longer needs a new workflow version. This replaces the "Not overridable" point of the 2026-11-12 entry.

- **Value.** A JSON object, for example `{"thinking": {"type": "adaptive"}, "output_config": {"effort": "low"}}`, or its JSON text. It is checked with the rule the node's own value has: anything but a JSON object is ignored with a warning and the deployed value stands, and an empty object or empty text sends no fields. The run's log names the overridden parameter, not its value.
- **Replacing a value.** Greengrass merges nested objects key by key, so a later `merge` adds keys to an earlier object instead of replacing it. Reset `/WorkflowNodeOverrides` in the same deployment revision, or give the value as JSON text.
- **Older LocalServer.** A LocalServer built before this change ignores the parameter with a warning. Workflow tuning does not replay it, like every other override.

### Fixed - Workflow tuning scores an inspection node under its attempt policy (2026-11-21)

Workflow tuning replayed every sample of an inspection-format **Bedrock Inference** node (`answer_format: inspection`) with one call and a 30-second read timeout, whatever the node's `attempts`, `attempt_timeout_s` and `budget_s`. The device runs the node under that policy, so a node limited to 14 seconds on the device had 30 seconds in tuning.

- **Replay.** A score run of an inspection-format node now applies the latest version's policy the way the device's executor does: up to `attempts` calls, each with `attempt_timeout_s` as its read timeout and no automatic retry inside the call. A failed call or an answer that is not valid inspection JSON is retried, except a `ValidationException`, `AccessDeniedException` or `ResourceNotFoundException`. With `budget_s` set, a retry starts only while the budget leaves a whole `attempt_timeout_s`. The outcome is the last attempt's. A node at the default policy (1 attempt, 30 s, no budget) is scored exactly as before, and the legacy answer formats keep one call.
- **Records.** Each inspection outcome records `attempts`, the number of calls made. The score run records the policy as `attemptPolicy` (`attempts`, `attemptTimeoutS`, `budgetS`) and returns it in its views, and each scoring step logs the policy it applied.
- **Shared code.** The policy's defaults, its parameter rule and its terminal error codes moved unchanged to the shared `workflow_core` package, which LocalServer vendors, so the device and the Portal resolve the policy with one implementation. The device's behaviour does not change.

### Fixed - Synthetic data: source images outside the generation model's size limits (2026-11-21)

A synthetic data generation pass failed every variation when the source images were larger than the model accepts. The worker sent each source image to Bedrock as-is, so a 4608×3288 photo (15,151,104 pixels) against Stability Stable Image Inpaint, whose inputs must stay between 4,096 and 9,437,184 pixels, was refused with `ValidationException: Image total pixel count 15151104 is invalid` for all 50 variations of the pass.

- **Resize and restore (default).** Each catalog model now declares the input sizes it accepts (`input_image_limits` on `GET /synthetic/models`: Stability 4,096–9,437,184 pixels with each side at least 64 px; Amazon Nova Canvas up to 4,194,303 pixels with each side 320–4,096 px; Amazon Titan Image Generator v2 longest side at most 1,408 px). A source image outside them is scaled uniformly to fit before the model call, together with the Stability inpainting mask, and the generated image is scaled back to the source dimensions, so previews, `mask_region` and integrated records keep the source's coordinates. The preview records the model-side size as `resized_for_model`, shown in the full-size view. In-limit images are sent byte-for-byte as before. Integration annotates a restored full-size preview from its image header and `mask_region`, or from a pixel diff computed on copies bounded to 1,048,576 pixels and scaled back, so approving and integrating such previews stays within the handler's memory.
- **Option.** The new generation parameter `oversize_handling` (`resize_restore`, the default, or `fail`) is offered as **Images outside the model's size limits** in the create-session wizard, when the selected model declares limits, and on the session page above **Regenerate**, so a session whose pass failed on the limits can be rerun with resizing. ### Fixed - Workflow tuning for inspection-format Bedrock nodes, reference files and live tuning configuration (2026-11-13)

### Security - Component bucket ownership is asserted on every S3 call (2026-11-12)

The Greengrass component artifact bucket is named from the portal account id and region (`dda-component-<region>-<account>`). S3 bucket names are global, so a third party who knows an account id could create that exact name in their own account before the account's first publish; the publish scripts then found the name reachable, uploaded the component artifacts into it, and the component recipe pointed every edge device at that bucket (S3 bucket squatting). Every S3 call against the derived name now asserts `ExpectedBucketOwner` (the caller's own account), and a bucket of that name owned by another account is a hard error that is never adopted:

- **Publish scripts** (`gdk-component-build-and-publish.sh`, `portal-build.sh`, `publish-ecr-only.sh`, `build-inference-uploader.sh`, `com.dda.InferenceUploader/build-and-publish.sh`) verify ownership with `HeadBucket --expected-bucket-owner` before anything is pushed or uploaded, create the bucket only when S3 reports it absent and re-verify right after, and upload with an owner-asserted `PutObject` (`scripts/s3-bucket-owner-guard.sh`). `gdk component publish` uploads with the same assertion through `publish.options.file_upload_args` in `gdk-config.json`. On a conflict the script stops with a `SECURITY ERROR` naming the bucket and the account; nothing is uploaded and no component version is created.
- **Portal backend**: the component bucket policy writers (use case onboarding, account moves and deletes, shared component provisioning) and the static image / video pin Image_Transport (presigned staging PUT, HeadObject, GetObject, CopyObject, DeleteObject) assert the portal account as the owner. A pin submit against a bucket owned by another account fails with 502 before any Pin_Request or device shadow write. The presigned staging PUT signs `x-amz-expected-bucket-owner`; the upload-url routes return the header as `uploadHeaders` and the frontend sends it, so deploy the frontend together with the backend.
- **Infrastructure**: the compute stack's CORS and lifecycle writes to the bucket carry `ExpectedBucketOwner`, and `deploy-portal.sh` re-verifies ownership immediately after creating the bucket.
- **Inference-results bucket** (`dda-inference-results-<use case account>`, the default when a use case configures no `inference_uploader_s3_bucket`): the same derived-name exposure, since nothing creates that bucket for the operator. Every portal call against the derived default asserts the use case's account as the owner: the captures listing and reads, the telemetry clip and live-frame HEADs, the "Media location" and media-retention readiness probes, the debug-mode region probe, image readiness and image HEAD, the tuning Sample_Store reads and writes and the tuning lifecycle rules. On the device, the InferenceUploader, the telemetry live frames, the debug images and the tuning sample exporter and job runner assert that a bucket named `dda-inference-results-<account>` belongs to that account on every PUT and GET (the InferenceUploader also honours an explicit `s3BucketOwner` configuration / `S3_BUCKET_OWNER` environment variable, which the Portal now sets for the derived default). A bucket owned by another account answers 403: the portal shows the item as denied or unavailable and the device keeps the files local. An admin-configured override bucket is not a derived name and carries no assertion; its admission remains the use-case bucket allowlist's. Device-side changes ship with the next LocalServer and InferenceUploader component versions.

### Fixed - Bedrock max tokens above the model's maximum (2026-11-11)

A Bedrock request whose max tokens is above its model's maximum output is now sent again with that maximum. Bedrock refuses such a request before the model generates anything, and its refusal states the maximum: Amazon Nova Pro, for example, refuses 128000 and states 10000. With 128000 saved under Settings → Bedrock Configuration, every image of a **Bedrock:** auto-labeling job on a model with a lower maximum failed, and so did code assist, workflow generation and **Generate with AI** when such a model was configured. A request within its model's maximum is sent exactly as before, and the saved value does not change.

- **Which features.** Code assist, workflow generation (the Gen panel, `portal_workflows_generate` and the repair pass), **Generate with AI**, the assistant and auto-labeling with a **Bedrock:** model. Prompt-guided auto-labeling and the prompt tuning preview keep their own token budget: a budget above the model's maximum still fails with the limit Bedrock states, which the preview shows.
- **Cost and time.** A lowered request costs one more round trip. Nothing is remembered between requests, so a **Bedrock:** job on such a model sends two requests per image. Each lowering is logged as a warning in the function's log.

### Changed - Default Bedrock max tokens follows the model (2026-11-10)

With no max tokens saved under Settings → Bedrock Configuration, a Bedrock request now carries a default chosen for its model instead of 4096 for every model. Claude Opus 5.5, the default model, gets its maximum output, 128000 tokens; every other model keeps 4096. On a Portal with nothing saved, Node Designer **Generate with AI** returned 422 `GENERATED_SCAFFOLD_INVALID` on Claude Opus 5.5: its thinking counts toward max tokens, and together with the scaffold it passed 4096, so the scaffold was cut off. ### Changed - Authorization consistency and IAM scoping (2026-10-15)

Use-case creation, account grants, internal invocations and the portal's S3 data plane follow one authorization rule each, and every API route's authorization is committed in `infrastructure/ROUTE_AUTH.md` (generated from the synthesized stacks; the infrastructure tests fail on an unlisted unauthenticated method).

- **Use-case creation is PortalAdmin-only.** `POST /usecases` and `POST /usecases/verify-role` require the `create_usecases` permission; other callers get 403 `INSUFFICIENT_PERMISSIONS` (audited as `unauthorized_access`). - **Proof of control before any account grant.** A multi-account use case is accepted only for an account in the trusted use-case account list (`trustedUseCaseAccountIds`; else 400 `ACCOUNT_NOT_TRUSTED`, with no STS call) and only after the portal has assumed that account's `DDAPortalAccessRole` with the supplied external id (else 400 `ACCOUNT_CONTROL_NOT_VERIFIED`; STS unavailable → 503 `STS_UNAVAILABLE`), before the record or any component-bucket or EventBridge grant is written. - **Internal triggers are recognized by their source.** Auto-compile, auto-package and the publish chain are recognized as internal only when the event comes from another portal function (a marker that API Gateway events can never carry), not from a body or claim field. - **S3 data-plane grants are conditioned on the portal tag.** The portal's Lambda roles read and write a use-case bucket only when it carries `dda-portal:managed=true` and has ABAC enabled (deploy log: `Data-plane scoping: tag`); tag discovery stays unconditioned, and the portal's own buckets are granted by name. Every bucket attach (use-case create, `PUT /usecases/{id}`, **Allow**, `POST /s3-buckets`, the data-account configure) enables ABAC on a tagged portal-account bucket (audited as `bucket_abac_enabled`), probes that the portal can reach it, and reports `registration` — `tagged`, `abac_enabled`, `iam_reachable`, `remedy` — per bucket; the UI shows the remedy beside the bucket. A read-only audit script (`scripts/portal-bucket-abac-audit.py`) lists the registered buckets that are not yet compliant and applies the tag and ABAC on exactly the named ones.
- **Device access document.** Before each deployment, and when a use case's bucket or allowed buckets change, the portal writes one statement per use case into the `DDAUseCaseDeviceAccess` inline policy of the account's `GreengrassV2TokenExchangeRole` for buckets outside the `dda-*` / `*-dda-*` pattern and for a results-bucket override outside `dda-inference-results-*`, and removes it when the use case is deleted (`device_grants.device_access`, `grants_removed.device_access`). The Deployments and UseCases roles gain `iam:GetRolePolicy` / `iam:PutRolePolicy` on that role in the portal account. A read-only drift check (`scripts/portal-role-drift-check.py`) classifies a role's policies against the repository templates. The station installers write the account stack's device statement set.
- **Removed:** the unrouted `manifest_validator.py` module and an unreachable branch of the Data Management router (manifest transforms are served by the training routes, unchanged).

**Is this a breaking change?** Yes, for the flows below; each has a remedy.

| Flow | Before | After | Remedy |
|---|---|---|---|
| A UseCaseAdmin, DataScientist, Operator or Viewer creating a use case | 201 | 403 `INSUFFICIENT_PERMISSIONS` | A PortalAdmin creates it |
| Multi-account `POST /usecases` for an account outside the trusted list | 201 | 400 `ACCOUNT_NOT_TRUSTED` | Add the account to `trustedUseCaseAccountIds` and redeploy |
| Multi-account `POST /usecases` whose role cannot be assumed with the external id | 201 (grants written) | 400 `ACCOUNT_CONTROL_NOT_VERIFIED`; nothing written | Deploy `DDAPortalUseCaseAccountStack` in the account and supply its external id |
| A UseCaseAdmin re-provisioning shared components | Ran | 403 | A PortalAdmin re-provisions |
| A registered use-case bucket that is not tagged and ABAC-enabled at the deploy | Reachable through the unconditioned grant | `AccessDenied` on the portal's roles | Run the bucket audit and its `--apply` before the deploy (Admin Guide, "Bucket compliance before deploying") |
| A model imported earlier from a bucket outside the use case's allowed buckets (single-account) | Compile / package / publish worked | `AccessDenied` | Tag, ABAC-enable and allow the bucket, re-import, or accept the loss (Admin Guide) |

### Changed - Use case bucket configuration (2026-10-14)

Portal handlers now read and write S3 only in the use case's **configured buckets**: its S3 bucket, its Data Account bucket, and the **Additional S3 buckets** a UseCaseAdmin allows (**Use Cases** → **Edit** → **Allowed buckets**, or the **Allow for this use case** action on a bucket in Data Management). Every caller-supplied `s3://` URI or bucket name — model validation, import, inspection and conversion, vLLM registration and its fit check, training manifests and manifest transforms, pre-labeled dataset manifests, Data Management folders and upload URLs, the few-shot example references of DDA labeling jobs — is checked against that set before any role is assumed or any S3 call is made. Other buckets answer **400 `bucket_not_allowed`** with a `remedy` field naming the fix (allow the bucket, or place the object in the use case's configured bucket); a malformed URI or bucket name answers 400 `invalid_s3_uri` / `invalid_bucket_name`. Buckets inside the set are reached with the role the portal's shared S3 helper has always chosen for them (the Data Account role for the Data Account bucket, the use case's cross-account role otherwise); the two operations that used a different credential path before are listed in the table below.

- `POST /models/validate` and `POST /models/inspect` require the DataScientist role on the use case, as `POST /models/import` and `POST /models/convert` already did; the Import Model page tells other roles that validating and importing models requires DataScientist.
- The pre-labeled dataset routes require membership of the use case (DataScientist to create, validate or delete a dataset).
- `POST /labeling` with the DDA backend requires the `create_labeling_jobs` permission on the use case (DataScientist or above), like every other DDA labeling route; its `example_images` must be `s3://` references inside the use case's allowed buckets.
- Buckets the portal creates (`POST /s3-buckets`; **Create new bucket** in the onboarding wizard) are tagged `dda-portal:managed=true`, `dda-portal:created-by=portal` and — when created for a use case — `dda-portal:usecase-id`, ABAC-enabled, and allowed for that use case automatically; only buckets created outside the portal need the manual tag and the Allow step. Creating a bucket without a use case is a PortalAdmin action.
- Attaching a bucket to a use case (`s3_bucket`, `data_s3_bucket`, an Additional S3 bucket) requires that the bucket carries the portal tag and is readable through the use case's role, and that no other use case has it configured or is named in its `dda-portal:usecase-id` tag; a PortalAdmin may allow a shared or claimed bucket deliberately (audited). The portal's own artifacts and component buckets can never be allowed.
- API: `GET /usecases/{id}` returns `allowed_s3_buckets` and `additional_s3_buckets`; `PUT /usecases/{id}` accepts `additional_s3_buckets_add` / `additional_s3_buckets_remove` (at most 10 names per request, 100 additional buckets per use case) and reports `added` / `already_present` / `removed` / `not_present`; `GET /usecases/{id}/data/buckets` entries carry `allowed` and `portal_created`; `GET /s3-buckets` entries carry `eligible` and `portal_created` (advisory; the server decides at creation); `POST /s3-buckets` answers 409 `bucket_already_exists` for a name the account already owns.
- Audit: `s3_bucket_refused` on every refusal; `s3_bucket_allowed` (with `attribute` and `source`: `api`, `create`, `configure`, `auto_add`) and `s3_bucket_removed` on every change to a use case's allowed set.
- Frontend: Data Management marks buckets **Allowed** / **Not allowed** / **Portal-created**, defaults to the first allowed bucket and offers the inline **Allow for this use case** action to UseCaseAdmins; the onboarding bucket picker marks **Tagged for the portal** / **Not tagged for the portal** / **Portal-created** and shows **Create new bucket** to PortalAdmins only; the Use Case Edit modal gains an **Allowed buckets** section.
- The shared Lambda layer now ships boto3/botocore 1.43.101 (needed for the bucket `PutBucketAbac` and `TagResource` operations); every function on the layer runs that SDK instead of the runtime's bundled one.
- `deploy-infrastructure.sh` prints a warning when the registry enforcement value resolved for a deploy is not `true`. Production deployments run `PORTAL_REGISTRY_ENFORCED=true ./deploy-infrastructure.sh` after `backfill_portal_registry.py` has been applied (Admin Guide, "The enforcement flag"); role resolution itself is unchanged.

**Is this a breaking change?** Yes, for the flows listed below; each has a remedy. Everything else keeps working unchanged: Smart Import (convert → the use case bucket → import), SageMaker training output and its compile/package/deploy, previously imported models whose artifact lives outside the set (compile, package and deploy still work), reads of `data_s3_bucket` on a separate Data Account, cross-region buckets, S3 browsing of the configured bucket, training from a labeling-job export or a transformed manifest, DDA labeling / auto-label / preview dataset reads, use cases whose configured bucket has a legacy (uppercase / underscore) name, and deployments running with registry enforcement off.

| Flow | Before | After | Remedy |
